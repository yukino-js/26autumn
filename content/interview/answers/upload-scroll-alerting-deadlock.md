## Q1 · 断点续传怎么做？虚拟滚动（定高 / 不定高）怎么做？

### 断点续传（✅ 项目事实：`yukino-chat.md`）

**三端点状态机**：校验 → 上传分块 → 合并。

| 环节   | 实现                                                                                                                                                                                          |
| ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 校验   | 入参 `文件哈希 / 扩展名 / 分块总数`；最终文件存在 → **秒传**；否则逐个探测分块目录的 `chunk-<下标>`，返回**缺失下标数组**。**服务器状态就是磁盘上已存在的分块文件集合，无数据库记录**         |
| 上传   | multipart；哈希 8–64 位十六进制、扩展名 1–10 位字母数字白名单；**单块上限 10 MiB**；写入小写哈希命名目录                                                                                      |
| 合并   | 按序拼接 → 写最终文件 → 删分块目录；中途读失败删除半成品（防被误判秒传）；最终文件已存在直接返回成功，**合并幂等**                                                                            |
| 客户端 | **5 MiB/块**（服务端上限的一半，留 multipart 编码余量）、**并发 3 信号量**、每块**重试 3 次线性退避**（第 n 次等 n 秒）、总上限 **2 GiB**；哈希放 worker 二次摘要避内存峰值；全程穿透中止信号 |

流程：`哈希 → 校验 → 秒传? → 只传缺失块 → 合并 → 返回地址`。代价：依赖本地磁盘，多实例部署时校验与合并必须落同一实例（或共享存储）。

### 虚拟滚动（✅ `tiktok.md`）

**先纠偏**：虚拟滚动是**少渲染节点**，不是少加载数据；传输量靠服务端分页 + 字段裁剪解决。它优化 DOM 的样式计算/布局/绘制/合成、内存与 GC、滚动交互成本。

**定高**（一行公式）：

```ts
const start = Math.floor(scrollTop / itemHeight);
const end = start + Math.ceil(viewportH / itemHeight) + buffer * 2;
const offsetY = start * itemHeight; // 绝对定位或 transform
const totalH = n * itemHeight; // 撑滚动条
```

**不定高**的**三个问题**（项目原话）：总高度怎么撑、可视区间怎么找、真实高度怎么修正 → 预估高度 + 前缀和 + 二分 + 实测修正：

```ts
function findStartIndex(prefix: number[], scrollTop: number): number {
  let lo = 0,
    hi = prefix.length - 1;
  while (lo < hi) {
    const mid = (lo + hi + 1) >> 1;
    if (prefix[mid] <= scrollTop) lo = mid;
    else hi = mid - 1;
  }
  return lo;
}

function onMeasure(index: number, realHeight: number) {
  if (heights[index] === realHeight) return;
  heights[index] = realHeight;
  rebuildPrefixFrom(index); // 只重算该位置之后的前缀和
}
```

| 步骤   | 做法                                                                                                                                                       |
| ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1 预估 | 未实测前填设计稿典型高度，`total = Σheights` 撑开滚动区                                                                                                    |
| 2 定位 | `prefix` 前缀和上二分找 `start`（`O(log n)`）；可视集合内 `top = prefix[i]` 绝对定位                                                                       |
| 3 实测 | `ResizeObserver` / `useLayoutEffect` + `getBoundingClientRect` 量真实高度，不一致则改 `heights[i]` 并从 index 增量重算前缀和；越滚越准，滚动条抖动逐渐收敛 |
| 4 规模 | 单点更新 + 区间查询可用**树状数组**做到 `O(log n)`                                                                                                         |

**边界**（项目列出的手写代价）：快速滚动白屏、缩放尺寸偏差、容器 resize、SSR、**向上加载历史要补偿 scrollTop** 否则视口跳动；测量必须放布局完成后。取舍：定制强/场景收敛才手写（两三百行），通用中后台直接用 `@tanstack/react-virtual`。

## Q2 · 前后端治理告警的「归属率」：做了什么、指标、分子分母、为何监控、归属准确率

⚠️ **知识库无此指标落地记录**；下面是可讲的通用框架，**须明确说不是项目已做**。

**为什么监控这个节点**：告警治理漏斗是 `采集 → 聚合去重 → 归属 → 派单 → 处理 → 关闭`。归属是「能不能找到人」的分水岭——无归属或归错人直接拉长 MTTR、制造告警疲劳与责任推诿，最终导致静默/无人看。归属率是衡量**可观测性数据质量与责任拓扑健康度**的指标，不是业务 SLO。

| 指标                                                            | 分子                                                | 分母                                                                 | 说明                                                                                                   |
| --------------------------------------------------------------- | --------------------------------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| **归属覆盖率（归属率）**                                        | 带完整归属标签且校验通过的告警/错误事件数           | **有效告警总数**（去重后，排除维护窗口、测试流量、已静默、重复风暴） | 衡量「有多少告警能定位到责任主体」；口径必须先固定：按告警条数 / 按独立事件 / 按故障次数，三者差异极大 |
| **归属准确率**                                                  | 归属判定与**事后复盘/人工确认的责任方一致**的告警数 | 已归属的告警数                                                       | 有 owner ≠ 归对人；防止用「随便挂个默认组」把覆盖率刷高                                                |
| 未归属率 / 平均认领时长 / 误派单率 / 静默率 / 重复收敛比 / MTTR | —                                                   | —                                                                    | 配套漏斗指标                                                                                           |

**「怎样才算归属正确」**（三条判据，缺一不可）：

1. **主体正确**：落到具体模块/服务/团队/owner，且与事后根因责任方一致（而非告警触发点所在的服务——上游故障常让下游背锅）。
2. **证据链完整**：有 `trace_id` / `commit` / `release` / 堆栈反解到源码行与组件，能复现、能复核。
3. **可闭环**：派单被认领、有处理动作、复盘确认无转派。**转派过的应计为归属不准**（或单列转派率）。

**前后端各自做什么**（✅ 项目里有可比事实）：

- 前端：错误边界 + sourcemap 反解到源码行/组件、`userId / projectId / sdkVersion` 归属与版本维度（`data.md:126`）、rrweb 滚动窗口现场还原（`data.md:22-51`）、SDK 侧过滤跨域噪声。
- 后端：三支柱 metrics/traces/errors（`ieg.md:379-385`）、OpenTelemetry 跨服务串联、Prometheus + Grafana 看板与规则（`ieg.md:516-555`）、服务/实例/接口维度打标。
- 告警侧（✅ 项目事实）：`yukino-dev-agent` 的多源告警聚合——**同名去重、按源溯源、单源失败返回结构化错误不丢其它结果**、定向诊断带十个规范化字段（告警名/级别/服务/状态/触发时间/持续时长/描述/上下文/指纹/来源）。

> **面试口径**：「我熟悉归属类指标该怎么定义与验证；但本知识库里没有该指标的落地记录，不会把框架讲成项目已做。」

## Q4 · 续传时传 2.5M 要重新上传吗？HTTP 哪些字段能不从零开始？

**先拆两层语义**（这题最容易答混）：

| 层                            | 答案                                                                                                                                                                                                        |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **应用层分块**（✅ 项目做法） | 5 MiB/块，校验返回缺失下标。**已完整落盘的块不重传**；若 2.5M 这一块上传到一半断了（未写成 `chunk-<下标>` 文件），**这一块要从头重传**，但前面的块全部保留。服务器只认「完整块是否存在」，没有块内偏移状态  |
| **HTTP 层**                   | 标准 HTTP **没有上传续传字段**。`Range` 是**下载/GET** 语义；上传侧要么 `PATCH` + `Content-Range`（tus / resumable.js 约定），要么 S3 multipart（`uploadId` + `partNumber` + `ETag`），要么自己做应用层分块 |

**字段清单**：

| 字段                                                                        | 方向         | 作用                                                                        |
| --------------------------------------------------------------------------- | ------------ | --------------------------------------------------------------------------- |
| `Accept-Ranges: bytes`                                                      | 响应         | 声明支持范围请求                                                            |
| `Range: bytes=start-end`                                                    | 请求（GET）  | 指定字节区间                                                                |
| `206 Partial Content` + `Content-Range: bytes start-end/total`              | 响应         | 返回该区间；项目 `wanproxy.md:347` 的 `/api/files/:id/content` 就是这个实现 |
| `416 Range Not Satisfiable`                                                 | 响应         | 非法区间（项目里经 `TakeOver` 返回）                                        |
| `If-Range: <ETag \| HTTP-date>`                                             | 请求         | 资源没变才继续续传，变了返回全量 `200`，防止把新旧版本拼在一起              |
| `ETag` / `Last-Modified` / `If-Match`                                       | 双向         | 版本校验与并发控制，防覆盖他人修改                                          |
| `PATCH` + `Content-Range`                                                   | 请求（上传） | **非标准但通行的上传续传做法**，服务端要自己维护 offset                     |
| ❌ `Expect: 100-continue` / `Content-Length` / `Transfer-Encoding: chunked` | —            | 都不是续传字段，别混进来答                                                  |

> **面试口径**：「2.5M 不用整文件重传，但**本项目这一块要重传**——因为进度粒度是完整块。要做到块内偏移续传，得引入 `PATCH + Content-Range` 或 tus 协议，并让服务端持久化每个 uploadId 的已收字节数；我们选择块粒度是为了把状态机压到磁盘文件集合上，省掉数据库。」

## Q6 · 死锁怎么发生的？

✅ `mysql.md:588-610` 的经典案例：可重复读下两个事务并发「不存在则插入」，各拿**互相兼容的间隙锁 (5,10)**，随后各自的插入意向锁被对方的间隙锁阻塞 → 循环等待。

**四个必要条件**（缺一不可）：互斥、持有并等待、不可剥夺、**循环等待**。破坏任一条即可解，工程上最常破的是「循环等待」（固定加锁顺序）。

| 场景     | 成因                                                                                                                 |
| -------- | -------------------------------------------------------------------------------------------------------------------- |
| DB       | 多表/多行加锁顺序不一致、间隙锁互相兼容后抢插入意向锁、大事务长持锁、无索引导致锁范围放大                            |
| 分布式锁 | `SETNX` + `EXPIRE` 非原子，中间宕机 → 永不过期的锁；✅ `redis.md` 要求 `SET key value NX PX ttl` 原子设置 + TTL 兜底 |
| 应用并发 | 多个 mutex/channel 交叉获取、回调里同步等锁、连接池耗尽后互相等待、单线程事件循环里同步等待自己触发的异步结果        |
| 线程池   | 池内任务提交子任务并阻塞等待，池满后无人执行子任务（线程饥饿死锁）                                                   |

**排查与规避**（✅ 项目事实）：`innodb_deadlock_detect`（默认开）检测等待环后**回滚代价最小的事务**；`innodb_lock_wait_timeout` 默认 50s 兜底；`show engine innodb status` 看 `LATEST DETECTED DEADLOCK`；`sys.innodb_lock_waits` / `performance_schema.data_lock_waits`（`tiktok.md`）；业务上按主键升序固定访问顺序、事务尽量小、`insert ... on duplicate key update`、降读已提交去掉间隙锁、建索引缩小锁范围。注意：**热点行高并发下等待图扫描本身耗 CPU**，这是自研检测要面对的成本。

## Q7 · 设计一个死锁检测监控：图算法、环检测

### 建模：等待图（Wait-For Graph）

- **节点** = 事务 / 线程 / 协程 / 分布式锁持有者（带 `trx_id`、`pid`、`trace_id`、开始时间、SQL）。
- **有向边** `T1 → T2` = T1 正在等待 T2 持有的资源（带 `lock_id`、资源标识、等待起始时间）。
- **定理**：等待图中**存在环 ⇔ 存在死锁**（单资源实例模型下；多实例资源需用资源分配图的更一般判定）。

### 环检测算法（三选一，按需求）

```ts
// A. DFS 三色标记: O(V+E), 能直接输出环路径
function hasCycle(graph: Map<string, string[]>): string[] | null {
  const color = new Map<string, 0 | 1 | 2>(); // 0 白 1 灰(在栈) 2 黑
  const stack: string[] = [];
  function dfs(u: string): string[] | null {
    color.set(u, 1);
    stack.push(u);
    for (const v of graph.get(u) ?? []) {
      if (color.get(v) === 1) return stack.slice(stack.indexOf(v)); // 回边 => 环
      if (color.get(v) !== 2) {
        const c = dfs(v);
        if (c) return c;
      }
    }
    stack.pop();
    color.set(u, 2);
    return null;
  }
  for (const u of graph.keys())
    if (!color.get(u)) {
      const c = dfs(u);
      if (c) return c;
    }
  return null;
}

// B. Kahn 拓扑排序: O(V+E), 入度剥边, 剩下未出队的节点 = 环所在子图
function cycleNodes(graph: Map<string, string[]>): Set<string> {
  const indeg = new Map<string, number>();
  for (const u of graph.keys()) {
    indeg.set(u, 0);
  }
  for (const vs of graph.values())
    for (const v of vs) indeg.set(v, (indeg.get(v) ?? 0) + 1);
  const q = [...indeg.keys()].filter((k) => indeg.get(k) === 0);
  const seen = new Set<string>();
  while (q.length) {
    const u = q.shift()!;
    seen.add(u);
    for (const v of graph.get(u) ?? []) {
      indeg.set(v, indeg.get(v)! - 1);
      if (indeg.get(v) === 0) q.push(v);
    }
  }
  return new Set([...graph.keys()].filter((k) => !seen.has(k)));
}
```

| 算法                                 | 复杂度          | 适用                                                                          |
| ------------------------------------ | --------------- | ----------------------------------------------------------------------------- |
| **DFS 三色**（白/灰/黑，遇灰即回边） | `O(V+E)`        | 直接给出**具体环路径**，最适合告警要带证据链；InnoDB 的等待图扫描本质就是这个 |
| **Kahn 拓扑排序**                    | `O(V+E)`        | 实现最简单、易并行，输出「环涉及的节点集合」但**不直接给环路径**              |
| **Tarjan / Kosaraju SCC**            | `O(V+E)`        | 找所有强连通分量，`size>1` 或自环即环；适合批量分析多个环                     |
| Johnson 算法                         | `O((V+E)(C+1))` | 枚举所有简单环，只在需要全量环报告时用                                        |
| ❌ 并查集                            | —               | 只能判无向图环，**等待图是有向图**，不要用                                    |

### 监控系统设计

| 层           | 设计                                                                                                                                                                                                     |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 采集         | MySQL `performance_schema.data_lock_waits` / `sys.innodb_lock_waits`、应用侧锁注册表（谁持锁、谁在等、等多久）、分布式锁的 `owner + ttl`、Go runtime 的 goroutine 栈；统一带 `trace_id`、时间戳、资源 id |
| 构图         | 按滑动窗口聚合（如 5s），**过期边自动剔除**，避免用陈旧等待关系误报；按租户/实例分片构图控制规模                                                                                                         |
| 检测         | 周期 1–5s 跑 DFS；边数超过阈值时降级为采样 + Kahn；记录环长、环上等待最久的事务、回滚代价估算                                                                                                            |
| 告警         | 「持续 N 个周期仍存在同一环」才告警（区分瞬时锁竞争与真死锁）；带上环路径、SQL、持锁时长、建议牺牲者；按 severity 路由、相同指纹抑制                                                                     |
| 处置         | 只读告警 → 人工确认或自动回滚代价最小者；同时输出「固定加锁顺序」类的根因提示                                                                                                                            |
| 自监控       | 采集延迟、构图耗时、检测 CPU、漏报（用 `show engine innodb status` 的 `LATEST DETECTED DEADLOCK` 做对账）                                                                                                |
| 设计层消除环 | ✅ 项目锚点：`yukino-cache-go.md` 的 `isPeerRequest(ctx)` 让被转发请求不再二次 PickPeer，**从机制上消除环路**，比事后检测更彻底                                                                          |

> **加分边界**：分布式场景没有全局时钟，跨进程等待图会不一致 → 需要向量时钟/统一 trace 或退化为「超时 + 租约」检测；多实例资源下「有环」只是充分条件，还要结合资源可用数判定。

> 续传是应用层分块状态机：校验返回缺失块下标，服务器进度就是磁盘上的 chunk 文件集合，5 MiB/块、并发 3、重试 3 次；HTTP 的 `Range/206/Content-Range/If-Range` 是**下载**语义，上传要做到块内偏移得用 `PATCH + Content-Range` 或 tus，所以 2.5M 那块若没写完整要重传这一块，但前面的块不用。虚拟滚动是少渲染节点：定高用除法定位，不定高用预估高度 + 前缀和二分 + ResizeObserver 实测增量重算 + 绝对定位，历史加载要补 scrollTop。告警归属率这类指标我熟悉定义与验证，但项目里没有落地记录，不会当做过。死锁四必要条件里最容易破的是循环等待；检测就是建等待图、用 DFS 三色或 Kahn 找环，采集 `data_lock_waits` 与锁注册表，滑动窗口构图、持续多周期才告警，并带环路径与回滚建议。
