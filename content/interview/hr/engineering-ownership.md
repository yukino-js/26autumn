## 研发的业务意识怎么表达

> 我理解用户和业务，是为了做对工程选择。比如用户接入不了，要看 SDK 和文档；任务失败了，要能知道失败在哪一步；成本过高，要能分清模型消耗、执行资源和无效重试。我的职责是把这些问题落实为可以验证的研发交付。

不把参与需求讨论写成负责产品路线、定价或营收目标。想推动商业化，可以从接入成功、运行可靠、成本透明和付费场景反馈切入。

## 四个研发场景练习

以下均为假设题，回答时使用「我会」。

### 用户说 SDK 不好用

先复现用户最短接入路径，确认运行环境、接口版本和失败信息。根据问题决定改类型、异常、示例还是服务端行为。完成后跑通最小样例和失败路径，再收集反馈。

**可用经历：** 监控 SDK 的插件与子路径拆分、模型协议接入。不能说已替目标团队提高接入转化率。

### 长任务页面断开，用户重复点击执行

先确认任务身份和状态，区分「页面没收到结果」与「后端没有执行」。前端恢复展示应查询或订阅原任务；重新执行涉及副作用时，需要服务端幂等或业务确认。

**责任边界：** 网络重连不等于任务重试，任务重试不等于副作用可以重复。具体恢复语义必须以服务契约为准。

### Agent 创建沙箱后失败

明确任务与沙箱各自的生命周期、谁拥有清理责任、能保留哪些排查证据。对异常退出、取消、空闲超时和租户配额分别设计行为，再验证资源是否真的释放。

**可用经历：** 腾讯资源池的异常覆盖与归还前校验；个人沙箱实践。迁移的是思考方法，不能说故障模型完全相同。

### 为赶进度是否跳过验证

先区分必须保障的边界与可缩减的非核心范围。权限、数据正确性、资源释放等关键路径要有验证；时间不足时同步风险，建议缩小交付范围、灰度和保留回滚路径。

## 从「我做了功能」讲到「我负责结果」

| 普通表达            | 更完整的研发表达                                              |
| ------------------- | ------------------------------------------------------------- |
| 我接入了一个模型    | 说明输入输出、流式和错误边界，以及怎样验证接入                |
| 我加了重试          | 区分可重试错误、重试预算、取消和副作用风险                    |
| 我做了缓存          | 说明命中口径、失效与数据正确性，而不只报命中率                |
| 我接入了 A2UI       | 说明服务端重试、客户端降级，以及失败时用户看到什么            |
| 我用 Agent 修了 bug | 说明复现、修改、测试、人工 review 和 MR，而不直接等同安全上线 |

## 商业化与研发如何关联

> 我希望产品最终能为用户创造价值并形成商业回报。作为研发，我能直接负责的是把能力交付好，让用户能顺利接入、稳定使用、看懂成本、排查问题。B 端可能更关注集成与治理，C 端可能更关注任务完成与体验；具体优先级需要结合团队真实客户和业务数据判断。

这是本人愿景，不是断言目标团队已经同时经营 B/C 两类产品。不要承诺未经提供的续费率、付费转化率或营收。

## 提前同步风险的表达

> 我现在确认了 A，B 还没有证据。如果按当前方案交付，主要风险是 C。我建议先交付 D，并在某个时间点给出 B 的验证结果。如果优先级有变化，我会同步调整范围。

这是沟通模板，具体时间和事项必须对应真实任务。
