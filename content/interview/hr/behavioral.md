行为面不是「讲故事比赛」，而是 HR 用你的过去预测你的未来。每题的底层只有三个问题：**你真的做过吗？你怎么想的？换个环境你还会这么做吗？** 下面的答案都按 **STAR + 一个数字 + 一句反思** 组织，控制在 60–90 秒；不要逐字背，背「动作顺序」和「关键数字」。

## Q1 你最有成就感的一件事是什么

**结论：** 把阿里妈妈的经营托管 Agent 从 0 做到淘宝商家端上线，并且把「模型可能乱承诺」变成可测的工程约束。

**S（背景）：** 商家经营客服和讲师团队人力成本高，需要一个能回答经营问题、查订单/政策、还能持续迭代的 Agent。团队担心的不是「答不出来」，而是「答错了导致纠纷」。

**T（任务）：** 我负责确定性 workflow 与 agent 的混合编排、RAG 检索、生成前的置信度校验、A2UI 接入和数据飞轮。

**A（动作）：**

1. 用 LangGraph4j 编排 **8 类意图 → 5 个出口** 的分流状态机；指代消解、query 扩写、意图识别、RAG + BM25 双路召回、置信度校验、agent loop 都由 workflow 调度。
2. 把「查订单/查政策」这类 **必经步骤** 放在 workflow 里，agent 只在证据足够后做判断和回答，从架构上排除「模型跳过步骤导致错误承诺」。
3. 生成前做 **三信号加权的置信度打分**：证据不够先追问，追问后仍澄清失败就转人工。
4. 检索用 RRF 粗排 + reranker 精排，并用 500 题五桶评估集做迭代。

**R（结果）：** 已在淘宝商家端落地；450 道可回答题上 `recall@5 98%`、答案覆盖率 97%、人工核验幻觉率 0.7%；置信度门控误放率 0%、误拦率 17%。

**反思：** 最大的成就感不是数字，而是 **把不确定的模型放进了确定的业务约束里**。误拦 17% 说明我们宁可多问一句，也不乱承诺；下一步是优化追问策略和阈值，把误拦降下来。

**采分点：** 先讲业务风险，再讲架构，再讲数字，最后讲边界。**雷区：** 一上来讲 LangGraph4j、RRF、reranker，HR 会失去主线；把「0% 误放」说成「模型不会错」——它是门控后的结果，不是模型本身。

## Q2 实习中压力最大的时刻

**结论：** 腾讯 IEG 的一次堆外内存泄漏，现象是 RSS 持续增长、但 V8 堆稳定；如果定位不到，就只能靠重启兜底。

**S：** 管理端是长期运行的服务，RSS 持续上涨会触发 OOM；但 `heapUsed` 很平稳，说明不是 JS 堆里的对象泄漏。

**T：** 我需要在不大规模改架构的前提下，定位根因并验证修复。

**A：**

1. **先分诊口径**：对比 RSS 与 `heapUsed`/`heapTotal` 两条曲线，判断是堆外而不是 JS 堆；再看 native/external 指标和连接池句柄。
2. **用工具定位**：用 Valgrind Memcheck 跑 ffi-napi 调 C++ `.so` 的路径，定位到 protobuf message 创建后没有释放。
3. **补释放路径**：在 NAPI 层补 `destroy` 调用，确保 message 生命周期结束就释放。
4. **兜底与验证**：用进程池隔离 `.so` 调用，避免 native 崩溃/泄漏影响主进程；修复后用 RSS 与 `heapUsed` 曲线持续观察。

**R：** RSS 曲线恢复稳定，V8 堆保持平稳；同类解析场景有了进程池隔离，单次 native 崩溃不再带走主服务。

**反思：** 这件事让我养成两个习惯：**先分诊是哪个内存口径，再谈工具**；**进程隔离是兜底，不是根因修复**。只重启不定位，问题会回来。

**追问「为什么不用 heap snapshot？」** heap snapshot 看的是 V8 堆；这次 V8 堆稳定，问题在堆外，所以要用 Valgrind/native 侧工具。**追问「怎么确认修好了？」** 不是跑一次不涨，而是持续观察 RSS 与 heapUsed 的相对走势，并确认业务路径没有新增泄漏点。

## Q3 讲一次失败或踩坑

**结论：** 腾讯五类公共选择器从类组件迁移到函数组件时，我第一版机械翻译生命周期，踩了闭包过期值和请求竞态。

**S：** 集群/备用集群/数据库/表等选择器原来是类组件，生命周期逻辑分散，团队决定迁移到函数组件。数量多、结构相似，我用大模型批量迁移。

**T：** 验收标准不是「能跑」，而是 **行为完全一致**：交互、联动、边界 case 都要对上。

**A：**

1. 第一版把 `componentDidMount/Update/Unmount` 机械翻译成 `useEffect`，JSX 和 props 透传没问题，但异步回调捕获了当次渲染的旧 state。
2. 级联切换时，用户连续切条件，旧请求晚到覆盖新响应，下拉选项和选中态错乱。
3. 修法：effect 清理函数标记请求作废，或用 `AbortController` 中断；响应回来先校验「是否仍是最新请求」；state 按更新粒度拆分，避免对象合并丢字段。
4. 流程上改成 **规范先行 + 单组件迁移 + TDD + 小步提交**：先写生命周期映射和竞态规范，第一个组件人工精修做 few-shot，后面批量生成；每个组件迁移前后跑回归，出问题单独回滚。

**R：** 五类选择器完成迁移，级联联动回归通过；这套规范后面复用到其他组件。多面板挂载同一选择器时，请求从「每个实例一次」收敛为全局一次；级联切换只请求真正变化的层级。

**反思：** 重构不是重写，**验收标准是行为一致**。大模型可以加速机械翻译，但依赖数组、过期闭包、竞态、setState 合并语义这些高风险点必须人工 review + 测试兜底。

**雷区：** 把失败说成「别人代码烂」；把「用了大模型」当成亮点却不讲人工把关。

## Q4 和领导或导师出现分歧怎么办

**结论：** 阿里做经营托管 Agent 时，团队对「纯 agent 还是 workflow + agent」有分歧；我用「失败成本 + 可测指标」把争论变成实验。

**S：** 纯 agent 灵活、迭代快；但经营场景里「查订单/查政策」是必经步骤，模型一旦跳过就可能给出错误承诺，带来纠纷。有人担心 workflow 会把系统做死。

**T：** 在不拖慢上线的前提下，选一个能兼顾灵活性和可控性的架构。

**A：**

1. 先对齐目标：不是「谁的技术方案更先进」，而是「错误承诺的成本有多高、能不能承受」。
2. 把流程拆成「必经步骤」和「可自由判断」两类：查订单/查政策/知识检索走 workflow；证据足够后的判断和表达交给 agent。
3. 用 500 题评估集对比不同策略，重点看误放率/误拦率、答案覆盖率、幻觉率；先小流量灰度，再放量。
4. 把结论写成规范，后续迭代按同一口径回归。

**R：** 混合架构上线，误放率 0%、误拦率 17%；团队对「哪些步骤必须确定、哪些可以交给模型」有了共同语言。

**反思：** 分歧不可怕，可怕的是用立场代替指标。**先定义失败成本，再设计实验，最后用数据说服**；如果数据不支持我，我也会改。

**追问「如果领导坚持他的方案？」** 「我会先执行，同时把风险和验证指标说清楚；在小范围里保留对照，等数据出来再复盘。不会阳奉阴违，也不会因为坚持己见耽误上线。」

## Q7 你如何学习一项新技术

> 我分四步：**先读官方文档和源码，再写最小 demo，再看生产边界，最后写成文档/分享。**
>
> 例 1：做阿里 Agent 时学 LangGraph4j。我先读状态图、checkpoint、streaming 的文档，再写一个最小分流图，重点看「节点失败怎么恢复、状态怎么持久化、流式怎么中断」，最后落到 8 类意图 → 5 个出口的状态机。
>
> 例 2：做 A2UI/MCP 调研时，我先读协议消息模型，再对照官方 catalog 和示例跑通，最后把「传输契约、组件模型、安全边界」写成 `content/docs/a2ui.md` 和 `mcp-app.md`。
>
> 例 3：参与开源时，直接读 issue 和源码。比如 module-federation/vite 的 CJS/ESM 入口崩溃（PR #860）、coze-js 的 Android UA 缺失（PR #257），都是先复现、再定位、再提 PR。
>
> 我的判断标准不是「我听过这个名字」，而是「我能不能讲清它的失败模式、边界和替代方案」。

**采分点：** 给具体技术 + 具体动作 + 产出物。**雷区：** 「我学习能力很强」但没有例子；「我看官方文档」但没有 demo/落地。

## Q8 你如何快速熟悉业务

> 我在阿里做经营托管 Agent 时，业务不是从代码里读出来的，而是从 **角色、流程、数据和风险** 四个面切进去的：
>
> 1. **角色**：商家、客服团队、讲师团队分别解决什么问题，谁最痛。
> 2. **流程**：从商家提问到查订单/查政策/给方案，哪些步骤必须走、哪些可以跳。
> 3. **数据**：工单、知识库、评估集、线上反馈，哪些指标能定义「答得好」。
> 4. **风险**：错误承诺、纠纷、合规，哪些错误不可接受，必须先拦。
>
> 然后做一个最小闭环：先覆盖高频意图，再上评估集，再看误放/误拦，最后用数据飞轮迭代。**我不会先写一个「通用 Agent」再找场景**，而是先找「哪一步最痛、哪一步可测」。

**追问「如果业务你不熟悉怎么办？」** 「先找最懂业务的人访谈，再跟着走一遍流程，最后用自己的话复述给对方确认；不复述就动手，很容易做错方向。」

## Q9 讲一次跨团队合作

> 腾讯的 JSError 自动修复 Harness 是一个跨团队链路：前端监控负责采集错误、sourcemap/componentStack 反解、用户行为和录屏上下文；Agent 负责定位/修复/验证；CI 负责推分支、创建 MR。
>
> 我的角色是把「错误上报」到「MR」这条链路串起来：定义修复任务需要哪些上下文、哪些字段必须带、失败怎么回退、MR 里要包含什么归因和验证信息。难点不是写一个 Agent，而是 **让不同团队对「什么算修复成功」有共同标准**。
>
> 我的做法是先跑通一条最小链路：一个真实 JSError → 反解 → 修复任务 → 分支 → MR，再逐步加错误类型和验证步骤。这样每个团队都能看到自己的输入输出，合作成本最低。

**采分点：** 讲清「我协调了什么」而不是「我们团队做了什么」。**雷区：** 把跨团队说成「我指挥了所有人」。

> 我最大的不足是 **容易先钻细节，后看全局**。比如排查内存泄漏时，我会先想去看 native 代码，而不是先分诊 RSS 和 heap；做 Agent 时，我会先想调检索，而不是先定义业务指标。这让我在局部很扎实，但有时会拖慢整体判断。
>
> 改进方式：先问三个问题——「这件事的成功指标是什么」「最可能的 2 个原因是什么」「30 分钟内没有进展找谁」；写方案先写一页纸的结论和取舍，再展开细节。现在我会刻意先给 30 秒版本，再进技术细节。

**雷区：** 「我太追求完美」「我工作太努力」；「我没有不足」。

## Q16 讲一次你说服别人的经历

> 阿里做经营托管 Agent 时，团队里有人倾向纯 agent，认为 workflow 太重、迭代慢。我没有直接反驳，而是把问题换成「错误承诺的成本」：
>
> 1. 列出哪些步骤是必经的：查订单、查政策、知识检索；这些一旦跳过，模型就可能编。
> 2. 提出混合方案：必经步骤走 workflow，证据足够后的判断交给 agent；这样既保留灵活性，又不会跳过关键步骤。
> 3. 用 500 题评估集对比，重点看误放率、误拦率、答案覆盖率；先小流量灰度。
>
> 最后团队接受了混合架构，上线后误放率 0%、误拦率 17%。我的体会是：**说服别人不是靠嗓门，是靠把隐性风险变成可测指标，再让对方自己看到数据。**

## Q17 讲一次别人说服你的经历

> 腾讯迁移五类选择器时，我一开始想「一次迁完、统一回归」，觉得这样效率高。团队 review 时提醒我：选择器之间有级联关系，一次改五个，出问题很难定位是谁影响的；而且这是存量系统，回滚成本高。
>
> 我采纳了「一个组件一次提交、迁移前后各跑回归、出问题单独回滚」的做法。后来确实有一个组件在级联切换时出现竞态，如果五个一起改，排查成本会高很多。这件事让我接受了一个原则：**在存量系统里，可回滚比一次做完更重要。**

## Q18 你怎么看待 AI 替代工程师

> 我觉得 AI 会替代「重复的、可验证的、边界清晰的」部分，比如模板代码、简单 CRUD、部分测试和文档；但不会替代「定义问题、做取舍、承担责任」的部分。Agent 能写代码，但它不知道这个需求该不该做、这个指标是不是自欺欺人、这个故障对用户意味着什么。
>
> 我自己做 Agent，但我不会迷信 Agent。我的做法是把它当成一个执行力很强但需要验收的同事：给它清晰的上下文、工具和权限边界，用评测和人工 review 兜底。**工程师的价值会从「写得多」转向「定义得准、验得严、扛得住」。**

## Q19 你是一个什么样的人

> 我是一个 **偏工程、重证据、愿意兜底** 的人。
>
> 偏工程：我喜欢把问题拆成可执行、可验证的步骤，而不是停留在讨论。重证据：我说一个方案好，会尽量给 baseline 和指标；没有数据就说「这是方案推导」。愿意兜底：遇到模糊地带，我不会说「这不是我的模块」；腾讯的内存泄漏、监控 SDK、迁移，很多都是跨层的问题，我会先把它接住，再找对应的人一起解。
>
> 缺点我也清楚：有时太钻细节，表达不够精炼；这个我在改，先给结论，再展开。

## Q20 你有什么兴趣爱好

> 我平时的主要爱好是 **写开源项目和看技术文档**，`yukino-code` 就是业余时间一点点写出来的；另外我会通过运动/看书来换脑子，保持状态。`[按真实情况替换：跑步、羽毛球、摄影、做饭等；不要编一个自己没做过的爱好]`

**HR 为什么问：** 不是查户口，是看你有没有工作之外的调节方式、是不是一个「正常好相处」的人。**回答纪律：** 真实、具体、一两句；不要编「我喜欢阅读哲学」这种容易被追问穿的内容；也不要说「我没有爱好，只有工作」。

## 稳定性与软实力四问（短场高频）

HR 短场常把这四题连着问，考的不是知识点，是**抗压、沟通、优先级判断和匹配度**。每题 60 秒，复用已有故事，不要另编。

### Q21 项目做完后你怎么复盘？数据不好时怎么推进？

> 我复盘只看三件事：**目标有没有达成、没达成卡在哪、下次改什么**。阿里那个 Agent 上线后，误放率是 0%，但误拦率 17%，说明门控偏保守。我没有把「误放 0%」当成功就结束，而是把误拦的样本捞出来分类：是证据不足、检索没召回，还是阈值太严；然后先用评估集做阈值消融，再小流量灰度。数据不好时我的顺序是：先确认口径有没有错，再定位是模型、检索还是流程的问题，最后才改方案——**不在口径没对齐的时候调参数**。

**采分点：** 有复盘结构 + 一个真实数字 + 改进动作。**雷区：** 把复盘说成「总结经验、继续努力」；数据不好就归因于「模型不行/需求变了」。

### Q22 资源紧张、排期冲突时，你怎么跨团队沟通？

> 我会先把「争资源」变成「排优先级」。腾讯做 JSError 自动修复链路时，前端、Agent、CI 三个团队都有自己的排期；我的做法是把链路拆成最小可运行版本，明确每个团队只需要提供什么、什么时候要，再一起确认「什么算跑通」。如果资源还是不够，我会把选项摆出来：砍范围、延时间、还是先保哪一段，让业务方做取舍，而不是我在中间硬扛。**沟通的目标不是让所有人满意，是让风险提前可见。**

**采分点：** 有具体协作对象 + 有取舍机制 + 不抢功。**雷区：** 「我会多沟通、多协调」；把冲突说成「我说服了他们」。

### Q23 你的职业方向会不会变？我们怎么相信你能待住？

> 我三段实习看起来方向不同，但主线是一条：字节练「测量」，腾讯 IEG 练「稳定」，阿里练「自动化」，合起来就是「把 Agent 从能聊做到能上线」。这不是试错式跳槽，是在补同一件事的不同能力。我现在明确想做 Agent 工程化，也知道自己还有哪些要补；频繁换方向对积累没有好处，我希望在一个有真实场景的地方做深。

**采分点：** 用主线解释三段经历 + 明确当前方向 + 承认要补的。**雷区：** 「我都可以」「看公司安排」；把三段实习说成「随便试试」。

### Q24 如果我们给你 offer，你会来吗？你还有什么在看的？

> 腾讯是我的优先选择，原因不是「大厂」，是这个岗位能把我三段经历串起来，而且腾讯云的 toB 场景对 Agent 工程化的要求最高。其他流程我会如实说，但不会拿它们来抬价；如果拿到 offer，我会在约定的时间内给明确答复，不会拖着占名额。

**采分点：** 明确意愿 + 诚实说其他流程 + 给答复节奏。**雷区：** 「我一定来」但后面失联；「我还有很多 offer」式炫耀；编造 offer 抬价。

:::note 行为面的通用追问链
HR 常用的追问不是新题，而是把同一个故事往下钻：**「当时还有别的方案吗？」「为什么选这个？」「如果重来一次你会怎么做？」「这件事里别人怎么评价你？」** 每个故事准备这三层，比准备 50 个故事更有用。
