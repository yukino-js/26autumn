## 故事怎么讲

使用「背景 → 本人任务 → 关键动作 → 证据 → 复盘」。第一轮约 90 秒。背景两句以内，重点留给自己的动作。没有明确证据的冲突、失败、评价和导师反馈，不因为符合 STAR 就编造。

## Q1 最有成就感的事

> 我想讲经营托管 Agent 的一部分。它服务商家经营，错误回答可能带来纠纷，所以我们需要把回答质量和流程约束一起考虑。
>
> 我参与 workflow 与 Agent 的混合编排，让检索、订单或政策查询等必要步骤由 workflow 调度，生成前再判断证据是否足够；不足时追问，仍然不能澄清就转人工。我也参与混合检索和评测，相关能力已经在淘宝商家端落地。
>
> 这件事让我有成就感，是因为研发工作真正进入了用户场景。我也看到质量与体验需要继续平衡，例如误拦会让原本能回答的问题被拦住，不能只追求某个数字漂亮。

追问：本人负责哪些节点？哪些是团队设计？怎么定义误放和误拦？评测与线上有什么差别？数据飞轮具体负责什么？没有业务降本金额，就不报金额。

## Q2 最困难、压力最大的事

> 腾讯实习里有一次内存问题，V8 堆内存比较稳定，但进程 RSS 持续增长。我先区分堆内和 native 内存，再用 Valgrind Memcheck 排查 ffi-napi 调用的 C++ 库，定位到 protobuf message 没有释放的路径。补充 destroy 调用后，再结合 RSS 和 heapUsed 曲线确认修复。
>
> 这让我学到，表面现象不能直接当根因。排查要按层次缩小范围，修复后也要在明确的负载和观察窗口下验证。

技术动作来自简历；当时影响范围、排期、个人心理压力、是否线上紧急事故的处置过程没有完整提供。若题目专门问「压力」，补充本人真实感受，不编造连续熬夜和救火情节。

## Q3 你做得不好的事或失败经历

当前简历没有提供一段明确的个人失败事件。不要把「误拦率 17%」自动改写为「我上线失败」，也不要把后来发现的问题自动说成是自己引入的 bug。

面试前选一件真实的小事，补齐：

1. 当时自己的错误判断是什么。
2. 对进度、质量或他人造成了什么实际影响。
3. 自己怎样承认问题、同步风险并修正。
4. 后来在哪个真实任务中验证改进有效。

可寻找的素材方向：需求理解偏差、估时不准、遗漏边界、过早抽象。只使用真实发生的事件。

## Q4 和 leader 或导师有分歧怎么办

**目前没有已确认的冲突事件，以下只能作为处理方法回答：**

> 我会先确认双方目标是否一致，再把分歧写成可以验证的问题。涉及方案取舍时，我会明确成本、风险和验证办法，用小范围实验或现有数据讨论。最终方案确定后，我会按分工推进，同时保留风险监控和必要的回退手段。

workflow 与 Agent 的边界可以作为技术取舍例子，但不能虚构成「导师坚持纯 Agent，我说服了他」。若要求真实经历，必须替换为本人确实经历过的分歧。

## Q5 优点是什么

> 我比较愿意把问题追到具体原因，也愿意把链路做完整。腾讯 native 内存问题让我练习分层定位；监控自动修复链路则把错误上下文、修复任务、验证和 MR 连接起来。我希望继续把这种习惯用在 Agent 的运行和调试上。

不要把「比较愿意」升级为「任何问题都能定位」，也不要编造导师评价。

## 用三个词描述自己：有理想、有激情、可靠

> 我会用有理想、有激情、可靠来概括自己。有理想，是希望长期做出对用户有价值的 Agent 产品；有激情，是我会持续关注新技术，也一直用个人 Coding Agent 做实践；可靠，是我重视把具体问题定位清楚、把结果验证好，比如腾讯实习中 native 内存问题的排查与修复。
>
> 我也热爱学习，能把学习用到实际开发里。从模型 API、Agent 编排到前后端交付，我已经有比较扎实的实践基础，希望在团队里继续深化。

这是本人自评。追问学习能力时，选一个真正掌握的模块讲清学习、实现与验证过程；不编造学习用时或同事评价。

## Q6 缺点是什么

选择本人认同且有实例的一项：估时、沟通、过度投入细节、对业务理解不够深入。以下是结构示例，不是既定自评：

> 我在某类任务里容易先钻实现细节，导致阶段同步不够及时。后来我开始在动手前确认验收标准，任务中按节点同步进度和风险。最近一次任务中，这让我更早发现了某个依赖问题。

没有真实实例时不背最后一句。不要把缺点包装成「太追求完美」。

## Q7 怎么学习新技术

> 我通常先找官方资料，跑通最小样例，再围绕一个实际问题做小实验。自己的 Coding Agent 给了我持续实践的载体，例如模型协议、缓存、上下文和工具加载。学完以后我会记录适用场景、失败边界和验证结果，判断是否值得引入业务。

追问可选一个真实模块展开：为什么要做、资料怎么找、最先遇到什么错误、最后怎样验证。避免只列工具名字。

## Q8 如何熟悉新业务

> 我会先把用户、核心任务、输入输出和失败代价弄清楚，再从一条完整请求链路看代码。接着确认模块边界、验收指标和上下游依赖，用一个小任务验证理解。遇到不确定的地方会带着具体问题向同事确认，而不是只看技术架构图。

这是入职方法；若被追问「淘天当时具体怎么做」，按真实过程补充，不能把方法直接说成已经逐步执行过。

## Q9 跨团队协作怎么体现

可用素材是 JSError 自动修复 Harness、native 绑定、A2UI，但简历只给出实现内容，未给出协作对象和过程。准备时补齐真实的接口约定、沟通对象、依赖、争议和验收。

> 我会把需求和接口写清楚，提前确认输入输出、异常和验收方式。依赖有风险时尽早同步，让相关同事知道我需要什么、预计什么时候完成、什么问题可能影响交付。

不能自动补成「我协调 DBA、安全、SRE 三个团队」。

## Q10 如何使用 AI 编程并保证质量

> 我会先明确任务边界和验收标准，让 Agent 在约束下生成或修改代码，再通过测试、类型检查和人工 review 判断结果。腾讯公共选择器迁移里，我参与沉淀生命周期到 hooks 的映射和 state 拆分规范，结合 TDD 和 Agent 批量迁移。我仍然对代码行为负责，不能把模型输出直接视为正确。

追问：生成测试能否独立验证需求？如何避免测试与错误实现互相印证？高风险改动怎样 review？自动创建 MR 与自动合并上线有什么区别？

## Q11 给实习表现打分

> 我会按交付、质量、协作和业务理解分别评价。能完成的具体模块可以用结果说明，不足的地方也要讲清楚。我觉得自己还需要继续加深平台工程和业务理解，而不是只增加技术功能数量。

如果要求十分制，用真实自评分，并配一个优点与一个具体不足；不要替本人预设「导师给我九分」。

## Q12 兴趣爱好、他人评价

只讲真实生活与原话。个人 Coding Agent 能说明持续投入，但不必让所有兴趣都服务于求职。女朋友在深圳可以回答稳定性问题，不能代她编造评价。工作之外的爱好、同学评价和导师反馈均待本人补充。
