## 你说熟悉云沙箱，具体做过什么

本人已补充通过实习熟悉云沙箱，但缺少可直接口述的细节。面试前填好这张卡：

| 必答项 | 需要本人补充                                             |
| ------ | -------------------------------------------------------- |
| 场景   | 哪段实习、什么任务、为什么需要云沙箱                     |
| 角色   | 使用、接入、封装 SDK、后端实现或运维中的哪一层           |
| 动作   | 创建、执行、文件交互、网络策略、取消与回收中具体做了什么 |
| 问题   | 遇到什么失败，怎样定位与修复                             |
| 验证   | 如何证明功能、隔离或资源清理符合预期                     |

可以先说真实参与范围，再承认未做过的部分。OS 级本地沙箱和腾讯 native 进程池提供相关基础，但不能拿它们替换云沙箱经历。

## 本地沙箱与云沙箱有什么不同

> 我的个人项目实践主要是本地权限与 OS 级执行约束。云端还涉及租户、身份、网络、资源配额、调度和生命周期，故障与攻击边界更复杂。我有相关思考基础，但不会把本地沙箱经验等同于云平台建设经验。

## Agent Team 不就是分布式 Harness 吗

> 它们有任务协作方面的联系，但不等同。个人项目里的文件邮箱、Worktree 和多 Agent 通信，主要解决协作与工作区隔离；分布式生产执行还要解决任务归属、状态恢复、重复执行和云资源管理。我会把已做的协作机制讲清楚，也承认后者需要继续实践。

## Agent 指标这么好，靠谱吗

> 我会限定在当时的评测样本、配置和判定规则下讲。比如 recall@5 的 98% 对应 500 题中 450 道可回答题的评测；误放率 0% 是实验观测，不能外推成生产绝对安全。相关分母和样本划分需要分别说明，指标也不能直接替代用户效果或收入。

## 误拦 17%，用户体验不是很差吗

> 这是需要面对的取舍。减少错误放行有价值，但误拦会让本来可回答的问题无法直接完成。我会结合样本看原因：检索不足、证据门控还是问题需要澄清，再分类型改进。同时要看错误放行、任务完成和人工兜底，不能只优化一个数字。

这是分析方法。未提供后续误拦下降结果，不能加上「最后降到某个数」。

## 缓存命中 >90%，是不是成本也降了 90%

> 不是同一个指标。简历中的命中率是在部分实测场景下取得，场景不同会变化。要评估成本还需要看命中 token 的计费、未缓存输入、输出、工具调用和执行资源。我会按真实账单或 usage 口径计算，不能直接用命中率替代降本比例。

## 你的 Coding Agent 是不是套壳

> 模型能力来自厂商，我负责的是围绕模型的工程层，包括协议接入、工具与权限、上下文、会话和协作。我会用具体代码、失败案例和评测说明做了什么，不以功能列表或「完全自研」概括全部价值。

## 自动修复会不会制造更严重的问题

> 自动修复的结果仍然需要验证。我的简历描述的是从错误上下文到修复、验证、推送分支和创建 MR 的链路，不能等同于无人审核直接上线。我会解释验证范围和人工 review 的责任边界。

## 全栈会不会什么都会一点

> 我希望围绕 Agent 执行链路形成深度，再用前后端能力交付完整功能。现在我可以用模型协议、权限和上下文这些具体模块说明自己的实践，同时用腾讯的故障治理说明工程基础。对未深入的领域，我会明确说还需要学习。
