## 一、etcd：强一致的分布式键值存储

etcd 的定位是“小而可靠”：数据量不大，但要求线性一致、支持 Watch 与租约，是 Kubernetes 等系统的元数据底座。理解它要抓住三条主线——Raft 共识决定写入是否提交、MVCC 决定历史版本如何保存与查询、Lease/Watch 决定它如何被用作协调与发现组件。

### 1.1 数据模型：带版本的键值空间

etcd 对外是一个扁平的键空间，所有键按字典序排列，天然支持前缀查询。与普通 KV 的差别在于每个键都携带版本信息：

- revision：全局单调递增的逻辑时钟，由 Raft 提案序列决定其顺序；一次事务内多个操作共享同一个 main revision，用 sub revision 区分先后。
- create_revision / mod_revision / version：分别表示该键创建、最后一次修改、被修改的次数。
- lease：键可绑定租约，租约到期后键自动删除。
- tombstone：删除并非立即抹掉，而是写入一条删除标记，历史版本仍可查询。

由于所有键有序，range 查询（`WithPrefix`、`WithRange`）是 O(log N + M) 的树遍历加顺序扫描，而不是全表扫描；排序与范围过滤也由同一套索引承担。这个模型直接决定了 etcd 擅长“按前缀组织的配置、服务实例、元数据”，而不适合存放大对象。

### 1.2 Raft：如何达成共识

Raft 把一致性问题拆成三个子问题：选主、日志复制、安全性。

选主。节点在 Follower、Candidate、Leader 三个状态间迁移。Follower 在 election timeout 内没有收到 Leader 心跳就转为 Candidate，递增任期并请求投票；获得多数票（N/2+1）者成为 Leader。有两点是工程上最关键的：

- 日志较新的节点优先当选。投票时先比较最后一条日志的任期，再比较索引，保证新 Leader 一定包含所有已提交日志。
- 选举超时随机化，在 [electionTimeout, 2×electionTimeout) 内取值，避免多个节点同时发起选举导致选票被反复瓜分（活锁）。

日志复制。客户端写入只能发给 Leader；Leader 把条目追加到本地日志（此时尚未提交），并行向所有 Follower 发 AppendEntries；当多数节点复制成功后，Leader 推进自己的 commit index 并把日志应用到状态机，随后通过下一次心跳把 commit index 告知 Follower。因此“多数派确认”是一次写延迟的组成部分，跨机房部署会直接放大写延迟。

安全性。Raft 用五条不变量保证状态机一致：

| 不变量               | 含义                                                   |
| -------------------- | ------------------------------------------------------ |
| Election Safety      | 同一任期内最多一个 Leader                              |
| Leader Append-Only   | Leader 从不覆盖或删除自己的日志                        |
| Log Matching         | 两条日志在相同 index/term 上一致，则此前所有条目都一致 |
| Leader Completeness  | 已提交的条目一定存在于所有后续 Leader 的日志中         |
| State Machine Safety | 同一 index 上所有节点应用相同命令                      |

etcd 在标准 Raft 上补充了几项工程优化：

- PreVote：节点在真正递增任期前先试探能否拿到多数票，避免网络分区恢复后把健康的 Leader 逼下台。
- CheckQuorum：Leader 周期性确认自己仍与多数节点连通，否则主动退位，减少“僵尸 Leader”读。
- Learner：只复制日志、不参与投票的角色，用于新节点先追平数据再晋升，避免扩容期间多数派被拖慢。
- 成员变更：通过 ConfChange 执行，且同一时刻只允许一个变更在进行；涉及多节点的复合变更会先进入联合配置（joint consensus）再退出，避免出现两个互不相交的多数派。

### 1.3 MVCC 与底层存储引擎

etcd 的 MVCC 由内存索引加本地存储引擎组成。内存中为每个键维护一个 keyIndex，记录该键在各代（generation）中出现过的所有修改版本；一次删除后再写入会产生新的一代。存储层把 revision 映射到实际的键值对。

读请求的处理路径是：先确定要读的 revision（0 表示读最新，正数表示读历史，小于 compact revision 则返回 ErrCompacted），在 keyIndex 中二分查到不晚于目标 revision 的修改版本，再用该版本从存储引擎取出键值；如果命中的是删除标记，则键不存在。这条路径意味着历史读的开销与当前数据量无关，只与目标键的修改次数有关。

Compaction 与 Defrag 是两件必须区分的事：

- Compact 只做逻辑删除，丢弃指定 revision 之前的历史版本，键空间的最新值不受影响；好处是控制内存索引与存储增长。
- Defrag 才真正重建底层文件、把空洞释放回文件系统。它需要逐节点执行，并会短暂阻塞该节点的读写。

两者配合的方式是：开启自动压缩，把 compact 控制在合理范围；当文件碎片率升高时择机 defrag。碎片率可以近似看作“文件总大小与在用大小之差占文件总大小的比例”，超过一个较高阈值（常见 50%）就值得整理。

本地存储引擎选择的是一个进程内嵌的、单文件的 B+ 树实现，它的特性与 etcd 的需求高度吻合：

| 引擎特性     | 具体表现                                                     | 对 etcd 的价值                             |
| ------------ | ------------------------------------------------------------ | ------------------------------------------ |
| 单文件 B+ 树 | 数据与索引在同一文件中，页式组织                             | 只需一个文件，备份与迁移简单               |
| 写时复制     | 修改页时复制路径上的页                                       | 崩溃后不会看到半写状态，天然具备崩溃一致性 |
| 单写多读     | 同一时刻只允许一个写事务，多个只读事务可并发                 | 与 Raft 单主写入模型一致，无需额外并发控制 |
| 内存映射读   | 把文件映射到虚拟地址空间，读操作零拷贝                       | 读多写少场景下读延迟低                     |
| 键全局有序   | 叶页内元素按键有序、页按键序布局，范围扫描由游标沿树遍历完成 | 天然支持范围扫描，与 etcd 的键序模型契合   |

它同时带来几项固有局限，需要在运维上应对：

| 局限          | 表现                                 | 应对                                                                       |
| ------------- | ------------------------------------ | -------------------------------------------------------------------------- |
| 写放大        | 写时复制会复制整条路径上的页         | 用批量提交把多次提案合并成一次后端写入，摊薄落盘开销                       |
| 单写锁        | 写入串行执行                         | 真实写入瓶颈通常在 Raft 共识而非引擎本身，扩容写入能力要靠更快的磁盘与网络 |
| 文件只增不减  | 删除不会缩小文件，空间以空洞形式存在 | 定期压缩历史版本，配合离线整理回收空间                                     |
| 大 value 低效 | 值越大，复制与序列化成本越高         | 通过请求大小上限约束单条数据规模，大对象应放到对象存储                     |

这可以解释一个常见误解：etcd 的写入能力瓶颈不是“键值存储引擎慢”，而是“每次写入都要经过多数派共识”。因此提升写吞吐的正确方向是改善磁盘落盘延迟与网络往返，而不是更换存储引擎。

### 1.4 Watch：基于流的事件订阅

Watch 不是轮询，而是建立在 gRPC 双向流与 MVCC revision 之上的增量推送。客户端指定键或前缀，可选指定起始 revision；服务端为每个 watcher 记录监听范围，并按是否落后于当前 revision 分成需要追赶历史的分组和只等实时事件的分组。当一次写入提交后，事件按 revision 顺序投递给匹配的 watcher。

```text
客户端 (gRPC Watch 流)
      |
      v
服务端 watch 组件
   |-- 已同步组：起始 revision >= 当前 revision，只等实时事件
   |-- 待同步组：起始 revision < 当前 revision，先从历史日志追赶
      |
      v
本地存储引擎（未压缩的历史事件）
```

使用 Watch 时要建立几个正确认识：

- 事件在同一键上严格按 revision 有序，跨键不保证全局有序，业务侧若需要全局顺序要自己用 revision 排序。
- 断线重连后可以从上次处理到的 revision+1 继续，不必全量重拉，前提是那段历史尚未被压缩。因此客户端必须处理 ErrCompacted，收到后走一次全量读取再重新 Watch。
- 支持进度通知（progress notify）：服务端定期推送一个只带当前 revision 的空事件，用于让客户端感知“连接还活着但暂时没有数据”。它也是检测静默断连的手段。
- 支持过滤（如只收 PUT 或只收 DELETE）与 PrevKV（事件携带变更前旧值），能显著减少无用传输，但会改变事件完整性，使用前要确认业务是否依赖旧值。
- 监听范围过大会增加服务端遍历与匹配成本；大量 watcher 监听相同前缀时服务端会批量分发，但客户端仍要避免“每请求一个 Watch 流”的用法。

### 1.5 Lease、KeepAlive 与服务发现

Lease 是一个带 TTL 的租约，键绑定租约后生命周期与之绑定：租约到期或被撤销，键自动删除。这正好描述“实例存活期间注册、实例消失后自动摘除”的语义。

服务发现的完整生命周期：

```text
注册方
  1. 申请租约 (TTL = 10s 量级)
  2. Put /services/{svc}/{instance} = 地址与元数据，绑定租约
  3. 后台按约 TTL/3 的节奏续租
  4. 优雅退出时撤销租约，实例立即下线

发现方
  1. 首次 Get 前缀，拿到全部实例与该次读取的 revision
  2. 从 revision+1 开始 Watch 前缀
  3. PUT 事件加入实例列表，DELETE 事件移除
  4. 定期全量读取兜底，防止长时间断连带来的漂移
```

可靠性来自租约的“超时即失效”语义：进程崩溃后无法续租，租约到期键被删除；网络分区期间续租失败，但只要 TTL 窗口内恢复就不会误删。这里有两个生产要点：一是 TTL 的取值是“故障发现速度”与“误判风险”的权衡，过短会因偶发网络抖动频繁摘除实例，过长则故障收敛慢；二是续租必须是后台持续行为，并且要把续租失败当作告警信号，而不是静默重试。

### 1.6 读一致性：两种模式

etcd 默认提供线性一致读，代价是每次读都要与多数派确认 Leader 身份，跨机房时会明显变慢。它提供两种读模式：

| 模式                 | 一致性                     | 延迟                 | 实现                                                                   |
| -------------------- | -------------------------- | -------------------- | ---------------------------------------------------------------------- |
| Linearizable（默认） | 最强，能读到已提交的最新值 | 最高，需要多数派确认 | Leader 记录 readIndex，发心跳确认自身仍是 Leader，等状态机应用到该索引 |
| Serializable         | 最终一致                   | 最低                 | 直接读本地状态机，可能读到陈旧数据                                     |

选择依据很直接：配置读取、选主、分布式锁等不能读旧值，用默认模式；只做展示、容忍秒级陈旧的大盘类查询可以用 Serializable 读来降低对 Leader 的压力。

### 1.7 部署、容量与调优

etcd 的性能瓶颈几乎总是磁盘：每次提案要写 WAL 并 fsync，每次提交要写后端存储。因此首要原则是使用低延迟本地盘（NVMe SSD），避免与其它高 IO 负载共享磁盘，文件系统优先选择对 fsync 友好的类型。

集群规模通常取 3 或 5 个节点：3 节点容忍 1 台故障，5 节点容忍 2 台；7 节点及以上写延迟随多数派规模上升，收益递减。成员应跨故障域部署，但要意识到跨机房会直接抬高写延迟，需要在一致性与延迟之间取舍。

关键参数与推荐方向：

| 参数                             | 默认       | 说明与调整方向                                                          |
| -------------------------------- | ---------- | ----------------------------------------------------------------------- |
| --quota-backend-bytes            | 2 GiB      | 后端存储配额；超过会触发 NOSPACE 告警并只读，需要监控文件增长并及时压缩 |
| --snapshot-count                 | 100000     | 触发一次快照的已应用条目数；调小可加快重启恢复，代价是更多磁盘写        |
| --max-request-bytes              | 约 1.5 MiB | 单请求上限，放大要同步评估内存与复制开销                                |
| --heartbeat-interval             | 100 ms     | 同机房保持默认；仅在高延迟跨机房时适度放宽                              |
| --election-timeout               | 1000 ms    | 必须显著大于心跳间隔，通常为心跳的 5～10 倍                             |
| --auto-compaction-mode/retention | 未启用     | 按 revision 或周期自动压缩，避免历史无限增长                            |

需要重点盯住的指标：

| 指标                                                                       | 关注点                                      |
| -------------------------------------------------------------------------- | ------------------------------------------- |
| etcd_disk_wal_fsync_duration_seconds                                       | WAL 落盘延迟，P99 升高说明磁盘成为瓶颈      |
| etcd_disk_backend_commit_duration_seconds                                  | 后端提交延迟，反映存储引擎压力              |
| etcd_server_proposals_failed_total                                         | 提案失败计数，正常应长期为零                |
| etcd_server_leader_changes_seen_total                                      | Leader 切换次数，频繁切换说明网络或负载异常 |
| etcd_mvcc_db_total_size_in_bytes / etcd_mvcc_db_total_size_in_use_in_bytes | 数据库总量与在用大小，两者差距即碎片        |
| etcd_server_slow_apply_total                                               | 应用缓慢计数，提示状态机追赶不上提交        |

容量估算上，内存需求与键数量和平均键值大小强相关，索引本身有额外开销；磁盘上还要为 WAL、快照和历史版本留出余量，配额不是“能存这么多业务数据”，而是“后端文件不允许超过这个大小”。一旦触发配额，集群进入只读，必须通过压缩加 defrag 恢复，所以监控后端文件大小是必需的。

### 1.8 etcd 的适用边界

etcd 适合：配置中心、服务注册发现、分布式锁与选主、需要强一致的少量元数据、需要变更通知的协调场景。它不适合：大 value（超过请求上限）、高写入吞吐的数据面（写入受多数派共识限制）、需要复杂查询或聚合的数据。把 etcd 当通用数据库或消息队列使用是常见的架构误用，遇到这类需求应转向专门的存储或消息系统。

## 二、Kafka：高吞吐的分布式消息日志

Kafka 的本质是“分布式、可分区的追加日志”，消息不是消费即删，而是按保留策略留存，消费方通过位移自行推进。理解这一点，就理解了它与传统队列在语义、回溯能力、消费模型上的全部差异。

### 2.1 架构与元数据管理

核心角色包括生产者、Broker、控制器与消费组。分区是并行与顺序的基本单位：同一分区内严格有序，跨分区只保证按 key 的局部有序。消息路由规则是：指定 key 时按 key 的哈希选择分区，未指定 key 时客户端采用粘性策略在批次内尽量固定分区，以提升批处理效率。

早期 Kafka 依赖外部 ZooKeeper 管理元数据，当前版本已完全改用 KRaft：控制器组成一个 Raft 集群，元数据作为内部的元数据日志存储，由控制器选举产生活跃控制器。带来的直接收益是元数据变更与控制器故障转移从秒级降到更短，集群可以支撑更多的分区，同时少维护一套外部协调系统。

### 2.2 副本、ISR 与故障转移

每个分区有一组副本，其中一个为 Leader，其余为 Follower。ISR 是与 Leader 保持同步的副本集合。两个偏移量概念必须分清：

- LEO（Log End Offset）：副本下一条待写入消息的偏移。
- HW（High Watermark）：ISR 中所有副本 LEO 的最小值，消费者只能读到 HW 之前的消息，这保证了“读到即已复制”。

Follower 在 `replica.lag.time.max.ms`（默认 30 秒）内没有追上 Leader，会被移出 ISR。Leader 故障时，控制器从 ISR 中选取新 Leader；如果 ISR 为空，则取决于 `unclean.leader.election.enable`：允许时从落后的副本中选主，可能丢数据；禁止时该分区不可用，直到原 Leader 恢复。生产上通常选择禁止，用可用性换数据一致性。

### 2.3 消息不丢失与投递语义

“不丢”需要生产、Broker、消费三端协同：

| 端     | 关键配置                                                       | 作用                                       |
| ------ | -------------------------------------------------------------- | ------------------------------------------ |
| 生产者 | acks=all、retries 足够大、开启幂等                             | 等 ISR 全部确认；重试不产生重复            |
| Broker | replication.factor≥3、min.insync.replicas≥2、禁止 unclean 选主 | 至少两份同步副本才接受写入；落后副本不接管 |
| 消费者 | 关闭自动提交，处理完成后手动提交位移                           | 避免“先提交后处理”造成的丢失               |

投递语义取决于组合：acks=1 且自动提交接近至多一次；acks=all 且手动提交是至少一次；开启幂等生产者加事务并使用 read_committed 才是精确一次。需要特别指出，事务解决的是“跨分区写入与位移更新的原子性”，消费侧仍要做幂等处理，因为业务处理通常不是数据库事务的一部分。

精确一次的事务流程可以概括为：初始化事务、开启事务、写入若干分区、把消费位移也提交进事务、最后提交；消费者设置只读已提交事务的消息。这样“处理结果 + 位移”对下游是一个原子单元。幂等生产者的实现依赖 Broker 为每个生产者分配标识，并为每条消息附带分区内单调递增的序列号；Broker 据此发现并丢弃重复写入。因此幂等性保证的是“单分区、单生产者会话内不重复”，跨分区或生产者重启后的去重仍需事务与业务侧幂等配合。

### 2.4 消费组与再均衡

消费组内的消费者分摊分区，组间互不影响（广播语义）。分区分配由再均衡完成，触发条件包括成员加入或离开、心跳超时、处理超时、订阅变化等。

再均衡协议有两代：

- 急切式（Eager）：所有消费者先放弃全部分区，再重新分配，期间整个组停止消费（stop-the-world）。
- 协作式（Cooperative）：只迁移真正需要变动的分区，未受影响的分区持续消费，显著降低抖动。

新版本客户端还支持由 Broker 端主导的消费组协议，把分配决策从客户端搬到组协调者，减少客户端逻辑与再均衡停顿，属于部署时可评估的方向。减少不必要再均衡的常见配置思路是把会话超时与心跳间隔拉开（心跳远小于会话超时），把单次处理最大时长设为业务可接受的上限，并优先使用协作式粘性分配器。

分区分配策略决定“组内消费者如何分到分区”，常见几种：

| 策略 | 分配逻辑                           | 特点                                     |
| ---- | ---------------------------------- | ---------------------------------------- |
| 范围 | 每个主题把分区按区间顺序分给消费者 | 实现简单；订阅多个主题时容易分配不均     |
| 轮询 | 把所有分区依次轮流分配             | 比范围更均匀，但再均衡时迁移量大         |
| 粘性 | 尽量保留上次分配，只移动必要的分区 | 减少再均衡抖动，与协作式协议配合效果最好 |

粘性策略与协作式再均衡协议组合，能把“每次再均衡全量重新分配”变成“只迁移最小集合”，是降低消费抖动的主要手段。

### 2.5 存储结构与查找

每个分区对应一个目录，内部按段（segment）组织。每个段由数据文件、偏移索引、时间戳索引配套，文件名即该段起始偏移。查找一条指定偏移的消息分三步：用文件名二分定位段，在偏移索引中定位到不大于目标的最近条目，再在数据文件中顺序扫描到目标。

段滚动由大小或时间触发：达到段大小上限，或达到滚动时间上限（默认保留 7 天量级的时间配置），任一满足即切换新段。索引是稀疏的（按间隔写入），因此索引文件远小于数据文件，代价是每次查找都要做一次小范围顺序扫描。日志清理支持删除与压实两种策略：删除按时间或大小丢弃旧段；压实按键保留每个键的最新值，适合变更日志类的语义。压实主题里，被删除的键会保留一个墓碑标记一段时间，以便消费方感知删除，随后标记本身也会被清理。段滚动与清理都不是即时行为：滚动阈值决定磁盘上最旧的数据何时可被追删，而活跃消费者只能读到高水位线之前的消息。

### 2.6 高吞吐从何而来

Kafka 的高吞吐是若干设计的叠加，而不是单一技巧：

| 设计           | 机制                                 | 收益                                 |
| -------------- | ------------------------------------ | ------------------------------------ |
| 顺序追加写     | 日志只追加，不原地修改               | 顺序写吞吐接近内存带宽               |
| 操作系统页缓存 | 读写都经过页缓存，热数据零磁盘 IO    | 避免应用内自建缓存与 GC 压力         |
| 零拷贝         | 使用 sendfile 让数据从页缓存直达网卡 | 省去用户态拷贝与上下文切换           |
| 批量与压缩     | 生产者攒批，端到端压缩               | 摊薄网络与存储开销，吞吐随批大小提升 |
| 分区并行       | 分区分散在多个 Broker                | 水平扩展消费与写入能力               |

零拷贝的差别可以用数据路径长度说明：传统路径是磁盘到内核、内核到用户态、用户态到套接字缓冲区、套接字到网卡，多次拷贝与切换；Kafka 借助 sendfile 让数据在内核内部从页缓存流向网络协议栈。代价是消息在被消费前不做逐条解包，压缩与校验发生在合适的位置。

### 2.7 生产注意事项

- 分区数不是越多越好：分区增加会带来更多文件句柄、更长的元数据、更频繁的再均衡与更高的故障恢复时间。
- 单条消息与单批消息都有大小上限，超限需要调整生产者批大小、请求大小与服务端限制三处，且要评估内存。
- 保留策略要按价值而不是按容量直觉设定，日志类数据用时间保留、变更日志用压实保留。
- 消费者必须避免“拉取后长时间处理导致超过最大处理间隔”，否则会被踢出组触发再均衡；可以用独立线程池处理并控制提交节奏。
- 监控重点包括：ISR 收缩次数、活跃控制器切换、每秒消息数与字节数、消费组滞后（lag）、请求队列与网络线程饱和度。

### 2.8 Kafka 的适用边界

Kafka 适合：事件驱动、日志与埋点采集、流处理、需要回放与多订阅方的数据管道、需要削峰填谷的异步任务。它不适合：极低延迟的请求-响应（一次网络与持久化延迟足够致命）、需要强一致读后写的元数据协调（那是 etcd 的领域）、消息量极小且运维成本敏感的简单通知（Redis Streams 或轻量队列更划算）。若只是把 Kafka 当“能存消息的队列”，往往低估了它的分区与再均衡语义，也高估了团队维护集群的意愿。

## 三、groupcache：去中心化的进程内缓存

groupcache 不是一个独立部署的缓存服务，而是一个进程内库：它以只读缓存 + 自动回源的方式，把缓存逻辑嵌入应用，并通过节点间的一致性哈希与请求合并，避免集中式缓存的单点与网络热点。

### 3.1 缓存组与请求路径

一个缓存组持有回源函数、本地缓存与请求合并器，可选地持有节点选择器。请求路径可以概括为：

```text
Get(key)
  -> 查主缓存（本节点负责的键）
  -> 查热缓存（从其它节点镜像来的热点键）
  -> 未命中则进入请求合并，同键并发只执行一次加载
        -> 一致性哈希选节点
             -> 命中本节点：调用回源函数
             -> 命中远端：通过 RPC 取回
             -> 远端失败：降级为本地回源
  -> 本地回源结果写入主缓存；远端结果只有一定概率写入热缓存
```

它的设计哲学是无中心、不可变、只读。因为缓存值不允许依赖“当前时间”或使用过期机制，键必须唯一描述数据，这也意味着数据更新靠换新键或重建缓存组，而不是原地更新。

### 3.2 一致性哈希

节点选择使用带虚拟副本的一致性哈希环。每个真实节点通过哈希函数映射成多个虚拟副本点，这些点排序后构成环；查询时对键取哈希，在环上二分找到第一个不小于该哈希的点，其归属节点即目标节点。

| 方案        | 节点增减时的影响范围           | 负载均衡度         |
| ----------- | ------------------------------ | ------------------ |
| 取模 hash%N | 几乎全部键重新映射             | 依赖哈希均匀性     |
| 一致性哈希  | 仅相邻节点区间的键迁移，约 1/N | 虚拟副本越多越均匀 |

虚拟副本数量是精确度与内存的权衡：副本越多，环上分布越均匀、迁移越平滑，但环的元数据越大、查找常数越高。默认副本数在数十的量级，节点规模不大时无需调整。

### 3.3 singleflight：把并发回源合并成一次

缓存击穿指某个热点键失效瞬间，大量并发请求同时回源把后端压垮。groupcache 用 singleflight 解决：对同一个键，第一个到达的调用执行回源，其余调用挂起等待同一个结果，回源完成后一次性分享给所有等待者。

```go
// 语义示意，非可直接运行的实现
func (g *Group) load(key string) (Value, error) {
    v, err := g.loadGroup.Do(key, func() (interface{}, error) {
        // 二次检查缓存：合并只覆盖真正并发重叠的调用
        if hit, ok := g.lookupCache(key); ok {
            return hit, nil
        }
        // 选节点；远端失败则本地回源
        if peer, ok := g.peers.PickPeer(key); ok {
            if v, err := g.getFromPeer(peer, key); err == nil {
                g.maybePopulateHot(key, v)
                return v, nil
            }
        }
        v, err := g.getLocally(key)
        if err != nil {
            return nil, err
        }
        g.populateCache(key, v, &g.mainCache)
        return v, nil
    })
    return v, err
}
```

这里有一个容易被忽略的细节：singleflight 只能合并时间上重叠的调用。两个请求若一前一后错过缓存（第一个回源完成前的检查时序错开），可能顺序触发两次加载。因此在合并函数内部会再查一次缓存，避免同一键被重复写入、重复计算占用字节预算。

### 3.4 双缓存与字节预算

每个缓存组把容量预算同时约束在主缓存和热缓存上，而不是各分一半：

- 主缓存保存“本节点是哈希归属者”的键，是绝大多数命中来源。
- 热缓存保存“不属于本节点、但在本地很热”的键，用来避免热门键把某个节点的网卡打成瓶颈。

回源策略决定了二者的写入概率：本地回源结果一定进主缓存；从远端取回的结果只以低概率（控制在十分之一左右）写入热缓存，防止镜像数据无序膨胀。容量超限时的驱逐策略是：默认从主缓存淘汰最旧的数据；当热缓存占用超过主缓存的一个较小比例（约八分之一）时，改为优先淘汰热缓存。这样热缓存始终被压制在次要地位，不会挤占主缓存空间。

需要注意“字节预算”是按键与值的实际长度累计的，而不是按条目数，并且键本身的长度也计入。这使得大 value 会更快触发驱逐，符合内存缓存的直觉。

### 3.5 节点变更与故障

groupcache 自身不提供服务发现。节点集合通常由外部系统（如 etcd、Consul）在启动时注入或运行时更新，节点上线后加入哈希环，下线后移除，随之发生键归属的迁移与缓存预热。远程请求失败时的降级路径是本地回源，这保证了正确性但会在节点故障瞬间把流量打到后端存储，因此故障期间的容量评估必须考虑“缓存失效放大”。

### 3.6 内置统计

缓存组自带一组计数器，用于判断“命中了多少、多少回了源、对等节点是否正常”：

| 指标           | 含义                                     |
| -------------- | ---------------------------------------- |
| Gets           | 所有读取请求，包含来自对等节点的请求     |
| CacheHits      | 命中本地缓存（主缓存或热缓存）           |
| Loads          | 需要加载的次数，约等于读取数减命中数     |
| LoadsDeduped   | 经过请求合并去重后真正执行的加载         |
| PeerLoads      | 从对等节点成功取回（远端加载或远端命中） |
| PeerErrors     | 对等节点取回失败                         |
| LocalLoads     | 本地回源成功                             |
| LocalLoadErrs  | 本地回源失败                             |
| ServerRequests | 通过网络从对等节点收到的请求数           |

命中率下降与去重率下降是两类不同的信号：前者说明缓存容量或键分布有问题，后者说明热点键并发集中、合并压力大。对等节点错误上升则提示哈希环上的节点不可达，需要结合节点发现检查。

### 3.7 与集中式缓存的对比与适用场景

| 维度     | groupcache              | Redis 类集中式缓存 |
| -------- | ----------------------- | ------------------ |
| 部署形态 | 嵌入应用进程，去中心化  | 独立集群，中心化   |
| 写能力   | 不支持，只读回源        | 完整读写与数据结构 |
| 过期语义 | 无 TTL，按字节 LRU 淘汰 | TTL、多种淘汰策略  |
| 命中延迟 | 进程内命中，微秒级      | 一次网络往返       |
| 持久化   | 无                      | RDB/AOF 等         |
| 一致性   | 依赖键的不可变性        | 可做主从/集群复制  |
| 额外依赖 | 无，只需节点发现        | 需要运维缓存集群   |

适合 groupcache 的场景：读多写少、数据可视为不可变、对延迟极敏感、希望避免引入并运维独立缓存服务、能接受“更新靠换键”。不适合：需要频繁写或删除、需要 TTL、需要跨语言访问、数据规模超出单机内存。它与集中式缓存并不互斥——常见做法是用 groupcache 挡住进程内热点，用 Redis 承担需要共享状态和过期语义的部分。

## 四、gRPC：基于 HTTP/2 的远程过程调用

gRPC 把接口定义、序列化、传输与调用语义标准化，使跨语言的服务调用像本地方法一样自然。它的能力边界很大程度上继承自 HTTP/2，因此理解协议层是理解 gRPC 各种行为的前提。

### 4.1 调用分层

一次调用自下而上经过：TCP/TLS 传输、HTTP/2 帧层、gRPC 消息层（长度前缀帧）、Protobuf 序列化、生成的 Stub、以及横切的拦截器。客户端把方法名、元数据与消息编码成 HTTP/2 的 HEADERS 与 DATA 帧；服务端按 `:path`（形如 /包名.服务名/方法名）路由到对应处理器，解码后调用业务逻辑，再以同样的方式返回状态码与响应消息。

gRPC 的状态码不是 HTTP 状态码，而是 17 个标准 code（如 OK、NOT_FOUND、DEADLINE_EXCEEDED、UNAVAILABLE、RESOURCE_EXHAUSTED 等），随响应以 trailer 形式返回。业务层重试、熔断、告警都应该基于这套状态码，而不是 HTTP 状态码。

### 4.2 HTTP/2 提供的四项关键能力

| 能力     | 机制                                              | 对 gRPC 的意义                           |
| -------- | ------------------------------------------------- | ---------------------------------------- |
| 多路复用 | 单连接上并行多个 stream，每个 stream 有独立 id    | 一个连接承载大量并发调用，避免连接数爆炸 |
| 双向流   | 同一 stream 上双向传输 DATA 帧                    | 支撑四种通信模式，尤其是服务端与双向流   |
| 头部压缩 | HPACK 对头部做静态表加动态表编码                  | 元数据与状态码可低成本频繁传输           |
| 流控     | 连接级与 stream 级两套窗口，用 WINDOW_UPDATE 更新 | 防止接收方被快发方压垮                   |

流控是双层结构：接收方分别维护连接窗口和每个 stream 的窗口，发送方只能发送不超过两者剩余额度的数据。对高吞吐的大消息场景，默认初始窗口可能偏小，可以在两端调大初始窗口以提升吞吐，代价是潜在的缓冲内存。

### 4.3 Protocol Buffers 的编码

Protobuf 是二进制、带字段编号的编码格式，每个字段写成“标签 + 值”。标签由一个 varint 编码的整数构成，低三位是线类型（wire type），高位是字段编号：

```text
字段编号 << 3 | 线类型   ->  varint 编码的标签
线类型 0: varint (整型、bool、枚举)
线类型 1: 64 位定长 (fixed64、double)
线类型 2: 长度前缀 (string、bytes、嵌套消息)
线类型 5: 32 位定长 (fixed32、float)
```

整数用 varint 变长编码，小数值占用更少字节；有符号负数用 ZigZag 映射成无符号后再编码，避免负数的补码把 varint 拉长到最大长度。字段编号是向后兼容的核心：只要不复用编号、不改变已有字段的类型，就可以在两端先后升级而不破坏通信；新增字段对旧端是未知字段，会被保留或跳过。让协议演进不破坏兼容的规则可以归纳为：

| 变更                 | 是否兼容 | 说明                                               |
| -------------------- | -------- | -------------------------------------------------- |
| 新增字段             | 兼容     | 旧端忽略未知字段，新端读到默认值                   |
| 删除字段             | 兼容     | 必须保留编号不被复用，否则新旧端会误解数据         |
| 改字段名             | 兼容     | 编码只依赖编号，不依赖名字                         |
| 改同线类型的整数宽度 | 谨慎     | 如 32 位与 64 位整数线类型相同但语义不同，可能截断 |
| 切换线类型           | 不兼容   | 解析失败或得到无意义结果                           |
| 改字段编号           | 不兼容   | 等同于删除旧字段再新增，破坏语义                   |

相对 JSON 的优势在于：没有字段名，只有编号，体积更小；解析无需文本扫描与浮点格式化，编解码更快；有编译期类型检查与跨语言一致的规范。代价是可读性差、必须维护 .proto 契约、二进制协议在浏览器与人工调试时不友好。

### 4.4 四种通信模式

| 模式          | 语义                   | 典型场景                              |
| ------------- | ---------------------- | ------------------------------------- |
| 一元（Unary） | 一请求一响应           | 常规 CRUD、查询                       |
| 服务端流      | 一请求多响应           | 日志/事件推送、大结果集分页、实时行情 |
| 客户端流      | 多请求一响应           | 文件分片上传、批量写入、指标汇聚      |
| 双向流        | 多请求多响应，两侧独立 | 聊天、实时协作、双向订阅              |

流式调用把“分页/轮询”变成协议内建的连续传输，减少请求开销并能及时推送；但它也意味着更长的连接生命周期、更难的重试（部分消息已消费时重试语义需要业务定义）和更复杂的背压处理。

### 4.5 拦截器

拦截器是 gRPC 的横切扩展点，分为客户端与服务端两类，各自又分一元与流式。一元拦截器接收“方法信息、请求、连接信息、处理器”，返回响应，层层包装形成洋葱模型：请求按注册顺序进入，响应按相反顺序返回。

生产上常见的拦截器职责包括：日志与访问指标、认证与鉴权（从元数据取令牌）、panic 恢复（把崩溃转成错误状态码而不是进程退出）、限流、链路追踪注入与提取、重试与超时兜底。设计时要避免在拦截器里做阻塞的慢操作（例如同步写日志到慢设备），因为它在每个请求的关键路径上。

### 4.6 名字解析与负载均衡

客户端把“目标地址”抽象成名字解析器、负载均衡策略、子连接三层：

- 名字解析器负责把逻辑名（如 etcd 中的服务前缀、DNS 名、xDS 资源）解析成一组实际地址及属性。
- 负载均衡策略从地址列表中选出目标，常见有 pick_first（依次尝试直到可用）与 round_robin（轮询可用地址），也支持自定义策略。
- 每个地址对应一个子连接，连接状态（连接中、就绪、失败）影响选择结果。

与 etcd 集成时，解析器 Watch 服务前缀，实例上下线会实时更新地址列表；配合轮询策略即可实现客户端负载均衡。这里要区分两类失败：连接建立失败（可换地址重试）与请求失败（只有幂等请求才应重试）。子连接的连接状态检查能显著缩短故障摘除时间。

### 4.7 可靠性：超时、重试、KeepAlive 与流控

- 截止时间（deadline）通过 context 传播，gRPC 会随请求携带剩余超时，下游据此裁剪自己的处理预算，避免上游已超时而下游还在空转。传播的是剩余时间而非原始超时，因此逐跳递减是天然正确的。
- 重试需要显式配置：指定可重试的状态码集合、最大尝试次数、指数退避与抖动，并且只应对幂等操作启用，否则可能放大副作用。对于非幂等操作，更稳妥的思路是在业务层用幂等键或去重表。
- KeepAlive 通过 HTTP/2 PING 帧探测连接活性，能在对端静默断开（如中间设备丢包但未发 FIN）时及时发现；但心跳过密会带来额外流量与服务端压力，需要与服务器的最小 ping 间隔约束配合。
- 服务端优雅关闭使用 GracefulStop 语义：停止接受新调用，等待在途调用完成，再关闭连接，避免发布时把正在进行的请求打断。

### 4.8 生产注意事项

- 大消息要评估流控窗口与内存，必要时分片或改用流式，而不是简单调大上限。
- 连接复用与连接池需要区分：一元高并发通常复用少量连接足够，跨地域或存在长尾阻塞的场景可以考虑多连接以隔离。
- 错误处理要基于 gRPC 状态码与错误详情，而不是把业务错误塞进响应体的字符串里；这直接影响重试、熔断与可观测性。
- 拦截器链要短而稳定，按“追踪、认证、恢复、限流、日志”的顺序组织，避免语义相互干扰。
- 面向浏览器或受限网络时，gRPC 需要代理或 Web 协议转换，选型时要把这一层成本计入。

### 4.9 适用边界

gRPC 适合内部服务间的高性能同步调用、需要流式传输的场景、多语言团队共享强类型契约。它不适合：需要浏览器直接访问且无法引入代理、对外公开的简单 API（HTTP/JSON 更通用）、消息量小且团队不愿引入代码生成与契约维护成本的场景。

## 五、Prometheus：拉模型监控与告警

Prometheus 的核心是“多维时间序列 + 拉取采集 + 强大查询语言”。它把指标作为一等公民，用标签做维度，用 PromQL 做聚合与速率计算，配合 Alertmanager 完成告警闭环。

### 5.1 架构与数据流

```text
目标暴露指标 (/metrics)          Pushgateway (短生命周期任务)
        |                                  |
        v                                  v
              Prometheus Server
    服务发现 -> 抓取 -> TSDB -> 规则评估 -> 查询 API
        |                          |
        v                          v
  Alertmanager <--- 告警            Grafana / 其它消费者
        |
   远端写入 -> 长期存储 (远端只读 / 长期后端)
```

三条主线值得记住：抓取由服务端主动发起（拉模型），服务发现负责“该抓谁”，规则评估既产生告警也产生预聚合的 recording 规则。服务本身不感知被监控，这与“注册中心推送”的模型有本质区别：目标消失后它的序列随之出现陈旧标记并最终停止，因此“目标整体不见了”可以用 `absent()` 类查询来告警。

### 5.2 指标模型与四种类型

Prometheus 的样本是“指标名 + 一组标签 = 值 + 时间戳”。指标名描述“是什么”，标签描述“哪一类”，两者共同构成序列标识。标签不是越多越好，标签值的基数直接决定序列数量与存储成本。

| 类型      | 语义                             | 适用                       | 注意                                                |
| --------- | -------------------------------- | -------------------------- | --------------------------------------------------- |
| Counter   | 单调递增，只在重启时归零         | 请求数、错误数、处理字节数 | 必须用 rate/increase 转换为速率，不能直接比较原始值 |
| Gauge     | 可增可减的瞬时值                 | 内存、连接数、队列长度     | 可直接做算术与阈值判断                              |
| Histogram | 分桶计数 + 总和 + 计数           | 延迟、大小分布             | 可聚合、可分位数近似；分桶边界要按业务延迟范围设计  |
| Summary   | 客户端计算的分位数 + 总和 + 计数 | 单实例精确分位数           | 分位数不可跨实例聚合，且计算成本在客户端            |

延迟监控优先选择 Histogram：它的桶可以跨实例求和后再求分位数，适合“全局 P99”；Summary 的分位数在客户端计算，跨实例求平均没有意义。代价是 Histogram 需要预先设计桶边界，边界不合理会导致分位数失真。

每个被抓取的目标都有一个自动生成的 `up` 序列，取值 1 表示本次抓取成功、0 表示失败。当目标在若干抓取周期内持续不可达时，它的旧序列会被标记为陈旧并从查询结果中消失，这就是“实例下线后 `up` 也跟着消失”的原因，也是用 `absent()` 判断“整个目标不见了”的依据。`up` 本身既是可用性指标，也是最常用的抓取健康度信号。

### 5.3 PromQL 的核心查询模式

PromQL 以“选择器 + 范围 + 聚合 + 函数”组合出查询。几个高频模式：

```text
rate(http_requests_total[5m])                          # 每秒请求速率
histogram_quantile(0.99,                                # 从桶近似 P99
  sum by (le, service) (rate(http_request_duration_bucket[5m])))
sum(rate(http_requests_total{status=~"5.."}[5m]))       # 错误率分子
  / sum(rate(http_requests_total[5m]))
predict_linear(node_filesystem_avail_bytes[1h], 4*3600) < 0   # 磁盘耗尽预测
absent(up{job="svc"} == 1)                              # 整个目标消失
```

理解速率计算有一个关键点：`rate` 需要至少两个样本才能工作，窗口长度应远大于抓取间隔（经验上是 4 倍以上），否则会因样本不足产生空洞。直方图的 `_bucket` 序列带一个 `le` 标签，求分位数前必须先按 `le` 与其它维度聚合，缺了 `by (le)` 会得到无意义的结果。

### 5.4 服务发现与 relabel

抓取目标不写死在配置里，而是由服务发现机制动态生成候选目标，每个候选带一组元数据标签（以 `__meta_` 开头）。候选经过 relabel 过滤与重写，得到最终目标，抓取后还可以用 metric relabel 丢弃不需要的指标。

```yaml
scrape_configs:
  - job_name: kubernetes-pods
    kubernetes_sd_configs:
      - role: pod
    relabel_configs:
      - action: keep # 只保留带抓取注解的 Pod
        source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_scrape]
        regex: "true"
      - action: replace # 用注解覆盖抓取端口
        source_labels:
          [__address__, __meta_kubernetes_pod_annotation_prometheus_io_port]
        regex: ([^:]+)(?::\d+)?;(\d+)
        replacement: $1:$2
        target_label: __address__
      - action: labelmap # 把 Pod 标签映射成业务标签
        regex: __meta_kubernetes_pod_label_(.+)
```

常见服务发现机制与它们的来源：

| 机制          | 来源                                        | 典型元数据                     |
| ------------- | ------------------------------------------- | ------------------------------ |
| static        | 配置文件写死                                | 无                             |
| kubernetes_sd | API Server 的 Pod/Service/Node/Endpoints 等 | 名称、命名空间、标签、容器端口 |
| consul_sd     | Consul 目录                                 | 地址、标签、健康状态           |
| dns_sd        | SRV/A/AAAA 记录                             | DNS 名、端口                   |
| file_sd       | JSON/YAML 文件，支持热更新                  | 自定义标签                     |

relabel 是拉模型里最容易被低估的部分：它既决定了抓什么（过滤无关目标）、怎么抓（改写地址与协议），也决定了落库的标签维度（labelmap 与 labeldrop），因此也是控制基数的第一道闸门。

### 5.5 存储引擎

TSDB 的写入路径是：样本先追加到预写日志（WAL）保证崩溃可恢复，同时写入内存中的 head 块；head 块覆盖最近约三小时的样本，每两小时切分并落盘为一个不可变的持久块；持久块之间再按倍数（通常每次扩大为原来的数倍）合并成更大的块，直到达到单块时长上限。上限由保留时间决定——取“31 天”与“保留时间的十分之一”中的较小值，因此保留越短，单块越小。

时间戳序列用 delta-of-delta 编码（相邻间隔的变化量大多为零或很小），值与浮点数用 XOR 编码，两者配合把每个样本压缩到很小的字节数。理解压缩的意义在于估算存储：容量 ≈ 活跃序列数 × 每秒样本数 × 保留秒数 × 每样本字节数 × 冗余系数，再考虑索引与压缩波动。

高可用与长期存储的两个方向：一是本地多副本加远端写入，把数据复制到长期后端（Thanos、Mimir、VictoriaMetrics 等）并支持全局查询；二是用 Prometheus 做采集与短保留，长期查询完全交给远端。单机 Prometheus 不做副本间一致性保证，跨实例查询的重复与冲突要靠长期后端解决。

### 5.6 告警与 Alertmanager

告警规则在 Prometheus 中定义（表达式 + for 持续时间 + 标签与注解），状态机为：不活跃 → 待定（满足条件但未到 for 时长）→ 触发；条件恢复后进入已解决。`for` 是抑制抖动的重要手段，但没有 `for` 的规则会因瞬时尖刺频繁告警。

Alertmanager 负责去重、分组、抑制、静默与路由：

| 环节   | 作用                                                       |
| ------ | ---------------------------------------------------------- |
| 路由   | 按标签匹配路由树，决定通知发给哪个接收者                   |
| 分组   | 把同一故障相关的多条告警合并成一条通知，避免告警风暴       |
| 抑制   | 高级别告警抑制低级别告警（如整机宕机抑制其上所有服务告警） |
| 静默   | 按标签与时间窗临时屏蔽通知，用于维护窗口                   |
| 接收者 | 邮件、即时通讯、电话、Webhook 等通道                       |

告警与预聚合使用同一套规则语法，区别只在是否带告警注解：

```yaml
groups:
  - name: service.rules
    rules:
      - record: job:request_error_ratio:5m
        expr: sum by (job) (rate(http_requests_total{status=~"5.."}[5m]))
          / sum by (job) (rate(http_requests_total[5m]))
      - alert: HighErrorRatio
        expr: job:request_error_ratio:5m > 0.05
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: "{{ $labels.job }} 错误率超过 5%"
```

recording 规则把高频查询变成低基数序列，既加速大盘也降低查询成本；告警规则通常建立在 recording 结果之上，避免在告警表达式里重复复杂计算。

生产经验：告警要面向“需要人采取行动的故障”，而不是所有异常；每条告警都应有明确的处置手册；同一根因的告警要做分组与抑制，否则会迅速耗尽值班人员的注意力。

### 5.7 高基数治理

基数爆炸是 Prometheus 最常见的成本与稳定性问题。治理手段按优先级排列：

- 在设计阶段就避免无界标签：用户 ID、请求 ID、订单号、完整 URL 路径都不能做标签值。
- 用 relabel 与 metric relabel 在入库前丢弃或改写高基数标签，把路径参数归一化（如把 /users/123 归成 /users/:id）。
- 用 recording 规则做预聚合，把细粒度序列定期聚合成低基数序列供大盘与告警使用。
- 对确实需要的高基数分析，改用支持列式存储与采样追踪的系统，而不是硬扛在 Prometheus 里。
- 监控自身：关注活跃序列数、每秒样本数、抓取时长与目标数量，把“指标系统的指标”作为一等公民。

### 5.8 适用边界

Prometheus 适合：指标监控与告警、容器与微服务的动态发现、需要灵活多维聚合的场景、作为 SLO 计算的数据源。它不适合：事件与日志的全文检索（用日志系统）、高基数明细分析（用列式存储）、账单级精确计数（采样与抓取丢失会造成误差）、作为长期归档的唯一副本（应配合远端长期存储）。

## 六、Grafana：可视化与统一告警

Grafana 是查询与展示层：它不存储业务指标，而是把各类数据源的查询结果组织成面板、大盘与告警，并提供统一的访问控制与协作能力。

### 6.1 架构与插件体系

Grafana 是前后端分离的 Go 服务加浏览器前端，元数据（大盘、用户、告警规则、数据源）存储在关系型数据库或嵌入式数据库中。三类插件构成扩展体系：

| 插件类型 | 职责                             | 例子                            |
| -------- | -------------------------------- | ------------------------------- |
| 数据源   | 把统一查询接口翻译成具体后端查询 | Prometheus、SQL、日志与追踪系统 |
| 面板     | 把数据渲染成图表、表格、状态等   | 时序图、统计、热力图            |
| 应用     | 打包数据源、面板、页面与后端逻辑 | 专项监控套件                    |

后端插件通过进程内协议与主进程通信，数据以列式格式在前后端之间流动，这让不同结构的数据源能在同一套面板里呈现。

### 6.2 查询与渲染流程

打开大盘时，前端解析大盘模型，替换模板变量，向数据源代理发送统一查询请求；数据源插件把查询翻译成后端查询并执行，把结果转成统一的列式结构返回，前端据此渲染面板。理解这条链路有助于排查“面板空白”：可能是变量取值错误、查询语法不兼容、数据源权限不足或时间范围不对，而不是渲染问题。

模板变量是把大盘从“一张图”变成“可复用工具”的关键：可以在指标标签、查询语句、面板标题与链接中使用变量，从而在同一张大盘上切换服务、实例、环境。变量的取值方式分为查询型、自定义型、常量型与基于其它变量的级联型：

| 类型     | 取值来源                   | 典型用法             |
| -------- | -------------------------- | -------------------- |
| 查询型   | 从数据源查询标签值         | 服务名、实例地址     |
| 自定义型 | 手工枚举或用逗号分隔的列表 | 环境、区域           |
| 常量型   | 隐藏的固定值               | 数据源名、固定阈值   |
| 级联型   | 取值依赖另一个变量的当前值 | 选定服务后再选其实例 |

变量配合“全部”选项可以实现“默认看全局、下钻看单个实例”的体验，但要注意“全部”会在查询中展开为多值，若指标基数高会显著提高查询成本。

### 6.3 统一告警

Grafana 的统一告警把告警规则、评估与通知统一到一处，支持跨数据源查询，并用表达式流水线加工结果：

```text
查询节点 (Query) -> 归约 (Reduce) -> 数学运算 (Math) -> 阈值判断 (Threshold)
```

- 查询节点从数据源取原始数据。
- 归约把区间数据压成单值（如取最大值、平均值、最后一个值）。
- 数学节点做多查询间的算术，例如错误率。
- 阈值节点判定是否满足条件，配合“持续时间”（类似 for）避免抖动。

告警进入统一状态机后由通知策略路由到联系点，支持分组、静默与静默时段（mute timings），语义与 Alertmanager 类似。

### 6.4 生产级大盘设计

大盘的组织原则是分层与可下钻，而不是把所有图堆在一页：

| 层级   | 内容                                 | 目的               |
| ------ | ------------------------------------ | ------------------ |
| 概览层 | 流量、延迟、错误、饱和度（黄金指标） | 一眼判断“是否正常” |
| 服务层 | 单服务的依赖、实例、关键业务指标     | 定位到具体服务     |
| 组件层 | 数据库、缓存、消息队列、主机资源     | 继续下钻到根因     |

实践要点：

- 图表标题写清指标含义与单位，而不是依赖标签名。
- 用阈值标注 SLA 线，让“是否达标”不靠眼力。
- 用注解（annotation）标记发布、扩容、故障事件，把指标变化与变更关联起来。
- 大盘即代码：通过配置文件声明数据源与大盘，纳入版本管理与发布流程，避免手工改动无法追溯。
- 控制单页图的密度，把高频排查路径放在最上方。

### 6.5 适用边界

Grafana 适合：统一查询与可视化多数据源、对外/对内交付监控大盘、基于指标的告警编排。它不适合：作为唯一的数据存储（它不持久化业务数据）、需要复杂交互式探索的临时分析（专业分析工具更合适）、在没有数据源与指标治理的前提下“一键出好看大盘”。

## 七、OpenTelemetry：统一的可观测性采集层

OpenTelemetry 解决的是“信号分散、厂商锁定、埋点重复”的问题：它定义统一的 API、SDK 与传输协议，把追踪、指标、日志三类信号用同一套资源与上下文模型采集并导出到任意后端。

### 7.1 信号与总体架构

三类信号——追踪（traces）、指标（metrics）、日志（logs）——共享资源（resource）与上下文（context）概念。整体分层：

```text
应用代码
  |  调用 OTel API（与厂商无关的接口）
  v
OTel SDK（配置采样、批处理、导出、资源）
  |
  v
OTLP（统一传输协议，gRPC 或 HTTP）
  |
  v
Collector（接收 -> 处理 -> 导出，可级联）
  |
  v
后端（追踪、指标、日志、告警系统）
```

API 与 SDK 分离是它的关键设计：库作者只依赖 API，应用在启动时装配 SDK，因此“换后端”“关采样”“本地不上报”都不需要改业务代码。Collector 独立进程则把“如何接收、如何加工、发往哪里”从应用中剥离，便于统一治理。

SDK 层面由几类对象组成：追踪用 TracerProvider 管理 Tracer 与 span 处理器（负责采样、批处理、导出），指标用 MeterProvider 管理 Meter 与读取器（周期性地把聚合结果交给导出器），日志用 LoggerProvider 管理日志处理器；三类 Provider 共享同一个 Resource，因此同一进程产出的信号天然带相同的服务标识。使用方在启动时装配 Provider（设置采样、导出端点、资源、批处理参数），库作者只依赖 API 接口，这就是“不换代码换后端”的实现方式。进程退出前要正确关闭 Provider，flush 尚未导出的数据，否则最后一批遥测可能丢失。

### 7.2 Trace 数据模型与上下文传播

一次追踪由 trace_id 标识，包含若干 span。trace_id 是 128 位、span_id 是 64 位，在一条追踪内唯一。每个 span 至少记录：操作名、起止时间、父 span、属性（键值对）、事件与状态。span 之间的关系构成有向无环树，根 span 表示整个请求。

上下文传播依赖标准化的头部，最常用的是 W3C Trace Context：`traceparent` 携带 trace_id、span_id、采样标志与版本，`tracestate` 携带厂商扩展。跨进程调用时由客户端注入、服务端提取，从而把不同服务的 span 串成一条链。除了 HTTP，消息队列（在消息头里注入上下文）与 RPC 也有对应的传播方式，否则异步链路的追踪会断裂。

资源（resource）描述“哪台进程、哪个服务、哪个版本”，通常由一批语义约定属性构成，例如服务名、服务版本、实例 ID、部署环境。所有信号共享同一资源，这是把指标、日志、追踪关联起来的基础。

### 7.3 采样策略

采样决定“哪些追踪被记录”，直接影响成本与可观测性：

| 策略               | 决策时机              | 特点                                                               |
| ------------------ | --------------------- | ------------------------------------------------------------------ |
| 头部采样           | 追踪开始时            | 实现简单、开销低；无法基于整条链的结果决策                         |
| 基于比率的头部采样 | 开始时按比例          | 如 1/1000，适合高流量降噪                                          |
| 基于父级的头部采样 | 开始时继承父决策      | 保证同一条追踪在各服务采样一致                                     |
| 尾部采样           | 追踪结束后            | 可基于错误、延迟、业务标签决策；需要缓冲完整追踪，成本高、实现复杂 |
| 组合               | 头部降量 + 尾部精细化 | 生产常用：头部按比例，尾部保留错误与慢请求                         |

常见取向：低流量全采；中等流量按比例头部采样并让错误与慢请求强制保留；高流量用尾部采样按策略取舍。无论哪种策略，都要保证采样标志在上下文中正确传播，否则会出现“上游采了、下游没采”的断链。

采样决策随上下文传播有一个重要含义：头部采样一旦在链路的第一个服务做出决定，后续服务应继承而不是重新决定（基于父级的策略），否则同一条追踪可能在部分服务被记录、在另一部分被丢弃，形成残缺的链路。除追踪上下文外，还可以传播跨服务共享的业务键值对（如租户、渠道），但要注意这类数据也会随请求头传递，不应放入敏感信息。

指标信号通常不采样（它们本身就是聚合值），但可以用聚合视图或基数控制来降低成本；日志一般全量采集，靠采集端的过滤与丢弃策略控制量。

### 7.4 Collector 的 pipeline 与部署模式

Collector 的配置围绕 pipeline 组织：接收器（receiver）读取数据，处理器（processor）加工数据，导出器（exporter）写出数据；三者通过 pipeline 串起来，不同信号有各自的 pipeline。典型处理器包括批处理（把多个请求合并以提升导出效率）、内存限流（防止积压导致 OOM）、属性增删改、采样、过滤。

部署模式有两类，常见的是二者组合：

- 边车/主机级（agent）：每个节点或 Pod 部署，负责本机数据的接收与初加工，靠近数据源、故障域小。
- 集中式（gateway）：接收 agent 汇聚的数据，做统一采样、属性规范化与多后端分发，减少 agent 配置复杂度。

组合模式的价值在于：agent 只做简单可靠的转发，gateway 承担需要全局视角的处理（如尾部采样需要看到完整追踪）。但 gateway 会引入一跳网络与单点，需要做多副本与背压设计。

### 7.5 三类信号的关联

关联是可观测性真正产生价值的地方：

- 指标到追踪：在直方图的样本里记录 exemplar，把延迟分位数上的具体请求与 trace_id 关联；从大盘点开某个尖刺即可跳转到那条追踪。
- 日志到追踪：日志结构中注入 trace_id 与 span_id，日志系统据此提供“查看该请求的日志”。
- 追踪到日志/指标：从 span 的属性出发，查询同一时间窗内相关服务的日志与指标。
- 统一资源：所有信号带相同的服务名与实例标识，这是自动关联的前提。

实现关联要求埋点规范统一：同一个 trace_id 必须能在日志、指标 exemplar 与追踪中一致出现，因此“日志注入 trace 上下文”通常是落地时的第一优先级任务。

### 7.6 落地路径与常见问题

一个务实的落地顺序是：先统一资源属性并把日志与追踪关联起来，再接入自动埋点覆盖 HTTP、RPC、数据库调用，最后才是自定义业务指标与告警。自动埋点应覆盖尽可能多的框架边界，手动埋点只补充框架看不到的业务阶段。

常见问题：

- 采样策略与后端查询能力不匹配：采得太少导致问题难以复现，采得太多导致成本失控。应按“错误与慢请求全保留”的思路设计。
- 属性基数失控：把用户 ID、URL 参数写进指标或 span 属性，会迅速推高成本。属性要按“值得聚合的维度”设计。
- 传播断链：异步任务、消息队列、后台作业没有传递上下文，导致追踪片段化。
- Collector 成为瓶颈：缺少限流与批处理配置，突发流量下 OOM 或丢弃数据。
- 只上追踪不做关联：有了追踪却无法从指标或日志跳转过去，排查效率提升有限。

### 7.7 与既有监控体系的衔接

OpenTelemetry 与 Prometheus 并不互斥：可以用 OTel 指标 SDK 产生指标并通过导出器暴露或推送到 Prometheus 兼容后端，也可以用 Collector 同时导出到指标、追踪、日志三类后端。选择的关键在于团队是否愿意用一套 SDK 统一三类信号。如果已经深度使用 Prometheus 生态，通常的做法是“追踪走 OTel，指标继续用 Prometheus 客户端库”，并靠统一资源标签与服务发现把两者关联。

## 八、Redis Stack：内存向量存储与检索

把向量检索做进 Redis，价值在于复用已有的内存存储与运维体系，并在同一份数据上完成“相似度检索 + 标签过滤 + 全文检索 + 缓存”。它适合作为检索增强生成（RAG）等在线检索层，但在数据规模与分布式能力上有明确边界。

### 8.1 定位与数据模型

承载向量能力的是搜索模块，它在 Redis 之上提供索引、查询与聚合。当前版本已经把此前作为模块分发的搜索、JSON、时序、概率数据结构等能力并入主发行版，使用方式不再区分“要额外装哪些模块”。

数据组织分两层：

- 原始文档与向量以哈希或 JSON 存储，向量以二进制块形式保存在字段里。向量元素的数值类型可选，常见是 32 位浮点，也支持更低比特宽的类型以压缩内存。
- 索引描述“哪些字段可被检索、向量字段用什么算法与距离度量”，在内存中构建并支持增量更新，写入后即可被检索，没有独立的索引进度。

索引定义需要同时声明的要素可以归纳为：

| 要素           | 作用                         | 取舍                               |
| -------------- | ---------------------------- | ---------------------------------- |
| 文档键前缀     | 决定哪些键进入索引           | 前缀过大等于全库扫描，过小易遗漏   |
| 字段类型       | 文本、标签、数值、地理、向量 | 标签适合枚举过滤，文本适合全文检索 |
| 向量算法       | 精确或近似图索引             | 精确召回高、慢；近似快、需调参     |
| 向量参数       | 图度数、建索引与查询宽度     | 越大越准，内存与延迟越高           |
| 维度与量化类型 | 每个向量的长度与每维字节数   | 直接决定内存占用                   |
| 距离度量       | 余弦、欧氏、内积             | 必须与向量的语义匹配               |

### 8.2 索引算法：精确与近似

创建向量索引时需要选择算法。

精确搜索（FLAT，暴力遍历）逐一计算查询向量与所有文档向量的距离，返回最近的若干条。它的召回率是 100%，内存只需存放原始向量，查询复杂度与数据量成正比。适合数据量不大、对召回率要求极高的场景。

近似搜索（HNSW，分层可导航小世界图）把向量组织成多层图：底层包含所有节点，上层是稀疏采样的“高速公路”，查询从最高层贪心靠近，逐层下降到底层精搜。它的查询复杂度近似对数级，代价是额外图结构占用内存、建索引更慢，并且召回率是近似的。三个关键参数：

| 参数            | 含义                 | 调整方向                               |
| --------------- | -------------------- | -------------------------------------- |
| M               | 每个节点的最大出边数 | 增大提升召回率，但内存与建索引时间上升 |
| EF_CONSTRUCTION | 建索引时的搜索宽度   | 增大提升图质量，建索引更慢             |
| EF_RUNTIME      | 查询时的搜索宽度     | 增大提升召回率，查询更慢               |

面向压缩的图索引（如 SVS-VAMANA）在此基础上做了量化与压缩设计，进一步降低内存，部分压缩优化仅在特定实现中可用，开源版会回退到标量量化。选择它通常是因为“内存优先、可以接受一定的召回下降”。

对比取舍：

| 维度       | 精确搜索     | 近似图搜索             |
| ---------- | ------------ | ---------------------- |
| 召回率     | 100%         | 近似，随参数提升       |
| 查询复杂度 | 与数据量线性 | 近似对数级             |
| 内存       | 仅原始向量   | 原始向量加图结构       |
| 建索引     | 无需         | 需要，且耗时           |
| 增量更新   | 天然支持     | 支持，但可能影响图质量 |
| 适用规模   | 较小数据集   | 百万级以上             |

图结构的内存开销与维度关系不大，主要随 M 与节点数增长，因此在高维向量场景下，图结构相对原始向量的占比并不高；但在低维短向量场景中，图的相对占比会明显上升。

### 8.3 KNN 查询与混合检索

向量检索的查询语句把“过滤条件”和“KNN 子句”组合在一起。创建索引时声明字段类型与向量参数，查询时把查询向量作为参数传入，并按距离字段排序：

```text
FT.CREATE idx:docs ON HASH PREFIX 1 "doc:" SCHEMA
  title TEXT
  category TAG
  embedding VECTOR HNSW 6 TYPE FLOAT32 DIM 1536 DISTANCE_METRIC COSINE

FT.SEARCH idx:docs "(@category:{tech})=>[KNN 10 @embedding $BLOB]"
  PARAMS 2 BLOB <查询向量二进制>
  SORTBY __embedding_score
  DIALECT 2
```

查询执行时，引擎会把过滤条件下推，并根据过滤后候选集的规模在两种策略间选择：

| 策略         | 做法                                                       | 适用                             |
| ------------ | ---------------------------------------------------------- | -------------------------------- |
| 分批图搜索   | 沿图逐批取近邻，只保留满足过滤条件的文档，直到凑够或遍历完 | 过滤条件宽松、候选集大           |
| 先过滤后暴力 | 先得到满足条件的候选集，再对候选集精确计算距离             | 过滤条件苛刻、候选集小；结果精确 |

两种策略可以在执行过程中依据更新后的估算互相切换，因此同一个查询在不同数据分布下可能走不同路径。理解这一点有助于解释“为什么加了过滤条件后结果更准”或“延迟变化很大”。

距离度量要与向量语义匹配：余弦相似度适合文本语义（关注方向而非长度），欧氏距离适合空间特征，内积适合已经归一化的向量。度量选错会让“最近的文档”与业务直觉不符，且在归一化与未归一化向量混用时尤为隐蔽。

### 8.4 内存与性能调优

向量检索的成本主要在内存，优化手段按收益排序：

- 选择更低的向量数值精度。32 位浮点是最常见的选择，更低比特宽直接按比例减少向量内存，代价是精度与召回率下降，需要实测确认可接受。
- 降维。用主成分分析或自编码器把高维向量压到更低的维度，可以成倍减少内存与距离计算开销，但会引入信息损失。
- 调整图参数。在召回率可接受的前提下降低 M 与建索引搜索宽度，能显著减少内存与建索引时间。
- 数据分层。近期热数据放在内存检索，历史冷数据放到对象存储做离线检索，用业务上的“新旧”换容量。
- 批量与管线化查询。把多个查询合并发送减少往返，配合连接池降低建连开销。

容量估算可以按“向量原始大小 = 条数 × 维度 × 每维字节数”为基数，再叠加图结构、文档正文、索引与 Redis 自身开销。一个直观的例子：百万条 1536 维的 32 位浮点向量，仅原始向量就是数 GB 量级，而图结构只占其中较小一部分；这也说明真正的内存大头是向量本身，压缩向量类型往往比调图参数更有效。

运维观测上，索引信息命令可以给出文档数、倒排索引大小、向量索引大小等，用于判断内存去向；慢查询与延迟事件则用来定位查询尖刺。查询侧要避免在高峰期做大批量的全量重建索引，索引构建与数据写入的节奏需要错峰。

### 8.5 与 Vector Sets 的关系

新版本 Redis 在主发行版中引入了原生的向量集合数据类型，把向量检索下沉到数据类型层：向量直接存在键里，不需要先建二级索引；内部维护近似图索引并支持低位宽量化；通过新增的命令完成添加、相似度查询、删除与计数。它适合语义缓存、去重、相似推荐这类“纯相似度、无需复杂过滤”的场景；一旦需要标签过滤、全文混合检索或聚合分析，仍然应该使用搜索模块的查询能力。两者不是替代关系，而是按查询复杂度分工。

### 8.6 RAG 检索系统的设计要点

把向量检索用于 RAG，链路由“问题向量化 → 相似检索 → 组装提示 → 生成回答”构成。工程上真正决定效果与成本的是几个容易被忽视的环节：

- 分块策略。块太大引入噪声、太小丢失上下文，通常采用固定长度加重叠窗口，重叠用于避免关键句被切断。
- 混合检索。纯向量检索对专有名词、编号、代码标识不敏感，通常与关键词检索并行，再用融合排序合并结果。
- 重排序。对初筛结果用更强的交叉编码模型重排，能明显提升最终上下文质量，代价是额外推理延迟。
- 元数据过滤。先按权限、类型、时间过滤再检索，既提升准确率也避免越权召回。
- 缓存与降级。相同问题的向量化结果可以缓存；嵌入服务不可用时降级到关键词检索，保证可用性。
- 引用与可追溯。返回结果要携带来源标识，便于答案引用与问题定位。

数据入库的步骤是：把文档切成块（常用固定长度加重叠窗口）；对每块调用嵌入模型得到向量；以哈希或 JSON 写入键，字段包含正文、来源标识、块序号、向量与元数据；索引在首次创建时声明字段与向量参数，之后写入即可被检索，不需要等待索引重建。

检索的步骤是：把问题向量化；执行带元数据过滤的 KNN 查询，取回若干候选块与距离分数；可选地用关键词检索并行召回再做融合排序；可选地把候选交给重排序模型精排；最后把选中的块与来源标识组装进提示，交给生成模型并保留引用。整条链路里，嵌入与重排通常是延迟大头，检索本身在内网内存存储上往往只占很小一部分，因此优化要优先放在模型调用与缓存上。

### 8.7 与专用向量数据库的对比与选型

| 维度     | Redis 类内存向量存储         | 专用分布式向量数据库     | 托管向量服务   |
| -------- | ---------------------------- | ------------------------ | -------------- |
| 定位     | 通用内存存储加向量扩展       | 面向十亿级向量的专用系统 | 全托管检索服务 |
| 延迟     | 低，内存内检索               | 毫秒级                   | 毫秒级         |
| 规模     | 受单机内存限制，百万到千万级 | 水平扩展，十亿级         | 水平扩展       |
| 混合查询 | 向量加标签加全文较强         | 向量加标量过滤强         | 向量加元数据   |
| 运维     | 已有 Redis 则成本极低        | 需要独立集群与调参       | 无需运维       |
| 成本结构 | 内存成本高                   | 磁盘加内存               | 按量付费       |

选型建议：

- 数据量在百万到千万以内、延迟要求极高、已有 Redis 基础设施、需要向量与缓存/全文统一存储，选内存向量存储。
- 数据量到十亿级、需要水平扩展与复杂索引（多种量化、GPU 加速、离线批量），选专用向量数据库。
- 团队不想自运维、需要快速验证、用量波动大，选托管向量服务。
- 需要说明的是，向量检索的瓶颈常在“嵌入生成与重排序”而不只是检索本身，选型时要把整条链路的延迟与成本一起评估。

## 九、综合：可观测性体系与中间件选型

### 9.1 三支柱统一的可观测性体系

指标、追踪、日志各自回答不同问题：指标回答“有没有问题、问题多大”，追踪回答“问题发生在哪一跳”，日志回答“这一跳具体发生了什么”。统一体系的关键是三者可互相跳转。

```text
应用
  |-- 指标 SDK / 暴露端点   --> 采集器 --> 时序库 --> 大盘与告警
  |-- 追踪 SDK              --> Collector --> 追踪后端
  |-- 结构化日志 (带 trace_id) --> 日志采集 --> 日志后端
                                           |
             统一资源属性 + trace_id 关联这三条链路
```

落地分四步：先统一资源标签与日志的追踪上下文；再接入自动埋点覆盖框架边界；然后搭建分层大盘与黄金指标告警；最后持续做采样调优与基数治理。跳过第一步会导致后面所有关联都做不起来，是最常见的返工点。

### 9.2 消息与通知机制的选型

三种机制经常被混用，但语义差别很大：

| 维度     | Kafka                  | etcd Watch                      | Redis Pub/Sub 与 Streams             |
| -------- | ---------------------- | ------------------------------- | ------------------------------------ |
| 定位     | 分布式消息日志         | 配置与元数据变更通知            | 轻量发布订阅与内存流                 |
| 持久化   | 磁盘持久化，可回放     | 依托 MVCC，可回放（未压缩部分） | Pub/Sub 不持久；Streams 可持久       |
| 消费模型 | 消费组与位移管理       | 每个订阅者独立                  | Pub/Sub 广播；Streams 有消费组与确认 |
| 吞吐     | 很高，水平扩展         | 中等，受共识限制                | 高（内存内）                         |
| 顺序     | 分区内有序             | 同键按 revision 有序            | Pub/Sub 无保证；Streams 按流有序     |
| 典型用途 | 事件流、日志、异步任务 | 配置变更、服务发现、选主        | 实时通知、轻量队列                   |

选择判据：需要持久化、回放、多消费者与高吞吐，用 Kafka；需要强一致的少量元数据变更通知，用 etcd Watch；只要实时通知且允许丢失，用 Pub/Sub；需要消费组与确认但又想复用 Redis，用 Streams。用 Kafka 承载配置变更或选主会引入不必要的复杂度与延迟，用 Pub/Sub 承载不能丢的订单事件则必然出事。

### 9.3 服务注册与发现

基于租约与 Watch 的方案已经在前文展开。把它做成生产级组件还需要处理三件事：

- 客户端容错。本地缓存最后一次成功的实例列表，在注册中心不可用时仍能工作，避免注册中心故障引发全站不可用。
- 双通道健康检查。主动续租感知进程存活，被动健康检查感知“进程活着但依赖不可用”，两者结合才能正确摘除实例。
- 收敛速度与抖动控制。租约 TTL、心跳间隔、摘除阈值要一起设计，避免网络抖动造成实例反复上下线。

### 9.4 容量规划与故障演练

容量规划的方法论是：先压测得到单节点/单集群的吞吐与延迟曲线，确定瓶颈资源；再按业务增长与峰值系数估算目标流量；然后按分片/分区拆分到单节点并留出冗余；最后用真实流量验证。

几类中间件的容量口径：

| 组件       | 主要资源口径                                             | 关键约束                         |
| ---------- | -------------------------------------------------------- | -------------------------------- |
| Kafka      | 磁盘 = 日消息量 × 消息大小 × 副本数 × 保留天数           | 分区数与文件句柄、恢复时间       |
| etcd       | 内存 ≈ 键数 × 平均键值大小 × 索引系数；磁盘受配额约束    | 写吞吐受共识限制，配额超限转只读 |
| Redis      | 内存 = 数据量 × 冗余系数，向量场景另加图结构             | 单机内存上限与主从同步开销       |
| Prometheus | 磁盘 ≈ 活跃序列数 × 每秒样本数 × 保留秒数 × 每样本字节数 | 基数与抓取目标数                 |

故障演练按层级递进：单点故障（杀一个节点，验证自动转移与数据不丢）→ 网络故障（分区、延迟、丢包，验证超时重试与降级）→ 集群级故障（同故障域同时失效，验证恢复与降级）→ 依赖故障（DNS、下游超时，验证熔断与兜底）。演练要先提出可验证的假设，再在测试环境小范围验证、生产低峰灰度、定期全量演练，并保证每次都有复盘与修复闭环。

### 9.5 选型与实践建议

把前文的结论汇总成一份决策速查：

| 需求                     | 首选          | 备选           | 何时不选首选             |
| ------------------------ | ------------- | -------------- | ------------------------ |
| 强一致元数据、配置、选主 | etcd          | 专用协调服务   | 需要高写吞吐或大 value   |
| 事件流、日志、异步任务   | Kafka         | 云托管消息服务 | 团队无法承担集群运维     |
| 进程内只读缓存、抗热点   | groupcache    | 本地缓存库     | 需要写、需要 TTL         |
| 服务间同步调用、流式     | gRPC          | HTTP/JSON      | 浏览器直连、对外通用 API |
| 指标与告警               | Prometheus    | 托管监控       | 高基数明细分析           |
| 多源可视化与大盘         | Grafana       | 托管可视化     | 仅需极简图表             |
| 三类信号统一采集         | OpenTelemetry | 厂商 SDK       | 已深度绑定单一后端       |
| 在线向量检索             | Redis 向量    | 专用向量数据库 | 十亿级、需分布式扩展     |

几条贯穿全文的实践原则：

- 先明确语义再选组件。需要“至少一次”还是“精确一次”、需要强一致还是最终一致、需要回放还是即发即弃，这些决定了组件，而不是反过来。
- 把可观测性当作功能的一部分。没有指标、追踪与日志的服务上线即是盲区；采集本身也要治理基数与成本。
- 用超时、重试、熔断、降级作为标准配置。默认无超时、无上限重试是分布式系统故障扩散的主要来源。
- 容量与故障要提前演练。分布式系统的正确性往往在部分失效时才暴露，演练是唯一可靠的验证方式。
- 优先复用已有基础设施，但不要把“已经有一个 Redis”当作所有问题的答案。选型要看语义匹配度，而不是部署成本。
