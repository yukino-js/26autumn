本文讨论的是一组用 Go 实现的分布式基础设施组件, 覆盖互斥、路由、缓存一致性、消息投递、分布式事务、延迟调度与共识等主题。九个组件位于同一个 go.work 工作区下, 每个组件都是独立的 Go module (各自的 go.mod, Go 1.26), 可单独引用; 其中 timer 与 raft 另含可执行示例 (cmd/timer、cmd/raftkv)。

本文不以 API 手册或目录清单组织内容, 而是围绕每个组件的功能目标、实现思路、适用场景与局限展开, 重点回答三个问题: 它为什么这样设计, 边界在哪里, 什么时候不该用它。读者需要具备基本的 Go 并发编程与分布式系统背景; 对 Redis、MySQL、LSM 存储或 Raft 没有前置要求, 相关机制在正文中都会解释。

## 一、组件地图与组合方式

九个组件可以按"解决的问题层次"分为四类, 这种划分也决定了它们通常如何被组合。

| 组件             | 解决的问题                   | 核心机制                                             | 形态          |
| ---------------- | ---------------------------- | ---------------------------------------------------- | ------------- |
| redis_lock       | 跨进程互斥                   | token 所有权 + Lua 比较再执行 + 看门狗续期 + RedLock | 库            |
| consistent_hash  | 键到节点的稳定映射与数据搬迁 | 加权虚拟节点环 + 所有权索引 + 迁移 diff              | 库            |
| consistent_cache | 缓存与数据库的读写一致       | 读路径禁写标记抑制回填                               | 库            |
| red_mq           | 可靠消息投递                 | Redis Streams 消费者组 + 逐消息重试 + 死信           | 库            |
| tcc              | 跨参与方事务的最终一致       | 日志先行的 Try/Confirm/Cancel + 监控恢复             | 库            |
| time_wheel       | 海量延迟任务调度             | 槽位时间轮 (进程内) 与分钟分片 zset (分布式)         | 库            |
| timer            | 秒级定时任务平台             | cron 预展开 + 分片锁调度 + HTTP 回调                 | 可执行服务    |
| lsm_tree         | 高写入吞吐的本地存储引擎     | WAL + 跳表 memtable + 块式 SSTable + 分级 compaction | 库            |
| raft             | 多副本强一致复制             | 选举 + 日志复制 + ReadIndex + 成员变更               | 库 + 示例服务 |

组件间的实际依赖只有两条, 都是对 redis_lock 的复用:

- consistent_hash 的 Redis 环后端把环级互斥委托给 redis_lock, 保证拓扑变更 (增删节点、迁移) 不并发发生; 进程内跳表环后端则自带本地锁, 不依赖 Redis。
- tcc 的参考实现 (example 目录) 用 redis_lock 实现多协调者之间的监控循环互斥, 事务日志落在 MySQL。

timer 常被误认为是上述原语的组装, 但它实际上完全自包含: 不 import 其余八个组件, 自带基于 token 所有权的 Redis 分布式锁 (pkg/redis.ReentrantDistributeLock)、按天的布隆过滤器、有界工作池、包装 robfig/cron/v3 的解析器, 并基于 libs/yukino_http 提供 REST API。它与其余组件的关系是"同一类问题的另一种完整实现", 而非依赖关系。lsm_tree 与 raft 同样独立, 分别提供存储引擎与共识核心, 供需要本地日志或强一致决策序列的场景嵌入。

## 二、redis_lock -- 所有权安全的分布式锁

### 2.1 要解决的问题

分布式锁的最小错误是"释放了别人的锁"。典型事故链条是: 客户端 A 加锁后执行超时, 锁租约自动过期, 客户端 B 取到同一把锁, 此时 A 才执行释放, 却把 B 的锁删掉了。redis_lock 的设计目标是让这类错误在构造上不可能发生。

### 2.2 用 token 表达所有权

锁在 Redis 中是一个字符串键 (实际键名带 `REDIS_LOCK_PREFIX_` 前缀), 值为一个唯一 token, 由进程 ID 与 goroutine ID 拼成 (`pid_goroutineID`), 因此同一进程内不同 goroutine 得到的 token 也不同。所有会改变锁状态的操作都不是裸命令, 而是"先比较 token 再执行"的 Lua 脚本:

```text
Lock()   : SET key token NX EX ttl        (SetNEX)
Unlock() : Lua { if get(key) == token then del(key) }
Renew()  : Lua { if get(key) == token then expire(key, ttl) }   (DelayExpire)
```

比较与删除在同一段 Lua 内完成, 中间不会被其他客户端插入执行, 这是原子性的来源。获取失败返回包装了 `ErrLockAcquiredByOthers` 的错误, `IsRetryableErr` 用来区分"锁被占用, 稍后再试"和真实故障。

### 2.3 看门狗与等待策略

锁的租约是一个两难: 设短了业务没跑完就丢锁, 设长了持有者崩溃后等待太久。组件给出的答案是看门狗——如果调用方不显式指定 TTL (`WithExpireSeconds`), 就进入看门狗模式, 默认租约 30 秒, 后台每 10 秒续期一次, 每次把寿命延长 15 秒 (多出的 5 秒用于容忍网络延迟)。续期脚本返回非 1 时说明锁已易主, 看门狗判定 `errLockLost` 并退出, 而不是无限重试去争夺一把不属于自己的锁。看门狗的 context 派生自加锁时的 context, `Unlock` 成功路径之外的取消也会终止续期。

等待策略分两种: 默认非阻塞, 失败立即返回锁被占用; 以 `WithBlock` 开启阻塞模式后每 50 毫秒轮询一次, 直到获取成功或等待预算耗尽 (默认 5 秒)。

### 2.4 RedLock 与它的代价

单 Redis 实例不可靠, 因此提供跨多实例的 RedLock: 强制要求至少 3 个独立节点, 逐节点加锁, 只有多数派 (`len>>1+1`) 成功才算成功, 且单节点成功必须在超时预算内完成 (默认单节点超时 50 毫秒)。构造时还会校验"节点数 x 单节点超时 x 10 不超过锁的过期时长", 保证最坏情况下的累计超时也远小于租约, 否则直接报错拒绝创建。未达多数派时, 已拿下的节点会在 `context.WithoutCancel` 的新 context 中释放, 避免上游取消导致残留锁一直等到 TTL; 显式 `Unlock` 则遍历所有节点逐一释放。每个节点上的锁以 RedLock 的过期时长为 TTL, 若过期时长为 0 则回落到单锁的看门狗模式。

一个容易被忽略的语义: 该锁不可重入。token 按 goroutine 隔离, 同一 goroutine 对同一 key 二次加锁会失败或阻塞。需要嵌套语义时, 应在锁之上再维护一层计数。

### 2.5 适用场景与边界

适合: 短临界区的跨进程互斥、选主、幂等去重的最后一道闸门。

不适合: 把 RedLock 当作 CP 系统使用。在时钟漂移与网络分区下, RedLock 只能降低而非消除脑裂风险; 需要强一致的协调应交给 etcd、ZooKeeper 这类共识系统。此外固定 TTL 短于业务耗时会直接破坏互斥, 未知耗时的临界区应使用看门狗。

## 三、consistent_hash -- 带迁移计划的一致性哈希

### 3.1 要解决的问题

取模哈希在节点增减时会把几乎所有键重新映射, 引发缓存雪崩与全量数据搬迁。一致性哈希把扰动限制在新节点与其前驱之间的弧段, 但"找出这段弧里的键并搬走"通常留给调用方。该组件的定位是把两者都做完: 维护环, 并在增删节点的副作用中直接算出需要迁移的键集与迁移方向。

### 3.2 虚拟节点、权重与所有权索引

环上的桶由虚拟节点构成。每个物理节点按权重贡献 `weight x replicas` 个虚拟节点, 权重被钳制在 1 到 10 之间 (≤0 取 1, ≥10 取 10), replicas 默认 5。环级互斥的锁租约默认 15 秒。权重决定容量占比, replicas 决定环的平滑程度, 两个旋钮相互独立。

环本身是存储无关的 `HashRing` 接口, 除了基础的刻度操作 (Add 加刻度、Floor 找前驱、Ceiling 找后继、Rem 删除刻度、Nodes 列节点), 还维护两套簿记: 节点到虚拟节点数 (`AddNodeToReplica`), 以及节点到数据键的所有权索引 (`AddNodeToDataKeys`/`DeleteNodeToDataKeys`)。所有权索引是关键——`GetNode` 解析键归属时 (`Ceiling` 找到不小于键分数的刻度, 取该刻度上的第一个节点), 会登记"这个数据键属于哪个节点", 于是迁移 diff 有了数据源, 不需要扫描全量数据就能算出应迁集合。

哈希函数由 `Encryptor` 接口抽象, 内置实现 `FnvHasher` 是 FNV-1a 32 位后对 `math.MaxInt32` 取模, 把分数归一到环的有符号 32 位区间; 非测试代码中目前只提供这一种实现, 接口留出了替换空间。

### 3.3 增删节点与迁移算法

`AddNode` 的顺序是: 先拿全局环锁, 查重; 登记节点副本数; 逐个虚拟节点计算分数并上环; 每上环一个虚拟节点就调用 `migrateIn` 计算迁入键集; 最后批量执行所有迁移任务。

`migrateIn` 的核心是区间推导。对新虚拟节点, 先找它的环上前驱 (`Floor(score-1)`) 与后继 (`Ceiling(score+1)`), 其中 +1/-1 在 0 与 `MaxInt32-1` 之间显式回绕。落在左开右闭区间 (前驱分数, 本虚拟节点分数] 内的键才是应迁给新节点的, 这些键从后继节点的所有权索引里取出, 同步更新双方索引。当区间跨越分数区间的 0 点时, 代码用有符号 32 位算术把分数减去 `MaxInt32` 归一后再比较, 显式处理回绕, 而不是假设环是单调的。若该分数上已挂有多个节点, 则直接跳过迁移。

`migrateOut` 是镜像操作: 取本节点全部数据键, 选出落在自己弧段内的, 再找"下一个合法属主"。查找属主时跳过同节点的其他虚拟节点, 用已访问分数集合防止环上只剩同节点虚拟节点时无限递归; 若某分数上挂有多个节点, 直接交给同分数列表中的第二个。`RemoveNode` 对每个虚拟节点先算迁移目标, 再把该刻度从环上摘除, 全部计算完成后才执行迁移。

所有迁移回调以独立 goroutine 并发执行并各自 recover, 单个迁移任务 panic 不会中断整批; `AddNode`/`RemoveNode` 通过 WaitGroup 等待全部迁移完成后才返回——迁移不是发射后不管的异步操作, 但对并发修改同一批键的其他调用方而言仍存在短暂的双写窗口, Migrator 必须幂等。

### 3.4 两种环后端与限流

- 进程内跳表环 (`local.SkiplistHashRing`): 适合测试与单机。环状态由独立读写锁保护; 环锁是本地的带过期时间的互斥实体 (owner token + 到期自动释放), 与锁租约解耦, 不依赖 Redis。
- Redis zset 环 (`redis.RedisHashRing`): 适合多实例共享。环用有序集合存储, 分数是虚拟节点分数, 成员是该分数上节点列表的 JSON; 环锁直接复用 redis_lock; 另有一个哈希键维护节点到副本数, 以及每节点一个字符串键存储数据键集合的 JSON。

### 3.5 适用场景与边界

适合: 需要按节点权重分配数据、且节点会动态增减的分片场景, 尤其是迁移必须显式可控、不能靠缓存自然过期的情况。

不适合: 键空间极小或节点基本不动时, 直接取模更简单; 需要严格一致的分片归属 (例如基于它做存储分区) 时, 环的最终一致语义意味着迁移窗口内同一键可能被并发读写, 调用方必须让 Migrator 幂等。

## 四、consistent_cache -- 用抑制而非加锁解决缓存竞态

### 4.1 要解决的问题

经典 cache-aside 的读写流程看起来无害:

```text
read  : cache.Get -> miss -> db.Get -> cache.Set
write : db.Put -> cache.Del
```

并发下它会竞态: 一个在写入发生前就 miss 的慢读者, 会在写入删除缓存之后把旧值回填, 于是缓存一直提供陈旧数据直到 TTL 到期。加锁能解决但会让读路径阻塞在写路径上。该组件选择另一条路: 写路径开启一个短暂的读路径禁写标记, 标记存在期间所有回填都被抑制, 从而关闭旧值窗口。正确性来自抑制, 读路径永不阻塞。

### 4.2 写路径与读路径

写路径依次执行: 写禁写标记 (Redis 中是 `Enable_Lock_Key_{key}` 键, SET EX) → 删除旧缓存 → 落库 → 通过一个异步 goroutine 重新启用读路径。"重新启用"的实现不是等待, 而是对标记键执行 PEXPIRE, 把剩余寿命压缩到配置的启用延迟 (默认 1000 毫秒), 让标记在延迟后自然消失, 使所有在途读先落库, 避免刚释放标记就被慢读者污染。

读路径先查缓存: 命中且值为负缓存哨兵 (`NullData`, 常量值 `Err_Syntax_Null_Data`) 直接返回 `ErrorDataNotExist`; 命中则反序列化返回。未命中则回源数据库; 数据库也确实没有时写入哨兵防止穿透 (热 miss 不会反复打到数据库); 数据库命中则尝试回填, 但只有禁写标记不存在时才真正写入。

禁写标记的检查与回填在一次 Lua 调用里原子完成 (`PutWhenEnable`): 先读标记键, 存在则返回 0, 否则 `SET key value EX ttl` 并返回 1。若拆成两条命令, 检查与写入之间就会被写路径插入。

### 4.3 可调参数与适配层

默认值为缓存 TTL 60 秒、禁写标记 TTL 10 秒、重新启用延迟 1000 毫秒。勾选 TTL 抖动模式后, 每次写入的过期时间在基础 TTL 的 1 倍到 2 倍之间随机 (`base + rand[0, base]`), 打散集中失效。

组件对外只暴露四个接口: 缓存 (Enable/Disable/Get/Del/PutWhenEnable)、数据库 (Put/Get)、业务对象 (Key/KeyColumn/序列化 Write/反序列化 Read)、日志。内置 Redis 与 MySQL/GORM 两个适配器: MySQL 适配器的 Put 先 Create, 遇到重复键 (错误码 1062) 时按 KeyColumn 回退为 Updates, 因此同一对象的重复写入是幂等的。缓存与数据库的选型都不被绑死。

### 4.4 适用场景与边界

适合: 读多写少、能接受"短暂回源"的缓存一致性场景, 尤其是业务方不希望引入分布式锁的情况。

不适合: 需要强一致读的场景 (该方案只保证"最终不会有旧值"而不是"读一定最新")。关键约束是禁写标记的 TTL 必须覆盖最慢的一次写: 如果标记先于写完成而过期, 读路径会提前重新开放, 旧值窗口重新出现。默认的 10 秒标记加 1 秒延迟对多数负载足够保守, 但慢写业务需要调大。

## 五、red_mq -- Redis Streams 之上的重试与死信

### 5.1 要解决的问题

Redis Streams 已经提供了可靠投递所需的原语: 追加写、消费者组、每消费者的待确认列表 (PEL)、显式确认。缺的是策略层: 一条消息失败几次算失败, 毒消息去哪里, 消费者崩溃后遗留的消息由谁接手。red_mq 就是在这些原语上补齐策略。

### 5.2 生产者与消费者

生产者只做一件事: 把消息 XADD 到指定流, 附带一个最大长度以限制流的增长 (默认 500, `WithMsgQueueLen` 可调)。当前实现只设置了 MaxLen 而未启用近似截断, 因此是精确截断, 每次写入都会按上限裁剪。消费者创建时用 `XGROUP CREATE ... MKSTREAM` 以 "0-0" 起点建组建流, 组已存在 (BUSYGROUP) 时静默通过。

消费者由 (流, 消费者组, 消费者) 三元组定位。主循环的每一轮: 若配置了被遗弃消息回收, 先 XAUTOCLAIM 认领空闲超时的遗留消息 (每轮最多 1 条); 再以 `>` 读取尚未投递给本组的新消息 (每次 1 条, 阻塞等待 receiveTimeout, 默认 2 秒); 处理完成后投递死信; 最后走一遍本消费者已分配但未确认的消息 (PEL, 从 "0-0" 起读)。回调成功则确认并清除该消息的失败计数; 失败则计数加一; 回调 panic 被 recover 后同样计为一次失败。接收出错时退避 1 秒再重试。

### 5.3 逐消息重试与死信

失败计数是按消息维护的进程内 map。当某条消息的失败次数达到上限 (默认 3 次), 它被交给可插拔的死信信箱 (`DeadLetterMailbox` 接口) 处理。这里有一个重要的顺序约定: 必须先成功投递到死信, 再确认原消息; 投递失败则消息保留在 PEL 中不确认, 下一轮继续重试死信投递, 保证毒消息不会静默消失。默认的死信实现只打日志, 生产使用时通常会替换为"写入另一条流/落库/告警"。

轮询、消息处理与死信投递各有独立的超时 (默认分别为 2 秒、1 秒、1 秒), 因此单个卡死的回调不会拖垮整个消费者。被遗弃消息回收通过 `WithAbandonedMessageRecovery` 开启: 当某条待确认消息的空闲时间超过阈值, 组件会把它重新认领回来处理, 阈值应设得大于回调超时, 避免抢走仍在活跃执行的消息。

### 5.4 适用场景与边界

适合: 已经有 Redis、不希望再引入 Kafka/RabbitMQ 的场景; 中等吞吐、允许至少一次投递、需要明确失败终点的任务队列。

不适合: 需要严格顺序、极高吞吐或长期留存与重放的消息系统。流会随写入增长, 截断是必要的; 死信与重试计数是进程内状态, 跨重启会丢失, 因此真正需要"恰好一次"语义时, 仍应像上层工具链那样在业务侧用唯一键做最终去重。

## 六、tcc -- 日志先行的分布式事务管理器

### 6.1 要解决的问题

TCC (Try-Confirm-Cancel) 把一次分布式事务拆成三阶段: Try 预留并冻结资源, Confirm 提交预留, Cancel 释放预留。困难不在正常路径, 而在协调者在 Try 与 Confirm 之间崩溃时如何收场。该组件的答案是把事务日志作为第一公民: 在任何网络调用发生之前先落日志, 每个参与方的 Try 结果即时持久化, 崩溃后由后台监控循环重放未完成事务推进到终态。

### 6.2 契约与状态模型

参与方实现 `TCCComponent` 接口: `ID` 标识自身; `Try` 接收事务请求并预留资源; `Confirm` 与 `Cancel` 都只接收事务 ID, 且必须幂等, 并返回带 ACK 标记的响应。组件需先注册进 `TXManager` 的注册中心, 重复 ID 会被拒绝。

事务日志抽象为 `TXStore` 接口: CreateTX 创建事务、TXUpdate 逐组件更新 Try 结果、TXSubmit 提交终态、GetHangingTXs/GetTX 查询未完成事务、Lock/Unlock 一对锁方法供多协调者互斥。存储选型不被绑定, 仓库内的参考实现把日志落在 MySQL 的 tx_record 表, 锁用 redis_lock。

事务的终态不是直接存储的, 而是从组件 Try 结果推导 (`getStatus`):

- 全部 Try 成功, 判定 successful;
- 任一 Try 失败, 判定 failure;
- 仍有未决组件且事务创建时间早于 (当前时间 - Timeout), 也判定 failure, 这是超时推断失败, 防止资源预留因协调者反复失去联系而永久泄漏;
- 其余情况判定 hanging, 在超时前被监控循环跳过。

### 6.3 事务主流程与恢复循环

`Transaction` 的执行是: 校验请求 (非空、组件不重复) → 创建日志 → 并发执行所有 Try (每个 Try 的结果立即 TXUpdate 落日志) → 主协程收到第一个失败就取消上下文通知其余 Try → 排空所有 Try 协程保证日志完整 → 在一个脱离原 context 的新 context 中推进二阶段。二阶段的失败不回传给调用方 (调用方拿到的是 txID 与 Try 阶段是否全部成功的布尔值), 而是记日志交给监控循环兜底重试。

监控循环每隔 MonitorTick (默认 10 秒) 扫描一次。它先尝试获取全局锁 (租约为 Timeout+1 秒), 拿不到就跳过且不视为错误 (多半是别的实例在干活); 拿到后拉取未完成事务, 用 8 个 worker 并发推进: 推导状态为 successful 则逐组件 Confirm, 否则逐组件 Cancel, 每个响应必须 ACK, 全部成功后 TXSubmit 提交终态。单个事务出错不影响整批; 循环自身出错时采用指数退避 (周期翻倍), 上限为配置周期的 8 倍。Timeout 默认 5 秒。

### 6.4 适用场景与边界

适合: 跨多个微服务、需要最终一致且可补偿的业务, 例如"下单扣库存 + 冻结余额", 资源预留与释放天然可幂等。

不适合: 参与方无法提供预留语义的场景 (此时 Saga 更合适); 也不能把它当作强一致事务——在终态达成前, 数据处于"已预留未提交"的中间态, 所有读取方都必须理解这个中间态。Confirm/Cancel 非幂等是最常见的落地错误, 会导致重试不断产生副作用。

## 七、time_wheel -- 进程内与分布式两套延迟调度

### 7.1 时间轮与堆的取舍

用堆或 `time.Timer` 管理海量延迟任务, 每次插入是 O(log n), 且容易退化成"一个任务一个 goroutine/定时器"。时间轮把任务按到期时刻映射到槽位, 游标每 tick 前进一步, 插入与删除都是 O(1), 且由单个 goroutine 驱动全部任务。代价是精度受 tick 间隔限制, 且实现需要处理"超过一圈"的任务。

### 7.2 进程内时间轮

进程内实现是一个槽位数组 (默认 10 槽), 每个槽挂一条任务链表, 另有"key 到链表元素"的索引用于 O(1) 取消; 以相同 key 重复 AddTask 会先移除旧任务再挂入新任务, 天然支持重新调度。调度时把到期时刻转换成 (槽位, 圈数): 延迟除以 (槽数 x tick 间隔) 得整商作为圈数, 余数加上当前游标位置决定槽位; 游标每经过一圈把圈数减一, 归零才真正执行。这样一个小轮子也能承载任意远的未来任务。

所有状态由单 goroutine 独占, 通过 select 串行处理 tick、新增、删除三类事件, 因此无需加锁。每个任务在独立 goroutine 中执行并 recover, 单个任务 panic 不会杀死轮体。停止操作由 sync.Once 保证幂等。

### 7.3 分布式时间轮

进程内时间轮无法跨实例。分布式实现 (`RTimeWheel`) 改用 Redis 的有序集合按分钟分片: 任务的执行时刻 Unix 秒作为分数, 任务体 (含 key、回调 URL、方法、请求体、请求头) 作为成员, 落到 `yukino_time_wheel_task_{分钟}` 键上。配套一个删除标记集合 `yukino_time_wheel_delete_set_{分钟}`, 取消任务时不是真的从有序集合中删, 而是打标记。

关键操作全部是 Lua:

- 加入任务时先 SREM 清除该 key 的删除标记, 再 ZADD 写入任务, 使重新调度同一 key 的任务自动撤销旧取消;
- 取消任务时 SADD 写入删除标记, 并在标记集合大小首次变为 1 时设置 120 秒过期, 限制内存同时覆盖时钟偏差;
- 弹出到期任务时, 在同一脚本内读取删除标记 (SMEMBERS)、按分数区间取出到期任务并从集合中移除 (ZRANGEBYSCORE + ZREMRANGEBYSCORE)。读取与移除原子完成, 这是它能在多实例下不重复触发的根本原因。

运行循环每秒触发一次, 以"当前分钟起点到当前秒"为分数窗口取任务, 跳过已删除的, 交给 16 个 worker 并发发起 HTTP 回调, 单轮整体超时 30 秒。回调方法与地址在入队时就被校验 (只接受 GET、POST 两种方法和 http(s) 前缀), 执行前还会再校验一次。

### 7.4 适用场景与边界

适合: 进程内的高并发短延迟任务 (超时关闭、心跳、重试), 以及跨实例的秒级到分钟级延迟回调。

不适合: 需要毫秒级精度的场景; 分布式实现依赖分钟分片, 因此取消时必须传入与加入时相同的执行时刻, 调用方需要自行保存该时刻。任务体是 HTTP 回调描述, 因此业务逻辑要暴露成可回调的接口。

## 八、timer -- 面向生产的秒级定时任务平台

### 8.1 定位与进程结构

timer 是一个多实例可水平扩展的定时任务服务, 完全自包含: 自带基于 token 所有权的 Redis 分布式锁、布隆过滤器、有界工作池、cron 解析器 (包装 robfig/cron/v3) 与 JSON HTTP 客户端, 依赖注入用 dig 组装。进程启动时拉起四个应用, 另起一个 pprof 服务 (端口 9999):

| 角色         | 职责                                                              |
| ------------ | ----------------------------------------------------------------- |
| MigratorApp  | 周期性地把启用的 cron 表达式展开成具体任务行, 并预热 Redis 缓存   |
| SchedulerApp | 按 (分钟, 分片) 抢占分片锁; 内部级联启动 Trigger 与 Executor 服务 |
| MonitorApp   | 上报未执行任务数与启用定时器数等 Prometheus 指标                  |
| WebServer    | 定时器与任务记录的 REST API, 并挂载 /metrics 指标端点             |

其中 Trigger (按秒级分数窗口从分片缓存中取出到期任务并派发) 与 Executor (执行 HTTP 回调, 记录结果, 用布隆过滤器去重) 不是独立应用, 而是 SchedulerApp 内部级联的两个服务, 随调度器一起启动。

这种拆分的关键收益是热路径极短: cron 不在每次触发时求值, 而是在 Migrator 中预先展开, 因此调度与执行阶段只做有序集合读取和 HTTP 调用。

### 8.2 预展开与分片加锁

Migrator 每 MigrateStepMinutes (默认 60 分钟) tick 一次, 以当前小时为粒度抢锁 (初始租约 20 分钟), 读取全部启用定时器, 对每个 cron 表达式展开下一个窗口 `[整点(now+步长), 整点(now+2x步长))` 内的触发时刻并批量写入任务行 (每个定时器之间 sleep 5 秒做节流), 最后把窗口内的任务写入 Redis 缓存。重新展开是幂等的 (任务行有 timer_id+run_timer 唯一键), 因而锁只是减少重复工作而非正确性前提; 成功后把锁续期为 120 分钟的持有租约。

Scheduler 每 TryLockGapMilliSeconds (默认 100 毫秒) 遍历固定数量的分片 (默认 10), 对当前分钟与上一分钟分别提交调度任务。每个 (分钟, 分片) 只有一个实例能抢到锁; 锁租约分为两段: 抢占窗口 70 秒 (刚好覆盖一分钟处理窗口), 分片成功处理完后由 Trigger 回调 ack 把锁续期为 130 秒的持有租约, 使同一 (分钟, 分片) 在持有窗口内不会被本实例的下一轮调度或其他实例重复处理。

Trigger 拿到分片键后按秒级步长 (默认 1 秒) 扫完一分钟窗口, 逐窗口取任务: 优先读该 (分钟, 分片) 的 Redis 有序集合缓存 (分数为执行时刻 UnixMilli, 成员为 `定时器ID_时刻` 编码), 缓存未命中则回查数据库中状态为未执行的任务, 并按 `timerID % 分片数` 过滤出本分片的部分。每个任务以 `定时器ID_执行时刻` 交给有界工作池, 交给 Executor 执行。

### 8.3 去重、指标与配置

Executor 执行前先查布隆过滤器 (按天分键, TTL 24 小时): 命中或出错时回查数据库中的任务状态, 只有任务已不是"未执行"才跳过, 因此布隆的假阳性不会误杀真正待执行的任务。该过滤器把两个哈希位置 (murmur3-128 的两半分别作为一个哈希函数) 存进一个 2^24 位的 Redis 位图, 只作为最廉价的一层提示, 最终去重仍以持久化状态为准。

定时器定义本身由 Executor 内的本地缓存提供 (每 2 分钟刷新一次), 缓存未命中时回查数据库; 定时器状态不是启用时直接放弃执行。回调支持 GET、POST、PATCH、DELETE 四种方法。执行后异步上报指标 (执行计数 counter 与执行延迟 summary)、写入当天去重标记、回写任务状态与响应内容。Monitor 则每分钟抢一次分钟级锁, 上报上一分钟窗口内仍未执行的任务数与启用定时器总数两个 gauge。

WebServer 基于 libs/yukino_http 实现, 默认端口 8092, 提供定时器定义的增删改查、按应用/名称列表、启用/停用, 以及任务执行记录查询; 启用/停用/创建/删除用应用粒度的 3 秒锁做限频。启用定时器时立即预展开未来两个迁移步长的 cron 触发时刻, 写好任务行与缓存后再切换状态, 避免等到下一轮 Migrator。Prometheus 指标经 WebServer 的 /metrics 端点暴露。

配置上各角色都有内置默认值 (如分片数 10、调度工作池 100、触发工作池 10000), conf.yml 仅 MySQL DSN 与 Redis 地址/密码必填。动态分片在代码中留有痕迹 (`TaskCache.BatchCreateBucket` 会按 `分片数 + 任务数/200` 写入每分钟的桶数键), 但没有任何调用方, 调度器直接返回配置的固定分片数。表结构 DDL 随仓库提供 (timer.sql、task.sql), 需要运维手工执行, 组件不负责建表与 schema 演进。

### 8.4 适用场景与边界

适合: 需要跨实例可靠调度、任务以 HTTP 回调形式接入、且对秒级精度满意、希望自带指标与去重的中小规模定时平台。

不适合: 需要任意精度或复杂依赖编排的调度 (Airflow 之类的 DAG 引擎更合适); 动态扩缩分片未启用, 分片数需要按峰值负载人工估算。

## 九、lsm_tree -- 从 WAL 到分级合并的存储引擎

### 9.1 写放大与读放大的权衡

LSM-Tree 的思想是把随机写转换为顺序写: 写入先进内存缓冲与预写日志, 再批量顺序落盘, 后台持续合并。代价是同一份数据可能存在多个层级, 读取需要从新到旧逐层查找, 空间放大与读放大都需要 compaction 来控制。该组件是一个无外部依赖的完整实现, 覆盖预写日志、跳表内存表、块式磁盘表、布隆过滤与分级合并。

### 9.2 写入路径与日志

写操作先追加预写日志, 再写内存表。日志记录采用变长整数编码: 键长度、值长度、键、值, 文件以 O_APPEND 追加方式打开, 崩溃后重开不会覆盖已写内容; 日志文件按内存表世代命名为 `walfile/{世代}.wal`, 重放时逐条解析并灌回内存表。需要明确一个边界: 当前日志记录只有长度前缀与原始字节, 没有校验和字段, 也没有 fsync, 因此无法检测尾部截断之外的数据损坏, 进程崩溃前的写入也可能仍在页缓存中。这是教学实现的取舍, 生产存储必须补上校验与 fsync 策略。

### 9.3 内存表与磁盘表

内存表由 `MemTable` 接口抽象 (Put/Get/All/Size/EntriesCnt), 默认实现是跳表, 提供有序遍历供落盘时顺序写出。当活跃内存表的估算大小上浮 25% 后仍超过单表预算 (SSTSize, 默认 1MB) 时, 它被转为只读并投入刷盘队列, 同时新建内存表与一个新世代的日志。

磁盘表文件命名为 `{层级}_{序号}.sst`, 由三类块加一个固定 32 字节的尾部组成: 数据块、每个数据块对应的布隆过滤器块、索引块。数据块内的记录做前缀压缩 (共享前缀长度、非共享键长、值长三个变长整数 + 键后缀 + 值), 每块目标大小 16KB。索引项保留一个分隔键 (`GetSeparatorBetween` 取前一块最后一个键, 满足"不小于前一块最大键、小于后一块最小键") 加该数据块的偏移与长度, 因此定位是二分而非扫描。尾部用四个变长整数记录数据区、过滤区与索引区的位置与长度, 这也是尾部大小固定的原因。

单次读取的顺序是: 活跃内存表、只读内存表 (新者优先)、层级零的各个表 (新者优先)、层级一到层级 N 每层做一次层内二分 (层内键区间不重叠, 至多命中一个表)。命中候选表后, 先在索引上二分定位数据块, 用该数据块的布隆过滤器判断键"可能存在", 再读块逐条比对。布隆过滤器以 FNV-1a 为基础、旋转双哈希生成 k 个位 (k 按 `0.69 x m / 键数` 钳制在 1 到 30, m 默认 1024 位), 把不存在键的读取大幅减少。

### 9.4 合并策略

后台合并由单个 goroutine 驱动, 监听两个信号: 内存表刷盘与层间合并。内存表刷盘把只读内存表写成层级零的表, 成功后删除其 WAL。层间合并的触发条件是该层总大小超过 `SSTSize x 10^层数 x 每层表数上限` (每层表数上限默认 10): 取该层前半段的键范围, 收集该层与下一层中与之重叠的表, 用一个临时内存表归并去重后写出新的下一层表, 单表大小上限随层数按十倍递增 (`SSTSize x 10^(层数+1)`)。清理旧表文件后递归触发下一层, 形成级联下推。

恢复发生在 NewTree 时: 扫描目录中的 SST 文件按 (层级, 序号) 重建各层节点; 再按世代顺序重放 walfile 目录中的日志, 除最后一个外的每个日志都成为等待刷盘的只读内存表, 最后一个成为活跃内存表并继续追加。

### 9.5 适用场景与边界

适合: 需要高写入吞吐、键值语义简单、能接受后台带宽开销的本地引擎; 教学与嵌入式审计日志 (例如把执行事件按 key 追加进去)。

不适合: 需要事务与快照隔离、删除语义、或不能承受 compaction 带宽抖动的场景。当前实现对外只有 Put/Get 两个操作, 没有 Delete、没有任何形式的墓碑, 也没有 MVCC 与 fsync 策略调优, 不应存放不能丢失的数据。

## 十、raft -- 从零实现的共识核心与 KV 状态机

### 10.1 定位

这是对 Raft 的一次完整而非发散的实现: 选举状态机 (追随者、预候选、候选、领导者四态)、随机化选举超时、可选的预投票 (`Config.PreVote`)、日志复制、成员变更、线性一致读, 以及按批量驱动模型封装的对上层接口。它的用途是演示共识算法的结构, 而不是提供生产级协调服务。

### 10.2 分层与驱动模型

附带的 raftkv 示例分三层: 上层是 HTTP 键值服务 (端口 8091, PUT 把路径与请求体作为一个提议写入, POST `/{nodeID}` 提议一个加节点的成员变更); 中间是 raftProxy 驱动层 (每 100 毫秒 Tick 一次, 把提议通道接到 Node.Propose/ProposeConfChange, 消费 Ready 后调用 Advance); 底层是共识核心与内存存储。

真正的驱动核心是 `Node` 的单 goroutine 运行循环: 通过 channel 串行处理 tick、本地提议、网络消息、成员变更; 共识核心的所有变化被打包成 Ready 批次 (软状态、硬状态、未持久化日志、已提交日志、待发消息、线性读结果) 交给上层。上层调用 Advance 后, 由 Node 循环自身完成硬状态持久化、日志追加到 Storage 与应用索引推进; 而发送消息与应用已提交条目则留给嵌入方处理。示例的 raftProxy 对 Ready 批次只做 Advance, 待发消息被直接丢弃, 已提交条目也没有写入 KV 状态机——这正是"传输层置空"的具体含义: 消息会被生成但不会真正跨进程发送, 状态机应用通道在示例中永远为空。

共识核心本身是纯状态机, 不含网络。每个角色用函数指针表达其 tick 与消息处理行为; 维护每个对等体的复制进度 (Match/Next)、投票记录、出站消息队列与线性读追踪。处理一条消息时先比较任期: 更高任期的消息会让本节点退位为追随者, 但 MsgPreVote 与被接受的 MsgPreVoteResp 除外, 这是预投票不打断集群的关键; 更低任期的消息直接忽略。

### 10.3 选举、复制与线性读

选举由随机化超时触发 (超时为 ElectionTick 加一个 [0, ElectionTick) 的随机量)。启用预投票时, 节点先进入预候选并发起预投票 (预投票不增加任期); 只有拿到多数派预投票才真正竞选并自增任期, 这样可以避免一个刚恢复的网络分区节点用高任期打断稳定集群。领导者当选后立即追加一条空日志条目确立权威, 之后通过追加日志与定期心跳 (HeartbeatTick) 维持权威, 提交索引在多数派 Match 达到后推进; 跟随者收到追加请求时做日志一致性检查, 冲突时以 RejectHint 提示领导者回退 Next。成员变更以 EntryConfChange 类型的日志条目提交, 同一时刻只允许一条待决的变更条目 (pendingConf), 应用后改变集群配置。

线性一致读不追加日志, 而是走 ReadIndex: 单节点集群直接返回当前提交索引; 多节点时, 领导者先确认提交索引处条目的任期等于当前任期 (防止新领导者用旧提交应答), 记录当前提交索引并广播一次带请求上下文的心跳, 收到多数派应答后即可确认自己仍是领导者, 再把读状态交给调用方 (或对转发请求的跟随者回 MsgReadIndexResp)。这样读的代价是一次心跳往返, 而不是一条日志。跟随者收到的提议与读请求会转发给领导者。

### 10.4 存储抽象与示例的边界

存储被抽象成接口: InitialState 提供初始状态、Entries 按区间取日志、Term 取任期、FirstIndex/LastIndex 取首尾索引、Append 追加、SetHardState 持久化硬状态。内置一份内存实现 (MemoryStorage), 因此可以直接嵌入使用。

必须强调示例服务的边界: 示例是单节点配置 (ID 为 1, peers 只有自己), ElectionTick 10、HeartbeatTick 1, 预投票未开启; 传输层置空, 存储默认在内存中。因此它适合单进程验证状态机、驱动模型与日志语义, 不能用于真实多节点部署。若需要生产共识, 应使用成熟的 etcd/raft 实现。

## 十一、组合选型: 什么时候用哪个

把上面的组件放回真实系统, 可以按下面的问题定位:

| 你的问题                 | 优先选择              | 需要警惕                                     |
| ------------------------ | --------------------- | -------------------------------------------- |
| 跨进程互斥               | redis_lock            | 固定 TTL 短于业务耗时; 把它当选主共识用      |
| 节点动态增减下的数据分片 | consistent_hash       | 迁移回调必须幂等, 存在短暂双写窗口           |
| 缓存与库的最终一致       | consistent_cache      | 禁写标记 TTL 必须覆盖最慢写                  |
| 可靠异步任务投递         | red_mq                | 进程内重试计数不跨重启, 需要业务侧唯一键兜底 |
| 跨服务最终一致           | tcc                   | 参与方必须能预留资源且 Confirm/Cancel 幂等   |
| 海量延迟任务 (内存)      | time_wheel 的进程内轮 | 精度受 tick 限制                             |
| 跨实例延迟回调           | time_wheel 的分布式轮 | 取消必须携带原执行时刻                       |
| 完整定时任务平台         | timer                 | 动态分片未启用, schema 由运维负责            |
| 高写入本地存储           | lsm_tree              | 无 Delete/事务/校验和, 不存放不可丢数据      |
| 多副本强一致             | 生产 etcd/raft        | 内置 raft 传输层置空, 仅作教学与单机嵌入     |

一个值得记住的分层原则是: 这些组件都在回答"如何把一次操作安全地交给另一个进程或另一段时间", 而它们共同的前提是业务侧能够提供一个确定性的标识 (锁 token、fire key、事务 ID)。标识是幂等与恢复的锚点, 缺少它, 再精巧的组件也无法保证"只执行一次"。

## 十二、小结

九个组件共享一种克制的工程风格: 用尽可能少的原语表达清晰的所有权与幂等语义, 把正确性建立在显式的持久化状态与原子操作上, 而不是隐含的时序假设。redis_lock 用 token 表达所有权, consistent_hash 用所有权索引驱动迁移, consistent_cache 用标记抑制竞态, red_mq 用逐消息计数界定失败, tcc 用日志先行支撑崩溃恢复, time_wheel 用 Lua 原子弹出保证不重复触发, timer 用预展开压缩热路径, lsm_tree 用分级合并平衡读写放大, raft 用多数派与任期维持一致。理解每一条边界——尤其是那些"当前未做"的能力——比记住它们的 API 更重要。

相关主题可参阅 [Redis](redis)、[MySQL](mysql), 以及展示这些组件同族思想如何被组装进真实系统的 [yukino_taskflow](yukino-go-taskflow) 与 [yukino_agent](yukino-go-agent)。
