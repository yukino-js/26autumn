本文讨论的是一组用 Go 从零实现的分布式基础设施组件, 覆盖互斥、路由、缓存一致性、消息投递、分布式事务、延迟调度与共识等主题。它们被设计为可独立使用的库 (timer、raft 另含可执行示例), 既能单点验证算法, 也能被上层业务系统组装成完整的调度与执行平台。

本文不以 API 手册或目录清单组织内容, 而是围绕每个组件的功能目标、实现思路、适用场景与局限展开, 重点回答三个问题: 它为什么这样设计, 边界在哪里, 什么时候不该用它。读者需要具备基本的 Go 并发编程与分布式系统背景; 对 Redis、MySQL、LSM 存储或 Raft 没有前置要求, 相关机制在正文中都会解释。

## 一、组件地图与组合方式

九个组件可以按"解决的问题层次"分为四类, 这种划分也决定了它们通常如何被组合。

| 组件             | 解决的问题                   | 核心机制                                             | 形态          |
| ---------------- | ---------------------------- | ---------------------------------------------------- | ------------- |
| redis_lock       | 跨进程互斥                   | token 所有权 + Lua 比较再执行 + 看门狗续期 + RedLock | 库            |
| consistent_hash  | 键到节点的稳定映射与数据搬迁 | 加权虚拟节点环 + 所有权索引 + 迁移 diff              | 库            |
| consistent_cache | 缓存与数据库的读写一致       | 读路径禁写标记抑制回填                               | 库            |
| red_mq           | 可靠消息投递                 | Redis Streams 消费者组 + 逐消息重试 + 死信           | 库            |
| tcc              | 跨参与方事务的最终一致       | 日志先行的 Try/Confirm/Cancel + 监控恢复             | 库            |
| time_wheel       | 海量延迟任务调度             | 槽位时间轮 (进程内) 与分钟分片 zset (分布式)         | 库            |
| timer            | 秒级定时任务平台             | cron 预展开 + 分片锁调度 + HTTP 回调                 | 可执行服务    |
| lsm_tree         | 高写入吞吐的本地存储引擎     | WAL + 跳表 memtable + 块式 SSTable + 分级 compaction | 库            |
| raft             | 多副本强一致复制             | 选举 + 日志复制 + ReadIndex + 成员变更               | 库 + 示例服务 |

组合关系上有两条清晰的主线。其一是"锁与环": consistent_hash 需要一个环级互斥来保证拓扑变更不并发, 它直接复用 redis_lock。其二是"调度与执行": time_wheel、red_mq、redis_lock、tcc、consistent_hash 共同描述了一个完整的任务系统骨架——何时触发、如何抢占、如何保证只执行一次、失败如何恢复, 这正是一个上层应用 (如条件与定时任务平台) 需要的全部原语。lsm_tree 与 raft 相对独立, 它们提供的是存储引擎与共识核心, 供需要本地审计日志或强一致决策序列的场景嵌入。

## 二、redis_lock -- 所有权安全的分布式锁

### 2.1 要解决的问题

分布式锁的最小错误是"释放了别人的锁"。典型事故链条是: 客户端 A 加锁后执行超时, 锁租约自动过期, 客户端 B 取到同一把锁, 此时 A 才执行释放, 却把 B 的锁删掉了。redis_lock 的设计目标是让这类错误在构造上不可能发生。

### 2.2 用 token 表达所有权

锁在 Redis 中是一个字符串键, 值为一个唯一 token, 由进程 ID 与协程 ID 拼成, 因此同一进程内不同 goroutine 得到的 token 也不同。所有会改变锁状态的操作都不是裸命令, 而是"先比较 token 再执行"的 Lua 脚本:

```text
Lock()   : SET key token NX EX ttl
Unlock() : Lua { if get(key) == token then del(key) }
Renew()  : Lua { if get(key) == token then expire(key) }
```

比较与删除在同一段 Lua 内完成, 中间不会被其他客户端插入执行, 这是原子性的来源。获取失败返回可重试错误, `IsRetryableErr` 用来区分"锁被占用, 稍后再试"和真实故障。

### 2.3 看门狗与等待策略

锁的租约是一个两难: 设短了业务没跑完就丢锁, 设长了持有者崩溃后等待太久。组件给出的答案是看门狗——如果调用方不显式指定 TTL, 就进入看门狗模式, 默认租约 30 秒, 后台每 10 秒续期一次, 每次把寿命延长 15 秒 (多出的 5 秒用于容忍网络延迟)。续期脚本返回非 1 时说明锁已易主, 看门狗判定 `errLockLost` 并退出, 而不是无限重试去争夺一把不属于自己的锁。

等待策略分两种: 默认非阻塞, 失败立即返回锁被占用; 开启阻塞模式后每 50 毫秒轮询一次, 直到获取成功或等待预算耗尽 (默认 5 秒)。

### 2.4 RedLock 与它的代价

单 Redis 实例不可靠, 因此提供跨多实例的 RedLock: 强制要求至少 3 个独立节点, 逐节点加锁, 只有多数派成功才算成功, 且要求单节点成功必须在超时预算内完成。构造时还会校验"节点数 x 单节点超时 x 10 不超过锁的过期时长", 保证即使最坏情况下的累计超时也远小于租约, 否则直接报错拒绝创建。未达多数派时, 已拿下的节点会在一个脱离原 context 的新 context 中释放, 避免上游取消导致残留锁一直等到 TTL。

一个容易被忽略的语义: 该锁不可重入。token 按 goroutine 隔离, 同一 goroutine 对同一 key 二次加锁会失败或阻塞。需要嵌套语义时, 应在锁之上再维护一层计数。

### 2.5 适用场景与边界

适合: 短临界区的跨进程互斥、选主、幂等去重的最后一道闸门。

不适合: 把 RedLock 当作 CP 系统使用。在时钟漂移与网络分区下, RedLock 只能降低而非消除脑裂风险; 需要强一致的协调应交给 etcd、ZooKeeper 这类共识系统。此外固定 TTL 短于业务耗时会直接破坏互斥, 未知耗时的临界区应使用看门狗。

## 三、consistent_hash -- 带迁移计划的一致性哈希

### 3.1 要解决的问题

取模哈希在节点增减时会把几乎所有键重新映射, 引发缓存雪崩与全量数据搬迁。一致性哈希把扰动限制在新节点与其前驱之间的弧段, 但"找出这段弧里的键并搬走"通常留给调用方。该组件的定位是把两者都做完: 维护环, 并在增删节点的副作用中直接算出需要迁移的键集与迁移方向。

### 3.2 虚拟节点、权重与所有权索引

环上的桶由虚拟节点构成。每个物理节点按权重贡献 `weight x replicas` 个虚拟节点, 权重被钳制在 1 到 10 之间, 虚拟节点数默认每个权重单位 5 个。权重决定容量占比, replicas 决定环的平滑程度, 两个旋钮相互独立。

环本身是存储无关的 `HashRing` 接口, 除了基础的刻度操作 (加刻度、找前驱、找后继、删除刻度、列节点), 还维护两套簿记: 节点到虚拟节点数, 以及节点到数据键的所有权索引。所有权索引是关键——每次解析键归属时都会登记"这个数据键属于哪个节点", 于是迁移 diff 有了数据源, 不需要扫描全量数据就能算出应迁集合。

哈希函数由 `Encryptor` 接口抽象, 内置实现是 FNV-1a 32 位, 再做一次取模映射到环分数区间; 非测试代码中目前只提供这一种实现, 接口留出了替换空间。

### 3.3 增删节点与迁移算法

AddNode 的顺序是: 先拿全局环锁, 查重; 登记节点; 逐个虚拟节点计算分数并上环; 每上环一个虚拟节点就调用 migrateIn 计算迁入键集; 最后把所有迁移任务批量并发执行。

migrateIn 的核心是区间推导。对新虚拟节点, 先找它的环上前驱与后继。落在左开右闭区间 (前驱分数, 本虚拟节点分数] 内的键才是应迁给新节点的, 这些键从后继节点的所有权索引里取出, 同步更新双方索引。当区间跨越分数区间的 0 点时 (低分虚拟节点可能拥有跨 `MaxInt32 -> 0` 的弧段), 代码用有符号 32 位算术把分数归一后再比较, 显式处理回绕, 而不是假设环是单调的。

migrateOut 是镜像操作。取本节点全部数据键, 选出落在自己弧段内的, 然后递归查找"下一个合法属主": 跳过同节点的其他虚拟节点, 用已访问集合防止环上只剩同节点虚拟节点时无限递归; 若某分数上挂有多个节点, 直接交给同分数列表中的下一个。

所有迁移回调以独立 goroutine 执行并各自 recover, 单个迁移任务 panic 不会中断整批, 也不会污染环状态——环的修改在回调执行前已全部落定。

### 3.4 两种环后端与限流

- 进程内跳表环: 适合测试与单机, 环状态由独立读写锁保护, 与锁租约解耦。
- Redis zset 环: 适合多实例共享。环用有序集合存储, 分数是虚拟节点分数, 成员是该分数上的节点列表; 环锁直接复用 redis_lock; 另有两个键分别维护副本数索引与数据键索引。

### 3.5 适用场景与边界

适合: 需要按节点权重分配数据、且节点会动态增减的分片场景, 尤其是迁移必须显式可控、不能靠缓存自然过期的情况。

不适合: 键空间极小或节点基本不动时, 直接取模更简单; 需要严格一致的分片归属 (例如基于它做存储分区) 时, 环的最终一致与迁移回调的异步执行意味着短暂的双写窗口, 调用方必须让 Migrator 幂等并处理并发读写。

## 四、consistent_cache -- 用抑制而非加锁解决缓存竞态

### 4.1 要解决的问题

经典 cache-aside 的读写流程看起来无害:

```text
read  : cache.Get -> miss -> db.Get -> cache.Set
write : db.Put -> cache.Del
```

并发下它会竞态: 一个在写入发生前就 miss 的慢读者, 会在写入删除缓存之后把旧值回填, 于是缓存一直提供陈旧数据直到 TTL 到期。加锁能解决但会让读路径阻塞在写路径上。该组件选择另一条路: 写路径开启一个短暂的读路径禁写标记, 标记存在期间所有回填都被抑制, 从而关闭旧值窗口。正确性来自抑制, 读路径永不阻塞。

### 4.2 写路径与读路径

写路径依次执行: 写禁写标记 → 删除旧缓存 → 落库 → 通过一个异步 goroutine 延迟重新启用读路径。延迟启用让所有在途读先落库, 避免刚释放标记就被慢读者污染。

读路径先查缓存: 命中且值为负缓存哨兵直接返回"数据不存在"; 命中则反序列化返回。未命中则回源数据库; 数据库也确实没有时写入哨兵防止穿透 (热 miss 不会反复打到数据库); 数据库命中则尝试回填, 但只有禁写标记不存在时才真正写入。

禁写标记的检查与回填在一次 Lua 调用里原子完成: 先读标记键, 存在则返回 0, 否则写缓存并返回 1。若拆成两条命令, 检查与写入之间就会被写路径插入。

### 4.3 可调参数与适配层

默认值为缓存 TTL 60 秒、禁写标记 TTL 10 秒、重新启用延迟 1000 毫秒。勾选 TTL 抖动模式后, 每次写入的过期时间在基础 TTL 的 1 倍到 2 倍之间随机, 打散集中失效。

组件对外只暴露四个接口: 缓存 (Enable/Disable/Get/Del/PutWhenEnable)、数据库 (Put/Get)、业务对象 (键、序列化、反序列化)、日志。内置 Redis 与 MySQL/GORM 两个适配器, 因此缓存与数据库的选型都不被绑死。

### 4.4 适用场景与边界

适合: 读多写少、能接受"短暂回源"的缓存一致性场景, 尤其是业务方不希望引入分布式锁的情况。

不适合: 需要强一致读的场景 (该方案只保证"最终不会有旧值"而不是"读一定最新")。关键约束是禁写标记的 TTL 必须覆盖最慢的一次写: 如果标记先于写完成而过期, 读路径会提前重新开放, 旧值窗口重新出现。默认的 10 秒标记加 1 秒延迟对多数负载足够保守, 但慢写业务需要调大。

## 五、red_mq -- Redis Streams 之上的重试与死信

### 5.1 要解决的问题

Redis Streams 已经提供了可靠投递所需的原语: 追加写、消费者组、每消费者的待确认列表 (PEL)、显式确认。缺的是策略层: 一条消息失败几次算失败, 毒消息去哪里, 消费者崩溃后遗留的消息由谁接手。red_mq 就是在这些原语上补齐策略。

### 5.2 生产者与消费者

生产者只做一件事: 把消息 XADD 到指定流, 附带一个最大长度以限制流的增长。需要留意的是, 当前实现只设置了最大长度而未启用近似截断, 因此是精确截断, 即每次写入都会按上限裁剪。

消费者由消费者组标识与消费者标识共同定位。主循环先以 `>` 读取尚未投递给本组的新消息, 再走一遍本消费者已分配但未确认的消息 (PEL), 两条路径共用同一个回调。回调成功则确认并清除该消息的失败计数; 失败则计数加一。

### 5.3 逐消息重试与死信

失败计数是按消息维护的。当某条消息的失败次数达到上限 (默认 3 次), 它被交给可插拔的死信信箱处理。这里有一个重要的顺序约定: 必须先成功投递到死信, 再确认原消息; 如果投递失败, 消息被保留而不确认, 保证毒消息不会静默消失。默认的死信实现只打日志, 生产使用时通常会替换为"写入另一条流/落库/告警"。

轮询、批处理与死信投递各有独立的超时, 因此单个卡死的回调不会拖垮整个消费者。此外还提供被遗弃消息的回收: 当某条待确认消息的空闲时间超过阈值, 组件会把它重新认领回来处理, 阈值应设得大于回调超时, 避免抢走仍在活跃执行的消息。

### 5.4 适用场景与边界

适合: 已经有 Redis、不希望再引入 Kafka/RabbitMQ 的场景; 中等吞吐、允许至少一次投递、需要明确失败终点的任务队列。

不适合: 需要严格顺序、极高吞吐或长期留存与重放的消息系统。流会随写入增长, 截断是必要的; 死信与重试计数是进程内状态, 跨重启会丢失, 因此真正需要"恰好一次"语义时, 仍应像工具链那样在业务侧用唯一键做最终去重。

## 六、tcc -- 日志先行的分布式事务管理器

### 6.1 要解决的问题

TCC (Try-Confirm-Cancel) 把一次分布式事务拆成三阶段: Try 预留并冻结资源, Confirm 提交预留, Cancel 释放预留。困难不在正常路径, 而在协调者在 Try 与 Confirm 之间崩溃时如何收场。该组件的答案是把事务日志作为第一公民: 在任何网络调用发生之前先落日志, 每个参与方的 Try 结果即时持久化, 崩溃后由后台监控循环重放未完成事务推进到终态。

### 6.2 契约与状态模型

参与方实现三个方法: Try 接收事务请求并预留资源; Confirm 与 Cancel 都只接收事务 ID, 且必须幂等。事务日志 (TXStore) 负责创建事务、逐组件更新 Try 结果、提交终态、查询未完成事务, 并提供一对锁方法供多协调者互斥。

事务的终态不是直接存储的, 而是从组件 Try 结果推导:

- 全部 Try 成功, 判定 successful;
- 任一 Try 失败, 判定 failure;
- 仍有未决组件且事务创建时间早于 (当前时间 - 超时), 也判定 failure, 这是超时推断失败, 防止资源预留因协调者反复失去联系而永久泄漏;
- 其余情况判定 hanging, 在超时前被监控循环跳过。

### 6.3 事务主流程与恢复循环

一次事务的执行是: 校验请求并解析组件 → 创建日志 → 并发执行所有 Try → 主协程收到第一个失败就取消上下文通知其余 Try → 排空所有 Try 协程保证日志完整 → 根据推导状态推进二阶段。二阶段的失败不回传给调用方, 而是记日志交给监控循环兜底重试。

监控循环每隔一个周期扫描未完成事务并推进。它先尝试获取全局锁, 拿不到就跳过且不视为错误 (多半是别的实例在干活); 出错时采用指数退避, 上限为配置周期的 8 倍。每个事务的推进相互隔离, 单个事务出错不影响整批。

### 6.4 适用场景与边界

适合: 跨多个微服务、需要最终一致且可补偿的业务, 例如"下单扣库存 + 冻结余额", 资源预留与释放天然可幂等。

不适合: 参与方无法提供预留语义的场景 (此时 Saga 更合适); 也不能把它当作强一致事务——在终态达成前, 数据处于"已预留未提交"的中间态, 所有读取方都必须理解这个中间态。Confirm/Cancel 非幂等是最常见的落地错误, 会导致重试不断产生副作用。

## 七、time_wheel -- 进程内与分布式两套延迟调度

### 7.1 时间轮与堆的取舍

用堆或 `time.Timer` 管理海量延迟任务, 每次插入是 O(log n), 且容易退化成"一个任务一个 goroutine/定时器"。时间轮把任务按到期时刻映射到槽位, 游标每 tick 前进一步, 插入与删除都是 O(1), 且由单个 goroutine 驱动全部任务。代价是精度受 tick 间隔限制, 且实现需要处理"超过一圈"的任务。

### 7.2 进程内时间轮

进程内实现是一个槽位数组, 每个槽挂一条任务链表, 另有"key 到链表元素"的索引用于 O(1) 取消。调度时把到期时刻转换成 (槽位, 圈数): 延迟除以 (槽数 x tick 间隔) 得整商作为圈数, 余数决定槽位; 游标每经过一圈把圈数减一, 归零才真正执行。这样一个小轮子也能承载任意远的未来任务。所有状态由单 goroutine 独占, 通过 select 串行处理 tick、新增、删除三类事件, 因此无需加锁。每个任务在独立 goroutine 中执行并 recover, 单个任务 panic 不会杀死轮体。停止操作由一次性保护保证幂等。

### 7.3 分布式时间轮

进程内时间轮无法跨实例。分布式实现改用 Redis 的有序集合按分钟分片: 任务的执行时刻作为分数, 以分钟为单位落到不同键上, 旧分片自然老化。配套一个删除标记集合, 取消任务时不是真的从有序集合中删, 而是打标记。

关键操作全部是 Lua:

- 加入任务时先清除该 key 的删除标记, 再写入任务, 使重新调度同一 key 的任务自动撤销旧取消;
- 取消任务时写入删除标记, 并在标记集合首次出现时设置一段过期时间, 限制内存同时覆盖时钟偏差;
- 弹出到期任务时, 在同一脚本内读取删除标记、按分数区间取出到期任务并从集合中移除。读取与移除原子完成, 这是它能在多实例下不重复触发的根本原因。

运行循环每秒触发一次, 以当前分钟起点到当前秒为分数窗口取任务, 跳过已删除的, 对每个任务发起 HTTP 回调。回调方法与地址在入队时就被校验, 只接受 GET、POST 两种方法和 http(s) 前缀。

### 7.4 适用场景与边界

适合: 进程内的高并发短延迟任务 (超时关闭、心跳、重试), 以及跨实例的秒级到分钟级延迟回调。

不适合: 需要毫秒级精度的场景; 分布式实现依赖分钟分片, 因此取消时必须传入与加入时相同的执行时刻, 调用方需要自行保存该时刻。任务体是 HTTP 回调描述, 因此业务逻辑要暴露成可回调的接口。

## 八、timer -- 面向生产的秒级定时任务平台

### 8.1 定位与角色划分

timer 把前面几个原语组装成一个多实例可水平扩展的定时任务服务。它分成五个运行角色加一个 Web 服务, 进程启动时一起拉起, 并通过 Prometheus 暴露指标。

| 角色      | 职责                                                     |
| --------- | -------------------------------------------------------- |
| Migrator  | 周期性地把启用的 cron 表达式展开成具体任务行, 并预热缓存 |
| Scheduler | 按 (分钟, 分片) 抢占分片锁, 把调度工作交给 Trigger       |
| Trigger   | 按秒级分数窗口从分片有序集合中取出到期任务并派发         |
| Executor  | 执行 HTTP 回调, 记录结果, 用布隆过滤器去重               |
| Monitor   | 上报未执行任务数与启用定时器数等指标                     |
| WebServer | 定时器与任务记录的 REST API                              |

这种拆分的关键收益是热路径极短: cron 不在每次触发时求值, 而是在 Migrator 中预先展开, 因此调度与执行阶段只做有序集合读取和 HTTP 调用。

### 8.2 预展开与分片加锁

Migrator 每过一个配置周期拿一次小时级锁, 读取全部启用定时器, 对每个 cron 表达式展开未来一个窗口内的触发时刻并批量写入任务行, 最后把任务写入 Redis 缓存。重新展开是幂等的, 因而锁只是减少重复工作而非正确性前提。

Scheduler 周期性遍历固定数量的分片, 对当前分钟与上一分钟分别提交调度任务。每个 (分钟, 分片) 只有一个实例能抢到锁; 分片键按分钟与分片编号编码, 天然做到同一分钟内各分片并行、跨实例互斥。锁的租约分为"抢占窗口"和"持有租约"两段, 前者是一个刚好覆盖一分钟处理窗口的初始租约, 后者在分片成功处理完后把锁续期为更长时间, 使同一 (分钟, 分片) 在持有窗口内不会被本实例的下一轮调度或其他实例重复处理。

Trigger 拿到分片键后按秒级步长扫完一分钟窗口, 逐窗口从有序集合取任务, 交给有界工作池执行。每个任务以"定时器 ID 加执行时刻"编码, Executor 由此还原出定时器与计划时刻。

### 8.3 去重、指标与配置

Executor 执行前先查布隆过滤器 (按天分键): 命中或出错时回查数据库中的任务状态再决定是否跳过, 因此布隆的假阳性不会误杀真正待执行的任务。该过滤器把两个哈希位置存进一个有界的 Redis 位图, 只作为最廉价的一层提示, 最终去重仍以持久化状态为准。回调支持 GET、POST、PATCH、DELETE 四种方法。执行后异步上报指标、写入当天去重标记、回写任务状态与响应内容。

配置上各角色都有默认值, 仅数据库与 Redis 地址必填。分片数的默认值是 10; 动态分片逻辑在代码中存在但整体停用, 当前直接返回配置的固定值。进程同时暴露一个 pprof 端口用于诊断。

### 8.4 适用场景与边界

适合: 需要跨实例可靠调度、任务以 HTTP 回调形式接入、且对秒级精度满意、希望自带指标与去重的中小规模定时平台。

不适合: 需要任意精度或复杂依赖编排的调度 (Airflow 之类的 DAG 引擎更合适); 动态扩缩分片当前未启用, 分片数需要按峰值负载人工估算。建表与索引由运维负责, 组件不负责 schema 演进。

## 九、lsm_tree -- 从 WAL 到分级合并的存储引擎

### 9.1 写放大与读放大的权衡

LSM-Tree 的思想是把随机写转换为顺序写: 写入先进内存缓冲与预写日志, 再批量顺序落盘, 后台持续合并。代价是同一份数据可能存在多个层级, 读取需要从新到旧逐层查找, 空间放大与读放大都需要 compaction 来控制。该组件是一个无外部依赖的完整实现, 覆盖预写日志、跳表内存表、块式磁盘表、布隆过滤与分级合并。

### 9.2 写入路径与日志

写操作先追加预写日志, 再写内存表。日志记录采用变长整数编码: 键长度、值长度、键、值, 以追加方式打开, 因此崩溃后重开不会覆盖已写内容。重放时逐条解析并灌回内存表。需要明确一个边界: 当前日志记录只有长度前缀与原始字节, 没有校验和字段, 因此无法检测尾部截断之外的数据损坏。这是教学实现的取舍, 生产存储必须补上校验与 fsync 策略。

### 9.3 内存表与磁盘表

内存表是跳表实现, 提供有序遍历, 供落盘时顺序写出。当活跃内存表的估算大小超过层级零的单表预算时, 它被转为只读并投入刷盘队列, 同时新建内存表与一个新世代的日志。

磁盘表由三类块加一个固定大小的尾部组成: 数据块、每个数据块对应的布隆过滤器、索引块。索引项保留一个分隔键, 满足"不小于前一块最大键、小于后一块最小键", 因此定位是二分而非扫描。尾部用几个变长整数指向过滤器与索引块的位置, 这也是尾部大小固定的原因。

单次读取的顺序是: 活跃内存表、只读内存表 (新者优先)、层级零的各个表 (新者优先)、层级一到层级 N 每层做一次层内二分 (层内键区间不重叠, 至多命中一个表)。命中候选表后, 先用该数据块的布隆过滤器判断键"可能存在", 再读块逐条比对。布隆过滤器把不存在键的读取大幅减少。

### 9.4 合并策略

后台合并由两个信号驱动: 内存表刷盘与层间合并。内存表刷盘把只读内存表写成层级零的表。层间合并针对数量超限的层, 取该层前半段的键范围, 收集与下一层重叠的表, 归并写出新的下一层表, 单表大小上限随层数按十倍递增。清理旧表后递归触发下一层, 形成级联下推。

### 9.5 适用场景与边界

适合: 需要高写入吞吐、键值语义简单、能接受后台带宽开销的本地引擎; 教学与嵌入式审计日志 (例如把执行事件按 fire key 追加进去)。

不适合: 需要事务与快照隔离、范围删除、或不能承受 compaction 带宽抖动的场景。当前实现没有 MVCC、没有范围墓碑、也没有 fsync 策略调优, 不应存放不能丢失的数据。

## 十、raft -- 从零实现的共识核心与 KV 状态机

### 10.1 定位

这是对 Raft 的一次完整而非发散的实现: 选举状态机 (追随者、预候选、候选、领导者四态)、随机化选举超时、预投票、日志复制、成员变更、线性一致读, 以及按批量驱动模型封装的对上层接口。它的用途是演示共识算法的结构, 而不是提供生产级协调服务。

### 10.2 分层与驱动模型

上层是一个 HTTP 键值服务, 中间是驱动层, 底层是共识核心与内存存储。驱动层的职责是把共识核心吐出的一批"待办"落地: 持久化硬状态、持久化日志、发送消息、应用已提交条目, 然后通知核心推进。这个"取出就绪批次—处理—推进"的循环把异步的共识状态机包装成了可预测的单 goroutine 模型。

共识核心本身是纯状态机, 不含网络。每个角色用函数指针表达其 tick 与消息处理行为; 维护每个对等体的复制进度、投票记录、出站消息队列与线性读追踪。处理一条消息时先比较任期: 更高任期的消息 (预投票相关除外) 会让本节点退位为追随者, 这是防脑裂的基本规则。

### 10.3 选举、复制与线性读

选举由随机化超时触发, 先进入预候选并发起预投票; 只有拿到多数派预投票才真正竞选, 这样可以避免一个刚恢复的网络分区节点用高任期打断稳定集群。领导者通过追加日志与定期心跳维持权威, 提交索引在多数派复制后推进。成员变更以特殊类型的日志条目提交, 应用后改变集群配置。

线性一致读不追加日志, 而是走 ReadIndex: 领导者记录当前提交索引, 广播一次带上下文的心跳, 收到多数派应答后即可确认自己仍是领导者, 再返回该索引对应的读状态。这样读的代价是一次心跳往返, 而不是一条日志。

### 10.4 存储抽象与示例的边界

存储被抽象成接口: 提供初始状态、按区间取日志、取任期、取首尾索引、追加、持久化硬状态。内置一份内存实现, 因此可以直接嵌入使用。

必须强调示例服务的边界: 传输层是置空的——消息会被生成但不会真正跨进程发送; 存储默认在内存中。因此它适合单进程验证状态机、驱动模型与日志语义, 不能用于真实多节点部署。若需要生产共识, 应使用成熟的 etcd/raft 实现。

## 十一、组合选型: 什么时候用哪个

把上面的组件放回真实系统, 可以按下面的问题定位:

| 你的问题                 | 优先选择              | 需要警惕                                     |
| ------------------------ | --------------------- | -------------------------------------------- |
| 跨进程互斥               | redis_lock            | 固定 TTL 短于业务耗时; 把它当选主共识用      |
| 节点动态增减下的数据分片 | consistent_hash       | 迁移回调必须幂等, 存在短暂双写窗口           |
| 缓存与库的最终一致       | consistent_cache      | 禁写标记 TTL 必须覆盖最慢写                  |
| 可靠异步任务投递         | red_mq                | 进程内重试计数不跨重启, 需要业务侧唯一键兜底 |
| 跨服务最终一致           | tcc                   | 参与方必须能预留资源且 Confirm/Cancel 幂等   |
| 海量延迟任务 (内存)      | time_wheel 的进程内轮 | 精度受 tick 限制                             |
| 跨实例延迟回调           | time_wheel 的分布式轮 | 取消必须携带原执行时刻                       |
| 完整定时任务平台         | timer                 | 动态分片未启用, schema 由运维负责            |
| 高写入本地存储           | lsm_tree              | 无事务/快照/校验和, 不存放不可丢数据         |
| 多副本强一致             | 生产 etcd/raft        | 内置 raft 传输层置空, 仅作教学与单机嵌入     |

一个值得记住的分层原则是: 这些组件都在回答"如何把一次操作安全地交给另一个进程或另一段时间", 而它们共同的前提是业务侧能够提供一个确定性的标识 (锁 token、fire key、事务 ID)。标识是幂等与恢复的锚点, 缺少它, 再精巧的组件也无法保证"只执行一次"。

## 十二、小结

九个组件共享一种克制的工程风格: 用尽可能少的原语表达清晰的所有权与幂等语义, 把正确性建立在显式的持久化状态与原子操作上, 而不是隐含的时序假设。redis_lock 用 token 表达所有权, consistent_hash 用所有权索引驱动迁移, consistent_cache 用标记抑制竞态, red_mq 用逐消息计数界定失败, tcc 用日志先行支撑崩溃恢复, time_wheel 用 Lua 原子弹出保证不重复触发, timer 用预展开压缩热路径, lsm_tree 用分级合并平衡读写放大, raft 用多数派与任期维持一致。理解每一条边界——尤其是那些"当前未做"的能力——比记住它们的 API 更重要。
