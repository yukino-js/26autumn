## 一、连接与 SQL 执行流程

### 服务端的两层结构

MySQL 在逻辑上分为 Server 层与存储引擎层, 二者的职责边界决定了"哪些能力是跨引擎的、哪些是引擎特有的".

| 层次       | 组成                                                       | 职责                                                                            |
| ---------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Server 层  | 连接器、解析器、预处理器、优化器、执行器, 以及所有内置函数 | 建立连接、解析与优化 SQL、权限校验、跨引擎能力 (存储过程、触发器、视图、binlog) |
| 存储引擎层 | InnoDB、MyISAM、Memory 等插件式引擎                        | 数据的实际存储与检索、事务、索引、锁、redo/undo                                 |

InnoDB 是默认引擎, 支持事务、行级锁、MVCC 与崩溃恢复, 是绝大多数 OLTP 场景的选择; MyISAM 不支持事务与崩溃恢复, 只维护精确行数, 现在基本只存在于历史系统.

### 一条 select 的完整路径

一条查询依次经过连接器、解析器、预处理器、优化器、执行器:

1. 连接器: 客户端与 MySQL 完成 TCP 握手, 连接器校验用户名密码并把该账户的权限装载到会话上下文中. 空闲连接超过 `wait_timeout` (默认 28800 秒) 会被服务端主动断开.
2. 结果级缓存: Server 层不提供查询结果缓存, 结果级缓存交给 Redis 等外部缓存. 注意 Buffer Pool 缓存的是数据页而不是查询结果, 两者不是一回事, 前者依然至关重要.
3. 解析器: 先做词法分析 (tokenization) 把 SQL 切成 token, 再做语法分析 (parsing) 判断是否满足语法规则并构建抽象语法树 (AST). 语法错误在这一步抛出.
4. 预处理器: 检查表与列是否存在, 解析名称歧义, 把 `select *` 展开为具体列.
5. 优化器: 基于成本 (cost-based) 生成执行计划, 决定用哪个索引、多表连接的顺序、是否使用索引下推或覆盖索引. `explain` 输出的就是优化器的产物.
6. 执行器: 按执行计划循环调用存储引擎接口读取记录, 对每一行判断是否满足条件, 满足则写入结果集.

执行器与引擎交互的三种典型形态:

- 主键等值查询: 执行计划中 `type = const`, 引擎沿聚簇索引一次定位, 最多返回一行.
- 全表扫描: `type = ALL`, 逐行读取并判断, 是优化红线.
- 索引下推: 联合索引中未参与定位的列被下推到引擎层过滤, 减少回表次数.

### 权限校验发生在哪一步

认证与权限装载发生在连接建立时; 语句执行前后还会按内存中的授权表检查库、表、列级权限. 通过 `GRANT` / `REVOKE` 修改权限会立即更新内存中的授权表, 无需执行 `FLUSH PRIVILEGES`. 只有在用 DML 直接改 `mysql` 库的授权表时, 才需要 `FLUSH PRIVILEGES` 让服务端重新加载.

### 一条 update 的路径与三种日志的协作

update 走与 select 相同的 Server 层流程, 差异集中在执行阶段, 涉及 redo log、undo log、binlog 三种日志:

1. 执行器调用 InnoDB 读取目标行; 若数据页在 Buffer Pool 中则直接返回, 否则从磁盘读入.
2. InnoDB 先写 undo log 记录旧值 (更新非主键列时记录反向的 update 操作), 用于回滚与 MVCC.
3. 修改 Buffer Pool 中的记录, 把该页标记为脏页; 数据页并不立即落盘, 由后台线程异步刷脏.
4. 写 redo log (记录"某页某偏移量做了什么修改"), 事务进入 prepare 状态.
5. 执行器写 binlog, 这是 Server 层的逻辑日志, 用于复制与备份恢复.
6. 提交事务, 在 redo log 中写入 commit 标记. 这正是两阶段提交, 目的是让 redo log 与 binlog 对同一个事务给出相同的"是否生效"结论.

InnoDB 以页 (默认 16KB) 为读写单位, 即使只更新一行, 也会把整页读入 Buffer Pool 并在页上修改.

### 长连接与短连接的取舍

建立连接需要 TCP 握手与权限校验, 成本不低, 因此生产环境普遍使用长连接加连接池. 长连接的代价是: MySQL 执行期间临时使用的内存挂在连接对象上, 只有连接断开才释放. 长连接长期不断开可能导致内存持续增长, 甚至被系统 OOM killer 终止.

处理方式:

- 周期性断开长连接: 使用一段时间或执行过大内存查询后主动断连, 由连接池重建.
- 调用驱动提供的连接重置接口, 例如 C API 的 `mysql_reset_connection()`, 它回滚未提交事务、释放锁与临时表、重置会话变量与游标, 无需重新鉴权.
- 合理设置连接池大小与 `max_connections` (默认 151), 超过上限后新连接会被拒绝.

下面几条命令用于观察连接状态与关键参数:

```sql
show processlist;                        -- Sleep 状态是空闲连接
kill connection <id>;                    -- 断开指定连接
show variables like 'wait_timeout';      -- 空闲连接最大存活秒数, 默认 28800
show variables like 'max_connections';   -- 最大连接数
```

### InnoDB 与 MyISAM 的对比

| 维度       | InnoDB                                 | MyISAM                         |
| ---------- | -------------------------------------- | ------------------------------ |
| 事务       | 支持 ACID                              | 不支持                         |
| 锁粒度     | 行级锁 (记录锁/间隙锁/临键锁) 加表级锁 | 仅表级锁                       |
| 外键       | 支持                                   | 不支持                         |
| 索引组织   | 聚簇索引, 叶子节点存整行数据           | 非聚簇, 索引叶子存数据文件地址 |
| 崩溃恢复   | redo log 保证 crash-safe               | 不支持, 崩溃可能丢数据         |
| MVCC       | 支持                                   | 不支持                         |
| `count(*)` | 需要扫描, 可走最小的二级索引           | 维护精确行数, 常数时间返回     |

选型结论: 需要事务、高并发写、崩溃恢复的场景用 InnoDB; 只有纯只读、可接受丢数据的历史场景才可能用 MyISAM.

## 二、InnoDB 的物理与内存结构

### 表空间、段、区、页、行

层级关系为表空间 (tablespace) 大于段 (segment), 大于区 (extent), 大于页 (page), 大于行 (row). 开启 `innodb_file_per_table` (默认开启) 后, 每张表对应一个独立的 `.ibd` 表空间文件.

- 段: 按用途划分的区的集合. 索引段存 B+ 树非叶节点, 数据段存叶子节点, 回滚段存 undo log.
- 区: 分配空间的基本单位, 默认 1MB; 对 16KB 的页, 一个区包含 64 个连续页.
- 页: 读写磁盘的基本单位, 默认 16KB, 分为数据页、undo 页、溢出页等.
- 行: 记录按行格式存放在数据页中.

按区而不是按页分配, 是为了让逻辑相邻的页物理上也相邻. B+ 树同层节点用双向链表相连, 若按页零散分配, 范围扫描会产生大量随机 I/O; 按 1MB 连续空间分配后, 范围查询更接近顺序 I/O.

按页而不是按行读写, 是因为一次 I/O 至少处理 16KB, 充分利用局部性: 访问一行后, 邻近行大概率也会被访问.

### compact/dynamic 行格式与隐藏列

InnoDB 的行格式有古老的 redundant, 以及紧凑的 compact、dynamic (默认)、compressed. dynamic 与 compressed 在 compact 基础上改进.

compact 下一条记录由额外信息与真实数据两部分组成. 额外信息包含三部分:

1. 变长字段长度列表: 仅当表中有 varchar 等变长字段时存在, 按列顺序逆序存放各变长字段的真实长度.
2. null 值列表: 仅当存在可空字段时存在, 每个可空列占 1 bit, 为 1 表示该列为 null; 全部字段非空时可省掉这块空间. null 值不占真实数据区空间, 只在位图中标记.
3. 记录头信息 (5 字节), 关键字段有 `delete_mask` (标记删除, 由 purge 线程后续物理回收)、`next_record` (指向下一条记录)、`record_type` (0 普通记录, 1 非叶节点, 2 最小记录, 3 最大记录).

真实数据区除用户列外还有三个隐藏列:

| 隐藏列        | 长度   | 是否必需 | 作用                                                 |
| ------------- | ------ | -------- | ---------------------------------------------------- |
| `DB_ROW_ID`   | 6 字节 | 否       | 无主键且无非空唯一键时由 InnoDB 生成, 作为聚簇索引键 |
| `DB_TRX_ID`   | 6 字节 | 是       | 最近一次创建或修改该记录的事务 ID, MVCC 的关键       |
| `DB_ROLL_PTR` | 7 字节 | 是       | 指向 undo log 中该记录的上一个版本, 串成版本链       |

### varchar 上限与行溢出

MySQL 规定, 除 TEXT/BLOB 外的所有列, 单行总字节数不能超过 65535. 因此单列 varchar 的真实数据上限需要扣掉长度列表与 null 位图的占用:

```text
真实数据最大字节数 = 65535 - 变长字段长度列表字节数 - null 值列表字节数
```

例如单列 `varchar(n)` 且允许 null 的 ascii 字符集表: 长度超过 255 字节时长度列表占 2 字节, null 位图占 1 字节, 可用的真实数据上限为 65532. 若字符集为 utf8mb4 (每字符最多 4 字节), 则 n 约为 65532 除以 4.

当一个 16KB 页放不下整条记录时发生行溢出:

- compact: 真实数据区保留该列前 768 字节加 20 字节溢出页指针, 其余数据放溢出页.
- dynamic 与 compressed (默认): 真实数据区只保留 20 字节溢出页指针, 完整数据全部放溢出页. 这样单个数据页能容纳更多行, B+ 树扇出更大.

### 数据页内部结构与页目录

16KB 数据页由七部分组成: 文件头 (含前后页指针, 构成双向链表)、页头、最小记录与最大记录 (Infimum 与 Supremum 两个虚拟记录)、用户记录、空闲空间、页目录、文件尾 (校验页完整性).

```text
+----------+----------+----------+----------+----------+----------+----------+
| File     | Page     | Infimum  | User     | Free     | Page     | File     |
| Header   | Header   | Supremum | Records  | Space    | Directory| Trailer  |
+----------+----------+----------+----------+----------+----------+----------+
                     |                                     |
                     |  页目录槽指向每组最后一条记录  <----+
                     v
  记录按主键升序组成单向链表; 页目录是它的稀疏索引, 支持二分定位
```

页内用户记录按主键升序组成单向链表, 链表查找是 O(n), 因此引入页目录: 页目录由若干槽组成, 每个槽指向一组中的最后一条记录, 组大小规则为最小记录独占一组、最大记录所在组 1 到 8 条、其余组 4 到 8 条. 查找时先对槽二分定位到组, 再在组内沿链表遍历最多 8 条, 整体接近 O(log n). 页间定位依赖 B+ 树: 非叶节点存主键与页号, 逐层下降; 同层页之间的双向链表支持范围扫描.

### 为什么使用 B+ 树

数据库索引受一条核心约束: 数据在磁盘上, 磁盘 I/O 次数决定查询性能, 因此要让树尽可能矮胖.

B+ 树与 B 树的区别:

- B+ 树只有叶子节点存数据, 非叶节点只存索引 (主键加页号); B 树所有节点都存数据. 相同数据量下, B+ 树非叶节点能放更多索引项, 树更矮, 磁盘 I/O 更少.
- B+ 树叶子节点用双向链表串联, 范围查询定位起点后可顺序扫描; B 树范围查询需要中序遍历回溯.
- B+ 树非叶节点是冗余索引, 插入删除时结构调整更简单.

与其他结构的对比:

| 结构   | 等值查询 | 范围查询               | 是否适合磁盘索引                         |
| ------ | -------- | ---------------------- | ---------------------------------------- |
| B+ 树  | O(log n) | 叶子链表顺序扫描, 优秀 | 是, 节点天然对应磁盘页                   |
| 哈希   | O(1)     | 不支持                 | InnoDB 不提供显式哈希索引                |
| 红黑树 | O(log n) | 可行                   | 否, 二叉树过高, 千万级数据树高超过 20 层 |
| 跳表   | O(log n) | 优秀                   | 否, 节点分散, 不适合按页组织             |

### 三层 B+ 树能存多少行

以 bigint 主键 (8 字节) 加页号 (6 字节) 约 14 字节估算, 一个 16KB 非叶页约可容纳 16\*1024/14 约等于 1170 个索引项. 若一行记录约 1KB, 一个 16KB 叶子页约存 16 行:

- 两层: 约 1170 乘 16, 约 1.87 万行.
- 三层: 约 1170 乘 1170 乘 16, 约 2000 万行.

千万级表通常只需三层, 点查最多三次磁盘 I/O, 根节点常驻内存时更少. 这就是"单表 2000 万行"经验值的来源, 但它是估算: 行越大、主键越长, 容纳行数越少. 这也是主键不宜过长的原因之一.

### Buffer Pool 与改进的 LRU

磁盘 I/O 慢, InnoDB 启动时申请一块连续内存作为 Buffer Pool (默认 128MB, 生产通常设为物理内存的 60% 到 80%), 按 16KB 划分为缓存页:

- 读: 命中直接返回, 未命中从磁盘读整页.
- 写: 直接修改缓存页并标记为脏页, 同时写 redo log; 后台线程异步刷脏, 把随机写转换为顺序写 redo 加延迟批量刷盘.

内部用三条链表管理: Free List 记录空闲页, Flush List 记录脏页并按修改时间有序以便刷盘, LRU List 管理冷热淘汰.

朴素 LRU 有两个问题, InnoDB 各做了改进:

1. 预读失效: 相邻页被预读进来却从未被访问, 污染 LRU 头部. 改进方式是把 LRU 链表分为 young 区 (热数据, 默认 5/8) 与 old 区 (冷数据, 默认 3/8), 新读入的页先插入 old 区头部, 真正被访问后再晋升.
2. 全表扫描导致缓存污染: 一次大扫描可能把热点页全部挤出. 改进方式是把晋升门槛交给 `innodb_old_blocks_time` (默认 1000 毫秒): 页在 old 区停留超过该时间后再次被访问才进入 young 区, 全表扫描的页通常在一次快速访问后被弃, 无法晋升.

### 刷脏的时机与参数

脏页不会立即落盘, 由后台线程按以下时机刷写:

1. redo log 空间不足: checkpoint 推进需要腾出 redo 空间, 强制刷掉对应脏页, 这是写入周期性抖动的主因.
2. Buffer Pool 空间不足: 需要淘汰页腾位置时, 若被淘汰的是脏页则先刷盘.
3. 后台线程定期刷: page cleaner 线程按 `innodb_io_capacity` 与 `innodb_io_capacity_max` 设定的 I/O 能力, 持续把脏页比例压回 `innodb_max_dirty_pages_pct` (默认 90) 以下.
4. MySQL 正常关闭时, 把所有脏页刷盘保证干净退出.

刷脏速度由 `innodb_io_capacity` (默认 10000, 机械盘应调低) 决定上限, 脏页比例逼近阈值时按 `innodb_max_dirty_pages_pct_lwm` 提前降速. 调优的核心是让刷脏速率跟上脏页产生速率, 避免 redo 写满触发的强制刷脏把前台写入拖慢.

### Change Buffer

Change Buffer 是 Buffer Pool 中的一块区域. 当被更新的二级索引页不在内存中时, InnoDB 不立即从磁盘读入, 而是把变更缓存在 Change Buffer 中; 该页之后被读取时再合并 (merge), 后台线程也会定期合并. 它把随机的"读页加修改"变成"先记账后合并", 显著减少随机 I/O.

关键限制是唯一索引无法使用 Change Buffer: 插入前必须把页读入内存判断是否违反唯一性, 页既然已在内存, 直接修改即可. 因此:

- 写多读少 (如日志、账单) 且使用普通索引的表收益最大.
- 业务能保证唯一性时, 从性能角度普通索引优于唯一索引.
- 读多写少的表收益小, 刚记账就要合并, 反而增加维护成本.

## 三、索引体系

### 索引分类与聚簇索引键的选择

- 按数据结构: B+ 树索引、哈希索引、全文索引. InnoDB 支持 B+ 树与全文索引, 不提供显式哈希索引, 但内部有自适应哈希索引作为优化.
- 按存储形式: 聚簇索引 (叶子节点存整行数据) 与二级索引 (叶子节点存索引列值加主键值).
- 按字段特性: 主键索引、唯一索引、普通索引、前缀索引.
- 按字段数量: 单列索引与联合索引.

建表时聚簇索引键按以下顺序确定:

1. 有主键则用主键.
2. 无主键则选第一个所有列均为非空的唯一索引.
3. 都没有则由 InnoDB 生成隐藏的自增 `DB_ROW_ID`.

```sql
create table t (
  id bigint unsigned auto_increment,
  name varchar(64) not null,
  a int not null default 0,
  b int not null default 0,
  primary key (id) using btree,
  unique key uk_name (name),
  index idx_name_prefix (name(10))
);
create index idx_a_b on t (a, b);
```

### 聚簇索引、二级索引、回表与覆盖索引

- 聚簇索引: B+ 树叶子节点存完整行数据, 索引即数据, 一张表只能有一个.
- 二级索引: B+ 树叶子节点存索引列值与主键值, 可以有多个.

回表指通过二级索引查询时, 先在二级索引 B+ 树找到主键值, 再拿主键值到聚簇索引查完整行, 两棵树各查一次.

覆盖索引指查询所需的全部列都能从二级索引叶子节点中得到 (索引列加主键), 无需回表, `explain` 的 Extra 显示 `Using index`. 例如联合索引 `(name, age)` 上, `select id, name, age from users where name = 'Alice'` 可以覆盖, 而 `select *` 需要回表取其余列. 高频查询可以把 select 的列纳入联合索引, 减少回表 I/O.

### 联合索引与最左前缀原则

联合索引 `(a, b, c)` 的排序规则是先按 a, a 相同按 b, b 相同按 c. 因此 a 全局有序, b 只在 a 相同的分组内有序, c 只在 (a, b) 相同的分组内有序. 索引能被利用的前提是索引键有序, 所以查询必须从最左列开始且不能跳列:

| 查询条件                          | 索引使用情况                                   |
| --------------------------------- | ---------------------------------------------- |
| `where a = 1`                     | 生效, 使用 a                                   |
| `where a = 1 and b = 2 and c = 3` | 全部生效                                       |
| `where b = 2` 或 `where c = 3`    | 失效, 缺最左列                                 |
| `where a = 1 and c = 3`           | a 用于定位, c 不能参与定位, 但可经索引下推过滤 |
| `where a > 1 and b = 2`           | 只有 a 决定遍历范围, b 不能继续用于定位        |

where 中条件的书写顺序不影响结果, 优化器会自行调整.

范围查询会终止后续列的匹配: `where a > 1` 中满足条件的记录内部 b 无序, 遍历范围只由 a 决定. `between` 与 `like 'xxx%'` 本质也是范围条件. `where a = 1 and b >= 2` 中 a 是等值条件, b 仍可继续缩小范围.

`order by` 同样遵循最左前缀: `where a = 1 order by b, c` 可利用索引免排序, 而单独 `order by b` 需要 filesort.

### 索引下推

索引下推 (Index Condition Pushdown, ICP) 把本应在 Server 层做的过滤下推到存储引擎层, 在遍历二级索引时直接用索引列过滤, 减少回表次数, `explain` 的 Extra 显示 `Using index condition`.

以联合索引 `(a, b)` 上的 `select * from t where a > 1 and b = 2` 为例: 没有下推时, 引擎按 a 的范围每找到一个主键就回表, 再由 Server 层判断 b; 有下推时, 引擎遍历二级索引时索引里就有 b 的值, 不满足 b = 2 的记录直接跳过, 只对满足的记录回表.

### 索引失效的典型情形

1. 违反最左前缀: 缺最左列或跳列.
2. 左模糊或左右模糊匹配: `like '%xxx'`、`like '%xxx%'` 失效, `like 'xxx%'` 有效.
3. 对索引列使用函数, 如 `where length(name) = 5`. 解决方式是用函数索引 (functional key parts) 或生成列: `alter table t add key idx_len ((length(name)))`.
4. 对索引列做表达式计算, 如 `where id + 1 = 7` 失效, `where id = 7 - 1` 有效, 优化器不会主动做代数变换.
5. 隐式类型转换: `phone` 是 varchar 时 `where phone = 13800000000` 等价于对索引列套 cast, 失效; `id` 是 int 时 `where id = '1'` 的转换作用在输入参数上, 有效.
6. `or` 前后类型不一致: 一侧是索引列另一侧不是时整体失效, 需要全表扫描兜底. 解决方式是给另一侧也建索引, 优化器可能使用 index merge.
7. 优化器基于成本判断走索引不如全表扫描, 例如返回行数占比过大或统计信息过期. 可用 `analyze table` 更新统计信息, 或在确认后使用 `force index` 干预.

### 前缀索引与区分度

区分度 (selectivity) 等于 `distinct(column) / count(*)`, 越接近 1 越好. gender 这类区分度极低的列不适合单独建索引, 扫描一半索引还要大量回表, 优化器可能直接放弃. 建联合索引时, 区分度高的列放前面能命中更多查询且过滤更快.

前缀索引对字符列的前 n 个字符建索引, 用于减小索引体积、增大单页索引数量. 选择 n 的方法是计算不同前缀长度的区分度, 使其接近完整列的区分度. 前缀索引的局限是无法用于 `order by` 消除排序, 也不能作为覆盖索引, 因为索引里只有前缀, 必须回表取完整值.

### 为什么推荐自增主键

1. 插入性能: 自增主键插入是追加写, 页写满开新页; 无序主键 (如 UUID) 插入位置随机, 频繁触发页分裂, 产生内存碎片与页空洞, 索引不紧凑.
2. 主键长度: 二级索引叶子节点存主键值, 主键越短 (bigint 8 字节对 UUID 字符串 36 字节), 所有二级索引越小, 扇出越大.
3. 自增主键的缺点: 分库分表下不全局唯一, 需要雪花算法等分布式 ID; 高并发插入时存在聚簇索引右侧热点与自增锁竞争; 会泄露业务量.

### explain 执行计划解读

核心字段:

- `id`: 查询序号, 相同时自上而下执行, 不同时数字越大越先执行.
- `select_type`: simple、primary、subquery、union 等.
- `type`: 访问类型, 性能从高到低为 `null > system > const > eq_ref > ref > range > index > ALL`. 其中 `const` 是主键或唯一索引等值查询, `eq_ref` 是联表时被驱动表走主键或唯一索引, `ref` 是非唯一索引等值, `range` 是索引范围扫描, `index` 是扫描整棵二级索引树, `ALL` 是全表扫描. 生产 SQL 至少应达到 range.
- `possible_keys` / `key`: 候选索引与实际使用的索引, `key` 为 null 表示未用索引.
- `key_len`: 实际使用的索引字节数, 可用于判断联合索引使用了几列.
- `rows` / `filtered`: 预估扫描行数, 以及过滤后剩余行的百分比.
- `Extra`: 关键提示, 见下表.

| Extra 值                | 含义                                         | 评价 |
| ----------------------- | -------------------------------------------- | ---- |
| `Using index`           | 覆盖索引, 无需回表                           | 好   |
| `Using index condition` | 索引下推                                     | 好   |
| `Using where`           | 在 Server 层过滤                             | 中性 |
| `Using filesort`        | 无法利用索引排序, 需要额外排序               | 差   |
| `Using temporary`       | 使用临时表, 常见于无索引的 group by/distinct | 差   |

一段典型的执行计划输出:

```text
id  select_type  table  type   possible_keys  key      key_len  rows    Extra
1   SIMPLE       t      range  idx_a_b        idx_a_b  8        12000   Using index condition
```

它说明: 使用联合索引 `idx_a_b` 的范围扫描, 走了索引下推, 预估扫描约 12000 行. 判断一个执行计划是否健康, 主要看 type 是否退化为 `index` 或 `ALL`、key 是否为 null、rows 是否异常放大、Extra 是否出现 filesort 或 temporary.

`explain analyze` 会真实执行 SELECT 并输出各算子的实际耗时与行数, 用于验证优化器的估算是否偏离实际; 慢 SELECT 依然会消耗相应资源, 生产环境慎用. 对 INSERT 与多表 UPDATE/DELETE 只输出执行计划与读侧实际统计, 写入不会生效; 单表 UPDATE/DELETE 不由迭代器执行器处理, 直接返回不可执行.

### count 的语义与优化

`count(expr)` 统计 expr 不为 null 的行数. InnoDB 对 `count(*)` 与 `count(1)` 的处理相同, 都不需要读具体列值, 只需判断存在这一行. 性能顺序为 `count(*)` 等于 `count(1)`, 优于 `count(主键)`, 优于 `count(非索引字段)`:

- `count(*)` 与 `count(1)`: 引擎只需返回存在这一行, InnoDB 会自动选择最小的二级索引来扫描.
- `count(主键)`: 需要读出主键值返回给 Server 层判空, 略慢.
- `count(非主键字段)`: 若该字段无索引则全表扫描, 且每行都要取值判空, 最慢.

InnoDB 不像 MyISAM 那样直接维护行数, 是因为 MVCC 下"表里有多少行"对不同事务是不同的答案, 无法维护一个全局精确值. 需要精确计数时可维护一张计数表并与业务操作放在同一事务中, 或使用 Redis 计数并容忍不一致; 近似值可用 `explain select count(*) from t` 的 rows 估算或 `show table status`.

### limit 深分页与优化

`select * from t order by id limit 1000000, 10` 之所以慢, 是因为必须扫描并丢弃前 100 万行, 若走二级索引还要回表 100 万次.

优化方式:

1. 游标续传式分页, 要求 id 可比较且连续: 记录上一页最大 id, 查询 `where id > #{lastId} order by id limit 10`, 直接索引定位.
2. 子查询延迟关联: 先用覆盖索引取主键, 再回表取 10 行.
3. 业务层限制最大页码, 深度检索改用搜索引擎。

延迟关联的写法:

```sql
select t.* from t
inner join (select id from t order by id limit 1000000, 10) tmp
on t.id = tmp.id;
```

### order by 与 filesort 的两种排序算法

`order by` 无法利用索引有序性时触发 filesort, `explain` 的 Extra 显示 `Using filesort`. InnoDB 有两种排序策略:

- 全字段排序: 把满足条件的行连同所有 select 字段一起放入 `sort_buffer_size` (默认 256KB) 排序, 排好直接输出. 单次排序完成, 但排序单元大, buffer 装不下时落盘归并.
- rowid 排序: 只把排序键与主键放入 sort buffer 排序, 排好后再按主键回表取其余字段. 排序单元小、buffer 内能放更多行, 但多一次回表随机 I/O.

选择由 `max_length_for_sort_data` 控制: 单行参与排序的字段总长超过该值走 rowid 排序, 否则走全字段排序. 优化方向是让排序尽量走索引 (覆盖索引 + 最左前缀) 免掉 filesort; 必须 filesort 时, 用覆盖索引减少参与排序的列、调大 `sort_buffer_size` 避免落盘.

### join 的算法与驱动表选择

InnoDB 的 join 以嵌套循环为基础:

- Index Nested-Loop Join (索引嵌套循环): 驱动表逐行取出关联键, 用该键在被驱动表的索引上等值查找. 若被驱动表关联列有索引, 每次查找是 O(log n), 这是最理想的形态.
- Hash Join: 关联列没有可用索引时, 把较小的表在内存中构建哈希表, 再扫描较大的表逐行探测. 它取代了旧版无索引时的 Block Nested-Loop Join, 避免被驱动表被反复全表扫描.

优化原则: 用小结果集做驱动表 (优化器通常自动选择); 被驱动表的关联列必须建索引, 否则退化为对大表的全量哈希或扫描; `join_buffer_size` (默认 256KB) 影响无索引 join 的内存效率. 多表 join 时优先保证每层被驱动表都能走索引.

### 什么时候建索引

适合建索引: 有唯一性约束的字段, 高频出现在 where 中的字段, 高频用于 group by 或 order by 的字段, 联表查询的关联字段.

不适合: 数据量很小的表, 区分度极低的字段, 频繁更新的字段 (每次更新都要维护 B+ 树有序性, 可能页分裂), 从不出现在 where、group by、order by 中的字段.

索引的代价是占用磁盘空间、降低写入性能 (每次增删改都要同步维护所有索引树), 以及冗余索引可能误导优化器.

## 四、事务、MVCC 与隔离级别

### ACID 与 InnoDB 的实现手段

- 原子性 (Atomicity): 事务中的操作要么全部完成要么全部不完成. 实现手段是 undo log, 每次修改前记录旧值或反向操作, 回滚时逆向执行.
- 持久性 (Durability): 事务提交后修改永久生效, 宕机不丢. 实现手段是 redo log, 采用 WAL, 提交时保证日志落盘, 崩溃后重放.
- 隔离性 (Isolation): 并发事务互不干扰. 实现手段是 MVCC (快照读) 加锁 (当前读).
- 一致性 (Consistency): 事务前后数据处于合法状态, 它是目的而非手段, 由前三者加应用层约束共同保证.

### 并发事务引发的问题

严重程度从高到低为脏读、不可重复读、幻读:

- 脏读: 事务 A 读到事务 B 未提交的修改, 若 B 之后回滚, A 读到的就是从未存在过的数据.
- 不可重复读: 事务 A 内两次读同一条记录结果不同, 期间 B 提交了 update.
- 幻读: 事务 A 内两次执行同一条件查询返回的记录数不同, 期间 B 提交了 insert 或 delete.

记忆要点: 不可重复读针对同一行的值变化, 幻读针对结果集行数变化.

### 四种隔离级别

| 隔离级别        | 脏读   | 不可重复读 | 幻读       | Read View 生成时机               |
| --------------- | ------ | ---------- | ---------- | -------------------------------- |
| 读未提交        | 可能   | 可能       | 可能       | 无, 直接读最新数据               |
| 读已提交        | 不可能 | 可能       | 可能       | 每条 select 前生成               |
| 可重复读 (默认) | 不可能 | 不可能     | 基本不可能 | 事务第一条快照读时生成, 全程复用 |
| 串行化          | 不可能 | 不可能     | 不可能     | 读写都加锁, 串行执行             |

隔离级别越高性能越差. 读已提交与可重复读的本质区别就是 Read View 的生成时机: 前者每次读都新建, 因此能看到其他事务已提交的最新值; 后者只在事务首次快照读时建立, 全程看到同一份快照.

```sql
select @@transaction_isolation;
set session transaction isolation level repeatable read;
```

一些互联网业务会把隔离级别改为读已提交: 该级别下不加间隙锁, 只有记录锁, 锁冲突与死锁概率更低, 并发写入吞吐更高; 代价是必须使用 row 格式 binlog 才能保证主从不一致问题被完整记录.

### MVCC 与 Read View 的可见性判断

MVCC 通过 undo log 版本链加 Read View 让读写互不阻塞, 快照读不加锁, 读的是历史版本.

两块基础数据:

1. 记录的隐藏列 `DB_TRX_ID` (最后修改该记录的事务 ID) 与 `DB_ROLL_PTR` (指向上一版本), 后者把版本串成链.
2. Read View 的四个字段: `m_ids` 是创建时活跃事务的 ID 列表, `min_trx_id` 是其中最小 ID, `max_trx_id` 是下一个将分配的事务 ID, `creator_trx_id` 是创建该 Read View 的事务自身 ID.

对版本链上每个版本取其 `trx_id` 依次判断:

| 条件                       | 结论                           |
| -------------------------- | ------------------------------ |
| `trx_id == creator_trx_id` | 可见, 是自己修改的             |
| `trx_id < min_trx_id`      | 可见, Read View 创建前已提交   |
| `trx_id >= max_trx_id`     | 不可见, Read View 创建后才启动 |
| `trx_id` 在 `m_ids` 中     | 不可见, 该事务仍活跃未提交     |
| 其余                       | 可见, 已提交                   |

不可见时沿 `DB_ROLL_PTR` 找上一个版本重复判断, 直到找到可见版本或到达版本链尽头.

### 可重复读下幻读是否完全解决

InnoDB 在可重复读下很大程度避免了幻读, 但并非完全:

- 快照读 (普通 select) 依靠 MVCC: 整个事务用同一个 Read View, 其他事务插入的新记录其 `trx_id` 必然不可见, 结果集行数稳定.
- 当前读 (`select ... for update`、`select ... for share`、insert、update、delete) 依靠临键锁 (next-key lock, 记录锁加间隙锁), 锁住扫描范围及其间隙, 阻塞其他事务插入.

仍会出现幻读的两个例外:

1. 先快照读后当前读: 事务 A 先普通 select (看不到 B 插入的行), B 插入并提交, A 再执行 `select ... for update`, 当前读读的是最新版本, 结果集突然多出一行.
2. 快照读之后 update 到了看不见的行: A 普通 select 看不到 B 新插入的行, 但 A 执行 update (当前读) 恰好更新了该行, 该行的 `trx_id` 变为 A 自己, 之后 A 的 select 就能看到它.

规避方式是在事务开始时就对目标范围执行 `select ... for update` 加临键锁, 从头阻止其他事务插入.

### begin 与 consistent snapshot 的差异

- `begin` 或 `start transaction` 只是开启事务, 并不立即启动. 事务真正启动 (分配事务 ID、可重复读下创建 Read View) 发生在之后第一条操作 InnoDB 表的语句执行时.
- `start transaction with consistent snapshot` 执行后立即启动事务并创建 Read View.

易错点: "可重复读下事务启动时创建 Read View" 严格说是"执行第一条快照读语句时". 用 `begin` 开启事务后到第一条 select 之间, 其他事务提交的修改是能被看到的.

### 长事务的危害与治理

危害:

1. undo log 无法清理: 只要长事务的 Read View 存在, 它可能访问的所有旧版本都必须保留, 回滚段持续膨胀, 磁盘占用上涨.
2. MDL 锁阻塞 DDL: 长事务持有元数据读锁, DDL 申请写锁被阻塞, 且申请队列写优先, 会连带阻塞后续所有查询.
3. 长时间占用连接与行锁, 放大锁等待与死锁概率.
4. 复制场景下造成从库大事务回放延迟.

排查思路是查询 `information_schema.innodb_trx` 中执行时间过长的事务, 应用侧尽量缩短事务、不要在事务中做 RPC 或 IO、避免 `set autocommit = 0` 导致的隐式长事务; 数据库侧可设置 `max_execution_time` 限制单条只读 select 的执行时长 (单位毫秒, 默认 0 表示不启用).

```sql
select * from information_schema.innodb_trx
where TIME_TO_SEC(timediff(now(), trx_started)) > 60;
```

## 五、锁

### 锁的分类与兼容性

按范围从大到小:

- 全局锁: `flush tables with read lock`, 整库只读, 用于逻辑备份.
- 表级锁: 表锁、元数据锁 (MDL)、意向锁、AUTO-INC 锁.
- 行级锁 (InnoDB 特有, 加在索引记录上): 记录锁、间隙锁、临键锁、插入意向锁.

共享锁 S 与排他锁 X 的兼容矩阵是: 读读共享, 读写互斥, 写写互斥.

### 全局锁与一致性备份

`flush tables with read lock` 让整库只读, 保证备份出的所有表处于同一逻辑时间点, 期间增删改与 DDL 全部阻塞. InnoDB 可以利用 MVCC 避免全局锁: 备份时开启一个可重复读事务拿到一致性快照, 备份过程不阻塞业务写, 即 `mysqldump` 的 `--single-transaction` 选项. 前提是所有表都是支持事务的 InnoDB, MyISAM 表没有 MVCC, 仍需全局锁.

### MDL 元数据锁

MDL 保护表结构, 无需显式申请, 事务提交时才释放: 对表做 CRUD 时自动加 MDL 读锁 (读锁之间不互斥), 修改表结构时加 MDL 写锁 (与读写锁都互斥).

经典事故链: 线程 A 开启长事务执行 select 持有 MDL 读锁不放; 线程 C 执行 alter table 申请 MDL 写锁被 A 阻塞; MDL 申请队列是 FIFO 且写锁优先, C 排队后, 后续所有新的 select 与 insert 都排在 C 后面被阻塞, 一条 DDL 导致全表请求挂起, 连接池打满.

防范手段: DDL 前检查并 kill 长事务; 先把会话的 `lock_wait_timeout` 调小 (默认约一年), 让 alter table 申请写锁时快速失败退出而不是长期排队; 大表变更使用 gh-ost 或 pt-online-schema-change 等在线工具.

### 意向锁

意向锁是表级锁, 用于快速声明"本事务将在表内某些行上加行锁": 加行级共享锁前先给表加意向共享锁 IS, 加行级排他锁前先给表加意向排他锁 IX.

存在的意义是: 另一个事务要加表级 S 或 X 锁时, 只需检查表上是否有 IX 或 IS, 就能知道表内是否存在行锁; 没有意向锁就得遍历全表检查每一行. 意向锁之间互不冲突, 它们只与表级 S/X 锁冲突. 普通 select 是快照读, 不加行锁也不加意向锁.

### AUTO-INC 锁与 innodb_autoinc_lock_mode

自增主键的值由 AUTO-INC 锁保证: 插入时对表加锁, 语句执行完立即释放 (不等事务提交). 大批量插入时锁持有时间长, 并发插入吞吐差.

`innodb_autoinc_lock_mode` 控制分配方式:

| 取值     | 行为                                                     | 特点                                                           |
| -------- | -------------------------------------------------------- | -------------------------------------------------------------- |
| 0        | 全部使用 AUTO-INC 锁                                     | 传统模式, 并发最差                                             |
| 1        | 可预知行数的插入用轻量级互斥量, 批量插入仍用 AUTO-INC 锁 | 折中                                                           |
| 2 (默认) | 全部使用轻量级互斥量                                     | 并发最好, 但批量插入的自增值可能不连续, 需搭配 row 格式 binlog |

### 记录锁、间隙锁、临键锁、插入意向锁

设表中已有 id 为 1、5、10 三条记录:

- 记录锁 (Record Lock): 锁单条索引记录, 分 S 与 X.
- 间隙锁 (Gap Lock): 锁一个开区间, 例如 (5, 10), 只阻止其他事务往间隙里插入. 间隙锁之间即使区间重叠也互相兼容, 这是死锁的常见来源. 间隙锁只在可重复读级别存在, 目的就是防幻读.
- 临键锁 (Next-Key Lock): 记录锁加上其前面间隙的间隙锁, 左开右闭, 例如 (5, 10]. 可重复读下加锁的基本单位就是临键锁, 特定条件下退化为记录锁或间隙锁.
- 插入意向锁 (Insert Intention Lock): 特殊的间隙锁. 事务插入时若目标位置被其他事务的间隙锁或临键锁覆盖, 会生成一个等待状态的插入意向锁并阻塞; 两个事务往同一间隙的不同位置插入互不冲突.

各语句的加锁行为:

| 语句                                      | 行锁                               |
| ----------------------------------------- | ---------------------------------- |
| 普通 select                               | 不加锁 (快照读)                    |
| `select ... for share`                    | S 型临键锁                         |
| `select ... for update` / update / delete | X 型临键锁                         |
| insert                                    | 插入的记录加 X 记录锁 (隐式锁机制) |

### 行级锁的加锁规则

可重复读下加锁基本单位是临键锁, 加在扫描过的索引记录上, 满足条件时退化. 设表中记录为 1、5、10、15.

唯一索引等值查询:

- 记录存在 (`where id = 5`): 临键锁退化为记录锁, 因为唯一索引保证等值只有一条, 锁间隙没有意义.
- 记录不存在 (`where id = 7`): 定位到第一条大于 7 的记录 (id = 10), 其临键锁退化为间隙锁 (5, 10), 只需防止别人插入 7.

唯一索引范围查询, 对扫描到的索引加临键锁并在边界优化:

- `id >= 10`: id = 10 的等值部分退化为记录锁, 之后 (10, 15] 与 (15, 正无穷] 为临键锁.
- `id < 10`: 扫描终止于 10, 其临键锁退化为间隙锁 (5, 10); 之前的区间为临键锁.
- `id <= 10`: id = 10 处不退化, 保持临键锁 (5, 10], 因为 10 本身也要被锁.

非唯一索引等值查询 (`where age = 22`, age 上有普通索引), 记录存在时需要一直扫描到第一个不满足条件的记录:

- 满足条件的二级索引记录加临键锁.
- 第一个不满足条件的二级索引记录退化为间隙锁.
- 满足条件记录对应的聚簇索引加记录锁.

非唯一索引范围查询时, 扫描到的二级索引全部加临键锁, 对应的聚簇索引加记录锁. 无索引时全表扫描, 每条聚簇索引记录都加临键锁.

排查当前加锁情况可查询 `performance_schema.data_locks`, 其中 `lock_mode` 为 X 表示临键锁, `X,REC_NOT_GAP` 表示记录锁, `X,GAP` 表示间隙锁.

### 更新没有命中索引会怎样

效果上等价于锁全表, 但机制上不是表锁: where 条件没有索引或索引失效时只能全表扫描, InnoDB 对扫描到的每条聚簇索引记录都加 X 型临键锁, 其他事务的任何插入与更新都被阻塞. 防范手段是 update 与 delete 的 where 必须走索引并在上线前用 explain 确认; 开启 `sql_safe_updates` 拒绝不带索引条件的更新; 大范围更新分批执行缩短锁持有时间.

### 死锁案例与规避

经典案例是间隙锁加插入意向锁: 可重复读级别下, 两个事务并发执行"不存在则插入".

```sql
-- 事务 A                                   -- 事务 B
begin;
select * from t where id = 7 for update;    begin;
-- A 获得间隙锁 (5, 10)                      select * from t where id = 8 for update;
                                             -- B 也获得间隙锁 (5, 10), 间隙锁互相兼容
insert into t values (7);
-- A 的插入意向锁被 B 的间隙锁阻塞
                                             insert into t values (8);
                                             -- B 的插入意向锁被 A 的间隙锁阻塞
-- 互相等待, 死锁
```

死锁的四个必要条件在此齐备: 互斥、持有并等待、不可剥夺、循环等待. InnoDB 的应对有两层:

1. 死锁检测 (`innodb_deadlock_detect`, 默认开启): 检测到等待环后回滚代价最小的事务. 代价是每个新等待都要扫描等待图, 热点行高并发下检测本身消耗 CPU.
2. 锁等待超时 (`innodb_lock_wait_timeout`, 默认 50 秒): 等不到就报错回滚.

业务层规避: 多行或多表操作按固定顺序 (如主键升序) 访问; 事务尽量小并尽快提交; "不存在则插入"改用 `insert ... on duplicate key update` 或唯一索引加捕获冲突; 隔离级别降为读已提交以去掉间隙锁; 为查询条件建合适索引缩小锁范围. 排查死锁可用 `show engine innodb status` 查看 LATEST DETECTED DEADLOCK 段.

### 乐观锁与悲观锁

- 悲观锁: 假设冲突必发生, 先加锁再操作. 落地为 `select ... for update` 与 `select ... for share`. 适合写冲突激烈的场景, 代价是锁等待与死锁风险.
- 乐观锁: 假设冲突少, 不加锁, 提交时校验. 落地为版本号或 CAS.

版本号方案的写法是 `update account set balance = balance - 100, version = version + 1 where id = 1 and version = #{oldVersion}`, 受影响行数为 0 说明被并发修改, 由业务层重试. 它适合读多写少; 高冲突下重试风暴反而更差. 扣库存等场景也可直接用条件更新的原子性: `update stock set num = num - 1 where id = 1 and num >= 1`.

## 六、日志、崩溃恢复与复制

### 三种日志的对比

| 维度     | undo log                 | redo log                         | binlog                        |
| -------- | ------------------------ | -------------------------------- | ----------------------------- |
| 产生层   | InnoDB                   | InnoDB                           | Server 层, 所有引擎通用       |
| 内容     | 逻辑日志, 旧值或反向操作 | 物理日志, 某页某偏移做了什么修改 | 逻辑日志, statement/row/mixed |
| 作用     | 事务回滚与 MVCC 版本链   | 崩溃恢复, 持久性                 | 备份恢复与主从复制            |
| 写入方式 | 随事务修改产生           | 循环写, 固定容量, 边写边擦除     | 追加写, 全量保留              |

undo log 的细节: insert 回滚记录主键 (回滚即删除); delete 回滚记录整行 (回滚即重插, 且 delete 只是打删除标记, 由 purge 线程最终清理); update 非主键列记录旧值, update 主键列会拆为 delete 加 insert. 每条 undo log 带事务 ID 与回滚指针, 串成版本链支撑 MVCC. undo 页本身的修改也写 redo log, 因此 undo log 同样是持久的.

undo 数据存放在 2 个独立的 undo 表空间中, 与用户表空间分离, 数量不可调整. 不再被任何 Read View 需要的历史版本由 purge 线程清理; 当某个 undo 表空间超过 `innodb_max_undo_log_size` (默认 1GB) 且其中历史版本均可回收时, 通过 truncate 回收磁盘 (`innodb_undo_log_truncate`, 默认开启). 长事务会让 purge 无法推进, undo 表空间持续膨胀, 这是长事务除了锁之外的另一大危害.

### redo log 与 WAL

问题在于脏页在内存中, 若刷盘前宕机, 已提交事务的修改就丢了, 违反持久性. WAL (Write-Ahead Logging) 的做法是修改数据前先把这次修改以日志形式顺序写入磁盘, 数据页延后刷盘, 崩溃后重放 redo log 恢复未刷盘的脏页.

redo log 相比直接刷数据页的优势: 它是顺序追加写, 而数据页刷盘是随机写, 顺序 I/O 快一个量级; 记录粒度小, 是页内增量, 而数据页刷盘至少 16KB; 事务提交只需保证 redo log 落盘, 把每事务一次随机写聚合成批量顺序写.

redo log 写满时会阻塞所有更新, 强制把脏页刷盘并推进 checkpoint 腾出空间, 这是线上"写入周期性抖动"的常见原因. 容量由 `innodb_redo_log_capacity` 控制, 支持在线动态调整, 环形写的机制本身不变.

### redo log 的刷盘时机与参数

redo log 先写内存中的 redo log buffer, 再落盘. 刷盘时机包括事务提交时、buffer 使用超过容量一半、后台线程每秒刷一次、MySQL 正常关闭时.

`innodb_flush_log_at_trx_commit` 控制提交时的行为:

| 取值     | 行为                                    | 崩溃影响                              |
| -------- | --------------------------------------- | ------------------------------------- |
| 0        | 提交时只留在 buffer, 每秒后台刷         | MySQL 进程崩溃可能丢约 1 秒数据       |
| 1 (默认) | 提交时必须 fsync 到磁盘                 | 真正 crash-safe                       |
| 2        | 提交时写入操作系统 page cache, 不 fsync | MySQL 崩溃不丢, 主机断电可能丢约 1 秒 |

金融等强一致场景用 1, 可容忍丢失的高吞吐日志场景可用 2 或 0.

### binlog 的格式、刷盘与组提交

binlog 记录所有表结构变更与数据修改, 不记录 select, 追加写并全量保留.

| 格式       | 内容                                     | 特点                                                                                              |
| ---------- | ---------------------------------------- | ------------------------------------------------------------------------------------------------- |
| statement  | 原始 SQL                                 | 日志量小, 但 `now()`、`uuid()`、`rand()`、不带 order by 的 limit 等非确定性语句可能导致主从不一致 |
| row (默认) | 每行数据变更前后的镜像                   | 绝对确定, 主从一致; 批量更新时日志量大                                                            |
| mixed      | 默认 statement, 检测到非确定性语句切 row | 折中                                                                                              |

binlog 刷盘时, 事务执行中先写线程私有的 binlog cache 保证一个事务的 binlog 原子写入, 提交时 write 到文件系统, 再由 `sync_binlog` 控制 fsync: 取 0 只 write 不 fsync, 断电可能丢多个事务; 取 1 每次提交都 fsync, 最安全; 取 N 则攒 N 个事务 fsync 一次. `innodb_flush_log_at_trx_commit = 1` 加上 `sync_binlog = 1` 即"双 1", 是不丢数据的标准配置.

双 1 下每个事务提交需要两次 fsync, 高并发下 fsync 成为瓶颈. 组提交 (Group Commit) 把多个并发提交的事务合并成一组, 由组内 leader 执行一次 fsync, 其余 follower 搭车, 把 N 次 fsync 摊薄为一次. commit 细分为三个阶段: flush 阶段把组内各事务的 binlog cache 写入文件; sync 阶段一次 fsync 刷组内所有 binlog, 可用 `binlog_group_commit_sync_delay` (等待微秒数) 与 `binlog_group_commit_sync_no_delay_count` (攒够事务数) 控制攒批以增加组员; commit 阶段按顺序完成引擎层提交.

### binlog 的保留与行镜像

binlog 追加写并全量保留, 需要主动清理: `binlog_expire_logs_seconds` (默认 2592000, 即 30 天) 控制过期时间, 超期的 binlog 文件自动删除; 也可用 `purge binary logs` 手动清理. 保留时长要覆盖"全量备份周期加可接受的恢复窗口", 否则误删恢复时无日志可重放.

`binlog_row_image` 控制 row 格式下记录的列镜像: `full` (默认) 记录每行全部列的前后镜像, 日志量大但信息完整、便于反向生成回滚 SQL; `minimal` 只记录主键与被修改列, 日志小但无法还原完整行. 主从复制与 Canal 类订阅通常依赖 `full`.

### 两阶段提交与崩溃恢复

redo log (引擎层) 与 binlog (Server 层) 是两个独立的写入动作, 中间宕机可能导致两份日志不一致: 先写 redo 后写 binlog 时, 写完 redo 崩溃会让本机恢复该事务而 binlog 缺失, 从库少一条更新; 反过来则本机事务未生效而 binlog 存在, 从库多一条更新.

解决办法是把 redo log 的写入拆成 prepare 与 commit 两个阶段, binlog 夹在中间, 以 binlog 是否完整作为事务是否提交的统一判据, 两份日志通过 XID 关联.

```text
  redo log (InnoDB)              binlog (Server)
       |                              |
       v                              |
  [prepare]  写 redo, 状态=prepare   |
       |                              v
       |                        [写入 binlog, 含 XID]
       |                              |
       v                              |
  [commit]   写 redo, 状态=commit    |
       |                              |
       v                              v
              事务完成, 两份日志通过 XID 关联

  崩溃恢复:
    redo=commit                --> 直接提交
    redo=prepare + binlog 完整 --> 提交 (binlog 可能已被从库消费, 必须保留)
    redo=prepare + binlog 不全 --> 回滚
```

崩溃恢复时扫描 redo log: 已 commit 的直接提交; 处于 prepare 的拿 XID 去 binlog 查, 找得到完整事件则提交, 否则回滚. 这样无论在哪一点崩溃, redo log 与 binlog 对该事务是否生效的结论都一致.

### Doublewrite Buffer

部分页写问题: InnoDB 页是 16KB, 而磁盘原子写单位通常是 4KB, 刷脏刷到一半宕机, 页就半新半旧地损坏了. redo log 记录的是基于完好页的增量修改, 页本身损坏时无法重放.

Doublewrite Buffer 的做法是刷脏页时先把页顺序写到 doublewrite 区域, fsync 后再写到真正的表空间位置. doublewrite 存储在独立的 `#ib_*.dblwr` 文件中, 目录由 `innodb_doublewrite_dir` 指定, 与用户表空间分离以避免 I/O 争抢. 崩溃恢复时若发现某页校验失败, 就用 doublewrite 中的完整副本还原该页再重放 redo log. 代价是每页写两次, 但第一次是大块顺序写加单次 fsync, 额外开销约 5% 到 10%.

### 误删数据后的恢复

redo log 是固定容量循环写, 边写边擦除, 只保证未刷盘的脏页不丢, 已刷盘数据对应的 redo 会被覆盖, 因此它不是历史归档, 无法用来恢复被删的数据.

恢复依赖 binlog: 先找到最近一次全量备份 (mysqldump 或 xtrabackup) 恢复到临时实例, 再从备份时间点开始重放 binlog 到误删语句之前, 跳过误删语句后继续重放. row 格式下单条误删也可以直接解析 binlog 反向生成回滚 SQL. 预防手段是定时全量备份加 binlog 归档, 开启 `sql_safe_updates`, 高危操作走审批平台, 以及配置延迟从库兜底.

### 主从复制的原理

主从复制基于 binlog, 涉及三个线程.

```text
  主库 (source)                          从库 (replica)
+---------------------+                +---------------------------+
| 事务执行            |                |                           |
|   v                 |                |                           |
| 写 binlog           |  binlog dump   |  I/O 线程                 |
|   +-----------------|--------------->|   v                       |
|                     |                | 写 relay log              |
|                     |                |   v                       |
|                     |                | SQL 线程                  |
|                     |                |   v                       |
|                     |                | 回放事件, 更新数据        |
+---------------------+                +---------------------------+
```

1. 主库执行事务, 两阶段提交时写入 binlog.
2. 从库执行 `change replication source to ... ; start replica;` 后, I/O 线程与主库建立长连接; 主库为该连接创建 binlog dump 线程, 持续推送 binlog 事件.
3. 从库 I/O 线程把收到的 binlog 写入本地中继日志 (relay log).
4. 从库 SQL 线程读取 relay log, 回放事件更新数据, 并写自己的 binlog (`log_replica_updates`, 默认开启), 以支撑级联复制.

复制的作用是扩展读能力、数据热备、故障切换、把大查询分流到从库.

### 异步、半同步与组复制

| 模式            | 行为                                                                                                | 可靠性                                     | 代价                     |
| --------------- | --------------------------------------------------------------------------------------------------- | ------------------------------------------ | ------------------------ |
| 异步复制 (默认) | 主库提交后立即返回, 不等从库                                                                        | 主库宕机可能丢未同步的 binlog              | 性能最好                 |
| 半同步复制      | 主库提交时至少等 `rpl_semi_sync_source_wait_for_replica_count` (默认 1) 个从库写入 relay log 并 ACK | 降低丢数据概率, 但从库只是收到而非回放完成 | 增加提交延迟             |
| 组复制 (MGR)    | 基于多数派协议, 事务提交需组内多数节点认证通过, 支持自动故障切换                                    | 强一致                                     | 性能低于异步, 网络要求高 |

半同步由 `rpl_semi_sync_source_enabled` 开启, 超时 `rpl_semi_sync_source_timeout` (默认 10 秒) 后退化为异步. 等待点由 `rpl_semi_sync_source_wait_point` 控制, 默认 AFTER_SYNC 是在写 binlog 之后、引擎 commit 之前等 ACK; 另一种取值 AFTER_COMMIT 在引擎提交后等 ACK, 存在"主库已提交但 ACK 未达即宕机"的窗口. 组复制是 InnoDB Cluster 的基础, 有单主与多主模式.

### 主从延迟的原因与治理

延迟定义为从库回放完成时间减主库提交时间, 即 `show replica status` 中的 `Seconds_Behind_Source`. 常见原因: 从库回放能力不足而主库是多线程并发写; 从库机器规格差或承担大量读查询挤占资源; 大事务 (如一次删除百万行或大表 DDL) 在从库至少要回放同样长的时间; 主库写入洪峰与网络延迟.

治理方式:

1. 并行复制: 主库在 binlog 中标记事务间的依赖关系 (基于 writeset 判断哪些事务修改了相同的行), 从库多个 worker 线程并行回放互不冲突的事务. 相关参数 `replica_parallel_workers` (默认 4), 配合 `replica_preserve_commit_order` 可保证从库的提交顺序与主库一致.
2. 拆大事务: 大删除改为分批 limit 循环, DDL 用 gh-ost 等工具.
3. 从库升配, 控制单个主库挂载的从库数量, 分散读流量.
4. 业务侧容忍或规避, 例如写后读主.

### 读写分离下读到最新数据

"写后立即读"打到有延迟的从库会读到旧数据, 方案按成本从低到高:

1. 强制走主库: 对一致性敏感的读 (如下单后查订单) 路由到主库, 其余走从库. 最常用也最可靠, 代价是主库读压力.
2. 会话内写后读主: 同一用户会话在写操作后一段时间内读主库.
3. 半同步复制: 降低但不能消除读到旧数据的概率.
4. 等待 GTID: 写请求返回主库 GTID, 读请求在从库执行 `wait_for_executed_gtid_set(gtid, timeout)`, 等从库回放到该事务再读, 超时则退回主库. 精确但实现复杂.
5. 缓存兜底: 写完同步写 Redis, 读先查缓存.

GTID 是形如 `server_uuid:transaction_id` 的全局事务标识, 随事务写入 binlog. 相比传统位点复制, GTID 复制的优势是: 从库自动声明已执行的 GTID 集合, 新主库自动发送缺失事务, 主从切换无需人工找 binlog 文件名与偏移量; 已执行过的 GTID 会被跳过, 天然幂等; 还便于校验一致性与变更级联拓扑. 当前版本 GTID 默认开启 (`gtid_mode` 与 `enforce_gtid_consistency` 均为 ON), 搭建复制时只需再声明 `source_auto_position = 1` 启用自动定位.

## 七、分库分表与在线 DDL

### 何时需要分库分表

触发信号 (经验值, 非绝对): 单表行数上亿或 B+ 树层高变为四层导致查询变慢; 单库 QPS/TPS 触及实例瓶颈 (连接数、CPU、磁盘 IOPS); 单库容量过大导致备份恢复与 DDL 时间不可接受.

应先穷尽低成本手段: 索引与 SQL 优化、读写分离、缓存、归档历史数据、分区表, 最后才考虑分库分表, 因为复杂度会陡增.

垂直拆分按业务或列拆: 垂直分库把不同业务域的表拆到不同库; 垂直分表把宽表按访问频率拆成主表与详情表, 减小单行大小, 提高单页行数与 Buffer Pool 命中率. 水平拆分按行拆: 水平分表在同一库内拆成多张结构相同的表, 解决单表过大但不解决单库瓶颈; 水平分库分表把数据按分片键分布到多个库的多张表, 同时解决存储与并发瓶颈.

### 分片键与分片算法

分片键选择三原则:

1. 查询维度覆盖: 绝大多数查询都携带该键, 例如订单表用 user_id, 保证"查某用户订单"能单分片命中. 带不了分片键的查询会广播全分片.
2. 分布均匀: 避免数据倾斜与热点, 例如以商家 id 分片时大商家会把单分片打爆.
3. 不可变: 分片键更新意味着跨分片迁移数据.

多维度查询冲突的解法有基因法 (在 id 末几位嵌入 user_id 的哈希基因, 两个维度都能路由)、异构索引表 (按另一维度冗余一份映射)、把复杂查询同步到搜索引擎.

常见分片算法:

| 算法     | 优点                             | 缺点                                                  |
| -------- | -------------------------------- | ----------------------------------------------------- |
| 哈希取模 | 分布均匀                         | 扩容时 N 变化导致全量重排, 需一致性哈希或成倍扩容缓解 |
| 范围分片 | 支持范围查询, 扩容只加新分片     | 写热点集中在最新分片                                  |
| 查表路由 | 分片关系存配置表, 灵活可调       | 多一次查询, 可缓存                                    |
| 组合     | 先按时间范围分库, 库内按哈希分表 | 路由规则复杂                                          |

中间件分为客户端 SDK (如 ShardingSphere-JDBC, 无代理开销) 与代理层 (如 ShardingSphere-Proxy, 对应用透明、跨语言).

### 分布式 ID

| 方案                 | 特点                                                                                             | 主要风险                                                    |
| -------------------- | ------------------------------------------------------------------------------------------------ | ----------------------------------------------------------- |
| 雪花算法 (Snowflake) | 64 位等于 1 位符号加 41 位毫秒时间戳加 10 位机器 id 加 12 位序列号; 本地生成无网络开销, 趋势递增 | 时钟回拨会产生重复 id, 需记录上次时间戳并在回拨时等待或报错 |
| 号段模式             | 中央数据库批量发放一段 id, 应用内存消费, 双 buffer 预取                                          | 依赖数据库可用性                                            |
| UUID                 | 全局唯一                                                                                         | 无序, 作为聚簇索引主键会频繁页分裂                          |
| Redis incr           | 简单                                                                                             | 依赖 Redis 可用性与持久化                                   |

### 跨分片问题与分布式事务

1. 跨分片查询: 不带分片键的查询需广播所有分片再归并, 排序、聚合、分页在中间件内存中合并. 跨分片深分页代价极高, 因为每个分片都要返回前 N 行. 解法是强制业务带分片键、使用异构索引、把复杂查询交给搜索引擎、使用游标分页.
2. 跨分片 join: 尽量避免. 解法包括字段冗余、广播表 (小字典表每分片全量一份)、绑定表 (订单与明细用同一分片键使 join 不跨片)、应用层两次查询内存组装.
3. 分布式事务: 本地事务失效. 强一致可用 XA/2PC, 但性能差且阻塞长; 主流是最终一致, 包括本地消息表、事务消息、TCC、Saga、Seata AT 等.
4. 全局唯一 ID: 见上一节.
5. 运维复杂度上升: 扩容迁移、多分片 DDL、监控与备份成本翻倍.

### 在线 DDL

直接 `alter table` 的风险是 MDL 写锁排队引发雪崩、拷贝表期间磁盘翻倍、主从延迟巨大. 可用的方案:

1. MySQL 原生 Online DDL (`algorithm=inplace, lock=none`): 多数加索引、加列操作不锁 DML, 但仍在主库本机执行, 大表耗时长、无法暂停, 从库回放该 DDL 时单线程容易造成延迟. `algorithm=instant` 对加列等操作只改元数据, 秒级完成, 应优先使用.
2. pt-online-schema-change: 建影子表, 用触发器同步增量, 分批拷贝存量, 最后 rename 切换. 触发器有性能开销, 且与业务写在同一事务中.
3. gh-ost: 建影子表, 订阅 binlog 获取增量 (无触发器), 分批拷贝, 原子 rename 切换. 支持限流、暂停与动态调速, 对业务影响最小.

通用纪律是低峰期执行、提前 kill 长事务、设置较小的 `lock_wait_timeout` 防止 MDL 排队雪崩、确保磁盘余量大于表大小.

### 平滑迁移与扩容

不停机的双写迁移方案:

1. 存量同步: 用迁移工具 (Canal 订阅 binlog 或 DataX) 把旧库存量数据同步到新分片集群.
2. 增量双写: 应用升级为同时写旧库与新库, 以旧库为准, 新库写失败记入补偿; 或继续用 binlog 订阅追增量.
3. 数据校验: 全量比对加抽样校验, 修复不一致.
4. 灰度切读: 读流量按比例从旧库切到新库并观察.
5. 切写: 读全量切到新库且稳定后, 写切到新库, 旧库保留只读观察一段时间再下线.
6. 全程准备回滚预案: 建立反向同步链路, 保证可以随时切回.

扩容技巧: 分片数按 2 的幂设计, 成倍扩容时每个旧分片的数据只会迁移到一个固定新分片 (`hash % 2N` 的结果要么不变要么加 N), 迁移量减半且可并行; 范围分片则直接追加新分片, 零迁移.

## 八、读写分离与缓存一致性

### 一致性目标应该定成什么

Redis 里存的是 MySQL 热数据的副本, 结构与主从复制同构: 事实源先写, 副本后收敛. 只要存在两份拷贝就必然有滞后窗口, 不放弃副本就做不到"任意时刻强一致".

想要强一致, 只能把两者纳入同一个分布式事务 (2PC/XA), 但这条路基本走不通: Redis 没有实现 XA 协议, 它的事务运行时错误也不回滚, 无法承担 2PC 参与者的语义; 即便可行, 每次写的提交延迟也会被较慢的一方拉齐, 缓存失去低延迟的意义.

因此工程共识是放弃强一致, 追求最终一致: 接受有界窗口内的短暂不一致, 用 TTL 兜底、失败重试、对账巡检保证收敛. 方案设计的核心只有三件事: 不一致窗口如何尽量短; 窗口卡住时如何补偿; 不一致如何被看见.

### 缓存写策略的四种组合

设某行数据在数据库中的当前值为 v0.

| 组合                                 | 过程                 | 问题                                                                   |
| ------------------------------------ | -------------------- | ---------------------------------------------------------------------- |
| 先删缓存再更新数据库                 | 删除缓存, 更新数据库 | 删缓存后、更新完成前, 并发读未命中会读到旧值 v0 并回填, 造成持续不一致 |
| 先更新数据库再删除缓存 (Cache Aside) | 更新数据库, 删除缓存 | 理论上仍有一致性窗口, 但成立条件苛刻, 概率极低                         |
| 先更新缓存再更新数据库               | 更新缓存, 更新数据库 | 更新数据库失败时缓存里是数据库从未有过的新值, 且无回滚手段             |
| 先更新数据库再更新缓存               | 更新数据库, 更新缓存 | 两个并发写回填乱序, 慢的写会覆盖缓存                                   |

组合四的乱序是结构性的: 数据库侧两次更新有行锁串行化, 顺序确定; 但两次更新缓存之间没有互斥, 先后无法保证.

Cache Aside 胜出的原因是: 删除操作幂等、无顺序要求, 不一致窗口最窄, 且不做无用功. 它理论上也有不一致窗口, 需要读线程在写线程更新数据库之前缓存未命中并读到旧值, 然后写线程完成更新与删缓存, 最后读线程才把旧值回填. 这要求"读数据库加写缓存"比"更新数据库加删缓存"还慢, 而写内存比写磁盘快一个量级以上, 时序窗口极窄.

### 为什么删除而不是更新缓存

1. 惰性计算: 缓存值常是多表聚合的计算结果, 写后可能根本没人再读, 立即重算纯属浪费.
2. 复杂度与正确性: 更新缓存必须知道如何重新计算这个值, 逻辑与业务深度耦合, 多处维护容易出错; 删除只需清掉副本, 下次读自然重算.
3. 并发安全: DEL 幂等且无顺序要求; 更新不幂等, 并发下有上面提到的乱序问题.
4. 与缓存定位一致: 缓存层是 LRU 管理的易失副本, 不应承担数据所有权.

### 延迟双删

延迟双删用于补救"先删缓存再更新数据库"的竞态: 删除缓存, 更新数据库, 延迟一段时间后再次删除缓存, 清掉更新窗口内并发读回填的旧值.

要点:

- 第二次删除是核心, 它精确清掉第 2 步窗口内被回填的脏值.
- 延迟 N 必须大于"读一次数据库加写一次缓存"的耗时; 若读流量走从库还要叠加主从复制延迟. 经验值 500 毫秒到 1 秒, 严谨做法是监控回填耗时的 P99 加从库延迟实测.
- 实现上绝不能用业务线程 sleep, 否则会占用连接池与线程、放大写接口响应时间, 进程重启还会丢失第二次删除. 正确做法是用 MQ 延迟消息, 或用本地延迟队列加持久化补偿表由后台线程扫描执行.

代价是延迟窗口内读仍命中旧缓存, 写链路变长, 排障复杂度上升. 它是并发读写激烈、脏值窗口敏感场景的增强手段, 不是 Cache Aside 的必配项.

### 删除缓存失败的重试分层

"更新数据库成功、删除缓存失败"是 Cache Aside 下长期不一致的最常见来源, 例如网络抖动、Redis 主从切换、连接池耗尽. 重试分三层:

1. 同步重试: 失败后立即重试一到三次, 带短超时, 消化瞬时抖动; 不可无限重试, 否则拖垮写接口响应时间.
2. 消息队列异步重试: 同步重试用尽后发送删除消息, 消费者重试到成功为止. 需保证 MQ 自身可靠, 即生产者确认加消费者手动提交 offset.
3. 顺序与幂等: 同一 key 的删除消息应哈希进同一分区并串行消费, 否则两次删除与中间的回填可能乱序; DEL 天然幂等, 重试任意次都安全.

### 用 binlog 订阅兜底缓存失效

应用层删除有三个盲区: 代码漏写删除、其他服务或脚本绕过应用直连数据库、重试消息丢失. binlog 订阅兜底的正是"数据库层实际发生的一切写入".

Canal 的原理是把自己伪装成 MySQL 从库, 向主库发送 dump 请求 (协议与主从复制的 I/O 线程相同), 接收并解析 binlog 事件为结构化变更, 再按主键发消息到 MQ, 由缓存失效服务执行删除. 它依赖 row 格式 binlog 才能拿到行级前后镜像.

工程要点: 按"库.表.主键"哈希选择 MQ 分区, 同分区单线程串行消费, 保证同一行的删除顺序与数据库提交顺序一致; 若消费动作是回填缓存而非删除, 消息必须携带数据库的 `update_time` 或版本号, 写入前与缓存当前版本比较, 旧则丢弃; 表结构变更影响缓存序列化结构时消费端要能跳过或重建; 链路自身必须被监控, 包括 Canal 断连或位点跳变、MQ 积压、消费失败率, 因为这条链路静默失效时缓存会悄悄不再更新; 时延通常为百毫秒到秒级, 比应用层直接删除长, 换来的是完整性与业务零侵入.

| 维度   | 应用层主动删除       | binlog 订阅                 |
| ------ | -------------------- | --------------------------- |
| 侵入性 | 每个写路径都要写     | 对业务代码透明              |
| 覆盖   | 仅应用写入           | 一切写入, 含脚本、直连、DBA |
| 顺序   | 靠应用代码保证, 易错 | 同主键单分区串行, 天然有序  |
| 时延   | 短                   | 较长                        |
| 成本   | 无额外组件           | 需部署维护 Canal 与 MQ      |
| 定位   | 主路径               | 兜底, 可与主路径共存        |

实践中两者常组合: 应用层做第一时间的删除, binlog 订阅兜底漏删与多路写入.

### 多级缓存与热点 key 重建

多级缓存 (进程内 L1 加 Redis L2) 的一致性难点: L1 是各进程私有的副本, 删除 Redis 对它无效, 需要失效广播, 例如删除 Redis 后经发布订阅发布失效事件, 各实例订阅并清理本地 L1; 或者给 L1 设极短 TTL 让其自然收敛. 回填方向同样有竞态: L1 过期后回源可能读到尚未删除的旧 L2 值, 不一致窗口是两级叠加.

热点 key 重建时, 重建必须串行, 用 singleflight 或互斥锁保证并发读只触发一次回源. 还有一个隐蔽的时序竞态: 写请求 A 删除缓存后, 读请求 B 未命中开始重建, 但 A 的数据库更新此时尚未提交, B 用旧值重建了缓存, A 随后提交, 缓存长期持有旧值. 解法有三种: 重建与同 key 写入串行化 (代价高, 仅用于极热 key); 重建时把数据库行的 `update_time` 一并写入缓存, 删除或重建消息携带版本号, 写前比较旧则丢弃; 重建改由 binlog 事件驱动, 把触发源从"读"变为"事件", 避开读写时序竞态.

该竞态本质是缓存版的"读未提交": 重建读到了正在被修改的值. MySQL 用 MVCC 与锁解决, 缓存层只能靠版本号或串行化.

### 读写分离对缓存一致性的影响

读流量走从库时, 缓存未命中的回源读的是从库: 从库可能尚未回放最新提交, 回填就把旧数据写进缓存, 不一致窗口从毫秒级扩大为主从延迟加 TTL. 危险组合是"先删缓存再更新数据库"加读从库, 此时延迟双删的延迟必须覆盖主从延迟, 否则两次删除都白做.

对策按成本从低到高: 缓存未命中回源一律走主库, 读写分离只承担缓存命中的读, 这是最简单可靠的默认推荐; 写后短时间内把同 key 或同用户的读路由到主库; 从库回填时携带数据库的 `update_time`, 消费删除或重建消息时比较版本; 回填前用 `wait_for_executed_gtid_set` 等从库回放到写请求的 GTID.

### 选型与兜底

| 场景                     | 方案                     | 说明                                    |
| ------------------------ | ------------------------ | --------------------------------------- |
| 读多写少, 容忍秒级不一致 | Cache Aside 加 TTL       | 行业默认, 覆盖绝大多数场景              |
| 并发读写激烈, 怕脏值窗口 | Cache Aside 加延迟双删   | 收窄窗口                                |
| 写入路径多, 代码难保删除 | 叠加 binlog 订阅兜底     | 中大型系统常见                          |
| 强一致要求 (资金/库存)   | 不用缓存, 或在读路径加锁 | 接受性能代价                            |
| 写多读少                 | 不缓存, 或用写回聚合写库 | 见 [Redis 技术手册](redis) 的写策略部分 |

任何方案都必须有的三道兜底:

1. TTL: 所有缓存 key 都必须设过期时间, 它是不一致窗口的上界与最终自愈手段. 没有 TTL 的设计, 一次删除失败就是永久脏数据.
2. 对账: 定时任务按主键比对 MySQL 与 Redis 的抽样或全量 (比较 `update_time` 或行校验和), 输出不一致报告并自动修复. binlog 链路上线后, 对账是验证链路真实有效的唯一手段.
3. 监控告警: 缓存删除失败率、重试队列积压、binlog 链路延迟、缓存命中率、对账不一致率. 不一致必须先可见, 才谈得上可控.

一句话总结: 缓存与数据库之间没有强一致, 只有更短的窗口、收敛的兜底与可观测的验证.

## 九、慢查询与调优方法论

### 慢查询日志的配置

慢查询日志是定位慢 SQL 的第一手数据来源:

```sql
set global slow_query_log = on;              -- 开启
set global long_query_time = 1;              -- 阈值, 单位秒, 默认 10
set global log_queries_not_using_indexes = on; -- 未走索引的语句也记录
show variables like 'slow_query_log_file';   -- 日志文件路径
```

`long_query_time` 默认 10 秒对多数业务偏大, 生产常调到 1 秒甚至更低; `min_examined_row_limit` 可过滤扫描行数过少的语句. 日志用 pt-query-digest 按指纹聚合, 关注每条 SQL 的总耗时、平均耗时、扫描行数与返回行数之比 (扫描/返回比越高越有优化空间).

### 一条 SQL 突然变慢的排查思路

第一步确认现场, 观察是否有大量线程堆积以及它们处于什么状态: `Waiting for table metadata lock` 指向 MDL 阻塞, 需找长事务 kill; `Waiting for lock` 与锁等待超时指向行锁冲突.

第二步定位慢 SQL: 打开慢查询日志并用 pt-query-digest 聚合分析, 或查询 `performance_schema.events_statements_summary_by_digest` 按 SQL 指纹看平均耗时与扫描行数.

第三步分析单条 SQL: 用 `explain` 看 type 是否退化为 `index` 或 `ALL`、key 是否为 null、rows 是否暴涨、Extra 是否出现 filesort 或 temporary; 对照索引失效的典型情形逐一排查; 若怀疑统计信息过期导致优化器选错索引, 可执行 `analyze table` 或在确认后 `force index`; 用 `explain analyze` 看真实执行耗时分布.

第四步分层归因: 数据层面看表是否突然变大、数据是否倾斜、是否深分页; 实例层面看 Buffer Pool 命中率、redo log 是否写满触发强制刷脏、脏页比例是否过高; 系统层面看磁盘 IO util、CPU、内存换页、备份任务或大查询挤占; 复制层面看是否读到了延迟从库.

第五步修复: 加改索引、改写 SQL (覆盖索引、延迟关联、拆大事务)、参数调优、缓存或分表等架构手段.

```sql
show processlist;
select * from information_schema.innodb_trx;
show engine innodb status;

select sql_text, timer_wait, rows_examined, rows_sent
from performance_schema.events_statements_history_long
order by event_id desc limit 20;

select * from performance_schema.data_locks;
select * from performance_schema.data_lock_waits;

explain select ...;
explain analyze select ...;
```

常用外部工具: pt-query-digest 聚合慢日志, pt-online-schema-change 与 gh-ost 做在线 DDL, sysbench 压测, Prometheus 加 mysqld_exporter 监控 QPS、连接数、Buffer Pool 命中率与主从延迟.

`show global status like 'Com_%'` 可用于读多写多的画像 (Com_select、Com_insert 等), 索引提示 `use index`、`force index`、`ignore index` 可用于干预优化器的选择.

### 单表容量的实际阈值

"2000 万行"不是硬性上限, 它来自 B+ 树层高估算: 行大小约 1KB、bigint 主键时三层可容纳约 2000 万行, 超过则层高变为四层, 每次查询多一次磁盘 I/O.

实际阈值取决于: 行大小 (窄表单页行数更多, 三层能容纳远超 2000 万行; 宽表几百万行就可能变慢); 主键大小 (决定非叶节点扇出) 与内存大小 (Buffer Pool 装得下热数据时层高的影响被抹平); 访问模式 (只按主键点查的表上亿行依然快, 大量范围扫描加回表的表更早遇到瓶颈).

治理顺序是 SQL 与索引优化、冷热分离与历史归档、读写分离、分区表、最后才是分库分表.

### SQL 注入的防御

注入的原理是拼接字符串使输入改变 SQL 语义, 例如把条件拼接为永真式即可绕过条件返回全表, 或用 union 拖出库名与用户信息.

防御按优先级:

1. 预编译或参数化查询是根本手段: SQL 结构先编译固定, 参数只作为数据传入, 无法改变语义. ORM 与主流驱动的占位符即是此机制.
2. 最小权限原则: 应用账号只授予必要的库表 DML 权限, 禁止 drop、file 等权限.
3. 输入校验与白名单, 尤其是 order by 列名、表名这类无法参数化的位置, 必须白名单枚举.
4. WAF、SQL 审计, 并且错误信息不回显数据库细节.

## 小结与适用场景

- 单机 OLTP 且数据量在千万级以内, 优先把 InnoDB 的索引、事务与日志机制用透, 大多数性能问题能在 SQL 与索引层面解决.
- 需要横向扩展读能力时用主从复制加读写分离, 但必须为一致性敏感的读准备回源主库或等待 GTID 的通道, 半同步只能降低而不能消除不一致概率.
- 需要自动故障切换且能接受更高写入延迟时用组复制, 它为强一致与集群化提供了基础, 但对网络质量与运维能力要求更高.
- 单库容量或并发触及瓶颈时, 先做归档、冷热分离与分区, 再考虑分库分表; 一旦分片, 就要一并解决分布式 ID、跨分片查询、分布式事务与平滑迁移.
- 引入 Redis 作为缓存副本时, 默认接受最终一致, 用 Cache Aside 加 TTL 作为主路径, 用 binlog 订阅兜底, 用对账与监控让不一致可见; 资金、库存等强一致场景不要用缓存糊弄.
- 大表结构变更使用 gh-ost 等在线工具, 并在变更前清理长事务、设置较短的锁等待超时, 避免 MDL 排队雪崩.
