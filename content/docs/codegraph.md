本文讲解 CodeGraph 的设计与实现: 它如何把代码库的符号、调用边、依赖关系预计算成一张可查询的知识图谱, 再通过 MCP (Model Context Protocol) 工具面喂给编码 Agent。读完之后, 你应该能判断它在什么场景下能显著压缩 Agent 的探索成本, 以及它在静态分析的哪些边界上必须诚实退让。适合正在搭建内部 Agent 基础设施、评估代码检索方案, 或想理解"确定性预计算 + 按需查询"这一路线的工程师阅读。

## 一、要解决的核心问题

任何用过 [Claude Code](./claude-code)、Cursor Agent 模式或 [Codex](./codex) 的人都见过这一幕: 你问"用户认证流程是怎么走的", Agent 立刻派出探索子任务, 开始执行 ls、grep、逐段读文件的循环, 几十次工具调用之后才真正开始处理你的请求。

CodeGraph 的核心判断是: 这种探索本质上把静态结构信息交给大模型的工作记忆反复重算。文件之间的调用、导入、继承关系是确定性的、AST 可推导的, 没有理由每次会话都让模型用 grep 重新发现。提前算一次、放在本地数据库里、通过协议直接喂给 Agent, 就够了。

| 对比维度     | grep 加逐文件读取          | CodeGraph                  |
| ------------ | -------------------------- | -------------------------- |
| 结构信息来源 | 每次会话由模型重新发现     | 索引期一次性从 AST 抽取    |
| 跨文件调用边 | 靠字面匹配, 易漏易误       | 显式解析为图上的边         |
| 动态分发跳转 | 基本无法跨越               | 启发式合成边桥接           |
| 结果确定性   | 依赖模型行为, 不可复现     | 同一次索引永远得到同一张图 |
| 单次查询成本 | 与仓库规模、问题难度正相关 | 亚毫秒级本地数据库查询     |
| 索引成本     | 零                         | 一次性, 随变更增量更新     |

它不做的工作同样明确: 不调用大模型做语义增强, 不引入向量检索与嵌入, 不依赖外部服务, 索引只落在开发机本地。

## 二、总体架构

### 2.1 分层管线

系统是一条严格单向的管线, 每一层只依赖上一层的产物:

```text
代码文件
  │  文件扫描 (尊重 .gitignore 与项目配置)
  ▼
抽取层 (tree-sitter: wasm 基线 + Rust 原生内核)
  │  产出 nodes / edges / unresolved_refs
  ▼
存储层 (SQLite: nodes, edges, files, unresolved_refs, FTS5)
  │  引用解析 (imports → 文件, calls → 定义, inheritance → 类型)
  ▼
引用解析层 (名字匹配 + 动态分发合成 + 框架路由)
  │  把 pending 引用落成确定的边
  ▼
图查询层 (BFS/DFS 遍历, callers/callees, 影响面, 类型层级, 死代码)
  │
  ▼
上下文组装层 (混合检索 + 图扩展 + markdown/JSON 渲染)
  │
  ▼
MCP 工具面 / CLI / 库 API / 浏览器查看器
```

关键点是抽取与解析分离: 抽取是纯语法工作, 可以并行、可以缓存、可以逐文件回退; 解析是跨文件工作, 需要等全量文件入图后再统一处理。这种切分让"改一个文件"的增量成本只落在抽取与受影响的解析子集上。

### 2.2 模块职责

| 模块       | 职责                                                                                                                                             |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 抽取层     | 文件扫描、语言识别、语法解析、节点与未解析引用的产出; 含 wasm 抽取器、语言配置表、原生内核路由与解码、解析 worker 流水线、单文件组件与模板抽取器 |
| 引用解析层 | import 解析、名字匹配、动态分发合成器、跨层合成器、框架路由解析器                                                                                |
| 数据库层   | node:sqlite 薄适配、schema、迁移、预编译查询、WAL 检查点阀门                                                                                     |
| 同步层     | 原生文件监听、增量同步策略、git 钩子兜底、git worktree 错位检测                                                                                  |
| MCP 层     | 工具定义与执行、Direct/Proxy/Daemon 三种运行模式、查询 worker 池、会话状态与去重、索引新鲜度检查                                                 |
| 图查询层   | BFS/DFS 遍历、callers/callees/影响面、类型层级、死代码、动态边界报告、命名符号流查找                                                             |
| 上下文层   | 混合检索、图扩展、markdown/JSON 格式化                                                                                                           |
| 检索层     | 查询语法解析与字段过滤、停用词、词干、驼峰拆词                                                                                                   |
| 安装层     | 多个 Agent 产品的检测与 MCP 配置写入                                                                                                             |
| 查看器     | 终端进度 UI 与本地只读 Web 图谱查看器                                                                                                            |

### 2.3 一次查询的生命周期

```text
Agent 调用 codegraph_explore("AuthService login session")
  → 会话层解析 projectPath, 定位最近的 .codegraph 索引
  → 查询池分配 worker (daemon 模式下)
  → 检索: 符号名精确匹配 + FTS5 全文 + 词干/驼峰扩展
  → 排序: 按符号种类、图内佐证度与生成/测试文件惩罚加权
  → 图扩展: 沿 calls / references / navigates 等边补充关联符号与调用路径
  → 预算分配: 按仓库规模分档, 逐个文件分配字符额度
  → 会话去重 (可选): 已在本次会话中返回过的行范围折叠为回指
  → 渲染: 逐字源码 + 调用路径 + 影响半径, 按文件分组
```

查询面追求的是"一次调用就是 Read 的等价物": 返回的源码与 Read 工具逐字一致 (同样的 `<n>\t<line>` 行号前缀, 可直接用于编辑), 同时附带谁调用它、改动会影响谁。

## 三、抽取与解析管线

### 3.1 为什么选 tree-sitter

tree-sitter 是增量解析器生成器, 把源代码变成语法树。三个特点让它适合面向 Agent 的探索工具:

- 增量解析: 改一行只重算受影响的子树;
- 容错: 语法错误照样解析, Agent 写到一半的代码也能工作;
- 纯语法不懂语义: 知道 `add(a, b)` 是调用, 但不知道 `add` 定义在哪, 不做类型推断、不做跨文件引用解析。

与之相对的是 LSP (Language Server Protocol) 路线: 语言服务器真正懂类型系统、导入解析、泛型实例化, 能回答精确的语义问题, 但通常要求项目能编译、每种语言一个独立进程、大项目首次加载成本高。

CodeGraph 选择 tree-sitter 是明确的工程权衡: 抽取层放弃类型级精度——表达式 `obj.foo()` 里 `obj` 到底是哪个类的实例, tree-sitter 答不上来。这份精度没有被白白丢弃, 而是下推到解析层: 对静态类型语言, 名字匹配器借助声明类型、返回类型与别名链把接收者类型大量找回来 (见 4.2); 真正留下的边界是没有声明的表达式类型推断。换来的是不要求项目可编译、一份二进制覆盖所有平台、增量解析快到毫秒级响应。对面向 Agent 的探索性查询, 这个折中是合理的; 对安全级污点分析, 这个折中不够, 那是数据流 facts + Datalog 查询那条路线的领地。

### 3.2 双引擎: wasm 基线与 Rust 原生内核

在 tree-sitter 之上叠加了一层 Rust 原生内核 (codegraph-kernel crate)。wasm 路径的成本下限是逐节点的 JS 与 WASM 边界编组开销——遍历 AST 时每个节点的类型、字段名、文本都要跨一次边界, 把整个解析与遍历搬到原生侧是唯一剩余的杠杆。

内核的设计一句话概括: 每个文件只跨一次 JS 边界。整个解析与遍历在 Rust 内完成, 返回五块扁平的类型化缓冲区:

| 缓冲区 | 内容                                                                      |
| ------ | ------------------------------------------------------------------------- |
| meta   | 版本字节、各表计数、字符串池长度、错误 JSON 偏移、内核侧耗时 (f64)        |
| nodes  | 定宽 96 字节行, 小端编码                                                  |
| edges  | 定宽 44 字节行, 小端编码                                                  |
| refs   | 未解析引用, 定宽 40 字节行                                                |
| arena  | UTF-8 字符串池, 行内以 (偏移, 长度) 引用, 全 1 哨兵 (0xFFFFFFFF) 表示缺失 |

节点种类与边种类以数组下标跨边界, 因此 `NODE_KINDS`/`EDGE_KINDS` 两个枚举数组的顺序本身就是线协议的一部分: 只能追加, 不能重排; 加载时还会校验内核自带的种类表与 ABI 版本号 (`KERNEL_ABI_VERSION`), 不匹配就整个退化为 wasm 路径。字符串池让同一批符号名只存一份, 也让"逐节点对象在主线程物化"被彻底去掉——批量索引时缓冲区可以从解析 worker 直达存储 worker 解码 (延迟解码传输), 主线程全程不接触逐节点对象。

两种引擎的关系是永久共存、按语言路由:

```text
                     ┌───────────────────────────────┐
  文件 + 语言  ──▶   │ 语言在原生路由集且有内核可用?  │
                     └───────────────┬───────────────┘
                         是 ┆                  否 ┆
                            ▼                     ▼
                 ┌──────────────────┐   ┌──────────────────┐
                 │ Rust 内核        │   │ wasm 抽取器       │
                 │ parse + walk     │   │ tree-sitter-wasm │
                 │ 一次边界跨越      │   │ 逐节点编组        │
                 └────────┬─────────┘   └──────────────────┘
                          │ 内核返回或抛异常?
                          │ 语法树含 ERROR?
                          └──── 任一命中 ──▶ 该文件回退 wasm
```

回退到 wasm 的情形有五种: 语言不在原生路由集、当前平台没有预编译内核 (或加载失败)、ABI 版本或种类表不匹配、单文件解析树含 ERROR (错误恢复行为以 wasm 为规范基准, 因为两种引擎的错误恢复并不完全一致)、内核调用抛异常。回退是逐文件的而不是整批的: 单个语言或单个文件的解析差异不会扩散成整库污染。`CODEGRAPH_KERNEL=0` 是全局 kill switch, `CODEGRAPH_KERNEL_PATH` 用于指定二进制路径, `CODEGRAPH_KERNEL_DEBUG=1` 打印内核未加载的原因。

### 3.3 语言支持与三层抽取策略

支持的语言覆盖主流语言与长尾资产 (配置表含 ArkTS、COBOL、VB.NET、Erlang、Solidity、Twig、YAML 等 40 余种标识), 抽取按三条策略分流:

| 策略                 | 语言范围                                                                                                                                                     | 说明                                                   |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------ |
| 原生内核 (wasm 兜底) | TypeScript/TSX、JavaScript/JSX、Java、Python、Go、C、C++、Rust、C#、Ruby、PHP、Swift、Kotlin、R、Lua、Luau、Scala、Dart 共 20 种 (Metal 与 CUDA 走 C++ 语法) | 每种语言上线前要过字节级一致性门                       |
| 仅 wasm              | Objective-C、Solidity、Pascal/Delphi、COBOL、VB.NET、Erlang、Terraform、Nix、CFML、ArkTS 等长尾语言                                                          | 多为打过补丁或 vendored 的语法, 移植风险高, 留在 wasm  |
| 自定义抽取器         | Svelte/Vue/Astro 的脚本块、Liquid、Razor、MyBatis mapper、DFM/FMX 表单; YAML/Twig/XML/properties 走无语法路径                                                | 由外层抽取器解析模板结构, 再把内嵌代码委托给语言抽取器 |

语言配置表 (`EXTENSION_MAP` 加 `codegraph.json` 覆盖) 同时承担扩展名识别与解析器选择。对单文件组件与模板语言, 抽取器会先建一个组件节点, 把文件与组件用 contains 边连起来, 再把脚本块里的顶层调用记在组件名下——这样"这个页面做了什么"能落到组件节点上, 而不是散落在匿名作用域里。

### 3.4 一致性保障

性能优化最容易付出正确性代价, 这个项目用一套字节级门禁把风险压住:

- 逐语言双引擎对比测试: 仓库为每种内核语言维护一个 `kernel-<lang>-parity` 测试 (TypeScript/JavaScript、C/C++、Python、Java、Kotlin、PHP、Ruby、Rust、C#、Swift、Scala、Dart、Lua、R 等), 对同一批文件分别用内核与 wasm 抽取, 做全对象、顺序敏感的多重集 diff——顺序差异会改变数据库行号进而影响解析, 因此也必须一致;
- 语法表一致性测试 (`kernel-grammar-parity`): 断言原生语法与 vendored wasm 语法的节点种类表、字段表逐项相等, wasm 侧语法被重新对齐到与原生相同的版本;
- 节点 ID 一致性 (`kernel-node-id-parity`): 节点 ID 是文件路径加限定名的哈希, 两个引擎必须算出同一个 ID;
- 发布门禁: 发布工作流打包各平台 bundle 时要求对应平台的预编译内核产物存在, 缺失即失败。

## 四、图谱模型

### 4.1 节点与边类型

图谱的节点种类与边种类都是固定枚举 (`src/types.ts` 的 `NODE_KINDS`/`EDGE_KINDS`), 顺序即线协议:

```text
节点 (23 种)
file, module, class, struct, interface, trait, protocol, function, method,
property, field, variable, constant, enum, enum_member, type_alias,
namespace, parameter, import, export, route, component, union

边 (13 种)
contains     父节点包含子节点 (文件→类, 类→方法)
calls        函数/方法调用另一个
imports      文件从另一个文件导入
exports      文件导出符号
extends      类/接口继承
implements   类实现接口
references   通用引用
type_of      变量/参数的类型
returns      函数返回类型
instantiates 创建类实例
overrides    方法覆写父类方法
decorates    装饰器作用
navigates    导航到屏幕/路由 (如 Expo Router 的 router.push('/x'))
```

union 覆盖 C/C++、Objective-C、Rust 等语言的联合体声明, 作为一等节点入库。navigates 由前端路由解析器与链接合成器产生, 把"点击这里会去哪个页面"变成一跳查询。

### 4.2 引用解析的阶段与前置约束

抽取阶段把未能解析的引用写入 unresolved_refs 待解析队列, 解析器用 worker 池分批消费。批次顺序有一条明确的前置约束——接线 (wiring) 引用必须先于 calls 提交入库: 解析策略只读 implements/extends 两类边 (`RESOLUTION_READ_EDGE_KINDS`), 产出这两类边的批次必须先提交, 下一批才派发。即使被中断的同步让队列里两类引用交错排列, 这条约束也保证读到的是已落库的边。

解析分三步:

1. 先解析接线引用: imports 落到文件 (处理 TypeScript/JavaScript 的 tsconfig 路径别名、JVM 全限定名、C/C++ include 目录、PHP include、COBOL copybook、Nix 路径导入、Go 模块、cargo workspace、monorepo workspace 包), extends/implements 同时落为类型层级边;
2. 再解析 calls 落到定义: 名字匹配采用多策略 (限定名、精确名、文件路径、链式调用、回调值引用); 对同名定义数量过大的"泛在名"拒绝出边, 防止噪声;
3. 最后做第二遍 conformance pass: 第一遍无法解析的链式工厂调用 (目标方法声明在接收者所 conforms 的超类型上), 等继承边就位后重解, 成员引用沿超类型 BFS。

链式调用的第二遍覆盖 11 种语言: 点链/作用域链形态的 Java、Kotlin、C#、Swift、Rust、Go、Scala、Dart、Objective-C、Pascal/Delphi 共 10 种, 外加 PHP 的 `$this->prop->method()` 属性链形态; Rust 走 `::` 作用域链, 其余走点链; `new X().m()` 构造接收者形态同样参与重解。C/C++ 的链式调用不进这个延迟队列——它们的接收者类型推断 (下述) 在第一遍就直接解决; TypeScript/Luau 也不在其中, 渐进类型缺少可靠的声明返回类型可作重解依据。

名字匹配是体量最大的部分, 其精度方向高度一致: 让"名字猜测"退让给"类型事实"与"作用域事实"。各语言共享的底线包括: 经字段或参数声明类型的调用落到声明类型自己的方法; 经类名的调用到达继承来的类方法; 标准库与第三方库的调用留在库内; 裸名只解析到引用处可见的符号; 调用落到参数个数或标签匹配的重载 (覆盖 C/C++、Java、Kotlin、C#、Swift、Scala、Dart、VB.NET、Solidity 等重载语言, Swift 按参数标签, Erlang 按 `模块:函数/元数`, 元数缺失的动态 MFA 只在模块恰好有唯一元数时解析); 生产代码不连到测试套件里的同名符号; 被压缩产物里的同名函数不参与名字解析。

在此之上, C/C++ 叠了一层体量几乎与其余部分相当的接收者类型推断机制, 跨文件调用解析的边界也由此大幅外扩:

- 声明类型即事实: 经指针、引用或值声明的接收者, 其调用按 C++ 名字查找落到声明类型自身或继承来的方法; 别名被追到真实类型; 跨多行的声明、名字带限定符或注解的声明照常读出, 字符串字面量里的"声明"不参与; 限定名永远不会到达仅共享末段名字的类, `std`、`absl` 等库命名空间的小写名不会接到项目里的同名类;
- 推导类型: `auto` 局部变量的类型从初始化式读出, 结构化绑定按 `pair`/`tuple` 元素拆开, range-for 的循环变量拿到 range 的元素类型, 函数包装器同样换算成书写类型; 方法的归一化返回类型 (nodes 表的 `return_type` 列) 支撑 `Foo::instance().bar()` 这类链式接收者推断;
- 成员链: 经其他成员到达的成员上的调用 (`thread->rnd.Next()`、`options.statistics->getTickerCount(…)`) 沿每一跳成员的声明类型逐跳解析; `std::vector` 上的成员调用不会落到项目里的同名方法;
- 容器元素: `front()`/`back()`/`at()` 的返回值、下标读取 `statuses[i]`、解引用的迭代器 `(*it)->Visit()`、map 迭代器的 `it->second`、智能指针、optional 与 `absl::StatusOr` 经 `->` 或 `get()`/`value()` 取出的值, 都落到元素类型的方法; 元素或被持有类型在项目之外时不出边;
- 重载选择: 在调用处可见的重载里按参数个数与类型匹配择优; 仅差一个 `const` 的双胞胎重载按 C++ 的偏好选择; `nullptr` 实参落到 `std::nullptr_t` 重载; 被 `= delete` 的重载永不被选 (除非全体都被删除);
- 模板机制: 显式特化按其模板命名, 并由调用处书写的模板实参选中; 带显式模板实参的成员模板调用拿到模板返回的类型; 声明为类模板成员类型的接收者 (`SkipList<Key, Comparator>::Iterator`) 归位到该模板的成员;
- 宏世界: 函数式宏定义的方法 (`PROTOBUF_DEFINE_ACCESSOR` 一类) 在宏调用处索引成方法节点, 参与链式调用与重载选择; 反过来, 名字在调用处是可见宏的"调用"直接丢弃, 绝不连到其他文件的同名函数;
- C 的可见性: 调用优先落到本文件可见的函数 (含 include 头文件里的 `static` 拷贝), 越过其他文件的 `static` 副本; 只在某个无人定义的 `#ifdef` 之下才存在的定义, 让位给构建实际编译的定义——判定依据是 Makefile 的 `-DX`、CMake 的 `option(X …)`、configure 的 `AC_DEFINE(X)` 等构建文件与组件内源码的 `#define`;
- 测试支架: gtest `TEST_F`/`TEST_P` 体按 fixture 派生类的成员处理, 体里的裸调用因此到达 fixture 的方法与类型。

上述机制一律是三值结果: 解析出边、确定无边 (类型确定没有该方法、库外类型) 或未知 (模板参数类型、读不到的声明)——未知退回名字策略, 从不猜。错误边的代价永远高于缺失边。

### 4.3 动态分发桥接

静态解析穿不过事件分发、回调注册、渲染边界这类跳转, 这是 grep 永远做不到的部分。合成器用启发式规则把断点连起来, 全图合成通道 (`SYNTH_PASSES`) 按注册表顺序执行, 覆盖的模式包括:

| 模式类别   | 示例                                                                                                                                              |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| 事件总线   | 字符串键的 EventEmitter 订阅与发射按事件名对接、字段观察者通道、Spring/Laravel 事件、MediatR 分发、Erlang behaviour, 扇出有上限                   |
| 渲染链路   | React setState→render、JSX 子组件、Vue 模板事件绑定与子组件、Angular 模板、SvelteKit load 与页面组件、Flutter setState→build、ArkUI 状态→build    |
| 接口分发   | Java/Kotlin/C#/Swift/Scala/Go/Rust/ArkTS/JS 家族的接口到实现与覆写、gRPC stub 到实现、C++ 虚函数覆写                                              |
| 函数指针   | C/C++ 函数指针分发 (独立内核扫描 pass)、宏构造的命令表 (注册表风格)                                                                               |
| 跨语言桥   | Swift 与 Objective-C 的 selector 桥接、Kotlin 的 expect/actual、React Native 桥与 Fabric 原生实现、Expo Modules 双端                              |
| 状态存储   | Redux thunk、RTK Query、Pinia store、Vuex dispatch、Go 函数字段分发                                                                               |
| 任务与消息 | Celery/Sidekiq 任务到消费者、GoFrame 路由、MyBatis Java 与 XML 互连、HarmonyOS emitter 与页面路由                                                 |
| 跨层调用   | 客户端字面量 fetch/axios 路径接到本仓路由 (http)、队列任务接到消费者 (queue)、总线/套接字事件接到处理器 (event/socket), 每条边带 channel 与注册点 |

所有合成边一律标记 `provenance: 'heuristic'`, 并携带 `synthesizedBy` 通道名与 `registeredAt` 注册点元数据, Agent 可以分辨某条边是解析出来的还是猜出来的。这是让调用链能跨越动态分发边界的关键, 也是"部分覆盖比没有更糟"这一判断的来源——半截桥接会让 Agent 钻进文件补齐, 反而增加读取次数; 实测 excalidraw 仓库上只桥一半会把 Read 次数推高, 把整条流补全才归零。

与合成边配套的是查询期的动态边界报告: 当静态路径断开时, 检测并如实播报动态分发点 (计算成员调用、反射、字符串总线) 与候选运行时目标, 但不猜测合成边、不修改图。诚实报告断点比编造连接更有价值——完全连通的流不会走到这个模块, 静默优于错边。

### 4.4 框架感知路由

路由声明被抽成 route 节点并连向处理器, 因此 Agent 可以问"某个接口的实现在哪、影响哪些下游", 一次影响面查询直接出结果。框架解析器注册表覆盖:

- 前端与全栈: Next.js (pages/app 路由、`route.ts` 端点、`<Link href>` 导航)、React Router、TanStack Router、Vue Router/Nuxt、SvelteKit、Astro、Angular;
- 后端: Express、NestJS、Django、Flask、FastAPI、Rails、Spring、Play、ASP.NET、Laravel、Drupal、Go 标准库与 Gin/GoFrame、Rust 的 Axum/Actix;
- 移动与桌面: SwiftUI/UIKit/Vapor、Expo Router、React Native 桥接 (legacy bridge、TurboModules、Fabric 视图组件与 Expo Modules); Flutter 与 ArkUI 不做路由节点, 前者合成 setState→build 重渲染边, 后者合成状态→build、emitter 事件与页面路由边;
- 遗留与企业: CICS 事务跳转、Terraform、MyBatis。

前端路由做"路由 + 导航"双向解析: 页面文件成为绑定组件的路由节点, 字面量导航调用产生 navigates 边。计算型目标与无路由匹配的路径如实留空而不是猜测。框架检测按项目内容触发, 多 app 仓库内每个 app 的路由只与本 app 内的导航匹配。

### 4.5 边的来源与置信度

边的来源标记 (provenance) 是一个二分事实: 启发式合成边一律显式标记为 heuristic, 并携带合成通道名与注册点元数据; 解析得到的边不带标记。查询、覆盖率统计与 MCP 响应都以"是否 heuristic"为界, 它决定了 Agent 应当把某条边当作事实还是线索。反射、依赖注入容器、运行时动态分发、框架约定入口是无法可靠静态化的部分, 覆盖率口径对此诚实标注。

## 五、存储与检索

### 5.1 为什么是 SQLite 而不是图数据库

存储后端是 Node 内建的 `node:sqlite` (`DatabaseSync`, 要求 Node 22.5+; 随包发行自带运行时), 外面包了一层 better-sqlite3 形状的薄适配, 没有原生构建步骤, 也没有 wasm 回退。这个选择与"捆绑 Node 运行时"的决策互为因果: 捆绑 Node 意味着自带真正的 SQLite (含 WAL 与 FTS5), 因而零原生插件、无需编译或重构建, 也不存在外部驱动的锁竞争问题。

对"找调用链、找定义、找路由"这类问题, 关系表加全文索引加图遍历已经足够; 图数据库带来的部署复杂度与运维成本, 在本地单机场景下没有对应收益。

### 5.2 数据模型

| 表                 | 要点                                                                                                                             |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| nodes              | 主键 ID、种类、名称、限定名、文件路径、语言、起止行列、文档串、签名、可见性、导出/异步/静态/抽象标记、装饰器、类型参数、返回类型 |
| edges              | 源、目标、种类、元数据、行列、来源; 外键级联删除; 以 (源, 目标, 种类, 行, 列) 唯一索引去重 (NULL 坐标经 IFNULL 折叠)             |
| files              | 路径主键、内容哈希、语言、大小、修改时间、索引时间、节点数、错误、生成标记                                                       |
| unresolved_refs    | 待解析引用队列, 状态 pending/failed (failed 行留待下次同步重试), 候选列表, 失败名尾索引                                          |
| name_segment_vocab | 符号名拆词段到名字的查找表, 让自然语言提示词能对照图验证 (FTS 分词器把驼峰名保留为单个 token, 所以段表在节点写入路径上物化)      |
| project_metadata   | 键值对                                                                                                                           |
| nodes_fts          | FTS5 虚表, 外部内容表模式加同步触发器, 索引名字、限定名、文档串、签名                                                            |
| synthesis_inputs   | 记录内容曾触发合成的文件路径, 源文件被删除后同步仍能据此判定要重放合成                                                           |
| schema_versions    | 迁移簿记: 已应用的版本号、时间与描述                                                                                             |

files 表的生成标记在索引期由文件名约定或文件头部生成横幅判定, 用于排序降权与跳过压缩产物, 这与 sourcemap 的职责天然互补: sourcemap 负责"压缩产物到源码"的映射, 图谱负责"源码内部结构"。

### 5.3 连接与写入工程

连接配置围绕本地单写者场景做了调优: 忙等待超时、WAL 日志模式、同步级别、页缓存、临时表放内存、内存映射。

围绕 WAL 有一整套工程设施, 因为长时间批量索引会让 WAL 异常膨胀:

- 批量索引期间关闭自动检查点, 由后台阀门在 worker 线程定时做被动检查点;
- 索引期的软阈值取"固定值 (256 MB) 与索引大小四分之一中的较大者", 上限 2 GB, 超过时对写入施加背压; 静息时修剪到 64 MB; 两个环境变量可调: `CODEGRAPH_WAL_VALVE_MB` 与 `CODEGRAPH_WAL_HEAL_MB`, `CODEGRAPH_WAL_VALVE_DEBUG=1` 打印每次决策;
- 每次打开连接时修复被强杀进程遗留的超大 WAL;
- 批量写入窗口临时删除二级索引, 结束后一次性重建, 全文索引触发器同样先删后整体重建。

这套设施解决的是一个真实故障模式: 写入速度远快于检查点速度时, WAL 可以膨胀到数据库本体的十几倍 (实测见过 64 GiB), 磁盘与恢复时间都会失控。

### 5.4 确定性混合检索

检索路线是确定性的混合检索, 不含向量检索与嵌入。实现是精确符号查找加 FTS5 加词干扩展加图遍历:

- 查询语法支持字段过滤: `kind:`、`lang:`/`language:`、`path:`、`name:`, 带引号值;
- 词干变体由后缀剥离生成 (如 caching→cache、eviction→evict), 驼峰与下划线拆词后也参与匹配;
- 提示词侧的段匹配 (`name_segment_vocab`) 用英文停用词表过滤自然语言词;
- 拼写近似走有界编辑距离 (Damerau-Levenshtein 式 DP, 提前退出) 的模糊兜底。

对结构性问题 (找调用链、找定义、找路由) 精确匹配远优于相似度排序; 对模糊语义问题 ("哪里在处理用户限流") 该方案靠全文检索与词干尽力而为, 这是它相对嵌入路线的短板。检索结果的 `score` 只用于相对排序, 不做归一化: FTS 路径返回无界的 BM25 量级, 模糊/精确路径返回约 0-1。

### 5.5 影响面分析

图遍历提供两套基本算法 (广度优先与深度优先), 并针对深度受限的遍历做了一个细节处理: 记录每个节点被展开时的最浅深度 (`enterAtDepth`), 使一个节点先经长路径到达、后经短路径到达时能被重新展开, 从而不因边的顺序而丢掉它的下游。查询接口覆盖:

| 能力                           | 语义                                                   |
| ------------------------------ | ------------------------------------------------------ |
| callers / callees              | 一跳或多跳的调用方与被调方                             |
| impact radius                  | 沿入边反向追踪, 改动会影响到的节点子图                 |
| type hierarchy                 | 父类型与子类型链路及实现计数                           |
| usages                         | 所有引用该符号的入边来源                               |
| file dependencies / dependents | 文件级依赖与反向依赖, 走符号级跨文件边而不是导入声明边 |
| dead code                      | 无引用符号检测, 附每个候选"为何不被断言"的原因         |

文件级依赖必须走解析后的符号图, 而不是 imports 边: imports 边连接的是文件与它自己的局部导入声明 (同文件), 真正的跨文件依赖信号在已解析的 calls/references/instantiates/extends 等边上。这个细节直接决定了 `affected` 命令与影响面查询的正确性。

影响面分析的价值在于把"改这个安全吗"从主观判断变成可量化的数字: 波及符号数、是否触及对外路由、是否触发高扇出符号, 都可以作为自动化门控的输入。

### 5.6 上下文组装

上下文组装层 (`ContextBuilder`) 把检索与图扩展的结果渲染成面向模型的载荷: 先做混合检索得到入口符号, 再沿图扩展, 然后按预算抽取代码块、汇总相关文件、生成摘要与统计。它支持 markdown 与 JSON 两种格式 (`format: 'markdown' | 'json'`), 节点数、代码块数与单块字符数都有默认上限 (50/10/2000)。

一个值得借鉴的设计是低置信度诚实退让: 当查询只命中孤立的高频词、没有入口被两个以上不同查询词佐证时, 子图携带 `confidence: 'low'`, 输出里明确说明"这些入口可能不准确, 请用精确符号名重新查询", 同时给出最接近的目录。默认的"我已覆盖全部相关内容"式措辞一旦出错, 会把 Agent 送去读文件补齐; 诚实承认不确定性反而能把它引回精确工具。

## 六、MCP 查询面

### 6.1 工具集

对外定义八个工具, 全部声明只读与幂等注解 (`readOnlyHint`), 全部支持 `projectPath` 参数用于 monorepo 多项目查询:

| 工具                                  | 语义                                                                                                                                                          |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| codegraph_explore                     | 主工具: 接受自然语言问题或符号名集合, 一次返回相关符号按文件分组的逐字源码, 加调用路径与影响半径; 声明 `anthropic/alwaysLoad`, 避免宿主把它延迟到工具搜索之后 |
| codegraph_search                      | 按名字找符号, 只返回位置                                                                                                                                      |
| codegraph_callers / codegraph_callees | 调用方 / 被调方, 可用文件路径或后缀消歧同名符号                                                                                                               |
| codegraph_impact                      | 改动影响半径, 重构前使用, 深度默认 2                                                                                                                          |
| codegraph_node                        | 双模式: 单符号详情 (歧义名一次返回所有定义体, 可附源码与调用轨迹), 或传文件路径替代读取工具读整个文件 (带依赖它的文件列表, 2000 行上限与 Read 对齐)           |
| codegraph_files                       | 索引内文件树, 支持路径、glob 过滤与 tree/flat/grouped 格式                                                                                                    |
| codegraph_status                      | 索引健康度: 文件、节点、边数量与最近索引时间                                                                                                                  |

### 6.2 默认只暴露一个工具

默认配置下只向 Agent 暴露 explore 一个工具 (`src/mcp/tools.ts` 的 `DEFAULT_MCP_TOOLS`), 其余七个需要通过 `CODEGRAPH_MCP_TOOLS` 环境变量 (逗号分隔的短名白名单) 显式重新启用——白名单会整体替换默认面, 被裁剪的工具从 ListTools 里真正消失, 而不是调用时才被拒绝。另有一条小仓库门控: 索引文件数少于 500 时, 即便设置了白名单, 暴露面也会被收窄到 explore/search/node 三件套。这个决定背后有清晰的推理:

- 治理面积小: 一个工具的行为可预期, 提示注入面与误用面都最小;
- Agent 只会调用它本来就会调的工具: 与其新增需要精确输入才能给出精确输出的入口, 不如让已有的读取类工具在给定输入下做更多事;
- 工具数量膨胀会稀释选择: 少而强的工具比多而弱的工具更容易被稳定使用, 实测单工具面在大仓库上出现过灾难性回归。

### 6.3 explore 的输出预算

explore 的输出预算按仓库规模分档, 并且有一条单调性不变量: 更大档位的单文件字符上限不得小于更小档位——否则大仓库里一个超大文件只返回极小比例的内容, 反而逼 Agent 回去读文件。

| 索引文件数 | 总输出上限  | 默认文件数 | 单文件上限 | 建议调用次数 |
| ---------- | ----------- | ---------- | ---------- | ------------ |
| 少于 150   | 约 13K 字符 | 4          | 约 3.8K    | 1 次         |
| 少于 500   | 约 18K 字符 | 5          | 约 3.8K    | 1 次         |
| 少于 5000  | 约 24K 字符 | 8          | 约 6.5K    | 2 次         |
| 少于 15000 | 约 24K 字符 | 8          | 约 7K      | 3 次         |
| 少于 25000 | 约 24K 字符 | 8          | 约 7K      | 4 次         |
| 更大       | 约 24K 字符 | 8          | 约 7K      | 5 次         |

总输出被刻意压在宿主内联工具结果上限 (约 25K 字符) 之下: 超过上限, 宿主会把结果外置成文件, Agent 再读回来, 等于重新引入一次读取与缓存写入。因此大仓库的扩面靠更多次调用, 而不是靠更大的单次响应。调用次数建议只是建议, 服务端从不拒绝或限流额外的调用。

文件级预算分配是评分制的: 符号种类权重 (可调用符号与类型约 1.0, 成员约 0.5, 变量/常量约 0.3, 参数 0.15)、孤立符号降权 (无入边的弱种类符号按名字碰撞处理)、生成/测试/i18n 文件整体惩罚, 准入线随最高文件分数浮动。

explore 还支持可选的会话内去重 (`CODEGRAPH_EXPLORE_DEDUP=1`): 默认每次调用都重新返回源码 (包括新子 Agent 与上下文压缩之后), 开启后同一次会话里已经返回过、且内容指纹未变的行范围 (至少 8 行连续覆盖) 再命中时折叠为回指并提供行区间, 文件被编辑过则全量重发。

### 6.4 响应形态设计

最有价值的工程经验是关于错误形态的: 早期一两次真正的错误响应就会让 Agent 永久弃用整个工具集。因此错误响应被严格分类:

- `isError` 留给真正的故障 (附带重试一次的提示) 与安全拒绝 (敏感系统路径), 因为这里"放弃"正是期望的 Agent 反应;
- 一切预期内状态 (项目未索引、符号找不到、Windows 与 WSL 共享索引冲突、查询池繁忙超时) 返回成功形态的指引, 告诉 Agent 改用内置工具或如何请用户修环境。

辅助措施包括: 对歧义符号名一次返回所有重载的完整函数体, 杜绝 Agent 为了找到正确的重载去读文件; explore 输出永远不说"请改用读取工具", 而是引导再来一次 explore 并"把已返回源码当作已读"; 回答前对引用过的文件做内容哈希新鲜度校验 (预算内), 漂移的文件要么展示当前完整源码, 要么省略源码并明确标记, 绝不提供可能错位的切片。

### 6.5 运行模式

MCP 服务支持三种形态:

```text
Direct   一个 Agent 进程直接拉起 stdio 服务, 自带索引与监听
Proxy    轻量代理先探测同版本后台守护进程 (版本握手校验), 成功则做
         stdio↔socket 透明管道, 失败则回退进程内服务
Daemon   独立的分离式后台进程 (daemon.pid 锁仲裁), 多个 Agent 共用
         一个监听器、一个文件监听器与一份数据库连接, 最后一个客户端
         断开后按空闲超时 (默认 300s) 退出
```

守护进程模式解决的是"多个修复 worker 各建一份索引"的浪费: 它持有项目写者锁, 保证同一项目只有一个写入者, 读工具请求卸载到查询 worker 池。池的规模按真实核数推导 (`clamp(核数-1, 1, 16)`), 构造时先预热一个 worker, 按需增长; worker 崩溃会重生并重试一次在途任务, 累计崩溃预算 (12 次) 耗尽触发熔断, 调用方退化为进程内调度而不是让工具调用失败; 排队调用超过软超时 (默认 45 秒, 低于 MCP 客户端的硬超时) 返回"成功形态的重试指引", 而不是硬超时错误。

## 七、同步与增量

### 7.1 原生文件监听

同步层不使用第三方监听库, 直接用 Node 内建的 `fs.watch`: macOS 与 Windows 支持递归监听 (一条文件系统事件流或一个目录变更句柄, 描述符开销为常数); Linux 的递归监听不可用, 改为每个目录一个 inotify 监听 (开销是 O(目录数) 而非 O(文件数)), 有默认的目录上限, 资源耗尽 (ENOSPC) 时给出可行动的提示并降级, 建议用户提高 `fs.inotify.max_user_watches`。

`CODEGRAPH_NO_WATCH=1` 显式关闭监听, `CODEGRAPH_FORCE_WATCH=1` 显式开启 (覆盖自动检测); WSL2 下挂载的 Windows 盘 (`/mnt/单字母`) 上递归监听病态地慢, 会被自动关闭。

### 7.2 防抖策略

```text
文件变更事件
  │
  ├── 待处理文件数 ≤ 2  ──▶ 300ms 静默窗口 (单次保存近实时, 下限 100ms)
  │
  ├── 待处理文件数 > 2  ──▶ 默认静默窗口 (2s, CODEGRAPH_WATCH_DEBOUNCE_MS 可调)
  │
  └── 待处理文件数 > 500 ─▶ 放弃按事件同步, 改全量扫描对比
                            (分支切换、大规模检出)
```

目录结构变化与文件内容变化分开处理: 文件编辑从不触发全树遍历, 只有新建或重定向的目录才触发树刷新, 且刷新被合并到一个短的延迟窗口内。连续多次锁冲突或同步失败后, 监听器永久降级为关闭自动同步并回调通知宿主, 而不是静默提供过期结果。

### 7.3 兜底与特殊环境

自动同步被禁用的环境 (如 WSL 挂载的 Windows 盘) 可以安装 git 钩子作为兜底: 提交、合并、检出后在后台执行一次 `codegraph sync`。钩子片段用标记注释 (`# >>> codegraph sync hook >>>` / `# <<< codegraph sync hook <<<`) 包裹, 安装幂等, 卸载时只删除自己的片段并保留用户既有内容; 解析钩子路径时尊重 `core.hooksPath`。

git worktree 是另一个真实陷阱: 在 worktree 里运行但索引属于另一个工作树时, 结果反映的是别的分支的代码。同步层用 `git rev-parse --show-toplevel` 检测这种错位, 并在工具响应里给出一行提示, 建议在该工作树单独建索引。

### 7.4 索引新鲜度

索引漂移有三种可见信号, 每种都给出可行动的处置方式: 部分文件已变更但仍在等待同步时, 响应头部列出待重建索引的文件, 并说明这些文件的源码可能过时, 其余文件仍可信; 自动同步整体降级 (或恢复中) 时, 明确说明整个索引可能过期, 让 Agent 直接读文件确认; 对经项目路径查询、没有实时监听的项目, 漂移文件被单独标记为磁盘已变更, 且绝不从这类文件提供可能错位的切片。

## 八、工程化要点

### 8.1 打包与分发

核心决策是随包捆绑一份官方 Node 运行时。因为 Node 22.5+ 内置真正的 SQLite, 捆绑 Node 就意味着零原生插件、无需编译或重构建、不依赖用户机器上的 Node 版本。由于零原生插件, 打包就是纯文件拼装: 下载目标平台的官方 Node (校验官方 SHASUMS256), 拷贝编译产物与生产依赖, 归档。

| 维度         | 内容                                                                                              |
| ------------ | ------------------------------------------------------------------------------------------------- |
| 平台目标     | macOS (arm64/x64)、Linux (x64/arm64)、Windows (x64/arm64) 共 6 个; Unix 出 tar.gz, Windows 出 zip |
| 安装通道     | 安装脚本 (install.sh / install.ps1)、npm 包 (薄壳加按平台的可选依赖)、三条通道交付同一份捆绑产物  |
| 任意平台构建 | 纯文件拼装使任意操作系统都能构建任意目标, 无需交叉编译或原生构建机                                |
| Agent 接线   | 安装命令检测已装 Agent 并写入 MCP 配置, 不触发索引; 索引由项目内的 `codegraph init` 完成          |

安装脚本只负责装二进制; Agent 检测与 MCP 注册发生在 `codegraph install` 中。安装目标注册表覆盖 11 个产品: Claude Code、Cursor、Codex、opencode、Hermes、Gemini CLI、Antigravity、Kiro、GitHub Copilot 的 VS Code/CLI/JetBrains 三个形态; MCP 条目统一为 stdio 形式的同一条命令, Claude/Codex/Gemini/opencode 还会写入一段短的说明块到各自的指令文件。

### 8.2 供应链安全

对一个要装进开发者机器、接管 Agent 工具链的软件, 可验证的发布链路是企业安全评审的前提:

- npm 包通过可信发布 (基于 OIDC, 不存在可被窃取的长期令牌) 发布, 带来源证明, 可用官方命令验证;
- 发布包带签名的构建证明, 可用 `gh attestation verify` 验证构建来源;
- 所有产物由公开的发布工作流构建, 不由个人机器产出。

### 8.3 配置与权限模型

项目级配置集中在一个 JSON 文件 (`codegraph.json`) 里, 可提交进仓库供团队共享, 含一个自定义扩展名映射与四类 gitignore 风格的模式:

| 字段           | 作用                                                                       |
| -------------- | -------------------------------------------------------------------------- |
| extensions     | 自定义扩展名到语言 ID 的映射 (叠在内置表之上, 冲突时获胜)                  |
| exclude        | 强制排除路径, 即使文件已被 git 跟踪 (用于提交进仓库的第三方主题、SDK 目录) |
| include        | 强制纳入第一方源码, 即使被 gitignore 忽略 (内置默认忽略目录除外)           |
| includeIgnored | 显式允许索引被 gitignore 的内嵌仓库                                        |
| deprioritize   | 仍然索引但降低排序权重的外围目录                                           |

配置文件的所有解析失败模式都退化为"该条目不生效", 而不是抛错。

权限与安全边界体现在三处:

- 初始化时拒绝把文件系统根目录、用户主目录或其父目录作为索引根 (`--force` 可覆盖), 避免索引缓存与他人项目, 也避免监听器资源耗尽;
- 读取类工具对敏感系统路径做安全拒绝, 且这种拒绝不带重试指引, 因为"不碰这个路径"正是期望行为;
- 多项目查询时校验项目路径在允许范围内, `../` 探针无法越过项目根。

### 8.4 可观测性

遥测是完整的第一方设计, 逐字段文档化并强制白名单 (摄入端点源码随仓库公开):

| 事件         | 内容                                                                           |
| ------------ | ------------------------------------------------------------------------------ |
| install      | 配置了哪些 Agent、全局还是项目级、新装/升级/重跑                               |
| index        | 仅语言名列表、文件数的粗分桶 (小于 100 / 100-1k / 1k-10k / 10k+)、耗时的粗分桶 |
| usage_rollup | 本地按天聚合的工具调用计数, 含成功/失败计数与 Agent 名和版本                   |
| uninstall    | 移除了哪些 Agent                                                               |

明确不收集: 源码、路径、文件名、符号名、查询词、IP、任何个人数据; 机器 ID 是首发包裹时铸造的随机 UUID。关闭机制遵循"关闭就是关闭": `codegraph telemetry off`、`CODEGRAPH_TELEMETRY=0` 或跨工具标准 `DO_NOT_TRACK=1` 任选其一永久生效; 关闭后不记录、不连接、不发已退出提示, 并删除本地身份与未发送队列。查看器自身不发送任何遥测, 其服务器不建立出站连接, 浏览器页面只与本机回环地址通信。

除遥测外还有本地诊断: `CODEGRAPH_EXPLORE_DEBUG` 可以输出逐候选文件的评分输入、预算分配、去重节省与裁剪情况, 用于排查"为什么这个文件没被返回"。

### 8.5 性能与成本控制

规模能力的几个关键约束:

- 索引规模: 单机可完成十万级文件、百万级符号的索引 (参考基准包括 Swift 编译器约 2.7 万文件全量索引约 100 秒); 设计是流式写入而非全量内存, 因此在内存受限环境不会在早期就耗尽;
- worker 池自适应: 解析并行度、引用解析并行度、分析缓存都按真实核数 (cpuset/容器感知) 与真实可用内存 (Linux 上按 cgroup v1/v2 限额扣除当前用量与可回收页缓存) 推导, 解析池只在收益覆盖成本时自适应启用;
- 增量经济学: 同步成本随变更大小增长而非随仓库大小增长, 单次保存后监听器 300ms 触发、秒级内完成增量更新;
- 内存边界: 对无界扫描 (如所有函数节点) 使用惰性迭代而非一次性物化数组, 合成器逐节点流式处理, 避免符号密集项目把堆打爆;
- 大文件 (超过 `MAX_SOURCE_FILE_SIZE_BYTES` = 1 MB) 默认跳过, 不解析也不读入内存, 内容哈希改用尺寸戳记, 避免 GB 级 blob 撑爆读取。

### 8.6 CLI 与库 API

命令行面覆盖完整生命周期: 安装与卸载 (install/uninstall)、初始化与反初始化 (init/uninit)、全量与增量索引 (index/sync)、状态、查询 (query)、explore、上下文构建 (context)、单符号与文件读取 (node/files)、调用方与被调方 (callers/callees)、影响面 (impact)、受影响测试 (affected, 支持 `--stdin`/`--json`/`--filter`)、守护进程 (daemon)、遥测开关 (telemetry)、升级 (upgrade)、版本、锁清理 (unlock)。另有隐藏的 MCP 服务入口 (`serve`) 与提示钩子 (`prompt-hook`); 浏览器查看器 (`ui`) 目前需要 `CODEGRAPH_UI=1` 才会启用。

作为库嵌入时暴露同等能力:

```typescript
import CodeGraph from "@colbymchenry/codegraph";

const cg = await CodeGraph.init("/path/to/project");
await cg.indexAll();

const results = cg.searchNodes("UserService");
const callers = cg.getCallers(results[0].node.id);
const impact = cg.getImpactRadius(results[0].node.id, 2);
cg.watch();
```

从源码运行要求 Node 22.5+ (内建 `node:sqlite`), 而随包安装自带运行时, 对使用者透明。

## 九、影响面分析与基线收益

### 9.1 graph 与 agent 的接口设计原则

MCP 设计里最有借鉴价值的一组原则, 可以独立于本项目迁移:

| 原则                                            | 含义                                                                |
| ----------------------------------------------- | ------------------------------------------------------------------- |
| 优化目标是墙钟延迟与工具调用数, 不是 token 成本 | 少调用、快返回比省 token 更重要; 实测 token 与成本也因此更低        |
| 适配 Agent, 不要试图改变 Agent                  | 低显著性的渠道 (初始化指引、工具描述) 改措辞无法可靠改变工具选择    |
| 充分性原则                                      | 歧义名一次返回所有重载, 输出足够完整让 Agent 停下, 杜绝去读文件补齐 |
| 错误即弃用                                      | 一两次 `isError` 就会教会 Agent 放弃, 预期内状态永不返回错误响应    |
| 精确输入换精确输出                              | 收模糊描述的工具必然失败, 也不会被选中                              |
| 部分覆盖比没有更糟                              | 半截桥接会让 Agent 钻进文件补齐                                     |
| 地板模型验证                                    | 在较弱的模型上成立的可用性才能向上泛化到所有宿主                    |

### 9.2 基线收益的量级

在 7 个真实开源仓库、多种语言上做的对照实验给出的量级是: 工具调用减少约 88%、耗时下降约 53%、token 减少约 62%、成本下降约 44%, 7 个仓库的文件读取全部归零。收益密度与问题的"发现量"正相关:

| 任务形态                       | 收益                                                          |
| ------------------------------ | ------------------------------------------------------------- |
| 架构理解、跨模块修改、影响分析 | 最大, 因为无图时的探索成本最高 (文件读取臂需要几十次工具调用) |
| 简单的单文件问答               | 接近持平, 无图也不贵 (几次调用就能到答案)                     |
| 需要重建完整调用链的问答       | 大, 是嵌入检索路线几乎不可能完成的任务类型                    |

两条诚实声明同样重要。其一, 成本节省取决于问题的发现量而非仓库大小: 需要几十次工具调用才能回答的问题省得多 (57–78%), 十次以内就到答案的问题基本持平。其二, 上述数字测的是吞吐 (处理的 token、调用的工具、花的钱), 不测答完之后上下文窗口里还留着什么。在这个维度上它更贵: 同一批仓库的多轮会话里, 它答完后驻留在窗口里的检索上下文比逐文件读取的 Agent 多约 80% (最悬殊的一仓约 67k 对 18k token)——致密载荷答完仍留在窗口里, 小窗口长会话需要为此做预算。机制与它快的原因是同一个。

### 9.3 确定性带来的企业属性

抽取源自 AST, 不被大模型总结, 因此索引完全可复现, 同一份代码永远得到同一张图; 索引零边际成本, 不调用模型、不产生费用、不受模型下线或涨价影响; 无模型漂移, 不存在"换了嵌入模型导致检索结果变化"这类非确定性。代价是图本身不携带语义注解——对需要审计输出、需要可复现的事故复盘的企业场景, 这个取舍通常是加分项。

## 十、横向对比

按"如何表示代码"分类, 它处在图派加本地优先这一格:

| 方案               | 核心表示                  | 索引位置   | 给 Agent 的接口      | 主要场景             |
| ------------------ | ------------------------- | ---------- | -------------------- | -------------------- |
| CodeGraph          | AST 到图加全文索引        | 本地       | MCP                  | 各 Agent 的探索加速  |
| 编辑器内建仓库映射 | 语法标签加图排序          | 本地       | 拼到提示词           | 终端结对编程         |
| IDE 内建语义索引   | 分块加嵌入                | 远端或本地 | 问答入口             | 特定 IDE 内          |
| 企业代码搜索       | 编译器级索引加嵌入        | 远端实例   | 内建加 MCP           | 跨仓代码搜索         |
| 图数据库方案       | 属性图 (含模型生成的注解) | 服务端     | 服务接口加专用 Agent | 大代码库的企业级问答 |
| 代码评审平台       | 仓库依赖图                | 远端 SaaS  | 评审 Agent           | 拉取请求评审         |
| 整库打包           | 全库拼大文本              | 本地       | 复制粘贴             | 长上下文一次性投喂   |
| 静态分析查询       | 数据流事实加逻辑查询      | 本地       | 查询语言             | 安全分析             |

对比要点:

- 与语法标签加图排序方案: 后者用图排序在预算内把全库符号摘要拼进提示词, 是"预算化的单次上下文"; 本方案是"按需图查询", Agent 自己决定问哪一片。前者适合一次会话改几个文件的结对编程, 后者适合先摸架构再动手的 Agent 流水线。
- 与嵌入路线: 根本差异在精确性。嵌入擅长语义模糊查询, 但"谁调用了这个函数"这类精确结构问题不可靠, 相似度排序会把名字相近但无关的函数排上来。本方案反过来: 结构精确, 模糊语义靠全文检索尽力而为。
- 与编译器级索引方案: 精确性维度类似甚至更强 (懂泛型实例化与导入解析的所有边角), 代价是每种语言一个专门索引器且要能编译; 部署模型相反, 前者中心化, 本方案本地化。需要跨百仓导航的大型组织, 中心化方案仍是天花板; 不愿外传源码的团队, 本地化是硬性优势。
- 与重图数据库方案: 一轻一重。后者走图数据库加服务框架加多 Agent 编排的重型路线, 面向百万行级企业; 本方案是一个 npm 包加一个数据库文件。后者的图更"语义化" (把模型生成的文档串入图), 本方案坚持确定性抽取。
- 与整库打包方案: 哲学相反。它们假设长上下文模型能自己挑相关内容, 本方案假设 Agent 应该被引导只看相关子图。大仓库纯文本可达数千万 token, 整库投喂瞬间失效; 即便在超长上下文模型上, "应付得了"和"花得起"也是两回事。
- 与静态分析查询与通用事实库: 不同层次的目标。它们表达力远超本方案, 但面向静态分析工程师而非大模型 Agent; 安全分析场景两者互补而非竞争。

## 十一、企业落地建议

### 11.1 适合的场景

- 主力 Agent 属于已适配的工具列表之内;
- 经常在万级文件项目工作, 收益随发现密度增长;
- 源码不能出域 (合规、隐私要求);
- 重视调用链、影响面等精确结构化查询;
- 希望零基础设施试点;
- 计划建设错误自动修复、变更风险分析等 Agent 流水线。

### 11.2 不适合的场景

- 需要跨仓推理与集中治理: 它是单仓本地索引, 微服务架构下每仓一个实例, 跨服务的端到端链路仍需中心化方案;
- 主要诉求是语义模糊检索: 嵌入派更稳;
- 需要类型级精确性做安全分析: 应选编译器级索引或数据流分析路线;
- 需要 SLA、RBAC、集中配置下发与使用量报表的强管控环境: 当前无此能力面, 安全基线需要自行用环境变量预置。

### 11.3 组织层面的可迁移经验

即使不采用本方案, 它的若干实践对构建内部 Agent 基础设施有直接参考价值:

- 默认只暴露一个工具面, 降低治理面积与提示注入面;
- 用"地板模型"验证政策保证在异构模型栈上的稳定性;
- 只读与幂等注解让工具能被问答模式安全消费;
- "错误即弃用"的响应形态设计是 Agent 工具可用性的通用教训;
- 字节级一致性门加逐文件回退, 是"性能优化不破坏正确性"的工程范式;
- 把优化目标定成延迟与调用数而非 token 成本, 更贴近 Agent 工作流的真实约束。

### 11.4 缺口与风险

- 单仓边界: 不做跨仓图谱;
- 无集中管控: 没有 RBAC、SSO、集中配置下发与使用量报表;
- 能力边界: 反射、依赖注入容器、框架约定是静态分析的天花板, 覆盖率数据应如实标注; 接收者类型推断依赖声明类型与书写出的返回类型, 没有完整类型推断, 渐进类型语言 (TypeScript/Luau) 以裸名匹配为主; 部分语言为有限支持; 默认跳过超过 1 MB 的文件; 浏览器查看器尚未正式开放;
- 上下文驻留: 多轮会话残留内容较多, 小窗口长会话需要预算;
- 遥测默认开启: 严格环境需预置关闭。

### 11.5 一个典型的落地形态

把代码图谱接入"运行时错误自动修复"闭环, 是它收益密度最高的用法之一:

```text
错误上报 (前端 SDK 捕获, 服务端符号化栈帧)
  → 错误聚合 (按指纹分组, 按频次与影响面筛选候选)
  → 上下文组装: 错误元数据 + 符号化栈帧
              + 代码结构上下文 (图谱查询)
              + 行为约束 (AGENTS.md)
              + 修复模式 (skills)
  → Agent: 定位根因 → 建修复分支 → 写修复
  → 验证: 由图反向追踪受影响的测试文件, 定向执行
  → 提交合并请求, 附影响面摘要
  → 反馈: 观察发版后错误是否消失
```

在这个闭环里, 图谱解决的是中间三步的全部结构性问题: 栈帧落到哪个函数 (图节点带文件与行范围)、根因在哪个调用链 (合成边桥接渲染与状态更新链路)、改动会影响谁 (影响半径加路由节点)、该跑哪些测试 (`affected` 命令的反向依赖追踪)。三类知识分工明确: 行为约束回答"如何规范地干活", 修复模式回答"已知问题怎么修", 代码图谱回答"代码现状是什么"。前两者是静态知识, 后者是动态且仓库专属的, 谁也替代不了谁。

关键是把"是否信任模型"从主观判断变成工程规则: 影响半径低于阈值才自动提交, 触及对外路由或高扇出符号则降级为人工认领, 动态边界报告的断点如实标注低置信度而不强行合成结论, 受影响的测试全绿是硬性前置条件。自动化边界可以随覆盖率数据逐语言、逐框架地调整。

## 十二、上手与小结

安装 (自带运行时, 无需预装 Node):

```bash
# macOS / Linux
curl -fsSL https://raw.githubusercontent.com/colbymchenry/codegraph/main/install.sh | sh

# Windows
irm https://raw.githubusercontent.com/colbymchenry/codegraph/main/install.ps1 | iex

# 或 npm
npm i -g @colbymchenry/codegraph
```

初始化与日常使用:

```bash
codegraph install        # 检测已装 Agent 并注册 MCP (只接线, 不索引)
cd your-project
codegraph init           # 建索引目录并构图, 自动同步默认开启

# 在 CI 中只跑受影响的测试
git diff --name-only | codegraph affected --stdin --quiet | xargs vitest run
```

采用建议:

1. 把它定位为"压缩探索成本"的本地基础设施, 而不是代码理解的全部答案。它不理解运行时值, 也不做类型级推理; 图保证的是结构上下文的完整与精确, 不是答案本身。
2. 试点从已适配的 Agent 加一个万级文件项目开始, 用探索密集型的任务 (架构梳理、跨模块修改、影响分析) 衡量收益, 简单问答上看不到差别是正常的。
3. 企业落地的姿态应是"团队级自助试点 + 环境变量基线预置" (遥测、监听、WAL 阀门都有显式开关); 跨仓治理等待中心化方案成熟或另外选型。
4. 迁移到内部 Agent 基础设施时, 优先抄它的接口设计原则与一致性门禁, 而不是数据结构本身。
