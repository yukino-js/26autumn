本文剖析一个与官方 Claude Code CLI 配置兼容的终端 AI 编码助手的实现: 它如何组织构建与特性裁剪, 如何驱动"模型流式输出、工具并发执行、结果按序回吐"的核心循环, 如何设计工具注册与延迟发现, 以及如何用一层流适配器把多家模型协议收敛成同一种内部格式。适合想自建或二次开发终端编码 Agent 的工程师阅读。文中不含本机路径与版本快照, 关注的是设计本身。

## 一、它是什么, 解决什么问题

这是一个终端里的交互式 AI 编码助手, 与官方 Claude Code CLI 的配置文件保持兼容: 用户不需要改动原有配置即可替换使用。它的自我定位是复原核心功能、裁剪次要能力, 目标是与企业版和登录态特性追平。

它解决的问题可以拆成三层:

| 层次   | 问题                                                                                                |
| ------ | --------------------------------------------------------------------------------------------------- |
| 接入层 | 官方实现只对接自家模型与云平台; 团队常需要接入 OpenAI 兼容端点、Gemini、xAI 等多家供应商            |
| 编排层 | 终端 Agent 需要在流式输出中并发执行工具调用, 同时保证结果顺序、权限确认与中断语义都正确             |
| 工程层 | 一个上万文件、数十万行的大型 TypeScript CLI 在 Bun 运行时下会遇到解析与内存问题, 需要构建层面的解法 |

与通用 Agent 框架相比, 它的差异在于: 它不是让用户自己搭一个 Agent, 而是一份开箱可用的完整产品形态, 包含终端 UI、权限审批、插件体系、远程控制与 IDE 协议接入。与官方实现相比, 它的差异在于可裁剪的特性开关与可扩展的模型供应商层。

## 二、架构总览

整体是一条"入口快速路径分流, 命中则进完整 CLI"的结构。入口先处理一批零开销或低开销的快速路径: 版本查询、系统提示词导出、以独立 MCP 服务形态启动、守护进程工作进程、远程控制与桥接、后台会话管理、模板任务、工作树组合等。只有这些都没命中, 才加载完整的主程序。

主程序用命令框架注册大量子命令 (MCP 服务管理、服务器、SSH、打开、认证、插件、子代理、自动模式、诊断、更新等), 主命令负责权限初始化、MCP 连接、会话恢复与运行模式分发。交互式 REPL 内部另有大量斜杠命令入口, 覆盖目标驱动、构件、工作流、多实例协作等长尾功能。

核心循环由三部分构成:

| 组件      | 职责                                                                             |
| --------- | -------------------------------------------------------------------------------- |
| 查询函数  | 主 API 查询: 发送消息、处理流式响应、执行工具调用、管理会话轮次循环              |
| 查询引擎  | 包裹查询函数的高层编排: 会话状态、上下文压缩、文件历史快照、归属标注、轮次级记账 |
| REPL 屏幕 | 基于 React 渲染的交互界面: 输入、消息展示、工具权限确认、快捷键                  |

API 客户端负责组装请求参数 (系统提示词、消息、工具、试验特性开关), 调用所选供应商的流式端点, 并把统一的事件流交给上层。

## 三、构建体系

### 3.1 Bun 打包与代码分割

构建由 Bun 的打包器完成, 入口是 CLI 的 TSX 文件, 开启代码分割, 输出一个主文件加大量分块文件; 构建后自动复制需要随包分发的 vendor 资源 (音频采集、搜索用的外部二进制等)。

为什么必须代码分割, 是这份实现里最有价值的工程结论之一。Bun 使用的 JavaScript 引擎 (JSC) 会全量解析单个大文件的字节码并做即时编译, 17MB 的单文件产物使进程 RSS 暴涨到约 1GB (同样产物在 Node/V8 下因懒解析只需约 220MB)。分割成数百个小 chunk 后按需加载, 版本查询这类只触及少量模块的路径 RSS 从 966MB 降到 35MB, 完整加载也从 1GB 以上降到约 500MB。这不是风格偏好, 而是被内存数据验证过的硬约束。

同时提供另一条基于 Vite 的备选管线, 输出到分块目录, 并有构建后处理脚本对仅 Bun 支持的运行时 API 做兼容处理并复制 vendor 资源。

产物对运行时做了兼容: 构建后处理把仅 Bun 支持的动态 require 替换为在 Node 下也能工作的等价实现, 因此同一份产物既可用 Bun 直接运行, 也可用 Node 运行, 包同时提供两个可执行入口。vendor 路径解析统一走一个基于模块 URL 的定位工具, 保证源码运行与打包运行都能找到资源。

### 3.2 特性开关机制

代码统一通过编译期特性开关判断功能是否启用, 开关由环境变量按固定前缀注入。构建默认启用的特性集中定义在一处清单里, 开发模式全部启用。Bun 对特性开关的使用位置有编译期限制: 它只能直接出现在条件判断或三元表达式的位置, 不能赋值给变量或放进逻辑与链。

这套机制的价值在于: 复原型项目需要在保留全部代码路径的同时, 按构建裁剪功能面。默认清单里有大量以注释形式保留但未启用的特性 (例如跨实例收件箱、局域网管道、上下文折叠、子代理分叉、技能学习等), 需要时用环境变量显式打开, 无需改动代码。

### 3.3 质量闸门

- 静态检查与格式化用 Biome, 覆盖主程序、脚本与所有子包。由于代码来源包含反编译产物, 一部分规则被关闭, 只保留推荐基线; 不同文件类型有不同列宽与分号要求。
- 提交时由钩子自动执行检查与格式化。
- 类型检查必须零错误, 这是反复强调的验收标准。
- 预检查脚本把类型检查、检查修复与测试串成一条命令, 任务完成后必须通过。

值得注意的是, 这份实现对自己代码的完整度做了诚实标注: 仓库维护一张 Stubbed/Deleted Modules 表, 逐模块标注状态 (Restored 已复原 / Empty implementations 空实现 / Removed 已移除 / Simplified 简化), 例如 Analytics、GrowthBook、Sentry 三大遥测组件被明确标注为空实现、不上报不拉取。对二次开发者而言, 这比任何宣传都可靠。

## 四、核心 Agent 循环

### 4.1 消息到工具再到消息的循环

一轮交互的流程是: 用户输入进入当前分支 → 组装请求 (系统提示词、历史消息、工具定义、模型设置) → 选定供应商流式返回 → 边接收边累积文本与工具调用块 → 工具调用到的同时开始执行 (不等整条消息结束) → 收集工具结果 → 若还有待执行工具或用户排队消息, 进入下一轮 → 否则结束本次运行。

关键设计是流式工具执行: 大多数实现会等模型把整条消息输出完, 解析出全部工具调用, 再依次执行; 这里在工具调用块刚流到时就开始执行, 把模型剩余输出时间与工具执行时间重叠起来。这在长尾任务里能显著压缩墙钟时间。

### 4.2 工具并发调度

工具执行器维护一个被跟踪工具列表, 每项带状态 (排队、执行中、已完成、已回吐) 与并发安全性标记。并发规则是:

| 场景                 | 行为                                             |
| -------------------- | ------------------------------------------------ |
| 标记为并发安全的工具 | 可以与其他并发安全工具并行执行                   |
| 非并发安全工具       | 必须独占执行, 等待其他工具结束                   |
| 结果回吐             | 无论执行先后, 结果一律按工具调用被接收的顺序发出 |

并发安全性由工具自身根据解析后的入参判定 (例如读取不同文件可并发, 写入同一路径不可), 判定失败则保守地视为不安全。工具结果里还区分了可中断行为: 当所有在执行的工具都支持取消时, 界面才把当前状态标记为可中断。每个工具批次会创建一个追踪区间, 用于观测与成本归属。

这套设计解决的是"并发与顺序"这对矛盾: 执行可以乱序, 但呈现给模型的结果必须与调用顺序一致, 否则模型无法把结果与调用对应起来。

### 4.3 会话状态、压缩与队列

会话状态集中在一个 React 上下文与一个轻量 store 中, 另有模块级单例保存会话 ID、工作目录、项目根、token 计数、模型覆盖、客户端类型与权限模式。多阶段的状态更新通过更新函数进行, 而不是直接改对象。

上下文压缩把较早的消息替换为摘要, 并在消息流里插入压缩边界标记; 读取时只取边界之后的消息。这使压缩成为视图层替换而不是破坏性存储, 保留了回溯能力。

用户输入有明确的排队语义。排队命令管理器提供入队、带条件的出队/移除/过滤、可编辑弹出 (判断哪些排队项可以被弹回输入框编辑), 并通过订阅信号驱动界面更新; 后台会话则由独立的 attach/detach 与 ps/logs/kill 通道管理。交互式界面下, 排队中的命令有专门的展示组件 (PromptInputQueuedCommands)。

## 五、工具系统

### 5.1 工具接口契约

工具的接口定义包含: 名称与别名、描述生成函数 (可以根据会话是否非交互、权限上下文等动态生成描述)、参数 schema、执行函数、并发安全性判定、是否只读、是否破坏性、是否启用, 以及可选的延迟发现搜索提示词。

描述是动态的而不是静态字符串, 这一点值得注意: 同一个工具在只读会话与可写会话里可以给出不同描述, 也可以根据当前可用工具集调整描述, 从而让模型知道哪些动作在当前上下文里是可行的。

### 5.2 工具分类

内置工具包按职责分为若干类:

| 类别         | 代表工具                                         |
| ------------ | ------------------------------------------------ |
| 文件与检索   | 读取、编辑、写入、通配匹配、内容检索、笔记本编辑 |
| 执行         | Bash、PowerShell、交互式 REPL                    |
| 子代理与任务 | Agent、任务创建/更新/查询/列表/输出/停止         |
| 规划         | 进入计划模式、退出计划模式、验证计划执行         |
| Web 与外部   | WebFetch、WebSearch、MCP 调用、MCP 认证          |
| 代码智能     | LSP 查询、Skill 调用                             |
| 调度         | 定时任务的创建/删除/列表                         |
| 延迟发现     | 搜索额外工具、执行额外工具、结构化输出           |
| 环境         | 工作树进入/退出、配置、睡眠                      |

其中延迟发现三件套是这套工具系统的特色: 搜索额外工具用一个文本检索索引在未加载的工具里找候选, 执行额外工具按名字调用它们, 结构化输出用于让子代理返回结构化结果。

### 5.3 核心白名单与延迟发现

工具数量膨胀后的选择是"白名单加延迟发现", 而不是全量注册。核心白名单里的工具 (文件操作、执行、子代理、任务管理、规划、Web、代码智能、技能、工作流、调度、发现工具本身) 始终加载并直接可见; 其余内置工具与全部 MCP 工具被标记为延迟工具, 必须通过搜索工具发现后, 再用执行工具调用。

延迟发现的检索实现是自研的 TF-IDF 加关键词混合评分: 对每个延迟工具的名称与描述建索引, 查询时先按必需词 (+term) 做硬过滤, 再对候选打分, 最终按"关键词得分 × 0.4 + TF-IDF 得分 × 0.6"融合排序; 查询语法支持 select:精确名、discover:只看定义不加载、多词关键词与多选取。描述按工具名记忆化, 延迟工具集合变化时缓存键随之失效。同一套能力也用于提示输入框的预取建议: 从用户消息提取查询词, 在后台预取可能相关的工具并在界面上给出最多 3 条提示。

延迟工具集的变化通过附件消息通知模型: 新增或移除的延迟工具会以增量形式注入会话, 避免模型面对一份过时的工具清单。

### 5.4 延迟搜索的开关模式

延迟搜索由环境变量 ENABLE_SEARCH_EXTRA_TOOLS 控制, 支持三种模式:

| 模式     | 取值                       | 行为                                                                                                                                |
| -------- | -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 始终开启 | 未设置 / true / auto:0     | 非核心工具一律延迟, 需要发现后调用                                                                                                  |
| 自动     | auto 或 auto:N (N 取 1-99) | 当延迟工具定义的 token 规模超过阈值时才启用延迟, 阈值按上下文窗口的百分比配置 (默认 10%), token 计数 API 不可用时退化为字符数启发式 |
| 关闭     | false / auto:100           | 全部工具内联暴露                                                                                                                    |

默认是始终开启, 另有一个总开关 (CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS) 可以强制关闭延迟搜索。这里有一条容易被忽略的工程细节: 阈值判定要按实际调用的模型来判断, 而不是按会话主模型判断, 因为子代理可能使用更小的模型 (例如 haiku), 二者的工具搜索决策可能不同。

## 六、多 Provider 兼容层

### 6.1 供应商选择

首选直连 (Anthropic 官方 API)、AWS Bedrock、GCP Vertex、Microsoft Foundry, 以及通过兼容层接入的 OpenAI、Gemini、Grok (xAI)。供应商选择的优先级是: 登录流程写入设置的 modelType 最高, 其次是环境变量 (CLAUDE_CODE_USE_BEDROCK / USE_VERTEX / USE_FOUNDRY / USE_OPENAI / USE_GEMINI / USE_GROK), 都未设置时默认直连 firstParty。

### 6.2 流适配器模式

这是整个兼容层最重要的设计: 第三方协议格式全部通过"流适配器"转换成 Anthropic 的内部流事件格式, 下游代码零改动。适配器是一个异步生成器, 输入是供应商的原生数据块流, 输出是统一的流事件 (消息开始、内容块开始、增量、内容块结束、消息增量、消息结束)。

适配器需要处理的差异包括:

- 文本与推理内容的分块方式不同: 有的供应商把推理内容放在独立字段里, 需要映射为内部格式的思考块, 且空字符串也是有效信号 (某些模型的推理模式会返回空推理内容, 必须原样回传否则会被拒绝);
- 工具调用的增量组装: 工具调用按索引分片到达, 需要累积参数片段直到完整;
- 结束原因的映射: 各家枚举不同, 需要统一为内部的结束原因;
- 用量统计的归一化: 缓存读取与缓存写入 token 与普通输入 token 是三个不相交的分量, 需要分别映射;
- 内容块的开合管理: 一段回复里文本块与思考块可能交替出现, 适配器负责在切换时正确关闭与打开块。

把差异全部收敛在适配器里, 换来的是: 会话循环、工具执行、权限检查、UI 渲染等所有下游逻辑都不需要知道当前用的是哪家模型。

### 6.3 模型名映射

由于内部逻辑以 Anthropic 的模型家族 (haiku、sonnet、opus) 为语义基准, 接入其他供应商时需要把家族名映射到目标模型名。映射的优先级统一为:

1. 供应商专属的覆盖环境变量 (例如指定某个具体模型);
2. 通用的按家族覆盖环境变量;
3. 内置的默认映射表;
4. 原样透传。

Gemini 一侧更严格: 能识别出家族、却既没有指定模型也没有家族覆盖时, 直接报错而不是猜; 无法识别家族的模型名才原样透传。Grok 还额外支持用一份 JSON 映射表 (GROK_MODEL_MAP) 整体替换家族映射。此外仓库内置了一份国内模型供应商预设 (各家 OpenAI 兼容端点、定价与 coding plan 选项), 登录界面按"选供应商 → 选 API/coding-plan 接入方式 → 选模型 → 填 key"的向导式流程使用它。

### 6.4 登录与配置

首次配置走 REPL 内的登录流程, 提供若干栏目: Anthropic 兼容端点 (任意兼容 Messages API 的服务)、OpenAI 兼容端点 (本地运行时、国内厂商、自建网关等)、Gemini 原生接口, 前三者的字段是基线地址、API key 与三个家族对应的模型 ID; 另一栏目是第三方云平台, 引导设置对应环境变量。

## 七、UI 层

终端渲染基于一份分叉的 React 终端渲染框架, 而不是原版库。组件目录里有根 provider (应用状态、统计、帧率指标)、消息与会话行渲染、输入处理、权限审批界面, 以及一组设计系统复用件 (对话框、署名、快捷键提示、列表项、带主题文本)。分页选择器、进度条、主题 provider 等落在分叉框架包内。

状态管理方面, 中央状态与应用状态 store、默认状态工厂、轻量 store 工厂与选择器分离; 模块级单例保存跨组件的会话级信息。组件中大量出现编译期记忆化样板, 这是反编译产物的正常特征, 不影响设计判断。

一个值得单独记录的兼容性处理: ConPTY 之前的老版本 Windows 控制台 (build 号小于 17763) 上, conhost 的 VT 解析器处理增量更新会产生光标漂移, 残影会持续累积。实现会自动检测并启用兼容模式, 以约一秒 (默认 1000ms, 环境变量可调, 钳制在 100-10000ms) 的周期做一次全量重绘替代增量 diff 自愈; 环境变量 CLAUDE_CODE_LEGACY_CONSOLE 可强制关闭 (0)、强制周期重绘 (1) 或强制每帧全量重绘 (2, 牺牲闪烁换正确性)。此外还有基于 OSC 9;4 转义序列的终端进度/状态上报 (running、completed、error、indeterminate 四态, 可带百分比), ConEmu、Ghostty 1.2+ 与 iTerm2 3.6.6+ 支持, Windows Terminal 会把该序列误解为通知而被显式排除; 配套的桌面通知支持 iTerm2、Kitty、Ghostty 各自的转义协议与 BEL 响铃兜底。

## 八、平台化能力

### 8.1 ACP 接入

实现了 Agent Client Protocol 的一端, 使 Zed、Cursor 等 IDE 可以接入; 另有独立桥接包把 WebSocket 客户端桥接到该 Agent, 支持自定义端口、HTTPS、认证与会话管理。权限管道统一为一条"是否允许使用某工具"的回调, 会话模式可动态同步; 计划可视化支持计划更新消息, 带进度条、状态图标与优先级标签。

### 8.2 守护进程

守护进程模式由特性开关门控, 是一个长驻 supervisor, 管理工作进程的注册与生命周期。

### 8.3 远程控制与桥接

桥接模块包含桥接 API、会话管理、令牌认证、消息传输与权限回调。配套的自托管远程控制服务器提供 Web 控制台, 支持 ACP Agent 经桥接包接入, 含 WebSocket 处理器、中继处理器与事件流。用户也可以把客户端指向自部署的桥接地址。

### 8.4 构件托管

构件功能让模型把 HTML 页面、数据看板或报告上传到公开地址, 并设置自动过期。服务端实现为无服务器 Worker 加对象存储: 上传接口做令牌鉴权、内容类型校验、大小上限与有效期选择; 读取接口从对象存储读取并设置缓存头; 过期由存储层的前缀加生命周期规则实现, 计算层不参与。标识符默认用高熵随机串, 也支持自定义哈希 (覆盖语义为先删旧键再写新键)。部署只需标准脚手架加一条部署命令。这套服务是独立部署的, 不被主 CLI 导入。

### 8.5 消息渠道接入

除终端、IDE 与远程控制外, 主程序还有一条"消息渠道"通路: 会话可以挂接到即时通讯平台, 让外部消息进入会话、把权限审批请求发到渠道上。渠道以带 channel 能力的 MCP 服务器形态接入, 用 --channels 标志按名字组成允许清单, 在交互式与打印/SDK 模式下都可用。权限审批在渠道上是结构化事件而非文本: 服务端解析用户的确认回复后, 必须刻意发出带请求 ID 与行为结论的权限事件, 主程序才认账——纯文本回复不构成批准, 渠道服务器需要声明对应的实验能力才参与审批; 渠道回复与本地界面、桥接、钩子、分类器几路竞速, 先到者赢得这次裁决。仓库内置一份微信渠道集成, 以默认启用的内建插件形态注册: 它起一个 stdio MCP 服务接收微信消息并暴露回复与输入状态工具, 用独立的登录命令配置账号, 再按会话用渠道标志启用。

## 十、工程纪律

- 测试框架用 Bun 自带测试; 单元测试就近放置, 集成测试单独成组, 共享 fixture 集中在 mock 目录。
- Mock 规范严格: 只 mock 有副作用的依赖链, 不 mock 纯函数; 日志与调试模块必须使用共享 mock。
- 有一个重要的测试陷阱被系统性总结: Bun 的模块 mock 是进程全局的, 一个测试文件的 mock 会污染同进程其他文件, 且测试执行顺序不保证。核心规则是"不要 mock 被测模块的上层业务模块", 集成测试应 mock 底层 HTTP 客户端而非源 API 模块, 从而保证同目录的单元测试仍能测到真实逻辑。
- 类型纪律: 生产代码禁止任意类型断言, 优先用双重断言或补 interface; 未知结构用通用记录类型; 联合类型用类型守卫收窄。
- CI 覆盖静态检查、构建与测试, 另有远程控制服务器发布与 npm 发布等独立工作流。
- 提交信息遵循约定式提交规范。
- 另用工具检查未使用的导出。

## 十一、适用与不适用

适合的场景:

- 需要在终端里获得完整的 Agent 编码体验, 同时要求能接入多家模型供应商或自建网关;
- 需要自托管远程控制界面或构件托管服务, 而不是依赖厂商托管;
- 想在一个成熟的产品级代码库上做二次开发, 且能接受反编译产物带来的可读性代价。

不适合的场景:

- 只要一个轻量可嵌入的 Agent 内核, 不需要终端 UI、权限审批与插件体系: 这份实现体量偏大;
- 需要厂商级别的稳定 API 契约与长期支持: 复原型项目的接口稳定性弱于官方;
- 对遥测与特性开关的默认行为有严格合规要求的场景: 需要预置环境变量裁剪。

与替代方案的取舍:

| 方案            | 优势                       | 代价                                  |
| --------------- | -------------------------- | ------------------------------------- |
| 官方 CLI        | 稳定、完整、官方支持       | 供应商选择受限, 不可自托管扩展        |
| 本实现          | 多供应商、可裁剪、可自托管 | 代码可读性差, 接口稳定性弱            |
| 从零自建        | 完全可控, 体积最小         | 需要自行实现循环、并发调度、权限与 UI |
| 通用 Agent 框架 | 抽象清晰, 生态广           | 没有成品终端产品形态, 需要自行搭建    |

## 十二、小结: 可借鉴的工程点

1. 大型 CLI 必须代码分割。这是被内存数据验证过的硬约束: 单文件产物的常驻内存可以是分割后的几十倍。
2. 编译期特性开关加环境变量注入, 让一份代码支持按构建裁剪功能面, 同时保留全部代码路径。
3. 第三方模型协议统一走流适配器, 把异构格式收敛到内部格式, 下游零改动。
4. 工具数量膨胀后用"核心白名单加延迟发现", 而不是全量注册; 延迟发现的检索用轻量文本索引即可, 不必上向量。
5. 流式工具执行把模型剩余输出时间与工具执行时间重叠, 结果仍按调用顺序回吐, 兼顾延迟与正确性。
6. 工具描述动态生成而非静态字符串, 让同一个工具在不同会话上下文里给出恰当引导。
7. 在缺乏稳定外部契约时, 用进程全局 mock 的污染纪律来保证测试隔离, 是一条值得写进规范的经验。
