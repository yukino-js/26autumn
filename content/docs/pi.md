Pi 是一个终端里的可扩展编码 Agent harness。它的设计立场非常明确: 内核只保留最小能力, 其余一切通过扩展、技能、提示模板、主题与自定义 provider 加入, 打包为 Pi package 分发。本文按机制而非目录来组织, 讲清这套极简内核如何支撑树形会话、如何被 TypeScript 进程直接嵌入、durable 运行时怎样做到"先落盘再展示"、TUI 与 client/server 两种形态如何共用同一套会话机制, 以及 provider 与沙箱体系为何全部外置。读者应熟悉至少一个编码 Agent 的交互形态, 并对 Node、TypeScript 与终端程序有基本认识。

本文描述的是当前代码库的机制, 不涉及版本演进与发布记录; 其中标注为实验性的部分是维护者自己声明会随时变动的接口。

## 一、极简内核哲学与扩展机制

### 1.1 内核边界

贡献指南的第一句是 "pi 的内核是最小的"。不属于内核的功能应当做成扩展, 试图膨胀内核的 PR 会被拒绝; 就连扩展的 hook 点也要经过慎重讨论, 以免引入不可维护的复杂交互。配套的一条规则是 "你必须理解你的代码": 用 AI 写代码可以, 但不理解就提交不行。

这条哲学的直接后果是: sub-agent、plan mode 这类能力刻意不放进内核。内核提供强力默认, 同时给用户两条路——指挥 Pi 自己生成所需能力, 或安装现成的 Pi package。扩展不只是插件系统, 它是内核主动让位的结果。

内核的自我描述是最小集 (read、bash、edit、write 加会话管理), 但实际工具面更宽: 还包括 find、grep、ls 与 powershell。文件变更经专门的队列串行化, 避免并发工具调用互相踩踏。

### 1.2 资源阶梯七层

快速上手文档维护一张"从最弱机制开始"的选择表, 复杂度递增:

| 需求                         | 使用                    |
| ---------------------------- | ----------------------- |
| 文件夹级持久指令             | `AGENTS.md`             |
| 复用菜单里的提示             | prompt template         |
| 任务专属指令加附件           | skill                   |
| 可执行的工具、命令、事件处理 | extension               |
| 自定义终端组件               | Terminal UI             |
| 接入未支持的模型服务         | custom provider         |
| 打包分发多种资源             | Pi package (npm 或 git) |

这张表的价值在于它把"该用哪一层"变成工程决策而非偏好: 能用更弱的机制解决就不上扩展。

### 1.3 扩展机制

扩展是加载进 Pi 进程的 TypeScript 模块。工厂函数可以注册工具、命令、快捷键、provider、事件处理器、渲染器与终端 UI。仓库自带大量示例扩展, 大致分三类: 工程流程 (自动提交、git 检查点、受保护路径、权限门、计划模式、子代理、待办、结构化输出、自定义压缩等)、provider 与基础设施 (自定义 provider、调试 provider、沙箱、SSH、依赖打包、事件总线)、界面与娱乐 (用游戏验证 TUI 扩展能力的边界)。示例数量本身是设计声明: 扩展面被认为足以表达几乎任何工作流。

内核内置四个扩展: codemode、tool-search、mcp、llama (本地模型)。它们与用户扩展走同一注册面, 说明内核没有为特性保留特殊通道。

### 1.4 内核纪律的外化

极简哲学还体现在代码与供应链约束上:

- 只用可擦除的 TypeScript 语法, 以配合 Node 的 strip-only 模式——禁用 enum、namespace、parameter properties 等需要 JS emit 的构造; 禁止内联动态 import, 只允许顶层 import。
- 键位不许硬编码, 必须进默认键位表以保持可配置; 生成的模型数据文件不许手改, 必须改生成脚本后重新生成。
- 多会话并发开发有明确纪律: 同一工作目录可能同时跑多个会话, git 只允许 stage 显式路径, 禁止 `git add -A`、`reset --hard`、`checkout .` 之类会波及其他会话的操作。
- 供应链加固成体系: 直接外部依赖钉精确版本、`.npmrc` 设置只保存精确版本且拒绝刚发布不久的包 (缩小投毒窗口)、lockfile 是依赖事实源且默认禁止提交变更、安装器承担传递依赖的钉死、依赖的 lifecycle script 需走显式 allowlist、CI 用忽略脚本的方式安装并定时审计。

这些约束与内核最小化是同一取向: 把可变性与不确定性挤到边缘。

## 二、树形会话模型

### 2.1 entry 树与 active branch

会话不是线性的消息数组, 而是一棵树。消息与事件构成 entry, 每个 entry 有 ID 并指向父 entry; 每条路径是一个分支, 以当前 entry 结尾的分支是 active branch, 为下一次模型请求提供历史。

关键的语义差别在于"从更早处继续": 它不会删除后续 entry, 只是把 leaf 指针移回更早的 entry, 之后追加的内容在同一文件里长出新分支; 只有 fork 与 clone 才把选中的历史拷进新的会话文件。实现上对应 `SessionManager.branch()` 与 `createBranchedSession()` (packages/coding-agent/src/core/session-manager.ts), entry 类型是一组判别联合 (消息、思考级别变更、模型变更、用量、压缩、分支摘要、自定义、自定义消息、上下文编辑、标签、会话信息), 共享 id/parentId 的树结构。

持久化会话是 JSONL 文件, 天然追加友好: 分支不要求改写历史, 只追加指向旧 entry 的新 entry。

### 2.2 agent loop 与三种输入语义

一次提交的消息加入 active branch; Pi 用 system prompt、active branch、可用工具与模型设置组装请求, 经选定 provider 流式返回; 记录响应 (文本与工具调用), 逐个执行工具并记录结果, 这算一个 turn; 若工具结果或排队消息还需要模型请求就再来一轮, 否则 run 结束。

三种输入语义被区分得很清楚:

```text
steering   在当前 assistant turn 之后插入
follow-up  在 agent 做完 pending 工作后进入
abort      停止当前 run 并把排队消息退回编辑器
```

这种区分让"用户在 agent 工作中途插话"与"用户要求 agent 完成后接着做"不再混为一谈。

### 2.3 上下文组装

system prompt 由基础指令与发现的 context files 构成; 请求携带工具定义与技能描述; 技能的完整指令按需加载, 而不是全部预载。扩展可以追加指令或变换上下文——上下文事件把消息数组交给处理器, 处理器可返回新数组或就地修改。prompt 模板在编辑器输入变成 user 消息之前展开; 选中文件、图片、粘贴文本、shell 输出都可以成为消息内容。

### 2.4 compaction 是视图不是存储

压缩会插入一条摘要 entry, 在后续模型请求中替换更老的消息, 但原始 entry 全部保留在会话树里。这是整套模型里最值得强调的取舍: 压缩是有损视图, 不是有损存储。用户仍然可以回到被压缩的分支继续工作, 历史可回溯性没有因为压缩而丢失。

### 2.5 持久化格式与会话管理

默认会话按工作目录分组存放于用户级 agent 目录; 命令行参数、环境变量与 SDK 设置都可改位置。相关开关包括: 跑临时会话 (退出即不可恢复)、直接指定路径或 ID、启动前从既有会话分叉、打开当前目录最近的会话。导出支持 HTML 与 JSONL; 分享可上传为带查看链接的产物或私有 gist; 另有生成私有 bug 报告的路径, 报告包含环境与 provider 配置但不含凭据值。

文档反复提醒: 导出与分享之前必须自查, 内容可能包含提示、模型回复、工具参数、命令输出与文件内容。

## 三、TypeScript SDK 的嵌入方式

### 3.1 createAgentSession

包可以直接作为库嵌入 Node 或 Bun 进程, 拿到与 CLI 同款的 agent、session、工具、模型与资源。最小用法是创建一个会话、跑一个 prompt、读最后一条 assistant 文本、释放会话。CLI 自己用的就是同一套创建逻辑, 因此 SDK 不是附属品, 而是内核的另一种入口。

### 3.2 SessionManager 是上下文的权威

`SessionManager` 持有持久化或内存的 entry 树并跟踪 active leaf。它是"最终模型上下文"的唯一权威: 直接给会话的 agent 状态赋消息数组不能替换持久化上下文; 要恢复外部历史, 必须构造带这些 entry 的 manager。`inMemory()` 用于不落盘场景。这条约束在文档里被反复强调, 因为它划清了视图与真相源的边界。

### 3.3 AgentSessionRuntime

`AgentSessionRuntime` 提供新会话、切换会话、分叉、从 JSONL 导入四类操作 (packages/coding-agent/src/core/agent-session-runtime.ts)。每次操作都会替换活跃的 AgentSession 并为目标工作目录重建服务, 因此替换后旧的事件订阅失效, 需要重新绑定。分叉还区分"在选中 entry 之前"与"包含选中 entry"两种位置。实现上它持有一个运行时工厂, 每次重建时以目标工作目录、会话管理器与必要的信任上下文重新构造整套服务, 这让"换工作目录继续"成为一等操作。

### 3.4 prompt 语义与事件

`prompt()` 先处理扩展命令、展开基于文件的 prompt 模板, 再让普通用户消息进入 agent; 对已被接受的 run, 返回的 promise 在该 run (含自动重试) 结束后 resolve。会话正在流式输出时再发 prompt 必须显式选择 steer 还是 follow-up, 不选直接 reject 而不是猜。abort 停止并等待空闲, 另有一个"只等不停"的等待接口。

事件订阅区分层次: message_update 提供增量文本 (含 assistant 消息事件), message_end 是权威的完整消息, agent_end 表示一次底层 run 结束 (后面可能还有自动恢复或排队工作), agent_settled 表示 Pi 确定不再自动继续。把"run 结束"与"彻底空闲"分开, 是编排者能正确判断下一步的前提。

### 3.5 依赖注入面与内置扩展

创建会话的每个默认件都可显式替换: 模型运行时、模型与思考级别、设置管理器、会话管理器、资源加载器、工具集 (含排除与自定义工具)。默认资源加载器支持标准发现加定点覆盖; 完全自管资源可以传自定义加载器。

CLI 会把注册面里的内置扩展默认加载 (codemode、tool_search、MCP 与提供本地模型的 llama.cpp), SDK 会话一个都不加载; 要让 SDK 会话拿到前三者的能力, 需把对应扩展工厂 (createCodemodeExtension、createToolSearchExtension、createMcpExtension) 加进 DefaultResourceLoader 的 extensionFactories。其中 codemode 与 tool-search 注册为非活跃, 通过默认工具设置或 MCP server 的暴露策略激活; MCP 扩展在会话启动时连接 server, 因此需要显式绑定扩展。这个连接不阻塞首个 prompt: 只等待带直连工具的 server, 其余后台连接, 脚本与延迟发现的工具在真正用到时按需等待。延迟发现的 MCP 工具会记录进 transcript, 因此能在该分支的树导航、恢复与分叉后存活。

扩展还可以声明"可替换": 当别的扩展注册同名工具或命令时自动让位而非冲突——这是同一注册面上避免冲突的机制。仓库的 SDK 示例全部随仓库类型检查, 既可当文档也可当回归测试。

## 四、durable 运行时的持久化设计

### 4.1 核心不变量

durable 是一个实验性的持久化 agent harness。它自述的原则是: 会话、模型轮次、工具调用与自定义状态先提交到存储, 然后才展示; 进程在轮次中途死掉后, 重开存储即可从中断点续跑。规范文档给出的核心规则是"一个 Session 原子地提交不可变 entry、完整 task 记录与协作文档, 只有已提交状态可观察"。

配套的不变量值得逐条看:

1. 一次 Session 提交对所有记录与文档写入是原子的。
2. 文档更新只在存储提交成功后发布。
3. 所有可见进度都是持久的, 没有易失的发布路径。
4. 外部副作用不在提交事务内运行。
5. entry 与 ID 不可变, 提交后不复用。
6. 草稿在事务回调结束时被同步准备或中止, 写入草稿的值按值拷贝且必须是严格 JSON。
7. 变更线在存储结算与已提交状态采纳期间保持持有; 提交与关闭观察者同步运行只为捕获不可变状态。
8. 存储错误对打开的 Session 是致命的: 它不发布任何内容, 必须重新打开。

这套不变量是"先落盘再展示"能成立的前提, 也是它与"内存中跑完再持久化"最本质的区别。

### 4.2 记录模型

规范用一组明确的概念划分层次:

| 概念         | 含义                                                                     |
| ------------ | ------------------------------------------------------------------------ |
| Session      | 拥有一条变更线、若干会话、entry、task、提交与文档                        |
| conversation | 一个 transcript 作用域, 可以分叉另一个 conversation                      |
| entry        | 不可变的 transcript 记录, 可携带贡献给模型上下文的消息与供应用消费的数据 |
| task         | 附着在某个 conversation 上的持久状态机                                   |
| document     | 由协作文档操作与偶发完整基底表示的可变 JSON 状态                         |
| turn / run   | 一个 assistant 响应及其工具调用 / 从受理输入到最终答案的轮次序列         |

entry 记录把"面向模型的消息"与"面向应用的数据"分开存放, 并带一个 head 字段指向它选中的上下文首 entry, 还支持上下文级的编辑覆盖。分叉在记录模型里是显式操作: conversation 可以指向父 conversation 与分叉点。

### 4.3 存储后端与并发

| 后端   | 特性                                                                                             |
| ------ | ------------------------------------------------------------------------------------------------ |
| Memory | 不持久化                                                                                         |
| SQLite | 单数据库文件, WAL 模式配合常规同步级别: 进程崩溃后提交仍在, 最新的提交在断电或宿主失败时可能丢失 |
| JSONL  | 单目录追加文件, 可配置每次提交标记前 flush                                                       |

一个存储同一时刻只被一个进程拥有, 没有跨进程锁。可移植的 SQLite 与 JSONL 核心不依赖 Node API, 只要给定异步的数据库 facade 或文件系统, 就能跑在 Bun 或 Cloudflare Durable Objects 之类的运行时上。自定义后端可以跑共享的一致性测试套件。SQLite 适配器实现基于 Promise 的 exec/run/get/all/transaction/close, 事务回调接收事务句柄, 句柄在回调结束时过期。

### 4.4 compaction 与 overflow

压缩把模型看到的内容缩小: 总结更老的 entry, 追加一条压缩 entry 持有摘要并指向它保留的第一条 entry, 更老的 entry 留在存储里。手动压缩以任务形态运行, 可附指令, 可被取消; 摘要生成期间会话继续工作, 摘要在会话空闲时立即放置, 否则在下一个轮次边界放置。

自动压缩按会话配置: 超过后台阈值时在后台启动, 超过上下文窗口减去保留量时下一次请求同步等待压缩; provider 以上下文过长拒绝请求时触发溢出压缩并重试一次。多个摘要并发时由 stale 规则裁决: 切到当前活动上下文开始之前的摘要在放置时落为 stale, 切在该起点或之后的摘要无论何时被选中都正常放置。运行中的压缩暴露在活动文档里, 含原因、尝试次数与重试退避; 摘要开销计入用量统计; 压缩任务上有一个 hook 可以拒绝或自供摘要。

### 4.5 扩展注册表与 task graph

durable 把注册面做成命名扩展注册表: 安装与卸载统一接管工具、hook、task 定义、system prompt 段与工具和段落包装器的注册; 扩展用定义函数与包装函数构建。每个 conversation 的 agent 配置 (模型、思考级别、扩展与工具选择、指令、工作目录) 存为可回退的文档, 任务拥有的会话复制 owner 的 agent 配置。

task graph 视图把每个活任务挂成可观察状态或 watch, 包含 owner 边、已提交状态、后台与中止标记、拥有的会话。生命周期一致性也做了约束: 运行时的时间与上报接口在调用结束后抛错, 只做文档迁移的提交也会发布新值, 打开失败时不借调用方上下文关闭会话而是重抛原始错误。

### 4.6 provider 会话身份

durable 还会为每个会话持久化 provider 侧身份: 内置一个 provider 文档, 每个新建、任务拥有、原始创建与分叉的会话都在创建提交里生成自己的会话 ID, 分叉从不复制父会话的身份。这个身份被传给模型请求, 供 provider 做提示缓存与会话亲和; 重置、压缩、换模型与重新打开存储都不改变它。没有该文档的存量会话会在 Session 线上于首次模型或压缩请求前惰性创建并持久化, 并发调用方只观察到一个赢家。

### 4.7 执行环境抽象与远程执行

durable 把"工具在哪台机器上跑"抽象成 ExecutionEnv: harness 为每个 conversation 解析一个执行环境, 文件读写、命令执行、目录监听都经它落地。默认实现是 Node 执行环境, 按工作目录缓存; 创建钩子可以按 conversation 返回别的环境, 于是"这个会话的工具进容器、那个会话进远程机"成为配置而非改码。

配套的 env 包把远程执行做成一等能力: 一个用 Rust 写的小守护程序经 SSH 部署到远程机, 在 stdin/stdout 上讲一套带帧协议, 代执行文件操作与命令; 客户端侧的 RemoteExecutionEnv 实现同一个 ExecutionEnv 接口, 结果与"在远程机上直接跑 Node 执行环境"逐项对齐, 只有错误文案可能不同。分工经过刻意切分——路径解析、中止检查点、错误码映射、读取尺寸与解码留在客户端, 系统调用、进程、溢出文件与行扫描留在守护程序; 守护程序按 SHA-256 命名并在每次启动前校验。这套设计让"durable worker、存储与凭据留在本地, 工具跑在另一台机器"成为可验证的部署形态, 而不是把整个进程搬走。

## 五、TUI 与 client/server 两种使用形态

### 5.1 五种接口形态

所有接口共用同一套 agent 与 session 机制:

```text
interactive  终端 TUI
print        跑一个 prompt 输出最终回复
json         agent 事件按 JSONL 输出
rpc          stdin 收 JSONL 命令, stdout 回响应与事件
SDK          进程内直接创建与控制会话
```

RPC 客户端封装了切换会话、分叉、克隆、导出、读取树结构等命令, 并带超时等待与错误映射, 使外部程序可以用子进程形态驱动 Pi。

### 5.2 pi-tui 的渲染工程

`packages/tui` 是一个差分渲染的终端 UI 库, 工程深度体现在: 双屏管理 (主屏与备屏)、布局系统、编辑器组件、emacs 风格编辑原语 (kill ring、撤销栈、按词导航)、自动补全与模糊匹配、LaTeX 渲染、终端图像、Oklab 色彩空间、终端色彩探测、原生修饰键检测与输入缓冲、键位系统。组件模型的要求很具体: 组件为可用宽度渲染行数组, 每行必须适配宽度 (按可见列而非字符串长度测量, 因为 ANSI 转义、宽字符、emoji、组合字符都会改变显示宽度), 状态变化后要让受影响组件失效并请求重渲染。

TUI 文档给出的集成点建议也是分层的: 优先用扩展上下文里的选择、确认、输入、编辑器、通知、状态、组件替换等 API; 只有在需要自己的渲染、键盘或鼠标输入、焦点、布局或生命周期时才自建组件; 不要在扩展里再建一套终端渲染器。

### 5.3 fullscreen 默认与交互资产

交互模式的默认 TUI 形态是全屏, 走备屏渲染器, 可用参数或设置切回常规模式。配套设置包括退出时输出内容、滚动条、选中即复制、滚轮每次滚动行数。启动呈现可配置为隐藏全部或只隐藏启动细节而保留头部。另有两处终端兼容细节值得记录: 某些终端绘制半块图形会在行间留缝, 探测后改用文字标; 系统主题的颜色调整不做色度增强, 以免加浓柔和终端配色。

### 5.4 durable TUI

durable harness 的第一个使用者是实验性 TUI coding agent。单进程同时持有模型运行时、durable harness、其存储与 TUI, 复用认证、设置、system prompt、键位、主题与交互组件; agent 本体就是 harness 加内置编码工具。流式输出、工具、steer 与 follow-up、中止、模型与思考级别切换、压缩都可用; 打开当前目录最新会话时会续跑被中断的轮次 (中断的工具调用获得 interrupted 结果, 该轮次继续走完)。子代理工具在子会话里跑任务, 可在任意会话视图间切换 (子代理忙时也可 steer), 有面板实时渲染 task graph。

设计信号很明确: TUI 本身不做任何恢复处理, 只渲染会话的结构化视图——持久化与中断恢复全部下压到 harness。会话存于用户级目录下按工作目录哈希分组, 目录锁阻止第二个进程打开。入口是源码直跑, 没有独立可执行文件; 会话列表、fork 与树导航、扩展、提示模板、图片等尚未覆盖。

### 5.5 client/server

durable 的第二个使用者是实验性 client/server, 形态是 server、worker、presentation 三段。server 把每个会话存放在会话目录下的独立子目录, 包含元数据文件与 SQLite 存储; 列出与创建会话只读元数据。会话 worker 锁定目录、打开存储、持有 harness 直到退役, 只要 task graph 还有活任务就保持存活。

这套形态建立在 chord 之上——一个独立的应用组合运行时, 提供 facet、服务 (单例与按键两种)、复制状态与可插拔的远程服务边界; 服务按 facet 提供物生成, 没有手写的内置服务清单。几个切片能看出分层意图: 会话目录管理会话的创建、移除、附着与分离; 模型切片管理状态、默认持久化的选择与刷新; AgentController 是"面向表现层安全的根 durable conversation 门面", 用于提示、steer、follow-up、取消队列、中止、压缩与等待回答; Transcript 直接提供根会话的持久视图; SlashCommands 与 PresentationUI 是纯本地的表现层能力, 不进入 RPC 目录。表现层通过控制器驱动 worker 侧的根会话, 并渲染 Transcript 的完整复制值; 因为 durable harness 按提交发布精确操作, worker 自己不需要 reducer, 复制的重建、定序与缺口检测由协作文档层负责。

传输在 unix socket 之外加了自定义地址形态以支持远程接入, 远程接入经 relay, 认证要求先完成对应登录。插件以可重复的参数装载, 服务器或会话分支可分别选择, 选择持久化在会话里且不改变其他 worker; 重载时会原子重建插件包、加载新候选并切走退役代际。

已明确记录的未完成项有四项: 树导航 (durable 用分叉到新 conversation 实现分支, 导航需要分叉、一条开启新上下文的摘要 entry 与会话当前 conversation 指针); next-run 队列 (durable 只排队 steer 与 follow-up 输入); 子代理会话暴露 (服务只覆盖根会话); transcript 历史分页 (Transcript 只有自上次重置或压缩以来的活跃上下文)。

## 六、provider 与工具/沙箱体系

### 6.1 统一 provider 面

`packages/ai` 是统一的多供应商 LLM API, 大约四十多个 provider 模块, 每个配一份模型数据。覆盖面从主流闭源与开源通道到国内厂商及其区域变体一应俱全, 另含若干网关与订阅通道。测试替身 faux provider 被用于全部测试套件, 使 CI 不接触真实 API 与付费 token。

模型目录是生成物而非手写文件: 生成、补全、校验各有独立脚本, 贡献指南允许提交重新生成带来的无关上游模型元数据差异。采样参数支持按思考级别覆盖: 模型可以携带以 Pi 思考级别为键的采样参数, 解析时先按模型支持的级别钳制, 再按"模型默认、生效级别覆盖、请求级参数"的顺序逐键合并; 只有部分适配器应用, 其余 API 忽略。

### 6.2 认证模型

用户在 Pi 内登录选择 provider, 走订阅或存 API key, 再切换模型。认证支持环境变量、OAuth (含复制验证码的登录方式) 与工作负载身份联合 (从环境变量读取联合规则与身份令牌文件, 跨请求复用联合客户端以命中令牌缓存)。另有官方 AI 网关作为一等 provider: 登录后其模型像其他 provider 一样出现在模型列表, 登录成功还会提议把网关的 MCP server 写进全局 MCP 配置, 以复用同一份登录取代 MCP 的 OAuth 登录。

MCP 认证面也有较完整的支持: OAuth 客户端名、让 HTTP server 直接以某个 provider 的当前令牌作 bearer、自定义授权服务器元数据地址、授权码交换前校验授权响应的签发者、渐进式授权请求已授予与缺失权限的并集、以及用客户端 ID 元数据文档替代动态客户端注册。项目级 MCP 配置里不带连接信息的条目只覆盖同名全局 server 的启用、暴露与工具暴露策略, 便于在受信任项目里开关全局 server。

### 6.3 内置工具与 codemode

内置工具是 read、write、edit、bash (加 powershell、find、grep、ls), 配套文件变更串行化、输出累积、截断与路径处理。工具注册进统一注册面, 因此扩展可以包装、替换或动态生成工具。

codemode 是最特别的内置扩展: 它是沙箱化的 JavaScript 执行环境, 能力被限定为调用注入的工具与运行非 LLM 模型, 脚本本身不直接触达文件系统或网络。实现依赖编译到 WASI 的 QuickJS 做隔离。设计意图与"用代码代替连续工具调用"一致: 让模型写一段脚本批量编排工具, 而不是每个动作一轮对话。脚本经 `models` 绑定可列出聊天、图像与分类三类模型, 但聊天模型只能列出、不能从脚本运行; 真正可执行的是分类与图像生成两类非 LLM 调用, 它们共用同一个在飞调用上限 (默认 4), 单脚本超量的调用自动排队。脚本输出有两级约束: 软预算按 token 计 (默认 10000, 可用脚本首行的 options 注释调整), 超预算时保留首尾、把完整文本落到临时文件并在结果里给出路径; 硬上限则是失败线——文本加 base64 图像数据超过约 1677 万字符, 或 text()/image()/console 调用超过 10 万次, 脚本直接失败, 打印循环无法耗尽宿主内存。

### 6.4 权限模型与容器化

安全文档的表述非常直接: Pi 没有内置权限系统来限制文件系统、进程、网络或凭据访问, 默认以启动它的用户与进程的权限运行; 项目 trust 只控制加载哪些项目资源, 不做工具调用沙箱。启用的工具使用进程的操作系统权限, 扩展就在该进程内执行。

需要更强边界就容器化, 文档给出四种模式:

1. Gondolin 扩展: Pi 与 provider 认证留在宿主机, 内置工具与 shell 命令路由进本地 Linux micro-VM。
2. 纯 Docker: 整个 Pi 进程跑本地容器, 简单隔离。
3. Docker Sandboxes: 托管沙箱, provider 凭据留在宿主机并由代理替换, 不把真实 key 暴露给容器。
4. OpenShell: 整个 Pi 进程跑在策略控制的沙箱里, 对文件系统、进程、网络与凭据施加策略。

此外根仓库还带一个沙箱运行时依赖与一个沙箱示例扩展。可以看出沙箱能力全部外置为可选层, 与内核最小化是同一取向。

## 七、适用场景与边界

### 7.1 适用场景

- 希望把 Agent 嵌进自己工具链的团队。TypeScript SDK 暴露的就是 CLI 自己用的会话、资源加载器与运行时, 依赖注入面完整, 示例随仓库类型检查, 因此嵌入成本低且不易被内部改动打断。
- 需要长期可回溯的交互式编码。entry 树加 active branch 的模型让"回到更早的分支继续"不影响历史; 压缩只替换模型可见视图, 原始 entry 保留。
- 需要严格崩溃恢复的自动化。durable 的"先提交再展示"与原子提交不变量, 适合把 Agent 放进无人值守流程。
- 多形态部署。同一套会话机制支撑 TUI、打印、JSON 事件、RPC 与 SDK, 另有 server/worker/presentation 的三段形态服务远程客户端。
- 需要广覆盖模型通道。统一 provider 面与生成式模型目录让"接一个新模型服务"成为数据而非代码工作。

### 7.2 边界与未完成项

- 权限边界全靠外置。没有内置沙箱时, 工具调用与扩展拥有与 Pi 进程相同的操作系统权限; 处理不可信文件、仓库、扩展或无人值守自动化前必须先读安全文档并选择容器化模式。
- durable 与 client/server 是实验性接口, 声明会随版本变动; client/server 的树导航、next-run 队列、子代理会话暴露与 transcript 历史分页都还没有实现, durable TUI 也尚未覆盖会话列表、fork 与树导航、扩展、提示模板与图片。
- 内核最小化是双刃剑。默认不带 sub-agent、plan mode 等能力, 用户需要自己组合或安装扩展; 大量示例扩展示范了可能性, 但也意味着这些能力的成熟度取决于生态而非内核。
- 贡献门槛高。新贡献者的 issue 与 PR 默认自动关闭, 维护者按质量复查后决定是否重开; 这降低了维护噪音, 也提高了外部参与成本。
- 两条安装通道的安全级别不同。官方安装器从生成的安装锁文件装传递依赖并钉死它们, 而直接经 npm 全局安装不会钉死传递依赖; 文档明示这一差别, 迁移建议也由此而来。

### 7.3 值得借鉴的工程点

1. 树形会话模型: entry 带 parent 指针的 JSONL 树加 active branch, 分支不删历史, 压缩只是视图层替换——比线性消息数组加截断保留了更多可回溯性。
2. 最小内核加分层资源阶梯: 从指令文件到 package 每层复杂度递增, 文档明确引导用户从最弱机制开始, 把"该用哪一层"变成可讨论的工程问题。
3. SDK 与 CLI 同源: 嵌入方拿到的是 CLI 自己用的会话、资源加载器与运行时, 依赖注入完整, 示例随仓库类型检查, 因此 Agent 也能自我解释自己的工作原理。
4. durable 的提交不变量: 原子提交、无易失发布路径、外部副作用移出事务、存储错误即致命——这套约束是"进程死掉能续跑"可验证的原因, 而不只是口号。
5. 供应链加固成体系: 精确版本、发布年龄门槛、全链路忽略脚本、传递依赖钉死与 lifecycle script allowlist, 每条都针对真实的包投毒攻击面。
6. codemode 把"模型写代码编排工具"关进只暴露注入工具与非 LLM 模型的沙箱, 是 code mode 思路的轻量实现; 输出硬上限让沙箱不会因打印循环而失控。
7. fail-closed 与可移植并存: 存储核心不依赖 Node API, 便于换运行时; 而存储错误直接判定为致命, 避免"看起来成功但状态不明"的持久化。
