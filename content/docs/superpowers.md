Superpowers 是一套面向编码 Agent 的软件开发方法论, 其本体不是运行时或 CLI, 而是一批可组合的 markdown 进程文档 (技能) 加上少量粘合代码。它把"Agent 应该怎么干活"写成技能, 再通过每个宿主自己的会话启动事件强制注入模型上下文, 让方法论在用户不做任何特殊操作的前提下自动生效。本文要回答的是这套东西由什么构成、为什么可以这样构成、各条机制具体怎么实现, 以及它在什么场景下成立、在什么条件下不成立。读者最好已经了解至少一个编码 Agent 宿主 (Claude Code、Codex、Cursor 等) 的工作方式, 并对 TDD、代码评审这类工程实践有基本认识。

与同目录的 [OpenSpec](openspec) 不同, Superpowers 不定义文件协议, 也不提供校验器; 它的核心资产是行为规范文本与把它们送进模型上下文的注入器。

## 一、Superpowers 是什么

### 1.1 构成: 技能加注入器, 没有自己的运行时

从实现角度看, Superpowers 由三个可分离的部分组成:

1. 技能: `skills/` 下的 15 个目录, 每个含一个 `SKILL.md`, 是全部宿主逐字共享的单一事实来源。技能正文只描述动作, 例如"invoke a skill"、"read a file"、"dispatch a subagent"、"create a todo", 从不写死具体工具名。
2. 工具映射: 把动作词表翻译成宿主真实工具名的参考文件, 位于 `skills/using-superpowers/references/<harness>-tools.md`, 或内联在宿主的 bootstrap 注入器里。
3. bootstrap 注入器: 每个宿主一份, 在会话开始时把 `skills/using-superpowers/SKILL.md` 全文包进 `<EXTREMELY_IMPORTANT>` 标签注入上下文, 并附上工具映射。

仓库里没有任何 Superpowers 自己的进程在运行。bash/JS/TS/Python 代码只承担"把 markdown 送进上下文"和少量可视化辅助两类职责。因此它的失效模式不是崩溃, 而是注入没发生——此时磁盘上的技能文件是死的, 模型不会主动去读一个它不知道存在的目录。

### 1.2 四条哲学与对应的强制机制

方法论的四条原则不是口号, 每一条都有一个技能把它落成不可绕过的流程:

```text
Test-Driven Development  永远先写测试
Systematic over ad-hoc   流程优于猜测
Complexity reduction     简单是首要目标
Evidence over claims     声明成功之前先验证
```

| 原则                    | 承载技能                         | 强制手段                                                       |
| ----------------------- | -------------------------------- | -------------------------------------------------------------- |
| Test-Driven Development | `test-driven-development`        | Iron Law: 没有失败测试就不许写生产代码, 先写的代码必须删掉重来 |
| Systematic over ad-hoc  | `systematic-debugging`           | 四阶段根因流程, 未完成根因调查不许提修复方案                   |
| Complexity reduction    | `writing-plans`、`brainstorming` | YAGNI、计划只记录决策不抄代码、按"最小可独立测试交付物"切任务  |
| Evidence over claims    | `verification-before-completion` | 证据必须产生于当前这条消息内, 否则不得声明通过                 |

这套"强制"不靠代码拦截实现, 而靠提示文本的行为塑造: 1% 规则、反合理化清单、HARD-GATE 审批语义 (见第三节)。因此它的可靠性上限取决于技能文本的质量, 这也解释了为什么仓库把大量精力投入到写作方法学与压力测试上。

### 1.3 与 OpenSpec 的定位对比

两者都在解决"需求只存在于聊天记录时, 编码助手会自信地构建错误的东西", 但切入的层面不同:

| 维度     | OpenSpec                                        | Superpowers                                                               |
| -------- | ----------------------------------------------- | ------------------------------------------------------------------------- |
| 本质     | 协议层: 目录约定 + CLI 校验器 + artifact 体系   | 方法论层: 注入模型上下文的进程文档 + 宿主插件粘合层                       |
| 对齐载体 | 文件 (proposal/specs/tasks), 人和 AI 审阅同一份 | 对话流程 (审批门 + 计划评审), 文件是流程的产物                            |
| 交付物   | `openspec/` 目录, 归档即真相源                  | `docs/superpowers/specs/` 与 `docs/superpowers/plans/` 下的设计与计划文档 |
| 执行方式 | 交给任意 AI 工具按 tasks.md 实施                | 自带两种执行器: 每任务新子代理加评审, 或本会话内联加终审                  |
| 质量保证 | schema 校验 (关键词、场景计数)                  | 过程纪律 (Iron Law、证据引用 path:line、验证门)                           |

两者正交: OpenSpec 管 "agreement 长什么样", Superpowers 管 "agent 怎么干活"。Superpowers 的 spec/plan 文件体系本身是一套轻量 spec-driven development 产物, 只是校验靠技能内建的自审清单和评审子代理完成, 没有独立 CLI。

## 二、为什么把流程写成技能并强制注入

### 2.1 三个被反复观察到的失效模式

Superpowers 的设计动机可以还原为对真实会话的归纳:

1. 模型会跳过流程直接动手。面对"帮我做个 X", 模型倾向于立刻写代码, 而不是先确认 X 到底指什么。
2. 上下文压缩会冲掉方法论。长会话发生 compaction 之后, 之前注入的规则被挤掉, 行为随即退化。
3. "写在文档里"不等于"模型会读"。把方法论放进 README、写进项目 markdown, 模型不会主动加载它——除非它知道该文件存在且被要求读。

第一点对应技能的内容设计, 第二、三点对应注入机制的设计。移植指南的表述是: bootstrap 就是整个集成, 没有它技能文件是惰性的。

### 2.2 技能是行为塑造代码, 不是文档

仓库把 `SKILL.md` 当作需要测试的行为塑造代码来对待, 而不是给人看的说明。最直接的证据是 description 的写法: 技能 frontmatter 的 `description` 只写"何时使用", 绝不概括"做了什么"。这源于一次真实事故——某技能的 description 曾写了工作流摘要, 结果模型只执行了摘要里提到的那一次动作, 而技能正文要求的其实是两阶段流程。结论被写进技能写作规范: 概括流程的 description 会成为模型跳过正文的捷径, 正文于是退化成没人读的文档。

这条约束对任何给 Agent 编写工具或技能描述的场景都适用, 也是本文认为最值得迁移的一条经验。

### 2.3 bootstrap 技能本体: using-superpowers 的装置构成

`skills/using-superpowers/SKILL.md` 篇幅很短, 但每一段都是行为塑造装置:

- `<SUBAGENT-STOP>` 块: 被派发执行具体任务的子代理跳过 bootstrap。这防止 worker 重启 controller 的工作流 (头脑风暴、审批循环)。因为注释只靠模型自觉, 后续在 OpenCode 等用结构化信号 (会话是否带 parentID) 做了双保险。
- `<EXTREMELY-IMPORTANT>` 块与 1% 规则: 只要认为某个技能有 1% 可能适用, 就必须调用; 适用即无选择权, 不允许用"合理化"绕开。
- The Rule: 在任何回应或行动之前先调用相关技能, 包括提澄清问题、探索代码库、查看文件之前; 调用后宣告 "Using [skill] to [purpose]"; 技能有 checklist 则每项建一个 todo。
- Skill Priority: 多个技能适用时 process skills 先行——"Let's build X" 路由到 brainstorming, "Fix this bug" 路由到 systematic-debugging。
- Red Flags 表: 一组"合理化借口对现实"的对照, 例如把"这只是个简单问题"对应到"问题也是任务, 要检查技能"。这张表本身是反合理化装置, 依据来自技能写作方法学。
- Platform Adaptation: 指向各宿主的工具映射参考文件。
- 用户指令优先级链: 用户指令文件 (AGENTS.md/CLAUDE.md/GEMINI.md) 与直接要求高于技能, 技能高于默认行为; 只有用户明确要求时才跳过技能工作流。

### 2.4 注入链路: session-start 的三形状输出

shell-hook 形态的宿主共用 `hooks/session-start` 脚本, 逻辑链路是:

1. 从脚本自身路径推导插件根 (`SCRIPT_DIR/..`), 不依赖宿主注入的环境变量。
2. 读取并原样携带 `using-superpowers/SKILL.md` (含 frontmatter), 读取失败回退为错误字符串。
3. 用 bash 参数替换做 JSON 转义 (反斜杠、引号、换行、回车、制表符), 注释说明这比逐字符循环快几个数量级。
4. 组装注入文本: `<EXTREMELY_IMPORTANT>` 包裹的 using-superpowers 全文, 前面加一句说明"这是你的技能系统入口, 其余技能用 Skill 工具"。
5. 按环境变量检测平台, 输出三种互斥的 JSON 形状之一。

| 检测条件                                                                 | 输出形状                                                                    | 消费方                 |
| ------------------------------------------------------------------------ | --------------------------------------------------------------------------- | ---------------------- |
| 设置了 `CURSOR_PLUGIN_ROOT` (排最前, 因 Cursor 可能同时设置 Claude 变量) | 顶层 `additional_context` (snake_case)                                      | Cursor                 |
| 设置了 `CLAUDE_PLUGIN_ROOT` 且非 Copilot/Muse                            | 嵌套 `hookSpecificOutput.hookEventName=SessionStart` 加 `additionalContext` | Claude Code 及兼容宿主 |
| 设置了 `MUSE_PLUGIN_ROOT`                                                | 同 Claude 式嵌套                                                            | Muse                   |
| 其他 (Copilot 或未知平台)                                                | SDK 标准顶层 `additionalContext`                                            | GitHub Copilot CLI 等  |

互斥是硬约束: Claude Code 会同时读 `additional_context` 与 `hookSpecificOutput` 且不去重, 所以每个平台只能输出它消费的那一个字段, 否则要么不注入要么双重注入。脚本用 `printf` 而非 heredoc 输出, 以规避 bash 5.3+ 的 heredoc 挂起问题。

注册配置因宿主而异, 两套 schema 并存:

- `hooks/hooks.json` (Claude Code 及兼容宿主): SessionStart 的 matcher 为 `startup|clear|compact`, 即会话启动、`/clear`、上下文压缩后三种事件都重新注入——这直接针对"compaction 冲掉方法论"的失效模式。命令声明 `"shell": "bash"`, 在 Windows 上强制走 Git Bash。
- `hooks/hooks-cursor.json` (Cursor): 完全不同的 schema——`version: 1`、小写 `sessionStart` 键、相对路径命令, 没有 matcher/type/async 字段。

### 2.5 polyglot hook 分发器与 Windows 降级

`hooks/run-hook.cmd` 是一个 cmd/bash 双语文件: 第 1 行用 shell 语法把整个 batch 段当作 no-op heredoc 吞掉, Windows `cmd.exe` 则执行 batch 段。Windows 段依次探测常见的 Git Bash 安装路径与 PATH 上的 bash, 找到就用 bash 执行目标脚本并透传参数; 找不到 bash 则静默退出——插件仍可用, 只是没有 SessionStart 注入, 属于优雅降级而非报错。

被分发的脚本刻意不带扩展名 (名为 `session-start` 而非 `session-start.sh`): 某些宿主对任何 `.sh` 命令会自动前置 bash, 反而破坏分发器自身。仓库还用 `.gitattributes` 强制全部脚本使用 LF 行尾, 避免 Windows 下 CRLF 破坏 shell 脚本。

## 三、技能体系: 分类与触发方式

### 3.1 技能清单与分类

`skills/` 下恰好 15 个技能, 按职能分为四类:

| 分类          | 技能                                                                                                                                                                                                        |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Testing       | test-driven-development                                                                                                                                                                                     |
| Debugging     | systematic-debugging、verification-before-completion、diagnosing-superpowers                                                                                                                                |
| Collaboration | brainstorming、writing-plans、executing-plans、subagent-driven-development、dispatching-parallel-agents、requesting-code-review、receiving-code-review、using-git-worktrees、finishing-a-development-branch |
| Meta          | using-superpowers、writing-skills                                                                                                                                                                           |

其中多数技能带附属文件: 重型参考文档、提示词模板 (供派发子代理时逐字使用)、可执行脚本 (通过解释器调用, 避免被打包器剥掉可执行位)。

### 3.2 触发与路由机制

技能路由依赖两层信息: 宿主按技能元数据 (name 加 description) 做匹配, 模型按 description 里的"何时使用"判断是否加载。因为加载技能本身有 token 成本, 仓库刻意让 description 只写触发条件。

进入会话后, 触发顺序由技能内的路由规则决定:

- process skills 先行。诊断类、规划类技能先于实现类技能。
- 硬门阻断。brainstorming 里定义 HARD-GATE: 任何实现动作 (写产品代码、脚手架、装依赖) 之前必须完成所选路径的前置审批。规则强调"对想法的批准不等于批准还不存在的 artifact", 且审批只允许推进到下一阶段。
- 反合理化。每个技能都带 Common Rationalizations 或 Red Flags 表, 把"这太简单了不用走流程"这类借口逐条对应到现实。这类文本来自对真实失败会话的归纳, 并通过技能写作方法学的压力测试验证有效。

### 3.3 主干工作流七步

方法论的主干流程, 每一步由一个技能的自动触发点串起来:

```text
1. brainstorming        写代码前激活: 提问细化想法、探索备选、分节呈现设计、保存设计文档
2. using-git-worktrees  设计批准后: 建隔离工作区, 跑项目 setup, 验证干净测试基线
3. writing-plans        拿到批准的设计后: 拆成带文件路径、接口签名、验证步骤的任务
4. subagent-driven-development  拿到计划后二选一
   或 executing-plans            (每任务新子代理加评审, 或本会话内联加终审)
5. test-driven-development      实现期间: 强制红绿重构, 先于测试写的代码删掉重来
6. requesting-code-review       任务之间: 对照计划评审, Critical 阻塞推进
7. finishing-a-development-branch  完成后: 验证测试、呈现集成选项、清理 worktree
```

### 3.4 协作类技能的设计要点

brainstorming。核心目标是把想法经对话变成可被用户识别并纠正的设计, 成果定义为"一份你的伙伴能认出来并修正的理解"。它用三路径路由器在提问之前先给请求分类, 并大声说出分类以便用户否决:

| 路径          | 判定                                 | 流程重量                                                   |
| ------------- | ------------------------------------ | ---------------------------------------------------------- |
| Spike         | 可行性问题, 允许快速粗糙             | 几句话呈现问题加探针, 点头即可; 无设计文档无 spec          |
| Bounded       | 对仓库中已存在代码的良界变更         | 聊天内短设计加 STOP, 明确同意后才实现; 无 spec 文件        |
| Architectural | 新项目、新子系统、改动他人依赖的接口 | 全流程: 提问、方案对比、分节设计、书面 spec、writing-plans |

棘轮是单向的: 拿不准时取更重的路径, 任务中途发现隐藏复杂度就升级, 绝不降级; "bounded 意味着你要改的流程已经在代码里可读", 而 bounded 的批准与 architectural 的批准一样硬。过大项目先拆成子项目, 每个独立走 spec、plan、implementation。

using-git-worktrees。原则是"先检测既有隔离, 再用宿主原生工具, 最后回退到 git, 绝不与宿主对抗"。原生 worktree 工具优先, 因为在无原生工具时用 `git worktree add` 会制造宿主看不见也管不了的幻影状态; 回退路径要求创建前用 `git check-ignore` 确认目录被忽略, 防止把 worktree 内容意外提交进仓库。

writing-plans。计划保存为 markdown, 读者画像是"没见过这个代码库、也没看过这份 spec 的工程师"。计划只记录执行者无法独自做出的决策: 用哪些文件、哪些名字与签名、spec 里哪些值、哪些测试证明每个任务。关键构件包括: 任务定义前先映射文件与职责; 任务按"承载自身测试循环、值得一个陌生评审者把关的最小单元"切分; 每个任务写明 Consumes/Produces 的确切接口, 因为实现者只看到自己的任务; 计划头的 Review Focus 列出 spec 隐含但无任务测试覆盖、最可能伤到用户的输入或失败模式。判据是"计划是执行者无法独自做出的决策集合; 描述长于它描述的代码, 就说明计划已经把代码写了出来"。

subagent-driven-development。全库最复杂的技能, 原则是"每任务新子代理加任务评审加宽终审"。子代理绝不继承会话上下文, 由 controller 精确构造所需上下文。几个有代表性的设计:

- 执行纪律: 叙述至多一行; 任务之间不向人类请示; 冲突与歧义由 controller 裁决并记账, 格式为"决定、理由、判断错的代价"; 只有不可逆操作、安全敏感动作、约定需先问的副作用、计划糟糕到每条路都是猜测时才停下。
- ledger: 每个计划一个 workspace, ledger 文件是对抗 compaction 的恢复地图, 记录任务完成、裁决与延期的次要问题。首行指明所属计划, 避免不同计划共享进度。
- 任务循环: 派发实现者 (生成任务简报文件, 把精确值只放进简报, 禁止把累积历史贴进派发提示) 后处理四种报告状态; 再派任务评审者 (同时给出 spec 合规与代码质量两个裁决, 输入是简报、报告与 diff 文件); 有 Critical 或 Important 时进入 fix loop, 每任务最多五轮, 前几轮恢复原实现者, 后续换更强模型; 触顶时逐条裁决而不是继续循环。
- 成本工程: 每个角色用能胜任的最弱模型, 每次派发都显式声明模型 (缺省继承会话模型等于全用最贵); 注意回合数常常比 token 单价更贵; 工件以文件传递, 避免提示膨胀。
- 终审与收尾: 全分支一次宽评审, 用最强模型; 收尾前把所有裁决行按顺序收集进最终消息的清单, "一个随 workspace 一起消失的裁决, 是一个秘密做出的决定"。

executing-plans。本会话内联执行的 Native 模式, 与 SDD 共享同一 workspace 与 ledger 格式, 因此一个计划可以在执行中途换执行器并从同一 ledger 续跑。它放弃每任务新上下文, 用别的手段补回: 简报即 spec, ledger 即记忆, TDD 是每任务的门, 终审是第二双眼睛。它强调"看着测试失败是一个步骤而不是形式"——实现存在之前就通过的测试是关于测试本身的发现。

评审两端。requesting-code-review 规定何时评审、如何取基线、如何派评审子代理, 并明确两条反合理化: 协调者不要自己 inline 评审 diff (会烧上下文), 不要给评审者会话历史 (让它面对工作产品而非你的思考过程)。receiving-code-review 则管反馈的接收纪律: 先读、再理解、再对照代码库验证、再评估、再回应、最后逐项实现; 禁止社交表演式回应 (感谢、"你说得对" 之类), 任何一项反馈不清楚就停下问清全部再动手; 外部评审者的建议要实现前先验证是否适用本库, 与本项目架构冲突时用技术推理推回。

finishing-a-development-branch。顺序是验证测试、检测环境、呈现选项、执行选择、清理。菜单必须逐字呈现, 集成决策属于用户; 丢弃工作只在明确请求时发生, 且要求键入确切的确认词; 只有当 worktree 位于约定的 `.worktrees/` 或 `worktrees/` 目录下时才由 Superpowers 负责清理, 否则宿主环境拥有该工作区。

dispatching-parallel-agents。用于 2 个以上无共享状态、无顺序依赖的问题域, 典型场景是并行调试。关键机制句是"同一条响应里的多个派发调用等于并行执行; 每条响应一个等于串行"。它与 SDD 的边界很清楚: SDD 禁止并行实现者 (任务共享代码库会冲突), 本技能只用于独立问题域。

### 3.5 质量类技能

test-driven-development。Iron Law 是"没有失败测试就不写生产代码", 违反字面规则即违反精神。红绿重构循环里有两个标注为强制的验证步骤: 确认测试因功能缺失而失败 (直接通过说明在测既有行为, 报错说明测试本身要修), 确认本次测试通过且项目套件仍全绿且输出干净。测试范围也有明确规定: "其他测试"指项目套件而不是你自己的文件——任务里的范围界定限定交付物, 不限定验证范围。

systematic-debugging。Iron Law 是"未完成根因调查不许提修复"。四阶段依次为: 根因调查 (完整读错误、稳定复现、检查近期变更、在组件边界收集证据、沿数据流上溯到源头); 模式分析 (找同库可工作的相似代码、完整读参考实现、列举每一个差异); 假设与验证 (单一假设写下来、最小改动一次一个变量、失败就换新假设而不是叠加修复); 实现 (先建失败测试、只修已定位根因、修复连续失败三次则质疑架构而非继续试)。附属技术文档覆盖调用链回溯、纵深防御、基于条件的等待 (用条件轮询替代任意延时) 与污染源定位脚本。

verification-before-completion。证据门: 声明完成、修复或通过之前, 必须在本条消息内跑过验证命令并读完输出。"跳过任何一步等于撒谎而不是验证"。它为七类常见声明分别划定证据标准, 例如"测试通过"要求本次命令输出零失败, "构建成功"要求退出码为零 (linter 通过不算), "回归测试有效"要求走完红绿循环 (通过一次不算), "子代理已完成"要求看 VCS diff 而不是采信报告。

### 3.6 元技能 writing-skills

`writing-skills` 是整个方法论自举的支点: 写技能就是给流程文档做 TDD——test case 是压力场景, production code 是 `SKILL.md`, RED 是无技能时代理违规, GREEN 是有技能时遵从, REFACTOR 是堵漏洞保持遵从。它的 Iron Law 是"没有失败测试就不写技能", 同样适用于对既有技能的编辑; 写完技能必须走完部署流程, 禁止批量创建而不逐个测试。

技能写作规范的要点:

- 技能是可复用的技术、模式或参考, 不是"某次如何解决问题的叙事"。
- 是否创建看三条: 技术不显然、跨项目会再引用、他人受益。用正则或校验就能强制的东西应当自动化, 文档只留给需要判断力的地方。
- SKILL.md 结构骨架: Overview 核心原则、When to Use、Core Pattern、Quick Reference、Implementation、Common Mistakes、可选 Real-World Impact。
- 技能发现优化: description 只写何时用; 覆盖错误消息、症状、同义词、工具名; 动词开头的描述性命名; 控制 token 长度, 细节移入参考文件; 用显式的 REQUIRED SUB-SKILL 标记交叉引用, 避免会立即强制加载文件的链接语法。
- 文体要匹配失败类型: 压力下违规用禁令加合理化表; 输出形状不对用正面配方; 漏掉必备元素用结构化模板槽位; 行为按条件变化用可观察谓词绑定。
- 措辞微测协议: 全压力场景测试慢且贵, 先做措辞级实验——每次一个新鲜上下文样本, 永远带无指导对照组, 每变体多次重复, 人工读每个命中, 用方差判断措辞是否真的绑定行为。仓库引用的一项实证表明, 说服技巧可以显著提高遵从率; 但同一批实验也显示, 禁令式措辞在某些场景下并不优于正面配方, 因此文体选择被当作经验问题而非教条。

## 四、多 harness 适配架构

### 4.1 三个组成部分与两条规则

移植指南把多宿主架构拆成三个组件: 宿主无关的技能、每宿主的工具映射、每宿主的 bootstrap。配套两条铁律:

1. 移植永远不改 `skills/*/SKILL.md` 正文, 唯一允许的改动是在平台适配指针列表加一行。技能被视为精心调校的行为塑造代码, 为"合规"改写它会被拒绝。
2. 一切通过宿主自己的安装机制投递, 绝不改用户的全局或个人配置文件。如果安装机制装不下 bootstrap, 那是一条要上报的限制, 而不是手改用户配置的许可。

硬性验收标准只有一条: 宿主必须能在每个会话开始时自动注入, 不允许任何"每会话手动 opt-in"。干净会话发送一句"Let's make a react todo list", brainstorming 必须在写任何代码前自动触发。

### 4.2 三种集成形态

| ------------------------- | ----------------------------------------------------------------- | -------------------- | --------------------------------------------------------------------------- |

形态可组合: 技能发现机制与 bootstrap 机制可以是不同形态, 但两者都必须走宿主自己的安装机制。

能力清单用于判断一个宿主能否被支持: 自动会话启动注入是硬要求; 技能发现与调用若无原生工具, 官方认可的回退是直接读 `SKILL.md`; 文件读写、shell 是必需; 子代理派发、todo、web 可降级; Windows 多语脚本仅 shell 形态需要。指南还提醒: 有些"新宿主"其实就是现有集成的另一个安装器, 仓库可能一行代码都不用加。

### 4.4 Shape B 参考实现

OpenCode (JS)。插件自研迷你 frontmatter 解析器以避免额外依赖; 维护两套工具映射常量以兼容 V1 与 V2 两代 API (V2 没有 todo 工具, 改用 markdown 计划文件, 子代理调用形态也不同)。几个工程要点:

- bootstrap 内容模块级缓存。上下文钩子在每个 agent step 都会触发, 不能每步读盘解析。
- 子会话检测。bootstrap 驱动的是 controller 工作流, 注入到子代理会话会让 worker 重启设计循环; 因为技能里的 `<SUBAGENT-STOP>` 只靠模型自觉, 插件改用结构化信号——会话记录带 parentID 即为子会话, 跳过注入 (技能注册保留)。查询失败时 fail-open 按顶层会话处理且不缓存。
- 逐技能 try/catch。技能注册接口的 schema 不符会同步抛出并逃逸回调, 宿主会把整个插件异步硬禁用, 连 bootstrap 一起拆掉, 因此每个技能的注册必须隔离失败。
- 注入用户消息而非系统消息, 以避免每轮重复的 token 膨胀和多系统消息破坏某些模型。

Pi (TS)。扩展用五个生命周期处理器编排: 发现资源时返回技能目录; 会话启动与压缩后置注入旗标; agent 结束清旗标避免每轮重复; 上下文事件在旗标为真且现有消息不含 bootstrap 标记时插入一条 user 消息。插入位置跳过开头连续的压缩摘要消息。工具映射处理 Pi 的能力缺口: Pi 有原生技能但没有 Skill 工具, 因此映射为"技能适用时用 read 读取 SKILL.md, 或由人类显式调用"; 无标准子代理工具时在会话内做或说明缺失, 明确禁止虚构工具调用。

Hermes (Python)。插件在注册时逐技能注册进原生加载器, 并用 `pre_llm_call` 钩子在第一轮返回注入内容 (该宿主的会话启动返回值被忽略, 注入消息接口在该钩子中被拒绝, 这两个结论都来自实测)。技能目录解析支持两种安装布局, 都找不到就抛错——注释强调"bootstrap 静默跳过会让坏安装伪装成好安装"。

### 4.5 声明式与上下文文件宿主

- Kimi: manifest 里三件事——指向现有技能目录、声明式会话启动技能、内联一整段工具映射说明。无技能拷贝、无符号链接、无 hook。
- Muse: 能力声明显式枚举全部技能, hooks 用数组形式直接调用同一个 session-start 脚本。
- Codex: manifest 指向技能目录, 并用字面量空对象显式关闭 hooks——缺失字段或空数组都会触发自动发现回退, 把 Claude 的 SessionStart hook 连带注册回来。
- Devin: manifest 是纯元数据, 没有任何能力字段; 宿主读 manifest 后自动发现同级技能目录, 并在会话开始时把技能元数据放进系统提示词。
- Gemini: manifest 声明 `contextFileName` 指向扩展自带的上下文文件, 文件内容是两条引用, 宿主原样加载。

### 4.6 工具映射 references

`skills/using-superpowers/references/` 下的文件把技能动作词表翻译到各宿主工具面, 覆盖读文件、写文件、替换、shell、搜索、抓取、技能调用、子代理派发、todo 等动作。Claude Code 是参考宿主, 其词汇表即工具面, 无需适配; 该文件只补充 SDD 的廉价编排说明 (controller 本身作为编排子代理跑在中档模型上端到端执行, 前提是宿主支持嵌套子代理)。其余文件各自记录宿主特有映射与限制, 例如某宿主的子代理派发需要显式开启多代理配置, 某宿主的任务跟踪用产物文件而非任务工具。

### 4.7 分发与 Windows

分发渠道按宿主而定: 原生市场、git URL 安装、包清单字段、本地安装器。两条安装器怪癖值得记录: 安装器会静默丢弃未声明文件 (bootstrap 必须声明为可识别组件), 打包器会剥掉可执行位 (因此技能行文一律用解释器调用脚本, 如 `bash scripts/tool.sh`)。

Windows 适配分三层: hook 层用 `shell: "bash"` 强制 Git Bash 路线并配 polyglot 分发器与无扩展名脚本; 可视化伴侣服务器在 Windows-like shell 下强制前台模式, 因为无法可靠验证进程存活性, 且浏览器启动经参数传递而非 shell 以避免命令注入; in-process 形态天然绕开 shell 脚本问题。

## 五、零依赖 visual companion 服务器

### 5.1 定位与使用判据

brainstorming 附带一个可选的可视化伴侣: agent 把设计问题写成 HTML 屏推到本地服务器, 用户在浏览器里点选, 选择经 WebSocket 回流成结构化事件供 agent 下一轮读取。它不是一种"模式"而是一件工具, 按问题逐题决策, 判据是"用户看到比读到更容易理解吗"。浏览器用于 UI mockup、架构图、并排视觉对比、空间关系; 终端用于需求范围、概念性选择、权衡列表、技术决策。

它采用 just-in-time 提供策略: 第一次出现"展示比描述更清楚"的问题时才提供, 且提供必须是独立消息; 用户拒绝后继续纯文本且不再主动提供。启动、推屏、读取事件、迭代构成一个六步循环, 终端反馈是主反馈, 事件是结构化交互数据。

### 5.2 server.cjs 的实现思路

服务器只用 Node 内建模块, 协议、认证、文件沙箱全部手写:

- WebSocket 协议自实现 RFC 6455 的握手与帧编解码, 包含掩码校验与单帧负载上限, 并有专门的协议单元测试直接导入其导出。
- 端口策略: 环境变量优先, 其次复用会话上次绑定的端口 (让已打开的浏览器标签自动重连), 否则随机高端口; 端口被占用时一次性回退随机端口, 但若 token 来自显式环境变量则拒绝回退直接退出, 防止抢走持有首选端口的另一会话。
- 认证是安全核心: 每会话生成随机 token, 随 URL 查询参数下发, 首次加载镜像进按端口命名的 cookie; 每个请求用常数时间比较校验 token, 失败返回拒绝; WebSocket 升级需同时通过 token 认证与 Origin 检查。
- 文件沙箱: 只接受 basename, 拒绝空名、dotfile、非普通文件; 检查非符号链接、硬链接计数为一、真实路径位于内容目录内; MIME 白名单; 所有响应带安全头 (禁用 referrer、禁止缓存、禁止被嵌入)。

设计注释解释了为什么用 key 而不是 Host/Origin 白名单: key 统一覆盖环回、隧道、远程三种绑定, 并能击败 DNS rebinding。

### 5.3 生命周期与 PID 所有权

服务器在空闲超时或所有者进程死亡时退出。watchdog 周期性检查所有者进程是否存活 (无法验证时视为存活); 启动时若所有者进程已死 (某些跨用户或远程场景 PID 解析错误), 则禁用监控、只靠空闲超时。

停止脚本的核心是"确认 PID 属于本会话才发信号": 启动脚本把会话实例 ID 写入状态文件并传给 node 进程, 停止脚本用进程命令行精确匹配该 ID, 任何歧义都按失败处理并视为陈旧 PID。这防止服务器重启后 PID 回卷误杀无关进程。清理时只有临时会话目录才删除, 持久目录保留供回看 mockup。

### 5.4 浏览器端

注入浏览器的脚本导出纯函数供测试, 负责: 从会话存储读取 key 构造 WebSocket 地址; 断线指数退避重连; 断连超过阈值显示"已暂停"覆盖层; 恢复后用带 key 的地址重载以刷新 cookie; 捕获带选择标记的点击并发送结构化事件; 提供显式 API 供页面调用。外框模板提供明暗主题、连接状态指示与一组可直接使用的组件样式 (选项、卡片、并排对比、优缺点列表、线框元件)。

品牌区默认从远程加载一张带版本号的图片, 仅用于粗略估计用户量与版本分布, 查询参数只带版本; 设置任一禁用遥测的环境变量即切换为纯文字品牌且零远程请求。

## 六、证据化诊断流程

### 6.1 定位与职责边界

`diagnosing-superpowers` 是元技能, 用于会话表现异常时 (技能该触发没触发、无视计划、重复工作、token 消耗离谱) 产出带证据的报告。它完全由提示词模板驱动, 没有脚本。

核心原则是"每个发现都引用 path:line, 没有引用就没有发现; 每个数字都来自 transcript 或你运行过的命令, 绝不来自记忆"。职责边界刻意收窄: 它只报告, 不诊断 Superpowers 本身, 也不提议修改——报告出来后由分诊者决定 Superpowers 是否要改, 用户施压也不例外。

### 6.2 七步工作流

1. 问题受理: 一次一问, 直到能写出问题陈述 (点名会话、轮次范围、期望、实际、关心的可观察量); 记录目标是否是 bug 报告。伙伴不在场就把问题写下来并停住, 因为"替对方重建出来的陈述不是答案"。
2. 定位: 把会话解析为经验证的绝对路径, 身份确认要求会话 ID、工作目录、时间戳、内容匹配共同成立; 列出全部被拒候选及原因; 枚举子代理记录; 建工作区并登记发现的记录语义。
3. 分诊: 先亲自读被报告问题附近的区域, 再按七个维度并行派发分析子代理。
4. 报告: 按模板逐节填写并展示路径。
5. 提交 issue: 仅在报告判定相关或用户要求时, 先搜既有 issue, 填好模板并展示确切文本, 批准后才创建。
6. 导出: 仅在用户索要时, 询问脱敏级别, 用脱敏代理加独立审计代理的循环直到审计通过, 展示脱敏日志与文件清单后再归档。
7. 相似会诊: 被要求时把确认的发现转成签名, 在历史会话中并行检索并追加报告。

### 6.3 七个分析维度

| 维度              | 找什么                                                                                                      |
| ----------------- | ----------------------------------------------------------------------------------------------------------- |
| skill-timeline    | 逐人类轮的技能使用记录, 把请求文本与已装技能的触发条件比对, 报告调用了的、匹配但未调用的、迟到的            |
| plan-adherence    | 恢复会话商定的计划, 标记计划与执行之间的结构事件, 逐步映射跳过、乱序、静默修改、臆造与结构事件后的漂移      |
| repeated-work     | 把工具调用抽成键值分组计数, 区分编辑后重读 (不算)、压缩后重读 (算) 与无事重读                               |
| stumbles          | 所有停止前进的点: 错误与非零退出、同轮重试、被回滚的编辑、人类纠正、权限拒绝、hook 失败、限流、任务中途压缩 |
| quality-evidence  | 用会话自己的声明审判过程: 每次测试运行及结果, done/fixed/passing 声明在同轮内向前找支撑                     |
| request-conflicts | 抽取每条人类提示的指令, 报告互斥的人类指令、人类指令与指令文件的冲突、要求跳过步骤的指令及后果              |
| cost-and-time     | 只按给定语义解读用量记录, 报最长轮次与事件间隙、最大工具结果、压缩计数与定位, 不推测原因                    |

每个分析子代理只读、不改文件、不评 Superpowers, 返回固定结构 (发现、带绝对路径与短引文的证据、轮次、置信度), 没发现也要返回明确的"未发现"。

### 6.4 脱敏与导出

脱敏策略定义了一组占位符 (邮箱、人名、组织、密钥、主机、home 路径、仓库名、专有名词), 保留会话 ID、工具名、技能名、相对安装根路径、模型 ID、宿主版本与行号, 因为"没有它们这份 bundle 就没用"。两条原则值得单独指出: 某条记录涉密不代表命令或结果全部涉密; 如果脱敏移除了某个发现的支撑, 就记录受影响的发现与限制, 绝不为通过证据检查而保留敏感值。

上下文安全应对"一条记录可达兆字节"的情况: 读任何文件先测量, 绝不整文件输出, 先取行号与计数再取小字段, 单条输出超限就收紧。脱敏代理重写 bundle 内每个文件并记录占位符计数 (绝不写明文映射), 独立审计代理全文查找漏网内容, 只有无遗漏且无未决分类才返回干净。

## 七、测试与质量体系

### 7.1 两层分工

仓库把测试分成两层: `tests/` 测插件的非 LLM 代码是否正确 (bash 加 node 加 python 的集成测试); eval 测 agent 在真实 LLM 会话中的行为。技能行为测试不再放在 `tests/` 里, 而是走独立的 eval harness, 按需克隆 (仓库显式忽略该目录)。eval harness 在 tmux 里驱动真实的编码 Agent CLI, 由 LLM 扮演用户并按场景验收标准与确定性后置检查评判技能遵从。风险分层很清楚: 单个场景耗时长且真实会话跑在宽松权限下, 因此只有静态检查适合公共 CI, 真实会话扫描放在夜间或按需运行。

### 7.2 基础设施测试覆盖

`tests/` 下的目录按被测对象划分, 常见的模式是 bash 自带的通过/失败计数器加 trap 清理临时 fixture, 用 python 逐字段断言 JSON manifest, 用 node:test 或手写 runner。覆盖面包括:

- 可视化伴侣服务器: 协议单元测试、浏览器端逻辑、认证、品牌、生命周期、启停脚本的 PID 所有权。
- 各宿主注入器: hook 在三形状下的输出互斥、注册形状必须声明 bash、分发器正确派发; OpenCode 的 bootstrap 缓存与会话判定; Pi 扩展的处理器契约; Hermes 的注入路径与 bootstrap 大小上限。
- manifest 断言: 逐字段检查各宿主的插件清单, 包括确认 Codex 的 hooks 恰为空对象、Devin 清单不含能力字段、Kimi 的声明式启动与内联工具映射。
- 版本与发布工程: 版本位点同步脚本在 fixture 仓上的行为、shell lint 的收集与过滤。
- 结构化静态检查: 诊断技能只做 frontmatter、被引用文件存在性、不泄漏本地路径与个人信息、措辞约束等检查, 行为测试在仓库外的场景 eval 里。

### 7.3 行为测试与真实 CLI

需要真实模型判断的部分走真实 CLI 加输出字符串断言, 并保留少量 bash 测试补 eval 未覆盖的场景 (例如统计提交数、子代理派发次数、token 用量)。这类测试每个文件头都注明保留理由, 断言库对大小写不敏感, 因为模型会随意大写技能术语。一个反复出现的经验是: 同一个 prompt 变体要多次重复, 单样本会说谎; 对照组不可或缺。

## 八、适用场景与边界

### 8.1 适用场景

- 需要长时自主执行的中大型功能开发。主干流程从 brainstorming 到 subagent-driven-development 把"人类只做决策、Agent 连续执行"变成有门禁、有账本的过程。
- 多人或多 Agent 协作的工程。ledger、Rulings 清单、completion contract 解决的是"工作随上下文一起丢失"和"裁决死在参与者记忆里"这两类协作失效。
- 对交付质量而非速度敏感的场景。强制 TDD、每任务评审、终审、证据门都会增加成本; 计划里明确写了每任务新上下文与新评审者是最彻底但也最贵的选项。
- 需要把方法论分发给多种宿主。三形态适配架构与单一技能来源让同一套内容可以在十几个宿主上逐字运行。

### 8.2 边界与前提

- 它不是运行时。没有 CLI、没有守护进程, 全部效果取决于注入是否发生、模型是否遵从技能文本以及宿主能力是否够用; 子代理、todo、web 等能力缺失时相应技能降级。
- 强制是软的。审批门、Iron Law、证据门都由提示文本驱动, 没有代码级拦截; 遵从率通过措辞实验与压力测试提升, 但不能保证。
- 成本与纪律正相关。每任务新子代理加评审、终审用最强模型、显式声明模型分档都是成本工程, 但在小改动上这套流程明显过重, 三路径路由器与 spike/bounded 路径正是为此设的降级通道。
- 宿主差异是持续的维护负担。hook schema、JSON 字段、工具名、Windows shell 行为各不相同, 且宿主会变; 因此描述机制的不变量比描述具体实现更耐久。
- 诊断能力只报告不裁决。它能产出带证据的会话分析, 但明确不判断方法论本身是否有缺陷, 也不提议修改。

### 8.3 可借鉴的设计

1. bootstrap 注入模式: 方法论必须在会话开始事件 (含 clear 与 compaction 后) 强制注入, 而不是写在文档里指望模型去读。三形状互斥输出、每步触发的去重守卫、压缩后重注入、用结构化信号识别子会话而非依赖模型自觉, 这套注入器工程可以直接借用。
2. description 只写何时使用: 概括流程的描述会成为模型跳过正文的捷径。这条对任何给 Agent 编写工具或技能描述的场景都成立。
3. 证据纪律: "无 path:line 引用即无发现"、"新鲜验证"、"回归测试自身要过红绿循环"、"数字要么从记录里算出来要么是编的", 把 Agent 的输出验收从主观判断变成可检查的形式要求。
4. 反合理化设计: Red Flags 表、Common Rationalizations 表、"违反字面即违反精神"的表述、审批门只推进一阶段的语义, 全部来自对真实失败会话的归纳, 并有压力测试方法论支撑。
5. 措辞微测协议: 对照组、每变体多次重复、人工读命中、方差作指标, 是一套可直接复用的提示工程实验方法。
6. fail-closed 工程: PID 所有权校验、评审包的范围守卫 (空 diff 视为错误而非"评审干净")、插件逐技能隔离失败、脱敏双代理审计, 统一原则是"任何歧义按失败处理"。
7. 成本工程: 显式声明模型、注意回合数常比 token 单价更贵、工件以文件传递防提示膨胀、按每计划建 workspace 防恢复取证开销——这套子代理编排的成本手册与计划执行器实现同等重要。
