本文拆解一个自托管即时通讯平台: 单聊与群聊、WebRTC 音视频通话、分块断点续传文件传输, 并为每个登录用户内嵌一个完整的 AI coding agent 作为一等聊天参与者。内容覆盖数据模型、WebSocket 聊天枢纽、消息投递语义、通话信令、文件传输协议、缓存降级、Agent 的进程内运行时与 RPC 桥, 以及客户端的工程化组织。适合要做自托管 IM、或在既有产品中嵌入 Agent 的工程师阅读, 也适合作为"实时系统与长生命周期 Agent 如何共处一个进程"的参考。

## 定位与整体形态

### 能力边界

平台同时覆盖五类能力: 账号体系与权限管理; 联系人、群组、会话与富消息(文本、图片、文件、音视频信令通知); WebRTC 音视频通话(服务端只做信令); 大文件的分块上传与断点续传; 每用户一个内嵌 Agent, 支持工具执行、MCP、权限确认与计划模式。Agent 不是"调一次补全接口", 而是以库形式嵌入服务进程的完整 coding agent, 能读写文件、执行命令、在需要时向用户请求授权。

### 整体架构

```text
   React SPA ──HTTP POST(统一信封 JSON)──> Hono 应用: routes -> services -> Prisma -> PostgreSQL
   Zustand + Query                             │
```

### 运行时形态

服务端是纯 Node.js 进程: 入口先创建三个静态目录(头像、普通文件、分块临时目录), 再组装依赖包, 确保内置的 Agent 账号存在, 启动聊天枢纽与 Agent 管理器的定时器, 最后构建应用并监听端口。默认监听 `0.0.0.0:8000`, 开发态用 `tsx watch` 运行, 生产态构建后直接 `node` 启动。

依赖通过一个 `Deps` 接口集中注入路由: 数据库、缓存、通话管理器、聊天枢纽、五个业务服务(会话、用户、联系人、群组、消息)以及 Agent 管理器。没有全局单例, 便于测试时替换实现, 也让进程退出时可以按依赖顺序统一释放。

进程退出时的清理顺序是: 释放全部 Agent 运行时、停止心跳定时器、关闭 Redis、断开数据库连接。

### HTTP API 面

所有 HTTP 路由均为 POST, 按业务域分组:

| 分组      | 代表端点                                                          | 备注                     |

| 用户管理  | 用户列表、启用、禁用、批量删除、设管理员                          | 需管理员                 |
| 群组      | 建群、邀请入群、退群、解散、搜索群等                              | 部分端点需管理员         |
| 会话      | 打开会话、拉单人/群会话列表、标记已读、删除会话、校验是否允许打开 |                          |
| 联系人    | 申请好友、通过申请、拉黑、打标签、更新联系人等                    |                          |
| 消息      | 单聊/群聊历史、上传文件、上传头像                                 |                          |
| 分块上传  | 校验、上传分块、合并                                              | 见文件传输章节           |
| 聊天室    | 在线用户、通话成员                                                | 通话成员带房间可见性校验 |

### WebSocket 通道

| 通道            | 用途                     | 鉴权                                                     |
| --------------- | ------------------------ | -------------------------------------------------------- |
| `/wss`          | 消息、在线状态、通话信令 | query token 验签; 若带 `client_id` 则须与 token 主体一致 |
| `/agent/ws`     | Agent 的 JSON-RPC 流     | query token 验签                                         |
| `/dashboard/ws` | 管理员缓存看板推送       | query token 验签 + 管理员校验                            |

浏览器无法在 WebSocket 升级请求上添加自定义请求头, 因此 token 只能走 query。`/wss` 额外校验客户端自报的 `client_id`: 非空时必须与 token 主体一致, 否则握手直接回 403。动机是安全——若信任客户端自报的 id, 任何知道他人 uuid 的人都能顶掉其连接并接收消息。`/agent/ws` 与 `/dashboard/ws` 只认 token, 后者再叠加一次管理员校验。

### 中间件

- 鉴权: 只拦 POST, 登录、注册、改密三个公开路径直通; Bearer token 验签后把用户主体写入请求上下文。
- 限流: 每个中间件实例维护一张"IP 到时间戳数组"的滑动窗口表, IP 取 `X-Forwarded-For` 首段或套接字地址; 登录与注册各 10 次/分钟, 改密 5 次/分钟。
- 管理员: 查缓存或数据库中的管理员标记。
- CORS: 全放开并处理预检。

## 线协议与响应封装

### 全 200 加 body code

所有 HTTP 接口(含错误)一律返回 HTTP 200, 真实状态放在响应体的 `code` 字段: `{code, message, data?}`。服务层返回二元组或三元组, 由封装函数翻译: 成功码映射为 200, 参数类错误映射为 400, 其余映射为 500。这么做的取舍是: 前端只需解析一次响应体, 不必为每个业务错误分别处理 HTTP 层语义; 代价是丢失了 HTTP 状态码的通用语义, 网关与监控不能按状态码聚合错误率。

### 空列表与零值语义

两个刻意的约定值得单独说明, 因为它们是稳定的线协议契约:

1. 空数组在成功响应里统一改写为 `null`。客户端用对称的 `wireList()` 转换(`z.array().nullish().transform(v => v ?? [])`)在解析时还原为 `[]`。这样做的原因是序列化层希望区分"字段不存在"与"空集合", 而消费端统一拿到数组, 两边各做一次归一化。
2. 请求体解析采用零值语义: 只接受 JSON 对象, 字段缺失或类型错误一律回落零值(字符串归空串、数字归 0、字符串数组归空数组), 不做逐字段报错。需要区分"未传"与"传空"的字段额外走可空变体。

这套语义让消息管线与路由层可以用统一方式处理线上传输的原始整数与可能缺失的字段, 而不必为每种组合写防御代码。

## 认证与授权

### 手写 JWT

平台不依赖现成 JWT 库, 而是用 HMAC-SHA256 手拼 `header.payload.signature`: header 是固定的原始 base64url 字节, 签名用 `createHmac("sha256")`, 验签用恒定时间比较以防时序攻击, 并校验主体非空与过期时间。claims 只有主体、签发时间、过期时间三项, 有效期默认 336 小时(14 天), 没有 refresh 机制——token 过期后只能重新登录。

手写的收益是零依赖与完全可控的字节布局; 代价是任何自定义扩展(如密钥轮换、多种算法)都要自己实现, 且必须持续关注实现是否踩到规范边界。

### 口令哈希

口令用 bcrypt 哈希, cost 为 10, 并显式拒绝超过 72 字节的口令——这是 bcrypt 算法的输入长度上限, 超过部分会被静默截断, 显式报错可以避免"看似更长的口令其实等价"的误解。

### 已知安全缺口

改密接口免鉴权、按手机号重置密码, 这是刻意的重置流程(没有邮件或短信验证环节), 属于已知缺口: 公网暴露前必须补齐验证步骤。它仅有按 IP 的 5 次/分钟限流作为缓解。此外 JWT 无 refresh 意味着泄露的 token 在 14 天内持续有效。

## 数据层与缓存

### 数据模型

数据库定义八个模型。每张表都带一个自增整数物理主键 `id`, 但业务层互相引用的一律是 `uuid` 列: 聊天实体的 `uuid` 是带前缀的 12 位随机串(前缀加 11 位随机字符, 62 字符表), 前缀即路由语义——收件人 id 以 `U` 开头走单聊分支, 以 `G` 开头走群聊分支。用带前缀的字符串标识而非自增整数, 一方面避免跨表协调, 另一方面让业务层仅凭 id 前缀就能选择分发路径。唯一的例外是 AgentSession, 它直接以数据库生成的 UUID 作主键, 并以 `userId` 唯一约束保证每用户一行。

| 模型         | 要点                                                                                                                                                                                                |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| UserInfo     | 主体唯一; 手机号索引作为登录凭据; 状态与管理员用整数线路值; 记录最近上线/下线时间                                                                                                                   |
| Session      | 每用户每对端一行, 以拥有者视角存储; 软删除; 最后已读时间驱动未读计数                                                                                                                                |
| Message      | 冗余发送者昵称与头像以省去 JOIN; 送达状态; 通话信令以 JSON 存在独立字段                                                                                                                             |
| GroupInfo    | 成员用数据库原生数组; 入群模式分直接进群与需审批两种                                                                                                                                                |
| UserContact  | 双向联系人边, 状态覆盖正常、拉黑、被拉黑、删除、被删除、免打扰、退群、被踢                                                                                                                          |
| ContactApply | 好友与入群申请, 状态覆盖申请中、通过、拒绝、拉黑                                                                                                                                                    |
| ContactTag   | 联系人标签, 注册时默认创建 "Friends" 标签                                                                                                                                                           |
| AgentSession | 每用户一行; 对话上下文与激活技能以 JSON 存快照, 另存权限模式与最近活跃时间; 状态是六值数据库枚举(IDLE/RUNNING/WAITING/COMPLETED/ABORTED/FAILED), 取用会话行时残留的 RUNNING/WAITING 一律复位为 IDLE |

聊天域的状态与类型列刻意保持整数而不改成数据库枚举: 线路上传输的就是原始整数, 这些取值(如联系人状态的 0 到 7)是承重墙, 一旦改成枚举就会引入序列化层的不一致; 枚举只用于 Agent 内部状态。消息类型常量为: 0 文本、1 图片、2 文件、3 音视频信令、4 视频、5 系统通知, 客户端镜像同一组常量。

Agent 的交互(权限请求、提问)完全不落库, 只活在内存 broker 里: 交互是瞬态的人机往返, 重启后重放旧交互没有意义, 落库反而要处理过期数据的清理; 内存 broker 配合握手时的快照重放, 语义更干净。数据库侧只有 AgentSession 一张表承载 Agent 状态。

### 缓存: 两个读穿组

缓存服务使用两个读穿组: 用户信息组(按主体缓存用户投影, 不含口令与删除标记)与会话列表组(按拥有者缓存会话行)。双实现结构如下:

| 实现        | 启用条件                   | 行为                                                                                        |
| ----------- | -------------------------- | ------------------------------------------------------------------------------------------- |
| RedisStore  | 配置了 `REDIS_URL`         | key 加 `yukino:cache:<组>:<键>` 前缀, 另维护索引集合与元信息哈希供看板枚举; TTL 默认 300 秒 |
| MemoryStore | `REDIS_URL` 为空串(如测试) | 进程内实现, 无外部依赖                                                                      |

Redis 实现的读写一律用 try/catch 吞掉异常: 故障时降级为缓存未命中, 数据库始终是唯一事实源。这个原则很重要——对 IM 这类强一致读场景, "缓存不可用即失效"比"缓存不可用就报错"体验好得多。会话列表的读穿发生在加载会话时; 失效点包括打开会话、删除会话、标记已读、群会话批量触及等, 一律按拥有者整体失效。消息管线在解析发送者昵称与头像时也先查用户信息组缓存。

### 数据访问的稳健性

需要区分两类"缺失": 用户不存在与网络故障。缓存吞错策略把两者都归为未命中并回落数据库, 因此数据库层必须能明确表达"查不到"。此外, 消息表冗余发送者昵称与头像, 是为了让历史消息列表在发送者资料变更后仍能展示当时的信息, 同时避免每次渲染列表都做 JOIN。

## WebSocket 聊天枢纽

### 连接管理

聊天枢纽维护"用户主体到连接"的映射, 每个用户至多一条连接。三个生命周期动作值得展开:

注册。同一主体的旧连接会被安全关闭, 这是"顶号登录"语义。新连接先收到一帧纯文本欢迎消息。只有在非顶号替换(不存在旧连接)时才向其他在线用户广播上线通知并异步更新最近上线时间; 顶号场景不重复广播在线状态, 避免同一用户被反复标记上线。这个细节能显著减少推送噪音。

心跳。服务端用 30 秒定时器扫描, 超过 90 秒没有任何帧的连接直接注销; 一个周期内没收到 pong 的连接直接终止。客户端无需实现应用层 ping, 服务端使用协议层 ping/pong, 并监听底层 pong 事件刷新存活标记。

注销。若该用户还在通话中, 代其向房间剩余成员广播离开信令, 保证对端关闭死流; 随后广播下线通知并更新最近下线时间。

系统通知用定向推送: 构造一帧 `{type:5, send_id:"SYSTEM", content:topic}`, topic 覆盖联系人、群组、申请、会话、在线状态五类, 语义是"该列表脏了, 请重新拉取", 帧本身不携带数据。把"变更通知"与"数据拉取"分离, 让实时通道只负责失效信号, 数据一致性仍由 HTTP 接口保证。

### 消息管线

消息管线是实时通道全部入站帧的处理器, 设计为单消费者串行链:

1. 串行化。所有帧经一条 Promise 链顺序处理; 链深度超过 1024 时回发溢出帧 `{type:-1, content:"message send failed, please retry"}`, 让客户端重试而不是无限堆积。
2. 帧解析。采用 JSON 零值语义: 缺失的字符串字段取零值, 只有类型错误才拒绝整帧; 类型必须是整数。
3. 防伪。请求中的发送者字段被强制覆写为连接属主的主体, 昵称与头像从缓存或数据库重取, 客户端无法冒充他人。
4. 持久化。普通消息(类型非 3)先写消息表, 失败即静默返回。
5. 会话触达。单聊消息保证双方各有一行未删除的会话(软删的自动恢复); 群聊消息批量保证每个成员都有群会话行。也就是会话行是消息投递的副产物, 自动创建或恢复。
6. 扇出。计算目标集合: 单聊为接收者加发送者回显, 群聊为全体成员含发送者; 逐个检查是否在线后发送。至少送达一人且非信令帧时, 把消息状态置为已送达并记录送达时间。
7. Agent 分发。收件人是内置 Agent 时进入 Agent 分发路径。

这套顺序保证了一个重要性质: 持久化先行, 扇出在后。即使扇出阶段所有目标都离线, 消息也已落库, 离线用户上线后靠会话列表的未读计数与历史接口补齐, 不依赖实时通道的可靠性。

### 客户端帧分派

客户端的帧分派规则与上面的语义一一对应:

- 不是以 `{` 开头的帧(欢迎文本)直接忽略。
- 溢出帧弹提示。
- 类型 3(信令)先于系统帧分派给信令监听器, 因为通话失败会以"系统发送者加类型 3"的复合形态到达。
- 发送者为 SYSTEM 的类型 5 帧按 topic 查表, 使对应的 React Query key 整支失效。
- 其余消息帧以 uuid 去重后追加进已缓存的会话记录; 未打开过的会话不写缓存, 避免"伪造的 fresh 状态"抑制真实拉取。

连接生命周期上, 客户端采用指数退避重连(1 秒起步翻倍, 上限 30 秒), 重连成功后全量失效查询缓存; 连接由顶层组件跟随登录主体建立与断开。

## WebRTC 音视频

服务端不理解 WebRTC, 只把类型 3 消息的信令字段当作 JSON 信封路由。信令形状为 `{messageId, type, media, room_id}`: 当 `messageId` 为 `PROXY` 时表示服务器要介入房间生命周期, 为 `PEER_LEAVE` 时表示对端断连, 其余(sdp、candidate)纯转发。

### 服务端信令解释

通话管理器只有两张表: 房间到成员集合, 以及用户到房间(每用户至多一个房间, 即"忙"状态)。房间 id 派生规则保证两端算出同一个值: 群聊直接用群主体, 一对一用排序后的双方 id 组合, 客户端逐字复刻同一算法。

| 帧                            | 服务端动作                                                                                                         |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `PROXY/start_call`            | 校验对端在线且不忙(群聊则筛出在线空闲成员), 主叫入房, 向被叫转发邀请; 任一失败向主叫回失败帧与原因; Agent 直接拒绝 |
| `PROXY/receive_call`          | 一对一接听: 被叫入房并转发给主叫, 主叫收到后创建 offer, 以约定消除 glare                                           |
| `PROXY/join_call`             | 群聊接听: 新人入房, 只通知房间既有成员, 每人与新人单独建连                                                         |
| `PROXY/reject_call`           | 一对一拒接: 房间全员释放并转发; 群聊拒接是纯本地行为, 客户端不发帧                                                 |
| `PROXY/leave_call` / 对端离开 | 挂断: 释放并返回剩余成员转发; 若被叫未接听而主叫已挂, 补发帧关闭来电弹窗                                           |
| sdp / candidate               | 点对点原样转发, 收件人指向单个对端, 不广播                                                                         |

只有开始、接听、拒接三种信令会落库为消息, 供聊天记录保留通话痕迹; 客户端渲染历史时把类型 3 全部过滤。断连兜底由聊天枢纽的注销流程负责(见上文)。查询通话成员的接口返回房间内除自己外的成员, 并做可见性校验: 必须处于该房间内、或属于自己参与的一对一房间、或是群成员。

### 客户端 mesh 拓扑

客户端的通话管理器持有一张"对端到连接"的映射, 每个连接是一条 `RTCPeerConnection` 加一个聚合远端轨道的媒体流——群聊是全网状拓扑, 没有 SFU。几个关键细节:

- 创建连接对象时不带任何配置, 也就没有 STUN/TURN 服务器。ICE 只能靠 host candidate, 跨 NAT 的场景无法打通, 适用于局域网或同机部署。这是定位为自托管内网工具的自觉取舍, 而非疏漏。
- 信令复用聊天通道: 把房间与信令数据塞进类型 3 帧的信令字段。sdp 与 candidate 的收件人必须指向单个对端, 若误发群 id 会把一个人的 offer 泄露给全体成员。
- glare 消除靠角色约定: 一对一由主叫在收到接听回执后发起 offer, 群聊由既有成员向新人发起, 发起方始终唯一。
- candidate 竞态: 远端描述尚未就绪时, candidate 先进入队列, 设置远端描述后统一冲刷。
- 连接状态为失败即丢弃该对端; 一对一唯一对端消失即整场结束, 群聊则继续。
- 携带房间 id 且与当前房间不符的迟到帧直接忽略, 防止跨通话串台。

UI 层维护 `空闲/振铃/拨号/通话中` 状态机, 拨出 45 秒无应答自动挂断; 信令监听在模块加载时全局订阅, 因此任何页面都能响铃。通话弹窗渲染本地与远端视频瓦片、静音与挂断按钮以及计时, 对端数大于 0 即进入通话中并记录接通时刻。

## 分块断点续传文件传输

### 协议

服务端提供三个端点, 构成"校验、上传分块、合并"的状态机:

- 校验。入参为文件哈希、扩展名、分块总数。先看最终文件是否存在, 存在则直接返回已上传与访问地址(秒传); 否则逐个探测分块目录中的分块文件, 返回缺失下标数组。断点续传的服务器状态就是磁盘上已存在的分块文件集合, 没有任何数据库记录。
- 上传分块。multipart 表单, 服务端用正则白名单校验哈希为 8 到 64 位十六进制、扩展名为 1 到 10 位字母数字, 单块上限 10 MiB, 写入以哈希命名的目录。
- 合并。按序号排序拼接全部分块, 写出最终文件后删除分块目录。中途读失败会删除半成品最终文件, 避免被截断的文件在后续校验中被误判为秒传; 最终文件已存在时直接返回成功, 因此合并是幂等的。

最终文件以内容寻址命名(哈希加扩展名), 同内容天然去重, 经静态文件路由公开访问。由于哈希与扩展名都过了正则白名单, 路径穿越的攻击面被压掉。

这个设计的优雅之处在于"无数据库状态机": 分块目录即进度, 校验即查询, 合并在磁盘上完成。代价是依赖本地磁盘, 多实例部署时校验与合并必须落在同一实例(或共享存储)。

### 客户端: worker 哈希加并发限流

客户端分块上传的参数经过精心选择: 分块大小 5 MiB, 是服务端上限的一半, 留出 multipart 编码开销的余量; 并发分块数 3, 用信号量限流; 每块重试 3 次并线性退避; 总大小上限 2 GiB。

哈希在 Web Worker 中计算, 逐 5 MiB 切片做 SHA-256, 再把所有分片摘要拼接后做第二次 SHA-256 得到最终值。这样做的动机是 Web Crypto 没有增量摘要 API, 一次性哈希 2 GiB 需要整块 ArrayBuffer 驻留内存; 分片二次哈希把内存占用钳制在一个切片大小。哈希进度经消息通道回报, UI 分"哈希中"与"上传中"两段进度显示。

完整流程是: 哈希 -> 校验 -> 秒传则直接返回 -> 只上传缺失的分块(刷新页面后重选同一文件, 已上传分块不再传) -> 合并 -> 返回访问地址、文件名与大小。全链路穿透中止信号, worker 收到中止即终止。

上传成功后按 MIME 派生消息类型(图片走图片类型, 视频走视频类型, 其余走文件类型)并以帧发送。此外保留传统的单请求上传端点用于普通文件与头像: 普通文件上限 50 MiB, 头像上限 5 MiB 且扩展名白名单为常见图片格式; 落盘用流式管道避免大文件整体进内存, 存储名加随机前缀防碰撞, 并对文件名做清洗——剥掉路径分量只保留安全字符集。

## 每用户内嵌 Yukino Agent

这是平台与纯 LLM 聊天应用的本质区别: 集成的不是"调用补全接口", 而是完整的 coding agent(工具执行、MCP、权限、计划模式、上下文压缩), 以库的形式嵌入服务进程而非子进程, 每用户一个运行时, 工作区独立, 空闲后回收。

### 配置发现

Agent 配置按两级回退加载:

1. 首选库的标准配置: 读取用户级配置, 其次工作目录下配置, 允许 provider 列表为空; 取出第一个 provider、MCP 服务器列表、钩子与权限模式。
2. 无配置文件时用环境变量合成单 provider(协议默认走 OpenAI 兼容), 地址或模型为空则返回 `null`。
3. `null` 表示"Agent 不可用": 聊天主流程完全不受影响, 用户私聊 Agent 会收到一条"未配置"的聊天回复。

配置在进程内缓存一次, 因此运行期改配置需要重启。

### AgentManager: 注册表加聊天落库

Agent 管理器维护"用户到运行时"的懒创建映射, 每个用户的工作区独立。空闲回收由 60 秒定时器扫描: 既不在忙、连接数为 0、且空闲超过阈值(默认 30 分钟)就释放。

最关键的设计是消息汇点: Agent 的最终文本回复经"写消息表加枢纽广播"走与人类对端完全相同的路径, 发送者取内置 Agent 账号——于是助手消息天然获得历史记录、会话预览与未读计数, 刷新后依然存在。这正是"Agent 是一等聊天参与者"在实现上的落点: 它不维护自己的消息视图, 而是复用人类对端的那条链路。

分发入口只接受文本帧, 非文本消息回复一句固定提示; 群聊刻意不接入, 因为多人群聊里 Agent 的工具执行与权限交互无法清晰归属。账号接线在启动时完成: 确保内置保留账号存在(固定主体、名字与签名); 注册与登录时幂等地建立双向联系人边与会话行, 且该会话不可删除。

### AgentRuntime: 队列、回合与再水化

每个用户的运行时是长生命周期对象, 首次使用时创建或复用数据库中的会话行, 创建工作区目录, 并构造完整 Agent 栈句柄(客户端、会话、注册表、上下文窗口、团队与后台任务管理器等), 用 Promise 缓存防止并发重建。

再水化与持久化采用"数据库为唯一事实源"的策略: 从数据库的上下文 JSON 恢复对话, 并过滤掉可再生的系统提醒包裹消息, 防止跨重启累积; 每回合结束把消息快照写回数据库。构造底层 Agent 时显式禁用库自身的 JSONL 会话写入, 避免出现两套持久化。上下文窗口上限由 provider 配置决定, 每回合透传; 主动压缩通过斜杠命令触发, 与库的自动压缩共用同一份会话与恢复状态。

提示队列是单 worker 串行消费, 队长超过上限(默认 8)时向所有连接推送"仍在处理更早的消息, 请等待"的系统通知并丢弃。串行化的意义在于: 一个用户的多个提示若并发执行, 工具执行与文件修改会互相踩踏, 排队是正确性要求而非性能取舍。

回合执行的流程是: 斜杠开头走命令分支; 否则先通知回合开始, 追加用户消息, 同步 MCP 指令, 每回合新建权限检查器与全新的底层 Agent 实例, 然后用 `for await` 消费事件流交适配器翻译, 在收尾块中保存上下文。斜杠命令覆盖帮助、清空对话、强制压缩、在默认与只读计划两种权限模式间切换。取消通过中止控制器触发并让交互 broker 拒绝所有挂起交互; 销毁是幂等的, 会保存上下文、断开 MCP、停止后台任务与团队、并以正常关闭码关闭所有连接。

### EventAdapter: 事件流到 RPC 通知

事件适配器是每回合有状态的翻译器, 把库的事件映射成 RPC 通知或落库动作:

| 库事件              | 产出                                                 |
| ------------------- | ---------------------------------------------------- |
| 流式文本            | 累积进内部缓冲, 同时发瞬态通知(不落库)               |
| 思考文本与思考完成  | 对应的瞬态通知                                       |
| 工具调用            | 先冲刷已完成的文本块落库为聊天消息, 再发工具调用通知 |
| 工具结果            | 工具结果通知(输出、是否错误、耗时)                   |
| 回/循环完成         | 冲刷文本, 发完成通知(回合数、耗时、停止原因)         |
| 用量/错误/压缩/重试 | 对应通知; 取消引发的错误被吞掉                       |

冲刷的落库动作是: 取走累积文本, 经消息汇点写入消息表并广播, 再发流结束通知, 其中的消息 id 成为客户端后续 overlay 的锚点。语义即"流式增量是瞬态的, 完成的文本块每块冲刷成一条持久聊天消息"。

### InteractionBroker: 人机回环

工具权限与提问走交互 broker: 请求返回 Promise, 把 resolver 存入映射, 超时(默认 5 分钟)后 fail-closed——权限超时视为拒绝, 这与"不确定就拒绝"的安全默认一致。快照方法让重连的客户端立刻重放所有挂起提示, 因此网络抖动不会让权限卡悬空。权限请求由运行时的回调发起: 生成人类可读的工具动作描述, 推送权限请求给全部连接, 然后等待 broker。

## Agent 的 JSON-RPC 桥

### 服务端协议

RPC 桥使用 JSON-RPC 2.0 词汇。方向约定是不对称的: 服务器只推通知(无 id), 客户端只发一元请求(带 id), 客户端发的通知被静默忽略。这个单向性简化了状态机——客户端永远不需要实现请求路由。

握手流程: token 验签, 获取或创建运行时, 依次推送连接就绪通知(含模型、流式状态、就绪标记、锚点、token 用量、权限模式)、命令清单通知、以及 broker 快照中全部挂起的权限与提问。运行时创建失败(未配置)时回一条错误通知而不中断连接, 因此前端可以稳定地显示"Agent 不可用"。

客户端可调方法: 保活应答、权限响应(允许、拒绝、始终允许)、提问响应、会话取消。未知方法返回标准错误码, 参数不合法返回参数错误, 响应类方法返回 `{applied: boolean}`, 其中 `false` 表示 id 未知或已过期。入站帧上限 4 MiB。

### 客户端 agent store

客户端的分工可以浓缩为一句话: 提示词与已完成的回复走聊天通道, RPC 通道只承载聊天记录无法表达的东西——流式气泡、思考过程、工具卡片、等待中的权限与提问卡。

- 连接: 进入助手会话时建立, 离开即断开; 指数退避重连(1 秒起步, 上限 30 秒); 每次重连都以空 overlay 开始, 因为"进度只有依附于它所属的聊天记录才有意义"; 每 10 秒发一次保活请求防止代理因闲置而断连。
- 重连的丢数据窗口由两个机制兜住: 落库回复经聊天通道与 HTTP 历史重新取回, 挂起的权限与提问由握手时的 broker 快照重放, 于是交互类状态不会因断连而悬空。
- 状态机把通知折叠成一条带锚点的 item 时间线: 回合开始把锚点设为用户消息 id; 流式与思考通知增量拼接当前流式项; 流结束把流式项定格并绑定落库消息 id, 锚点前移; 工具调用对同名同 id 的重复公告去重(参数只在第二次公告到达); 循环完成或出错时把未答的权限与提问卡定格, 防止死卡常驻。
- 系统与错误行做去重: 与上一条完全相同即丢弃, 防止重连风暴刷屏。
- 响应请求是 fire-and-forget: 发出即本地更新卡片状态, 不等 `{applied}` 回执。

### 转录与 overlay 的缝合

聊天页把 Agent 的 item 按锚点缝进消息流: 以落库消息的 uuid 集合为基准, 锚点命中的 item 归入按锚点分组的 overlay, 经气泡组件的"之后渲染"回调渲染在该气泡之后; 未命中的进尾部 overlay 渲染在列表末尾。流式气泡的交接是零闪烁的: 一旦某个流式项绑定的消息 id 出现在落库集合中(即聊天通道已把落库消息推来), 该 overlay 项被跳过, 由真实消息气泡接管。

助手会话的输入器关闭附件上传(服务端对非文本也只回一句话), 流式期间显示停止按钮接会话取消, 斜杠命令菜单由命令清单通知驱动。item 渲染覆盖六类: 流式文本(复用消息渲染组件并带光标)、思考(可折叠)、工具(按工具名映射图标, 参数预览取首个非空键, 输出截断 5000 字符)、单行提示(按语义取图标)、权限卡、提问卡。

## React 客户端工程化

### 请求层与数据获取

- HTTP 封装: 对统一信封做 zod 校验; 普通请求 15 秒超时、上传 120 秒, 用超时信号与调用方信号合并, 允许业务侧主动中止; 业务码 401 时清空认证并跳转登录; 错误对象携带业务码, 网络错误统一为 -1。
- 查询客户端: 全局 `staleTime` 30 秒, 关闭窗口聚焦重取; 重试策略区分故障类型——后端明确拒绝的业务错误不重试, 仅传输层错误重试至多 2 次; mutation 缓存挂全局错误提示。
- 查询键按域分层, 聊天通道的系统帧按域整支失效。
- 把幂等的"打开会话"POST 当查询用(设置静态 `staleTime`), 借助查询缓存做请求去重, 避免重复打开同一会话产生多余写请求。
- 全部响应 zod 化, 空列表按前述约定还原, 头像在转换阶段把空值与默认值替换为生成头像。

### 状态分域

| store       | 持久化         | 职责                                                 |
| ----------- | -------------- | ---------------------------------------------------- |
| auth        | sessionStorage | token 与用户信息; 按标签页隔离登录态                 |
| preferences | localStorage   | 记住手机号(需跨标签页存活, 因此不随会话存储一起失效) |
| ws          | 无             | 主聊天连接、帧分派、重连                             |
| call        | 无             | 通话状态机, 桥接通话管理器                           |
| agent       | 无             | Agent 的 RPC 时间线                                  |
| dashboard   | 无             | 缓存看板快照, 固定间隔重连                           |

选择 sessionStorage 存认证状态是一个刻意的隔离决定: 同一浏览器的不同标签页各自独立登录, 适合多账号调试, 也降低了 token 在多标签页间被共享的风险。

### 页面与 UI 要点

路由用 `createBrowserRouter`: 根路径由 loader 鉴权, 未登录重定向; 主框架布局下挂会话、联系人、资料、具体会话、管理端五个子路由; 缓存看板独立于主框架。登录与注册页在已登录时反向重定向。

- 消息渲染: 静态模式加公式、图表等插件。由于渲染器携带语法高亮与图表库、体积较大, 在气泡与 Agent item 中都单独懒加载成独立分块。
- 气泡列表: 日期分隔条、入场动画、贴底滚动, 配合前述的流式渲染策略。
- 输入器: 富文本编辑器关闭全部 mark 与输入规则, 让字面 markdown 原样入库、由渲染端还原; 回车发送、Shift 加回车换行、输入法组字过程中不发送; 斜杠命令菜单虚拟化, 键盘导航与悬停高亮分离; 拖拽上传在助手会话中干脆不挂载, 因为禁用它会让停止按钮也被读作不可用。
- 生成头像: 用 FNV-1a 播种的随机数发生器在画布上绘制 5x5 镜像格, 按用户名记忆化, 作为缺省头像。
- 命令面板: 用 cmdk 加 `mod+k` 热键, 仅在打开时才拉取数据。
- 主题: 类名策略加系统跟随; 表格虚拟化用 spacer 行保持真实表格语义。
- 表单: TanStack Form 加 zod(手机号正则、密码最少 6 位、昵称 3 到 10 位), 登录页含封禁检测与重置密码弹窗。

### PWA 与可观测性

- PWA 采用自动更新策略, workbox 预缓存脚本、样式、文档与字体, 并对外部字体走缓存优先策略。manifest 的 scope 与 start_url 在生产构建下指向 `/yukino-chat/` 子路径 (开发态为根路径), 而 Vite 构建的 base 保持默认根路径。当前 manifest 的名称字段是模板残留 (仍写作 resume), 与产品名不一致, 属于上线前需要修正的细节。
- [浏览器监控 SDK](yukino-sentry)仅在开发环境初始化, 配合构建插件的 mock 上报端点把报告落为本地 JSONL, 用于本地闭环调试; 生产构建使用隐藏式 source map 并自定义插件把映射文件挪出发布产物, 兼顾可反解与源码不外泄; 另有插件给样式与模块脚本注入高优先级抓取提示。
- 错误边界分两级: 根级组件边界包裹整个应用, 路由级边界展示路由错误。

## 管理端与缓存看板

管理端页面挂在主框架下并受管理员守卫: 用户表支持启用、禁用、批量删除、设管理员, 群组表支持状态控制与删除, 长表用虚拟化。缓存看板页面配独立 WebSocket: 服务端每 2 秒推送缓存快照, 包含两个组各自的键数与字节统计以及逐条的键、大小与过期时间; 客户端可发送删除指令删除指定缓存键; 页面用数字滚动动画呈现统计, 断线后按 3 秒固定间隔重连。

看板的实现细节体现了一个通用模式: 缓存服务除了存取, 还额外维护索引与元信息, 才能支撑"枚举全部键"这种管理面需求——很多缓存实现只做到 get/set, 无法回答"当前缓存里有什么"。

## 测试策略

单测覆盖四个模块: JWT 的往返、错密钥与畸形输入, 随机 id 生成与文件名清洗; 通话管理器的房间 id 派生、忙状态、离开返回剩余成员与空房解散; 事件适配器的流文本累积与工具调用触发冲刷、回合计数; 交互 broker 在假定时器下验证权限超时 fail-closed。

除单测外还有两个对运行中服务器的冒烟脚本: 一个以数十次请求覆盖注册、登录、错误路径、联系人、群组、会话、消息与管理守卫全流程, 末尾循环登录直到触发限流以验证按 IP 限流(刻意放在最后, 避免污染后续请求的限流桶); 另一个覆盖聊天通道的握手、在线状态、单聊与群聊扇出、顶号驱逐、通话失败、Agent 通道握手与私聊分发、看板通道。

测试设计上值得注意的是单测环境强制 `REDIS_URL` 为空, 从而走内存缓存且不触数据库——这让单测无需外部依赖即可运行, 也间接验证了缓存降级路径。

## 部署形态与已知约束

| 约束             | 说明                                                                                                                                                   |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 单实例           | 连接表、通话房间、消息串行链、Agent 运行时表、限流桶都在进程内存, 无跨实例总线                                                                         |
| 无 TLS           | 明文 HTTP/WS, 需前置网关终结                                                                                                                           |
| 改密无验证       | 免鉴权按手机号重置, 只有按 IP 限流, 公网暴露前必须加验证                                                                                               |
| 无 STUN/TURN     | WebRTC 跨 NAT 打不通                                                                                                                                   |
| 外部依赖自备     | PostgreSQL 与 Redis 由部署方提供; Redis 可选, 为空时降级进程内存                                                                                       |
| 默认连接串需覆盖 | `DATABASE_URL` 默认 `postgresql://root:pass@localhost:5432/yukino_chat`, `REDIS_URL` 默认 `redis://localhost:6379`, `JWT_SECRET` 默认一个写死的字符串  |
| 迁移不自动执行   | 建表靠 `prisma migrate deploy`(`pnpm db:deploy`), 服务进程启动时不做迁移                                                                               |
| 容器化不可用     | `client/Dockerfile` 与 `client/docker/` 仍按 Go 服务端编写(拷贝 `server/go.mod` 后 `go build`), 与当前 TypeScript 服务端不符; 仓库内没有可用的编排文件 |
| 声明未消费的依赖 | 对象存储与压缩库被声明但零引用, 属于预留                                                                                                               |
| 常量未接线       | 环境中定义了 Agent 通道的入站上限, 但路由使用本地常量, 该配置项无消费者                                                                                |

这些约束大多属于"内网自托管"定位下的自觉取舍: 单实例换来了极简的内存态设计与可预测的调试体验, 代价是无法水平扩展。若要做多实例, 需要先解决四件事: 把聊天扇出改为跨实例总线、把通话房间状态外置、把 Agent 运行时按用户做粘性路由或外置会话、把限流桶换成共享计数器。

## 适用场景与小结

这个项目的价值密度集中在三处工程设计:

1. 线协议语义保真。从 JSON 零值解析、空列表的 null 序列化, 到通道容量溢出帧, 全部作为稳定的线协议契约保留下来, 冒烟脚本因此有可靠的回归面。
2. Agent 与聊天的合流。落库回复走与人类消息完全相同的"插入加广播"路径, 流式过程走独立 RPC 通道以锚点与消息 id 和转录缝合, 断线重连靠 broker 快照重放挂起交互。"转录是事实、overlay 是过程"的分工让刷新、顶号、多端都不丢结果。
3. 断点续传的极简状态机。服务器状态就是分块目录里的文件集合, 校验返回缺失下标, 合并幂等且失败时清理半成品; 客户端把哈希挪进 worker 用二次摘要规避内存峰值, 用信号量加退避重试控制并发。

适合的场景: 内网或小团队的自托管沟通工具; 需要在真实聊天场景里内嵌 coding agent 的探索; 学习实时消息管线、WebRTC 信令与断点续传的参考实现。

不适合的场景: 公网大规模部署(需先补 TLS、改密验证、跨实例总线与 TURN); 需要跨 NAT 音视频的生产场景; 需要多实例高可用的场景。

若要做产品化演进, 优先级最高的是补齐 Agent 交互的持久化与多实例路由——当前的纯内存 broker 与单实例运行时是体验最好但扩展性最弱的一环。
