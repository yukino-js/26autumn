本文讲解 Yukino Agent 这一 Node.js/TypeScript AI 应用的技术实现:它用 Next.js 16 App Router 把前端页面与后端 API 收进同一个进程,同时承载两个产品面——面向值班运维的 AI OnCall 助手,以及面向 GitHub 协作场景的 DevFlow 工程副驾。文档围绕产品定位、分层架构、端到端数据流、检索与编排实现、模型抽象、数据模型、前端状态、可观测性、配置体系、部署形态与性能成本取舍逐层展开,适合需要在既有 AI 应用上做二次开发,或正在设计 RAG + Agent 编排系统的工程师阅读。所有机制描述均以当前源码为准,Milvus 是唯一向量后端。

## 一、产品定位与核心用例

应用是公开表面(无登录),两个产品表面共用一套技术栈、一个 PostgreSQL 库、一个 Milvus 集合,但面向完全不同的任务。

### OnCall:AI 值班助手

OnCall 表面(根路径)服务的核心场景是"告警来了,值班人想知道发生了什么、该怎么处理":

- 知识问答:用户提问,系统先做检索增强,再让模型基于内部文档作答,并在回答中给出引用来源;回答以 markdown 流式返回。
- 交互式界面:模型可以在回答末尾附带一段声明式的 A2UI 协议消息,把告警列表、指标图表、静默表单渲染成真正可点击的界面;用户点击后的动作回到服务端,原界面原地刷新。
- 一键告警分析:AI Ops 按钮触发一次多轮编排,自动执行"拉活跃告警 → 按告警名查处理手册 → 查日志 → 出结构化报告"的运维 SOP,可选地把报告渲染成 A2UI 界面。
- 活跃告警面板:聚合一个或多个 Prometheus / Alertmanager 数据源的当前活跃告警,支持同名去重与按源溯源。
- 知识库运营:上传 md/txt/pdf/docx 文档即建索引;文档列表同时给出文件分类与本文件的向量块数量,便于发现"文件在、索引空缺"的陈旧状态。
- 能力扩展:管理员可以登记多个 MCP 工具连接(SSE 或 Streamable HTTP 传输),可以维护自定义指令预设与 SKILL.md 技能资产;每一次工具调用都落审计。
- 运维自检:就绪探针逐依赖报告连通性与延迟,配置自检列出必填项与可选项的配置状态。

### DevFlow:GitHub 工程副驾

DevFlow 表面(`/devflow`)把同一个技术栈推向软件协作场景,提供一整套工作台页面(仓库、issue、PR、CI、代码图、知识库、草稿、反馈、工作流、工作区):

- 仓库接入:同步 GitHub 仓库的 issue、PR、CI 运行与评论;也支持本地托管检出(managed checkout),把仓库文件落到 Node 进程磁盘,供文件工具与项目文档索引使用;支持 webhook 增量触发与周期后台重同步。
- 结构化分析:issue 分类/优先级/复杂度评估与负责人建议、PR 审查(敏感文件识别、测试覆盖识别、风险发现、合并建议)、CI 失败调试;分析结果可归档为记录,并可对相似历史问题做检索。
- 会话与知识:每仓库独立的知识库(上传文档与会话产出)与项目文档索引,检索走同一套 Milvus 混合检索,只是用标量过滤把范围圈到本仓库;问答带答案门禁与抽取式兜底。
- 代码理解:从托管检出中用正则抽取符号与关系,构建跨文件引用图,支持符号检索与影响面(impact)遍历;另有把 issue/PR/文档/人/决策串起来的跨实体知识图谱。
- 记忆:会话级结构化记忆与仓库级线程记忆,支持从记忆候选人工审核后沉淀为知识文档。
- 安全写操作:任何对 GitHub 的写操作(评论、建 issue、打标签、关闭)都落到 ActionDraft 草稿闸门,人工确认后才执行。
- 反馈闭环:回答可点赞/点踩,负反馈进入审核视图并可经通知通道触达维护者与回溯链接。

两个表面的能力对比:

| 维度     | OnCall                                                       | DevFlow                                       |
| -------- | ------------------------------------------------------------ | --------------------------------------------- |
| 面向对象 | 值班运维、内部知识问答                                       | 研发协作、仓库维护                            |
| 数据源   | 内部文档、Prometheus/Alertmanager、日志 MCP、可选 OnCall SQL | GitHub API、托管检出、上传文档                |
| 检索范围 | 共享集合中排除 `devflow:` 前缀的块                           | 共享集合中按 `devflow:*` 前缀过滤             |
| 主要编排 | ReAct 对话 + Plan-Execute-Replan 运维分析                    | 单步结构化分析 + 工具型聊天 + 多 agent 工作流 |
| 写操作   | 无(查询分析为主)                                             | 统一经 ActionDraft 人工确认                   |

## 二、分层架构与模块职责

应用是 Next.js 16 App Router 全栈结构,前后端同仓同进程。整体分为六层,依赖方向自上而下:

```text
表现层    React 19 客户端组件 / useChat 状态中枢 / Streamdown 渲染 / A2UI 渲染
   │
接入层    app/api/* Route Handler: 参数校验、统一响应包装、SSE 帧构造、CORS
   │
编排层    pipelines: chat(ReAct) / plan-execute-replan / knowledge-index /
   │                diagnostic-cases / DevFlow agents
   │
能力层    模型工厂 / Embedding / Rerank / 工具体系 / A2UI / Milvus /
   │        Prisma / 会话记忆 / 告警聚合 / 技能与提示词
   │
观测层    Langfuse + OTEL / yukino-sentry→Prometheus 指标桥 / 生命周期打点
   │
配置层    config: 集中读取环境变量并导出 as const 对象
```

关键设计约束有三条。其一,Route Handler 只做参数校验、调用管线和响应包装,所有 AI 逻辑下沉到编排层;管线不感知 HTTP,只依赖能力层的模型、工具、检索接口,因此可以被路由、脚本或其他入口复用。其二,凡跨越信任边界的数据(HTTP 请求体、LLM 输出、Milvus 响应、localStorage、MCP schema)一律先过 zod 校验,禁止类型断言。其三,可观测性与外部集成全部可降级——未配置时是 no-op,绝不阻塞业务路径。

### 为什么是 Next.js 全栈而不是前后端分离

密钥隔离是首要原因:LLM/Embedding/Rerank 的 API Key、数据库与 Milvus 连接串、GitHub 凭据都必须在服务端出现,Route Handler 天然构成服务端边界。其次是流式能力内建——Route Handler 可以直接返回 `ReadableStream`,手写 SSE 帧无需额外框架。第三是部署单元单一,一个构建产物同时含页面与 API,外部依赖(PostgreSQL、Milvus、Prometheus)由部署侧编排。最后是类型端到端共享:前端直接复用服务端的 zod schema 解析响应,契约变更在编译期暴露——例如对话响应、AI Ops 响应、A2UI 动作响应各自有对应的响应 schema,前端解析后判断业务状态而不是只依赖 HTTP 状态码。

代价是长连接占用单进程资源、多实例下内存记忆不共享、DevFlow 的托管检出依赖本地磁盘。这些在内部工具规模可接受,但决定了它不适合无状态化的弹性伸缩部署。

## 三、请求与会话的端到端数据流

### 非流式对话

一次 `POST /api/chat` 的处理链:请求体过 zod(session id + question)→ 读取会话记忆窗口 → 用问题做一次混合检索 → 把检索文档、记忆摘要、技能目录、自定义指令注入 system prompt → 用 quick 模型执行 `generateText` + 工具 + 步数上限 → 抽取 A2UI 块(失败则一次纠错重试)→ 回写记忆并触发异步摘要 → 返回 `{ message, data }`。响应 data 里除 answer 外还可能带 `a2ui`、`references`(引用来源,含标题、来源、分数、摘要与知识分类)与 `reasoning`(模型推理文本)。非流式路径同时从完成的步骤里聚合工具调用,逐条写审计。

### 流式对话

`POST /api/chat_stream` 复用同一管线的流式版本。服务端把 AI SDK 的流部件映射为应用自己的事件类型,再编码为 SSE 帧。事件清单:

| SSE event    | 载荷                    | 含义                                                      |
| ------------ | ----------------------- | --------------------------------------------------------- |
| `connected`  | `{ status, client_id }` | 连接建立,先发一帧便于客户端区分"连接失败"与"生成中无输出" |
| `message`    | 文本                    | 回答正文增量;多行文本按 SSE 规范拆成多条 `data:` 行       |
| `references` | 引用数组(单行 JSON)     | 本轮的检索依据,先于正文下发,客户端可提前渲染来源          |
| `reasoning`  | 文本                    | 模型推理增量(extended thinking)                           |
| `tool`       | `{ id, name, state }`   | 工具调用生命周期,state 为 call / result / error           |
| `a2ui`       | 协议消息数组(单行 JSON) | 过滤出的 A2UI 块                                          |
| `done`       | 文本                    | 流正常结束                                                |
| `error`      | 文本                    | 带内错误——HTTP 头已发出,无法再改状态码                    |

`send` 函数把载荷按换行拆成多行 `data:` 前缀,这是 SSE 规范对含换行载荷的正式编码:若把裸换行直接写进 `data:`,解析器会把它当作帧边界,后半段内容全部丢失。JSON 载荷(引用、A2UI、工具事件)由序列化保证是单行,因此天然安全;只有自由文本需要这套拆分。响应头包含 `text/event-stream`、禁用缓存与保持连接三件套,防止中间层缓存或截断。

### 流式消费

前端没有使用 `EventSource`,而是 `fetch` 后读取 `response.body` 的 reader——因为请求是带 body 的 POST,且需要 AbortController 主动取消。核心机制是流式解码加行缓冲:`TextDecoder.decode(value, { stream: true })` 让解码器保留跨 chunk 的不完整字节,避免多字节字符被切断变乱码;缓冲区按 `\n` 切分,最后一段不完整行留到下一轮;空行触发一次事件分发,`data:` 行累积后以 `\n` 拼接还原载荷。收到的 `error` 事件会被显式抛出并渲染错误气泡,而不是静默忽略。

取消链路是"客户端意图 → 传输断开 → 服务端资源释放"的接力:发送开始时创建 AbortController 并绑定到 fetch;组件卸载或新会话时 effect cleanup 主动 abort;读取循环每轮先检查信号是否已中止。当前实现的缺口是请求信号没有透传给服务端的模型调用,因此客户端断开后模型仍会跑完——服务端若把请求信号转成模型调用的中止信号,才能真正省下这部分费用。

### AI Ops 请求

`POST /api/ai_ops` 的请求体可选携带 `query` 与结构化 `alert`。纯函数构造器做三态归一:两者都缺省时用默认的"全量巡检"根指令;只给 query 时透传;给了 alert 时把它拼成"只诊断这一条告警"的定向 query(字段包括告警名、级别、服务、状态、触发时间、持续时长、描述、上下文链接、指纹、来源),同时把告警对象留给确定性报告回退模板。路由在边界处把 alert 的嵌套 map 剥掉只留扁平字符串字段,再在管线启动前写一条运行记录(status=running),在 done/exhausted/failed 时收尾;运行结束后异步把报告落成诊断案例。运行历史可通过列表接口(最近 20 条摘要)与详情接口(全量报告与步骤明细)回看,详情还带可选 A2UI 消息。

### A2UI 动作闭环

界面按钮点击时,前端把动作(名称、surfaceId、来源组件、上下文)与该 surface 当前完整消息数组一起 POST 到 `/api/a2ui_action`——界面自身状态就是请求上下文,服务端不另存 surface。服务端用 quick 模型 + 全量工具生成原地更新消息,过滤掉混入的 `createSurface`(它会让客户端 MessageProcessor 抛错并丢弃整批消息),校验失败同样走一次纠错。响应消息数组追加回原消息的 a2ui 字段并更新历史,用户看到的是同一条消息内的界面刷新,不产生新的对话轮次。没有产出有效更新或没有原地更新消息时,路由返回 502 而不是空成功。

## 四、模型与 Provider 抽象

### 双槽位模型

模型工厂导出 `thinkModel` 与 `quickModel` 两个实例:前者用于规划与重规划(plan-execute-replan 的 planner/replanner 以及报告重写与界面化),后者用于对话、步骤执行与 A2UI 纠错。两个槽位各自拥有独立的模型名、baseURL、apiKey,由 `LLM_PROVIDER` 选择 OpenAI 兼容实现或 Anthropic 实现。这是典型的"能力-成本匹配":关键决策用强模型,高频调用用快模型,成本和延迟都落在正确的位置。

设计上的三点余量也值得注意:两个槽位的 baseURL 独立,意味着可以让思考走一家、快速走另一家(虽然当前 provider 是全局开关,配置结构已为此留好余地);延迟可以分区隔离——把执行模型放到网络更近的端点而不影响规划质量;token 费用可按"单价 × 调用量"分层优化,把绝大多数调用导向便宜数倍的快模型。

### Anthropic extended thinking

extended thinking 是 Anthropic 私有特性,不属于 OpenAI 兼容协议,因此经 AI SDK 的 `providerOptions` 逃生舱透传:

```ts
providerOptions = {
  anthropic: {
    thinking: { type: "enabled", budgetTokens: maxOutputTokens - 1 },
  },
};
```

要点有三。budgetTokens 是思考块的最大 token 数且必须小于 max_tokens,这里取"最大输出减一",把绝大部分预算留给推理——符合 planner 场景"计划质量优先、正式输出可以很短"的取向。该配置仅在 provider 为 anthropic 时注入,并可用环境变量显式关闭,关闭时传 disabled 类型。所有 LLM 调用点(对话、单步执行、planner/replanner、报告重写、界面化)都统一注入,保证同一编排循环内思考行为一致。

### 兼容网关的协议修复

某些 Anthropic 兼容网关在非流式响应里返回 thinking 内容块时缺少官方 API 必带的 signature 字段,而 SDK 的响应 schema 把它标为必填,于是 SDK 报出"Invalid JSON response";更麻烦的是这个校验错误向上冒泡时 message 常常是空串,极难排查。模型工厂为此包装了全局 fetch:仅当响应是 JSON 时读取响应体,若发现 message 类型的 content 数组里有缺 signature 的 thinking 块,就回填空字符串再重建 Response;流式 SSE 原样透传(流式 chunk schema 不校验该字段)。两个细节值得注意——body 修改后删除 content-length 与 content-encoding 头,避免字节数与声明不符;JSON 解析失败时静默返回原始 body,包装器永不引入新故障。

这反映的工程态度是:对接兼容网关时面对的不是标准协议而是某家实现的方言。防御应放在传输层(fetch 包装)而不是业务代码;同时错误处理处把上游真实报文完整引出,保证下次再遇到协议方言时能直接从响应里看到原始报文。

### Embedding 与 Rerank

Embedding 只有唯一合法 provider(OpenAI 兼容 `/v1/embeddings`),换服务只需改 baseURL、apiKey、model 三个环境变量。批量嵌入按固定条数分片:OpenAI 兼容端点对单请求输入条数有上限(示例模型为 10 条),而 SDK 默认一次发 2048 条,大文档会报 "batch size is invalid",因此上层调用对分片完全透明。批量接口的顺序保证也被依赖:返回的向量顺序与输入严格对应,索引器据此做对位。

Rerank 是可选的第二阶段精排,指向 DashScope 风格的文本重排端点。它是 fail-open 设计:未配置 API Key 时直接跳过;配置了但服务抖动时,包装函数捕获异常并返回 null,检索退回融合顺序——精排是质量增强,不稳定的上游不应该拖垮 RAG 对话。响应校验也很严格:索引必须唯一且在范围内、分数必须有限且落在 [0,1],违反即判为无效响应;重试只针对限流与 5xx/传输层错误,用指数退避。

## 五、RAG 与向量检索

### 索引侧链路

`POST /api/upload` 接收 multipart 文件后依次:校验扩展名(允许 md/markdown/txt/pdf/docx)、校验大小上限、对纯文本做 UTF-8 合法性与 NUL 字节嗅探、把用户提供的文件名规约为安全 basename(去除路径分隔与特殊字符,保留 CJK,防目录穿越)、按内容哈希跳过同内容重复上传,最后落盘并立即建索引。上传接口带一个可选的知识分类提示,取值必须在允许集合内,否则回退到索引器的启发式分类。

pdf/docx 的文本抽取有完整护栏:PDF 限制文件字节数、页数与抽取字符数,拒绝加密与纯扫描件,并在每页前插入页码标记以便后续按页溯源;DOCX 先做 zip 炸弹防御(解析中央目录、限制条目数与解压后总字节、拒绝加密标志与 OLE 复合文档头)再转 markdown。抽取失败会明确返回"无可抽取文本"而不是把空内容索引进库。

索引器把文档按 markdown 感知的递归切分器切成块(chunk 约 1000 字符、overlap 200 字符),这个尺寸远低于索引器存储上限(8192 字符)与 Embedding 提供商输入限制,保证"被嵌入的文本"与"被存储的文本"始终一致。每个块取块内首个标题作为 title,无标题则继承前一块标题(块按文档顺序到达);知识分类的判定顺序是显式 frontmatter > 文件名前缀 `aiops-case-` > 文件名含 sop > 正文前部的语义启发 > 默认 document,分类值必须与前端标签映射保持同步。写入前先按来源删除旧块,再整批 embed 并 upsert——upsert 以主键幂等,同一文件重复重建天然收敛,不需要分布式锁。批量写不是关系型事务:它提供的是按主键幂等覆盖与写后即读可见,不提供部分失败整体回滚;上层重跑整个"删除 + upsert"流程即可收敛。

### 检索侧链路

检索入口在共享集合上做稠密 + 原生 BM25 混合检索,由 Milvus 服务端完成 RRF 融合,随后可选精排,最后截断到 topK。默认 topK 为 5。候选宽度计算考虑了两个后处理阶段:当需要排除 DevFlow 来源或启用精排时,候选池放大到"topK 的 4 倍与精排候选下限(20)的较大者",并封顶 50,给排除与重排留出余量。若调用方未传过滤表达式,视为 OnCall 视图,融合结果中所有 `devflow:` 前缀来源的块在进程内被剔除——这里刻意不用 Milvus 的取反 LIKE 表达式,以摆脱对过滤表达式语法支持的依赖,牺牲的是一点点候选宽度。DevFlow 调用方则传入显式过滤圈定仓库范围。检索器还暴露了原始候选入口(不精排、不截断,可选稠密/稀疏/混合三路),供 DevFlow 自己的去重、精排与扩展链使用,以及纯稠密入口专供需要绝对分数阈值的场景。

### Milvus 集合设计

一个集合同时承载两条检索路径,这是选型的核心收益:

| 字段/能力         | 设计                                                                                                     |
| ----------------- | -------------------------------------------------------------------------------------------------------- |
| 主键 `id`         | VarChar,由索引器生成 UUID                                                                                |
| 稠密 `vector`     | FloatVector,维度从首个 upsert 向量的长度推断,索引 AUTOINDEX + COSINE                                     |
| 全文 `content`    | VarChar,启用 analyzer(默认 standard,可切 chinese 以支持中英混合语料)                                     |
| 稀疏 `sparse`     | SparseFloatVector,`is_function_output`——由集合内的 BM25 Function 从 content 服务端派生,upsert 从不直接写 |
| 标量 `source`     | 由 metadata 的 `_source` 提升而来,支持按来源等值删除与布尔过滤                                           |
| 元数据 `metadata` | JSON 字符串,截断到 16384 字符;检索命中后解析回对象                                                       |
| 一致性            | 建集合用 Strong,保证写后即可读,双写对账确定                                                              |
| 融合              | `hybridSearch` 一次请求带稠密与稀疏两个子请求,`RANKER_TYPE.RRF` 服务端融合,k=60                          |

混合检索的工作方式是:稠密路传查询向量做近似最近邻,稀疏路直接传原始查询文本到 function-output 字段(稀疏向量由服务端派生),两路各召回至多"topK 与召回宽度二者较大值"条,服务端按 RRF 融合后返回。只输出需要回传的字段——向量字段本身(每条约数 KB)不回传,显著减少网络开销。可选的过滤表达式同时下推到两个子请求,表达式里的字符串值一律经过转义(先转反斜杠再转双引号),因此引号无法跳出过滤表达式形成注入。删除也走布尔表达式:按来源等值删除一次清掉某文件的全部旧块;按前缀删除服务 DevFlow 的每仓库知识库,删除前把前缀里的 LIKE 通配符转义,避免仓库标识里的下划线误伤其它文档。

### 分数语义与维度自检

返回的 `score` 语义随路径而变,调用方必须先分清手里是哪种分数:纯稠密是 COSINE 相似度([0,1] 的绝对量,可做阈值过滤),混合路径是 RRF 融合分(只取决于两路名次,是排名导向的量,不能与固定阈值比较),精排后是 [0,1] 的相关性分。把排名分当相似度用是 RAG 系统最常见的分数误用,因此检索器把纯稠密入口单列出来,专供需要绝对分数阈值的场景。

维度管理是另一处易错点。向量维度是集合的物理属性,换用输出维度不同的 Embedding 模型后,旧集合与新向量根本不兼容;若不自检,表现是"静默失败"(检索全错或直接拒绝)。客户端把防御做在启动路径上:写入前读回既有集合的维度比对,不一致则告警并整体 drop 重建,而启动时的目录重建会把数据重新填满。维度从不静态配置,以实际模型输出为权威来源——"换模型 = 知识库静默失效"于是变成"换模型 = 集合自动重建"。客户端的懒加载单例也做了针对性处理:构造是同步的,消除了异步单例的检查-赋值竞态;SDK 在构造时后台发起的连接请求若失败,其 rejection 会被显式接住,避免 Node 把它当致命错误,而真正被 await 的调用会通过自己的 promise 把同一个错误抛给调用方。

"集合存在但为空"与"Milvus 不可用"是两种不同故障:前者读操作返回空结果,后者一律抛错。SDK 把逻辑失败报告在响应体内(错误码字段),客户端对所有非成功状态一律抛出,保证调用方永远不会把错误响应当成"空结果"——这是检索系统最危险的静默失败。

### 上下文装配与间接注入防御

对话管线把检索文档注入 system prompt,并用显式边界标记(`==== Documents start ====` / `==== Documents end ====`)包裹,给模型明确的"这是资料不是指令"信号,以缓解知识库文档中夹带的间接 prompt injection。同时把当前日期注入上下文,解决模型训练截止带来的时间感缺失;把日志主题配置按环境变量注入,未配置时整行省略而不是给一个空值(避免模型看到空配置反而困惑或编造)。需要如实说明边界:边界标记只能降低模型被诱导的概率而不能根除;更稳健的方向是把检索文档放进独立消息而非 system prompt、对检索结果做指令性模式清洗,以及对高风险工具调用引入人工确认。

system prompt 里还有两段"可选注入":启用中的技能目录(只有名称与描述,正文按需加载)与管理员的自定义指令。两者的读取都是尽力而为——存储读取失败降级为不注入,绝不因此让对话失败。

### 引用来源与检索质量

检索命中的文档会转成结构化的引用对象(标题、来源、分数、去空白摘要截断到固定字符数、知识分类),随响应或 SSE 的 references 帧下发给前端。这样用户不仅看到答案,还能看到答案依据了哪些内部文档,这为 OnCall 场景"答案可溯源"提供了基础。

提升检索质量的方向按性价比排序:一是在混合检索之上加分数阈值过滤,但阈值必须基于纯稠密的 COSINE 分而非 RRF 排名分(检索器已暴露纯稠密入口供此用途);二是继续利用已落地的混合检索解决专有名词与告警代号的精确匹配;三是调优已接入的 fail-open 精排通路(候选宽度、精排 topK 与阈值);四是查询改写——用快模型把口语问题改写成检索友好的形式、拆开复合问题;五是建立"问题 → 期望命中文档"的评测集,用 Recall@K 与 MRR 量化每次改动,避免凭感觉调参。至于长上下文与 RAG 之争,更实际的判断是融合而非替代:长上下文省掉切分与检索的工程复杂度,但每轮塞入整库的成本与首 token 延迟不可接受,且检索的元数据过滤天然是权限门、命中的块天然是引用来源——可解释性与时效性仍是 RAG 的不可替代价值。

## 六、Agent 编排:ReAct 与 Plan-Execute-Replan

### ReAct 对话循环

对话管线使用 AI SDK 的多步执行能力:一次调用内部,模型发起工具调用 → SDK 执行工具 → 结果作为 tool message 追加 → 再次调用模型,直到模型不再发起工具调用或触达步数上限。停止条件声明为步数上限(25 步),而不是手写 while 循环。之所以用声明式条件:SDK 内部负责消息列表的正确性(assistant/tool 消息顺序、tool_call_id 配对、provider 特有的工具块格式),手写循环在并行工具调用、错误回填等边角极易出错;流式路径下多步循环的文本增量由 SDK 按序吐出,手写需要自己拼接多轮流,状态机复杂。25 是防失控保险——正常问答两三步即可完成,25 允许复杂的链式推理,同时把"模型陷入工具死循环"的成本上限锁死。

流式路径还有一处必要的纠偏:`streamText` 默认把错误吞进错误回调后结束文本流,客户端会看到一个空回答;管线显式捕获该错误并在流末尾重新抛出,让 SSE 路由能发出真正的 error 事件。记忆回写在 finally 中执行,且仅当已产生文本时才写入——中断或出错不污染记忆,同时保留了流被消费方提前切断时的部分回答(记忆保存的是含 A2UI 标签的原始文本,后续追问仍能看到界面上下文)。

与教科书 ReAct 的差异在于:这里没有显式的"思考/动作/观察"文本协议,而是利用 function calling 的结构化 ReAct——推理在模型侧(Anthropic 路径甚至是加密的思考块),动作是 schema 化的工具调用,工程上远比自由文本协议可靠。

为什么两条管线并存:对话用 ReAct(灵活、开销低),运维分析用 Plan-Execute-Replan(可控、覆盖全)。选型的本质判断是"当任务有确定性 SOP 时,把流程控制权从模型手里收回一部分,只把局部决策留给模型"。对 OnCall 这种"漏掉一个告警就是事故"的场景,可控性和覆盖率比灵活性重要;反过来闲聊与开放问答场景,规划的额外强模型调用纯属浪费。

### Plan-Execute-Replan 图拓扑

AI Ops 分析把"流程控制权"从模型手里收回一部分:LLM 只负责产出计划与判断是否完成,循环骨架由代码约束。控制流被编码为 LangGraph StateGraph 的节点与条件边:

```text
START → planner ──(plan 非空)──→ executor ──(还有步骤)──┐
             └──(plan 为空)──→ exhausted                 │
                                       ↑                  │
                                       └──────────────────┘
                          executor ──(本轮步骤跑完)──→ replanner
                                                        │
                    ┌──(done)──────────→ uiify → END      │
                    ├──(预算耗尽/剩余为空)──→ exhausted → END
                    └──(仍有剩余步骤)────→ executor ───────┘
```

五个节点各司其职:

- planner 用 think 模型 + 结构化输出把任务拆成有序步骤数组,产出并下发计划事件;计划为空时条件边直接路由到预算耗尽分支。
- executor 每次节点运行只执行一个计划步骤(quick 模型 + 全量工具,内部再允许至多 10 步工具小循环),执行前先校验该步骤是否引用了"当前已发现的工具",引用未知工具的步骤会被标记为跳过并写入观测文本,而不是放任模型凭空叙述一个它从未调用的工具。每步输出追加进累计明细。
- replanner 用 think 模型评估目标达成度,产出 `{done, remaining, summary}`:未完成时只列剩余步骤(差集语义),完成时给出综合报告。
- uiify 是收尾分支:先做报告结构校验与降级(见下),再可选地把报告渲染成 A2UI 界面,最后下发结束事件并接终点。
- exhausted 是预算耗尽的确定性出口:下发固定文案的结束事件并接终点。

条件边把分支语义集中在三个纯函数里,路由逻辑因此可独立审查与测试。整张图可离线断言节点集与边集,不调用模型即可验证拓扑。

### 双护栏:业务预算与框架限制

`MAX_ITERATIONS = 20` 是真实业务预算,replanner 之后的条件边检查已完成的 replan 轮数,达到预算或剩余步骤为空即路由到 exhausted。`RECURSION_LIMIT = MAX_ITERATIONS * 25 + 25` 只是 LangGraph 超步数的兜底:每一轮计划要消耗"每个计划步骤一个超步 + 一个 replanner 超步",给每轮留 25 个超步的宽裕预算,确保正常运行不会先被框架自身的递归限制掐断。两者必须同步调整,离线冒烟脚本对此有断言。这体现的分层原则是:业务预算由自己的代码管理(可审计、能给出明确的 exhausted 语义),框架限制只做最后一道保险。

### 状态定义与 concat reducer

图状态用 `Annotation.Root` 显式声明,共八个字段:分析任务 query、可选的结构化 alert、当前轮计划 plan、下一个要执行的步骤下标、跨轮次累计的步骤输出 detail、已完成的 replan 轮数、done 与最终报告 report。绝大多数字段是覆盖写(last-write-wins);只有 detail 用 concat reducer 追加:executor 每次返回的步骤输出被追加进既有数组,replanner 的评估输入与最终报告的步骤明细都依赖这份完整历史;若这里也用覆盖写,状态里将只剩最后一步的输出,评估会丢失全部上下文。

之所以用 `Annotation.Root` 而不是 langgraph 的 zod StateSchema:应用侧的 zod 走 v4 体系,其 `~standard` 接口缺少 StateSchema 所需的 JSON-Schema 属性,显式声明状态是正确选择。

图节点发布自定义流事件必须用 `getWriter()`,而不是 `writer()` 助手。在所用的 langgraph 版本中,`writer()` 读取的是 `configurable.writer`,而 Pregel 已不再填充该字段,于是事件被静默丢弃:图照常运行、模型照常调用,只是驱动收不到任何事件,最终表现为"管线挂死且无报错"。`getWriter()` 读顶层 `config.writer`,才是正确入口。这个失败模式之所以值得记录,正因为它完全静默。

### 事件契约

编排对外收敛为一条判别联合事件流,事件类型由 zod schema 推导,驱动在边界处对每个 chunk 重新校验后才下发:

```ts
type PlanExecuteEvent =
  | { type: "plan_created"; steps: string[] }
  | { type: "step_start"; index: number; step: string }
  | { type: "step_done"; index: number; output: string }
  | { type: "replan"; done: boolean; remaining: string[] }
  | { type: "done"; result: string; detail: string[]; a2ui?: unknown[] }
  | { type: "error"; error: string };
```

管线返回 `AsyncGenerator<PlanExecuteEvent>` 而不是 Promise、回调或 EventEmitter:编排可能跑几分钟,一次性 Promise 让调用方全程无感知;回调/EventEmitter 需要消费方维护注册与状态机,背压不可控,错误传播路径也不统一;AsyncGenerator 天然顺序化、暂停即背压、抛错语义清晰,且判别联合让消费方的分支完备性可被编译器检查。运行时形状与编译期类型同源——schema 与 `z.infer` 是同一份定义。

路由只消费事件、不感知图的内部结构,这意味着编排引擎属于管线内部实现细节,可以独立替换或演进。当前路由是把事件流的中间事件丢弃、只取最终结果的同步形态;若要改造成流式进度体验,只需把每个事件序列化成一帧 SSE,管线零改动,前端按事件类型渲染进度时间线即可——这就是"管线与传输解耦"的红利。

### 报告的确定性护栏

最终报告经过三层降级,保证一次跑完的运行永远产出结构合规的报告:第一层是 replanner 产出的 summary,经结构校验(去围栏、拒绝 JSON 形状、必须包含规定的中文标题);第二层是一次无工具重写,要求只围绕既有证据重组,不得引入新事实;第三层是确定性回退模板,完全由结构化告警输入与已执行步骤的输出拼成,不采用任何未经验证的推断,缺证据处明确写"未获取/证据不足"。这道护栏的动机很直接:AI Ops 的输出会被值班人用来处置生产系统,宁可给一份保守但可核查的报告,也不能给一份看似完整却编造根因的报告。界面化(uiify)也遵守同一原则:调用失败只记日志,绝不允许它丢弃已完成的报告。

### AI Ops 根指令与定向诊断

默认根指令把运维 SOP 写成编号步骤(先调工具取活跃告警 → 按告警名查处理手册 → 严格遵循文档 → 时间参数先取当前时间 → 日志查询带 region 与 topic → 汇总成规定结构的报告)。它把领域流程知识以 prompt 的形式注入 planner,并前置了工具使用规约(尤其是"任何时间参数先调取时间工具"这类经典坑),还给出报告的骨架标题以保证多次运行产出结构稳定。当请求携带结构化告警时,定向指令把它作为唯一分析对象,不允许扫描全量告警列表,并附上规范化的告警字段与操作员追加指令。

已知局限:报告重写与 replanner 的输入都把历史步骤输出全量拼接,多轮迭代后 token 会显著膨胀,改进方向是对历史输出做滚动摘要或只保留上轮结果加累计摘要。根指令目前是硬编码常量,不随告警类型或环境变化;更进一步的方案是把 SOP 本身也存入知识库,按告警类型动态装配。

### 运行持久化与案例回流

路由为每次运行落一条运行记录,记录查询、状态、报告、步骤明细与可选 A2UI 消息;状态区分 success(报告合规产出)、exhausted(预算耗尽,结果是固定文案)、failed。运行完成后,完成报告会被异步写成 `aiops-case-<hash>.md` 文件并即时建索引,结构化字段回填案例登记表——未来按告警名检索时,既能命中处理手册,也能命中历史同类事故。案例文件按内容哈希命名因此幂等重跑不会重复落盘;案例库有容量上限,因为 OnCall 表面公开且无鉴权,不能任由匿名重复运行无限增长文件目录。报告标题取首个 markdown 标题,摘要优先取"结论"段落,缺失时退化为报告开头。

## 七、工具系统与 MCP

### 三层分离

每个内置工具拆成三个协作部分:schema 用 zod 定义入参并带字段描述(描述会随工具注册进模型的 function calling 契约),operation 是纯函数实现且不引用任何 AI SDK 概念,wrapper 用 AI SDK 的 `tool()` 把前两者组装成模型可调用的工具。这样分层带来四点收益:operation 可脱离 LLM 单测;同一份 operation 既能被工具层包装给模型,也能被管线直接调用做预检索;模型可见的"工具说明书"集中在 schema 层,调提示词不会动到业务逻辑;若要换 agent 框架,只需重写 wrapper。

一个设计良好的工具由三要素构成:description 是写给模型看的使用说明书,决定"何时用、怎么用",描述要写清能力边界与护栏语义;inputSchema 生成 JSON Schema 注入 function calling 契约,字段级描述是在教模型构造正确入参;execute 返回字符串化 JSON,让工具结果作为 tool message 回填给模型。工具集本质上就是 agent 的能力边界——给什么工具,agent 就能诊断什么问题。

### 内置工具

| 工具                      | 角色         | 关键设计                                                            |
| ------------------------- | ------------ | ------------------------------------------------------------------- |
| `get_current_time`        | 时间锚点     | 消除模型的时间幻觉;OnCall 场景大量"最近一小时"类查询依赖它          |
| `query_prometheus_alerts` | 告警事实源   | 多源聚合;同名去重;单源失败不丢弃其它结果                            |
| `query_internal_docs`     | 知识源       | 把 RAG 检索暴露为模型可按需调用的能力(与管线预检索互补)             |
| `postgres_query`          | 业务数据源   | 对隔离的 OnCall 库执行 SQL,护栏是配置隔离、静态比对与运行时角色自检 |
| `load_skill`              | 技能正文加载 | 渐进式披露:system prompt 只带技能名与描述,正文按需加载              |

工具的 `execute` 统一返回 JSON 字符串。这不仅是因为 function calling 的 tool result 最终以文本进入消息流,也因为一致的输出风格降低了模型的理解负担。工具结果会原样计入上下文 token,因此工具实现要有输出预算意识:告警查询做了字段裁剪与同名去重,`postgres_query` 目前依赖模型自行生成带 LIMIT 的 SQL,执行层只有超时约束没有行数截断,更稳妥的做法是在工具侧强制截断行数并标注截断。

新增一个内置工具的标准路径是四步:在 schema 层定义入参并写字段描述;在 operation 层实现纯函数(内部调外部 API 要带超时、错误结构化为 `{success, error}`、对外部响应做宽松校验);在 wrapper 层包装并加入导出集合;最后无需改管线——对话管线与编排管线都展开同一个内置工具集,新工具自动对两条路径可用。若能力由外部系统提供且会持续演进,更优解是包成 MCP 服务,此时 agent 侧零改动。选型判断:稳定、核心、需深度定制的工具内置;多变、跨团队维护、多应用复用的能力走 MCP。

### 多源告警聚合

告警聚合是独立的能力模块,支持两类 provider:Prometheus 的 `/api/v1/alerts` 与 Alertmanager 的 `/api/v2/alerts`。数据源由一段 JSON 配置声明(名称、类型、baseUrl、可选 basic auth),未配置或配置非法时回退为单个 Prometheus 源。聚合过程并行拉取全部源,单源失败被记录进 sourceErrors 而不影响其它源;仅当全部源都失败时整体判失败。原始告警先按 provider 差异归一化(Prometheus 用 state/activeAt,Alertmanager 用 status.state/startsAt/fingerprint),只保留 active/firing 状态且有告警名的记录,计算人类可读的持续时长,把 label/annotation 中的字符串对保留下来(非字符串值丢弃),并从常见注解约定里提取上下文链接;最后按(来源、开始时间、指纹)排序后按告警名去重,同名只保留首次出现。就绪探针也复用这套配置逐源探测,单源不可达只让该项降级。

对模型而言,十条同因不同实例的告警是噪声,同名去重既压缩 token 也避免模型重复分析;失败返回结构化错误而不是抛出,让模型能读到"数据源不可用"并如实告知用户。`active_at` 转成人类可读的持续时长也是把计算前置到工具侧——模型对"持续三小时"的判断远好于对 ISO 时间戳的心算。

### postgres_query 的四层隔离

该工具允许模型对专用库执行任意 SQL,因此护栏必须严密:

- 配置层:连接串只来自管理员配置的环境变量,模型能给的只有 SQL 与操作类型两个参数(operate_type 取 query/insert/update/delete,只决定返回形状——查询回行集,写操作回受影响行数),"连哪个库"从不交给模型;未配置时工具直接报错并提示需要配置独立数据库与受限角色。
- 静态比对:解析目标 URL 与应用库 URL,库名或用户名相同直接拒绝,防止配置失误把工具指回应用库。
- 运行时自检:连上后先执行一条探测,用系统目录确认当前会话角色不是超级用户或具备建库/建角色/复制/绕过行级安全等特权,也不是应用角色或文件/程序角色的成员,任一项命中即拒绝。PostgreSQL 权限是最后防线,这条探测把配置错误变成显式报错。
- 会话卫生:每次调用新建连接并在 finally 中关闭,防止调用方 SQL 夹带的会话级设置(如改变角色)污染下一请求;叠加连接、语句、查询三层超时;以具名扩展查询协议执行,该协议不允许单请求多语句,天然挡掉堆叠注入。

每次新建连接的代价是一次握手与认证,对"每轮对话几次"的频率,正确性远重于性能。残余风险仍需说明:隔离库内仍是任意写,可生成无 WHERE 的更新或清表删除;无交互确认环节;查询结果没有行数上限。加固方向见第十五节。

### MCP 多连接

MCP 是标准化"应用向 LLM 提供上下文与工具"的开放协议:服务端声明 tools/resources/prompts,客户端通过 JSON-RPC 发现并调用,传输层支持 stdio、SSE、Streamable HTTP 等。它的核心价值是能力外置:工具系统的能力由独立的服务端维护,agent 应用零代码即可获得新工具——工具的热插拔。

本项目的工具来源有两处:内置日志源(由环境变量声明的单一 SSE 连接)与管理表里启用的多条连接(经管理接口维护)。每条连接只连接一次并在进程内缓存,缓存键包含连接定义的签名(传输方式、URL、请求头),定义变更多久缓存就失效;CRUD 之后显式清空缓存,让下一轮对话重建。连接失败不抛出,而是降级为"该连接无工具"并记录错误——MCP 挂了对话仍然可用,只是少了外部工具。跨连接的重复工具名会被重命名而不是静默丢弃。连接与列工具都有超时;管理接口的连通性探测支持"对已保存连接探测"与"对未保存配置的临时探测"两种形态,并把探测结果写回连接行。

schema 适配是接入 MCP 的关键点:服务端返回的是普通 JSON Schema,需要经 AI SDK 的 `jsonSchema()` 包装成其内部表示,包装前先做形状校验以防脏数据进入 SDK。调用的结果内容数组会被序列化为文本回填给模型。管理连接需要管理 Token(见下),因为连接行会决定服务端的出站连接目标。

### 技能资产与提示词预设

技能遵循 SKILL.md 约定:文件开头是 YAML frontmatter,含 name 与 description,正文是完整指令。校验规则完整——文件名必须恰为 SKILL.md、大小与字符数有上限、frontmatter 必须是键值映射、名称是 1 到 64 位的小写字母/数字/单连字符且首尾无连字符、描述非空且有长度上限。启用中的技能只把"名称: 描述"一行注入 system prompt 的技能目录,正文由 `load_skill` 工具按名加载;未知名称如实返回错误并列出当前可加载的技能,不编造内容。这是渐进式披露:技能再多也只在提示词里占一行,正文按需加载。

自定义指令预设同样由管理员维护,启用中的预设按更新时间倒序拼接进 system prompt。技能与预设的增删改都走对应路由(PATCH 切换启用状态、DELETE 删除),存储读取失败时目录注入降级为空,不影响对话。

### 管理门禁

OnCall 的产品定位是公开无登录,但有两类接口会改变服务端配置或暴露审计数据:管理 MCP 连接、读取工具调用审计。这些操作要求管理 Token(Bearer 或专用请求头),Token 用常量时间比较避免时序侧信道;未配置 Token 时受保护的写操作直接关闭(fail-closed),而不是放行——公开产品不能把"决定服务端出站连接"的能力默认开放。只读接口保持公开。

### 工具调用审计

每次完成的工具调用都会写入审计表,来源区分 builtin 与 mcp,记录会话、轮次下标、工具名、入参摘要、结果摘要、状态、耗时;非流式路径没有逐调用计时,耗时为 0。入参与结果摘要按固定字符数截断并折叠空白。写入是 fire-and-forget——审计失败绝不影响或延迟回答。查询接口按会话取最近若干条,返回最新在前。这为"某次回答为什么会这样"提供了可追溯的链路,也是把"LLM 触发的动作"纳入可审计范围的基础。

## 八、A2UI 交互界面

A2UI 是一套声明式 UI 协议:模型在 markdown 回答之后可选地附一个 `<a2ui-json>` 块,内容是协议消息数组(创建 surface、更新组件、更新数据模型),前端按本地组件目录渲染成真正的交互界面。服务端处理分四步。

提示词装配。界面规约由 SDK 的生成器组装成"协议规则 + 完整组件目录 schema 契约 + 领域 few-shot 示例",示例由 builder 函数生成,界面结构变化只需改 builder,提示词自动保持同步。这段规约被注入对话的 system prompt,并要求:只在有结构化数据时输出、必须先写 markdown 摘要、数据逐字拷贝工具结果、绝不编造。字段级红线是协议自带的 zod 版本与应用侧 zod 版本不可混用,因此所有边界处的 A2UI 数据都保持 `unknown[]`,在需要校验时才直接调用协议 schema。

抽取与校验。抽取器定位标签对、截出干净文本并用协议列表 schema 校验;没有标签不是错误(回答就是普通 markdown);有开标签无闭标签则报错并给出具体错误文案。

流式过滤。这是有状态的过滤器:普通文本立即放行,但会扣留"可能是被 chunk 切断的开标签前缀"的尾部——它计算当前缓冲区末尾与开标签前缀的最长匹配长度,只把这块可能跨块的尾巴留在缓冲里;标签块内容静默缓冲到闭合标签出现,再作为一个 a2ui 事件整体产出。流结束时未闭合的块会把开标签还原交上层按无效块处理,而不是把裸 JSON 泄漏进可见文本。

纠错重试。校验失败时把"原对话 + 无效输出 + 校验错误"回放给模型做一次无工具重试,要求只回一个修正后的协议数组;仍失败则降级为诚实的提示(流式路径下发一条 notice 事件),绝不编造界面数据。

客户端把 a2ui 事件解析后追加到消息的 a2ui 字段,由本地渲染组件配合协议处理器与本地组件目录驱动;另有一个无需后端的验证页,用固定消息集渲染全部扩展组件,用于回归组件目录。动作点击的原地更新闭环见第三节。AI Ops 报告另有一处界面化后处理:收尾节点用 think 模型可选地把报告渲染成 surface,报告里没有值得可视化的结构化数据则回"NONE",块无效时经一次纠错重试,调用失败只记日志——界面是昂贵多轮运行之上的装饰,绝不允许它的失败丢弃已完成的报告。

## 九、数据模型与持久化

### 关系数据

关系数据统一走 PostgreSQL,由 Prisma 通过 pg 驱动适配器访问;客户端缓存在 globalThis 上,避免开发热重载泄漏连接池。数据模型覆盖两个产品面:

| 领域               | 模型                                                                                              | 职责                                                               |
| ------------------ | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| OnCall 运行        | AiOpsRun                                                                                          | 一次编排的查询、状态、报告、步骤明细、可选 A2UI、告警名            |
| OnCall 案例        | DiagnosticCaseRecord                                                                              | 结构化案例登记:内容哈希、标题、告警名、摘要、文件名                |
| OnCall 审计与配置  | ToolCallAudit / McpConnection / ChatPrompt / SkillAsset                                           | 工具调用审计、MCP 连接、提示词预设、技能资产                       |
| DevFlow 仓库       | Repository / Issue / PullRequest / PrFile / PrReviewComment / WorkflowRun                         | 仓库与其同步的 issue、PR(含文件与行内评论)、CI 运行                |
| DevFlow 分析       | AnalysisResult / ActionDraft                                                                      | 分析结果归档;写操作草稿闸门                                        |
| DevFlow 知识       | KnowledgeDocument / KnowledgeDocumentBody / ProjectIndex / KnowledgeBaseConfig / RetrievalTestRun | 知识文档注册与正文侧表、项目索引状态、每仓库检索配置、检索测试记录 |
| DevFlow 会话与记忆 | Conversation / ChatMessage / ChatFeedback / ConversationMemory / ThreadMemory / MemoryCandidate   | 会话、消息、反馈、会话级记忆、仓库级线程记忆、记忆候选             |
| DevFlow 图与协作   | CodeSymbol / CodeRelation / KnowledgeGraphEdge / Workspace / TeamMember / User / AuditLog         | 代码符号与关系、知识图谱边、多仓分组、团队成员、用户与审计         |
| DevFlow 多 agent   | AgentWorkflowRun / AgentTaskRun                                                                   | 工作流与其任务级执行记录                                           |

几个模型设计细节值得说明:知识文档的正文放在 1:1 的侧表里,使文档列表查询永远不会拖出可能很大的正文,同时让"索引失败后可重试而无需重新上传"成为可能;仓库连接的分支与提交指纹落在项目索引行上,只有检出变化时才重建索引;团队的 GitHub Token 以 AES-256-GCM 加密后存库,密钥来自环境变量,因此数据库泄露不等于凭据泄露;审计日志对仓库是松散引用而非外键,保证审计轨迹在仓库被删除后仍然存活。

### 会话记忆

OnCall 的记忆是进程内的每会话对象,两层容量控制。会话内是固定大小的滑动窗口(6 条),超出后从头部丢弃消息;丢弃时若条数为奇数就补一位,保证丢弃偶数条,使窗口首条始终是 user 消息——消息流是严格的 user/assistant 交替,若丢弃后首条是 assistant,发给模型的历史就以"无对应 user 的 assistant"开头,协议对这类输入行为未定义,上下文逻辑也会被打乱。全局层用 Map 的插入序实现 O(1) LRU(命中时删除再插入以移到最新位,超容时淘汰最早的键),容量上限防止"前端每次新会话都生成新 ID"导致内存单调增长。

在滑窗之外还有摘要压缩:被逐出窗口的消息对进入待摘要缓冲,累计到阈值后由 quick 模型把"旧摘要 + 这批消息"压成一段有硬上限(约 1200 字符)的滚动摘要,注入 system prompt;触发阈值是累计 6 对消息(SUMMARY_TRIGGER_PAIRS)。压缩调用是 fire-and-forget,绝不阻塞回答;失败时保留旧摘要与待处理消息对,待下次重试;待处理缓冲自身也有上限,防止上游持续不可用时无界增长。摘要提交只在新摘要非空时进行,空回复不会擦掉已有摘要;已被折叠的消息按对象身份移除,因此在压缩期间新追加或缓冲的消息不会被误删。摘要注入的是历史事实,不改变当前轮的检索与工具行为。

局限要说清楚:纯内存实现不跨实例、不持久,进程重启即丢失,多实例部署需要 sticky session 否则上下文断裂。演进方向是记忆外置到共享存储并加 TTL。

## 十、前端状态与交互

### 状态中枢

前端用单一自定义 hook 承担 OnCall 页面的全部会话状态:会话态(session id、消息数组、是否流式中、模式)、持久态(同步 localStorage 的历史列表,有容量上限 50 条)、瞬态 UI(加载遮罩)、资源态(AbortController,放在 state 里以利用 effect cleanup 管理生命周期)。通知不是 React state,而是直接调用 toast 管理器,由组件库负责计时、动画与堆叠;业务侧只传消息与类型。

不引入外部状态库的理由是问题域不成立:状态只有一个页面、一棵组件树消费,无跨页面共享,也无时间旅行或中间件需求;hook 返回值已做引用稳定化,消费方重渲染颗粒度可控,引入状态库边际收益接近零还多一个依赖。选型原则是:状态管理库解决的是"共享与变更编排"问题,不存在该问题时不预付架构成本。

### 同构一致性与副作用

session id 与历史列表不能在 `useState` 初始值里产生,必须在挂载后的 effect 中填入:服务端渲染时随机 ID 必然与服务端产物不同(随机函数在两端结果不同),localStorage 在服务端根本不存在,若在首次渲染产出这些值就会 hydration mismatch。策略是服务端与客户端首次渲染都用空值(一致),挂载后再填入客户端真实值,此时已水合完毕,触发的是纯客户端重渲染。这是处理"浏览器专属状态"(随机 ID、本地存储、窗口尺寸、时间戳)的标准范式。代码对该规则有逐处豁免加理由注释,而不是全局关闭 lint 规则。

另一个流式场景特有的纪律是不能在 state updater 里做副作用:updater 必须是纯函数,开发态的严格模式会双调用以检测副作用,并发模式下还可能被重放;若在 updater 里写 localStorage,历史会被重复写入。解法是用局部变量追踪消息数组,先在局部变量上更新再整体 setState,持久化在 finally 中基于局部变量执行,副作用完全游离于 state 更新之外。这也是流式场景的必然选择——消息在异步循环中持续变化,闭包里的 state 是旧快照,只能用 ref 或局部变量跟踪。

### 流式渲染性能

流式期间每个文本增量都会触发一次状态更新,若整树重渲染会明显卡顿。手段是组合拳:消息项用 memo 包裹,对象引用不变即跳过渲染;更新时以前 N-1 条的不变引用加最后一条的新对象构造数组,让 memo 命中;markdown 渲染基于流式原生的渲染器封装,它会补全流中未闭合的语法并对已完成块做记忆化,使增量 token 只重渲最后一个未完成块而不是全文——普通渲染器会把未闭合的代码围栏后半段误当代码块渲染、流结束又跳变,这类渲染器补全语法即可避免闪变;hook 返回值与回调都做引用稳定化(函数式更新使添加消息的回调可空依赖)。

持久化本身有四层防护:写入 try/catch 吞掉配额与隐私模式异常、读取用过 zod 校验(非法形状降级为空)、容量截断、SSR 守卫;任何一层失败都降级为"无历史"而非报错。设计哲学是持久化是增强不是依赖。

自动滚动与流式光标也有细节:消息列表用带自动跟随的滚动原语,仅最后一条设滚动锚点,用户上翻时暂停跟随、回底后恢复;每条消息用 CSS 渲染包含跳过屏外绘制,构成轻量虚拟化。回答未到达时先渲染思考占位,流式中转发 streaming 标记给渲染器显示打字光标。流式期间输入框与发送按钮禁用、新建会话被拦截并提示——全局只有一个进行中的流,避免并发流对单一消息状态的竞写,这是"用状态机约束交互"而非"到处判空"。

### 样式与组件

样式只用原子类、不写自定义 CSS,组件样式内联于 className;状态变体交给无样式的组件原语管理(模式切换用受控切换组,选中态样式由组件内部变体决定);通知样式同理下沉到 toast 组件。交互细节(下拉的点击外部关闭、Escape 关闭、焦点管理、可访问性属性)下沉到经过测试的 headless 原语,业务组件只做声明式组合,全局事件监听不出现在业务代码里。

对 AI 协作的价值也值得记录:原子类的语义在 className 里自解释,生成代码不需要跨文件追踪类定义;无样式覆盖与优先级问题,不会引入级联 bug。本质上是把样式的自由度换成可预测性。

### 国际化

界面文案与 API 信封消息经统一的国际化方案提供中英双语;成功值 `"OK"` 是不翻译的协议常量,而错误文案(缺参数、文件类型不支持、历史不可用、管理门禁等)都做本地化。语言切换由独立组件完成,路由与文案 key 树的一致性有离线冒烟脚本校验。

## 十一、DevFlow 产品面实现

DevFlow 不是 OnCall 的附属页面,而是一套完整的工作台,其实现思路与 OnCall 共享能力层但编排各不相同。

### 数据同步与调度

仓库接入后,同步管道拉取 issue、PR(含变更文件与行内评论)、CI 运行(含作业与步骤)并归一化落库,带 GitHub 实体 id 的幂等 upsert。同步可由页面手动触发、由 GitHub webhook 增量触发(用共享密钥校验 HMAC-SHA256 签名,密钥为空时跳过校验仅供本地开发),或由进程内的周期循环后台执行——循环默认关闭,开启后按配置周期与数量上限重同步,启动钩子在服务初始化时启动它(serverless 环境应关闭)。每次同步记录时间与错误,便于前端展示健康状态。

### 结构化分析引擎

issue 与 PR 的分析是"确定性引擎 + LLM 增强"的混合结构:确定性部分用规则计算分类、优先级、复杂度、敏感文件识别、测试覆盖识别、风险发现、合并建议等,LLM 部分补充解释与建议,两者合并后落入分析结果记录。关键约束是任何被建议的负责人必须在允许集合内(团队成员与角色),防止模型编造不存在的人;同理,分析产出的写操作建议不能直接执行,而是生成 ActionDraft。

CI 调试与 issue/PR 分析共享同一套输入抽取与证据收集思路,并支持流式输出(分析过程以 SSE 推进度)。

### 会话 agent 与韧性层

DevFlow 聊天 agent 用原生工具调用对单仓库的已同步数据作答:查询 issue/PR/CI、检索本仓库知识、读取托管检出文件、词法搜索代码、检索项目文档,以及生成安全动作草稿。agent 另有一套 DevFlow 技能注册表(data/devflow-skills/ 下 6 个 SKILL.md 工程剧本:issue 分诊、PR 审查、CI 调试、项目调查、安全草稿、周报),轻量目录常驻 system prompt,触发词命中本轮消息的剧本再把完整工作流指令注入(渐进式披露),注册表加载或激活失败只降级为无技能继续对话。它的韧性层值得单独说明,因为这是长会话里最容易被忽视的部分:

- 重复调用断路器:同一轮内相同"工具名 + 规范化参数指纹"的调用超过阈值即短路,回填一条观测告诉模型"这已经调过了,用现有结果回答或换个路径",避免模型陷入重复调用。
- 错误分类与单次重试:把工具错误分为超时、限流、瞬时网络、权限、数据缺失、模型输出非法、运行时错误等类别,只对瞬时类别自动重试一次,其余直接作为结构化观测回填。
- 空答案兜底:预算耗尽而没有任何模型文本时,依据已调用的工具拼一条诚实的"查了这些但没有结论"的回答并持久化,而不是留下空消息。
- 失败轮持久化与上下文溢出投影:流失败时把本地化的失败说明作为助手消息落库,保证用户消息不成为孤儿、反馈仍有锚点;检测到上下文溢出错误时对历史做一次投影后重试一次。

### 每仓库 RAG 与答案门禁

DevFlow 的知识库复用 OnCall 的混合检索,但用来源前缀过滤圈定仓库,并支持每仓库的检索配置(方法 hybrid/dense/bm25、是否精排、topK、切分参数)。知识文档从上传、issue/PR/会话产出等多种来源进入(来源类型可辨),先落注册行再切块索引,失败可重试(正文已存侧表)。检索之上有答案门禁:从查询里提取强信号(如明确指代、具体实体),再结合证据强度决定是直接作答、走抽取式兜底,还是如实拒答;抽取式兜底直接从证据里挑句子组织答案,避免在证据不足时让模型自由发挥。问答结果带引用,并被前端渲染为可核查的来源。

### 项目文档索引与代码理解

托管检出是 DevFlow 的差异化能力:服务端把仓库浅克隆到本地磁盘,文件工具(列目录、读文件、词法搜索)在受控路径与大小上限内操作这些文件。项目索引在此基础上发现仓库的文档与清单文件,按检出指纹(分支与提交)判断是否需要重建,切块后以独立来源前缀写入同一个 Milvus 集合,并生成项目摘要(技术栈、顶层目录、来源覆盖等)。

代码理解用正则抽取符号(函数/类/变量等)与关系(导入、调用、定义、引用),构建跨文件图,支持按名/路径检索符号与从符号出发的影响面遍历;它在 PR 快照范围内也可运行,使"这个改动会影响谁"能落到具体符号。知识图谱则跨实体连接 issue、PR、文档、人与决策,提供子图遍历。

### 草稿闸门、记忆与反馈

写操作闸门是 DevFlow 的安全核心:模型(或确定性引擎)只能生成草稿,草稿带类型、目标、风险级别与状态,默认待确认;人工确认后才执行并记录执行结果或错误。这把"AI 给出建议"与"AI 实际改动仓库"严格分开。

记忆分两层:会话级结构化记忆(摘要、事实、决策、未决问题、任务、用户偏好、仓库上下文、引用)与仓库级线程记忆(由已封存会话合并而来),另有记忆候选——agent 提出的、需人工审核后才能沉淀为知识文档的条目。审核通过的记忆笔记以独立来源类型进入知识库,反哺后续检索。

反馈闭环:每条助手消息可点赞/点踩;负反馈带原因与备注进入审核视图,可经通知通道推送给维护者并附回溯链接。反馈状态(待审、处理中、已解决、已忽略)与通知状态分开记录。

### 多 agent 工作流

除单步分析外,还存在把"规划 → 观察 → 综合"显式分阶段的多 agent 工作流:一次运行落一条工作流记录与若干任务级记录,每个任务带角色、类型、输入、结果与状态,支持中断与恢复。它把长任务拆成可审计、可重放的任务链,代价是更高的 token 消耗与更复杂的编排,因此只用于确实需要多视角协作的目标。

## 十二、可观测性与错误处理

### Langfuse 追踪

观测层只有一个开关:三个 Langfuse 环境变量全部非空才启用,任一缺失时初始化、回调、trace 包装、generation 记录全部 no-op 降级——可观测性是增强不是依赖,未配置时对管线行为零影响;即便三变量齐备,追踪 SDK 启动失败也只告警并继续。

实现是 OTEL 原生的:构建 NodeSDK,span 处理器只有一个 Langfuse span 处理器,即标准 OTEL span 直接导出到 Langfuse。抗热重载的关键细节是 SDK 实例缓存在 globalThis 上——OTEL 全局 provider 注册是进程级永久的,而开发环境会反复重新求值模块文件,缓存保证只注册一次。启动时序上,服务启动钩子在 Node 运行时守卫后先初始化追踪再做知识索引,确保 telemetry 先于业务。

一次 AI Ops 运行产出"一条 trace + 若干 generation":图运行经 LangChain 回调处理器自动为图与节点建 span,运行生成的 session id 把同一次调用的 trace 归入同一 Langfuse 会话;五处 LLM 调用(planner、单步执行、replanner、报告重写、界面化)分别包在 generation 观测里,记录输入、输出、模型 id 与 token 用量(含输入/输出/总量)。之所以要用属性传播同时包住"建流"与"每次取 chunk":图流是惰性执行的,节点真正运行发生在取块时,执行上下文与建流时不同;若只在建流那一刻挂属性,节点运行期间创建的观测会散落,属性传播在每个挂起/恢复边界重建上下文才能保证归组。这是异步迭代与上下文传播组合的通用模式。

当前缺口也要如实说明:对话管线仍只有工具审计与出错时的控制台日志,没有 generation 级的追踪与 token 计量;AI Ops 路径则已完整。多实例排查时,完整的 generation 记录是"某次分析为什么跑了很久"的主要依据。

### yukino-sentry 到 Prometheus 的指标桥

应用自身是前端监控 SDK 的接入方与指标后端。浏览器端初始化 SDK,把上报地址指向本应用的 `/api/log`;上报端点把请求体解析后过宽松的批次 schema,非法批次记一条计数并返回 400,合法批次逐条分发为指标。指标桥覆盖除录屏外的全部上报类型:

| 类别         | 指标(前缀)                                                                                                                                         | 说明                                   |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------- |
| 事件与错误   | `yukino_sentry_events_total` / `errors_total` / `batch_error_groups_total`                                                                         | 事件总量、错误总量、批次错误分组       |
| 资源与请求   | `resource_errors_total` / `http_requests_total` / `http_request_duration_ms`                                                                       | 资源加载失败、请求计数与耗时           |
| 性能核心     | `web_vitals` / `navigation_timing_ms` / `resource_entries_total` / `resource_duration_ms` / `resource_transfer_bytes`                              | Web Vitals、导航分段、资源体积与耗时   |
| 运行时       | `long_tasks_total` / `long_task_duration_ms` / `browser_memory_bytes` / `browser_memory_breakdown_bytes`                                           | 长任务与内存                           |
| 交互与曝光   | `clicks_total` / `exposures_total` / `exposure_duration_ms` / `white_screens_total` / `page_views_total` / `page_dwell_ms` / `custom_events_total` | 点击、曝光、白屏、页面停留、自定义事件 |
| 上报自身     | `report_batches_total` / `report_batch_size`                                                                                                       | 批次计数与大小,便于发现上报链路异常    |
| 服务端运行时 | prom-client 默认指标 + 堆上限与使用率、分离上下文数、事件循环利用率、页错误、上下文切换、文件系统操作                                              | 覆盖 Node/V8 视角,与浏览器指标互补     |

两个工程亮点:标签基数防御,浏览器上报的字符串标签(错误名、点击目标、自定义事件名)是攻击者与重构都能控制的输入,每个标签键最多保留固定数量(50)的不同取值,溢出一律归并,否则一次坏上线就能把指标序列数量炸掉;registry 版本化缓存,registry 挂在 globalThis 上(路由 bundle 与开发热重载会重复求值模块,全局缓存保证每进程一个),并带版本号——指标集变更必须提升版本,否则长驻的开发服务器会继续用缺字段的旧缓存,新字段在类型上存在但运行时报错,第一次自增就抛异常;重建的代价只是一次计数器清零。

`GET /api/metrics` 直接吐 registry 内容。前端 SDK 侧还有一处容错:批次过大(如录屏与开发页的大量资源条目)会顶过上报请求体上限,因此单事件超过阈值时被丢弃,避免永久卡死的重试。

### 告警规则与处理文档的契约

AI Ops 的 SOP 是用告警名去检索处理手册,因此每条告警规则的名字必须与知识库中同名标题一一对应,否则检索落空、模型失去知识锚点。这条契约把四个模块串成闭环:前端监控采集 → 上报入库 → 指标暴露 → Prometheus 告警 → AI Ops 一键分析 → 报告与界面呈现。规则文件本身也演示了运行时指标的正确用法(存活、堆接近上限、疑似泄漏、分离上下文泄漏等),全部基于指标桥暴露的 Node/V8 指标。

### 面向 LLM 的错误处理

LLM 调用的错误与传统 API 不同:错误信息常常不在 `message` 里,而在响应体中(尤其兼容网关)。因此有三层针对性设计。结构化提取上游错误:捕获后提取名称、消息、状态码、URL、响应体与响应头序列化返回,而不是只回 `e.message`,因为 SDK 会把上游真实报文放在响应体里而非官方网关报错时消息常为空。SSE 错误事件化:流开始后无法改状态码,错误经 error 帧带内下发,客户端解析器收到后抛出并渲染本地化文案——错误处理与正常数据共用同一条流。工具层降级而非抛出:告警查询失败返回 `{success:false, error}` 结构,让模型看到"查询失败"这个事实并自行解释或换路径,而不是让异常中断整个循环;MCP 连接失败降级为空工具集并告警。

原则可以概括为三句话:面向 LLM 的错误要可读(喂给模型做决策),面向人的错误要可诊断(保留上游原始报文),面向流的错误要带内传输。

### 就绪与配置自检

就绪探针逐依赖检查并返回状态与延迟:数据库与向量库是核心检查,任一失败返回 503;Embedding、LLM、Rerank、Prometheus、MCP、告警源是信息性检查,配置缺失或不可达只降级为该项失败,不改变整体状态码。检查会为每项打上非敏感详情(如模型名或"未配置"),并对探测设置超时。配置自检只报告"是否已配置 + 非敏感详情"(连接串中的凭据部分被掩码),绝不回显密钥本身,并汇总出必填项的缺失清单(如 Embedding Key、LLM Key、管理 Token)。两者都把"配置错误"从运行期神秘故障前移成启动期可读结论。

## 十三、配置与环境变量体系

环境变量读取集中在配置层一处,用空值合并给出默认值,导出 `as const` 对象——这使环境变量的使用可审计,默认值本身即文档,且字面量类型精确;仅两处例外在使用点就地读取:对话管线的日志主题 region/topic id 与 MCP 多连接模块的管理 Token。数值型变量显式解析为整数,布尔型变量采用"默认开、显式关"的语义。样板文件给出键名清单与说明但不含真值,真实值文件必须被忽略并定期轮换。

## 十四、部署与运行形态

应用是单个 Next.js 进程,通过服务启动钩子完成三件按序的事情:初始化可观测性;把知识库目录下所有受支持文档重建索引(单文件失败只记日志并跳过,目录不存在只告警,绝不阻塞启动);启动 DevFlow 的周期重同步循环(未显式开启则 no-op)。启动即自检自愈的模式与集合维度自检组合,使"换 Embedding 模型"或"改知识库文件"都能在重启后自动收敛。

外部依赖由部署侧编排:PostgreSQL(关系数据)、Milvus Standalone(向量)、Prometheus(告警与抓取指标)、可选的 MCP 服务与 Langfuse。知识库文件、DevFlow 托管检出都保存在本地目录,意味着多实例部署时文件与索引会出现不一致,且托管检出需要可写的持久磁盘(serverless 环境应避免),演进时文件应迁到对象存储。

仓库自带一组脚本级离线冒烟验证(通过 tsx 直接运行,共二十余个),覆盖编排图结构与事件 schema、Milvus 真实链路、A2UI、文档切分与抽取、国际化、指标桥、OnCall 对话与运维协议,以及 DevFlow 的分析、图、记忆、工作流、工作区、技能、内容索引、迁移还原等。这些脚本用真实依赖或注入假件验证关键机制,是仓库当前的主要自动化保障;其中需要真实模型的部分要用环境变量显式开启,并可用一个更便宜的查询控制成本。此外还存在一个静态断言:递归上限必须大于业务迭代预算。

## 十五、性能与成本取舍

成本结构可以拆解为:每轮对话 = 一次 Embedding + (一到若干次工具循环)× 快模型;每次 AI Ops ≈ (一次规划 + N 次重规划 + 可选界面化 + 可选报告重写)的强模型调用 + 步骤数 × 快模型调用(每步至多十次工具小循环);DevFlow 的多 agent 工作流是额外的一层。已落地的优化:

| 手段                                               | 状态   | 效果                                    |
| -------------------------------------------------- | ------ | --------------------------------------- |
| 模型分级(think/quick)                              | 已落地 | 绝大多数调用导向便宜快模型,单点收益最大 |
| 记忆滑窗 + 摘要压缩                                | 已落地 | 限制历史膨胀,长会话不再线性增长         |
| 检索默认 topK 与候选池封顶                         | 已落地 | 控制注入 prompt 的文档量                |
| 双层步数封顶(对话 25、单步 10)                     | 已落地 | 锁死失控循环的调用上限                  |
| MCP 连接与工具集缓存                               | 已落地 | 摊销握手与列工具成本                    |
| Embedding 批量                                     | 已落地 | 网络往返从按条降为按批                  |
| 精排 fail-open                                     | 已落地 | 上游抖动不拖垮检索,但也不额外烧钱       |
| 对话路径 token 计量                                | 待补   | 成本观测目前只覆盖 AI Ops               |
| 报告重写/replanner 输入滚动摘要                    | 待补   | 多轮后 token 膨胀仍存在                 |
| 工具结果行数截断                                   | 待补   | 防大结果塞满上下文                      |
| 上游 prompt 缓存 / 检索结果短期缓存 / 规划步数上限 | 待补   | 进一步降本与防超长计划                  |

延迟方面,首 token 时间由三段时间叠加:检索(Embedding 调用 + 向量检索 + 可选精排)、工具装配(首次需 MCP 握手,之后命中缓存)、模型首 token(排队 + 预填充 + 解码)。可优化点很明确:检索与 MCP 工具装配无依赖关系,可以并行;system prompt 随检索文档变长会拖慢预填充,而默认 topK 与记忆窗口已经控制了这部分;快模型本身就是为低延迟选型。

稳定性方面,当前各外部依赖的故障语义并不一致:Milvus 故障会让对话检索硬失败(纯对话本可以无检索降级),MCP 故障则优雅降级为空工具集。对齐到"检索失败返回空文档并在提示中标注知识库暂不可用"是合理的下一步,这样向量库故障不再连带打挂纯对话。

## 十六、安全边界与已知缺口

需要如实列出当前实现的安全边界,以便判断适用场景。

全部 API 路由的 CORS 都是通配符,这允许任意网页以访客身份消耗本服务的模型额度,内网部署时还可能与员工浏览器组合放大暴露面;CORS 不是鉴权机制,生产环境应收敛到来源白名单并加认证。OnCall 的对话与查询接口无鉴权,任何能访问服务的人都可提问,会话 ID 由客户端自报,存在冒充会话读取服务端记忆的可能(记忆仅数条窗口)。`postgres_query` 的爆炸半径已从"全部数据面"压缩到"一个隔离库",但隔离库内仍是任意写:可生成无 WHERE 的更新或清表删除,超时能兜住单条慢语句却兜不住大量小语句,执行链路也没有交互确认;进一步加固应做 SQL 静态校验(诊断场景绝大多数是查询,可直接禁掉写语句)、把隔离库角色收窄为只读、强制结果行数截断、对高危语句引入人工确认、把所有执行的 SQL 落审计。知识库文件的写入与删除受管理 Token 保护,Token 未配置时受保护的写操作直接关闭,这是 fail-closed 的正确取向。DevFlow 的仓库 Token 加密存库,webhook 签名可校验。间接 prompt injection 无法根除,只能靠边界标记、来源可信、输出侧审计这类纵深防御降低概率;MCP 服务端被污染等价于 agent 被提权。

用威胁建模的视角看,最值得关注两点:数据完整性(隔离库内的任意写、上传同名覆盖他人知识库)与权限提升(prompt injection 诱导模型调用写工具)。工程上先做三件事性价比最高:给受保护操作之外的关键入口加认证并收敛 CORS;把 `postgres_query` 收窄为只读加 SQL 白名单并落审计;把对话路径的可观测性补齐,让成本与质量都可度量。

## 十七、工程质量规范

项目在若干处固化了面向 AI 协作的工程规范,它们同时也是可读的技术约束。

类型纪律:禁止不必要的类型断言与 `@ts-ignore`/`eslint-disable`,未知数据必须经 zod 校验获得类型。这让类型系统说真话——断言是"程序员对编译器撒谎",而 AI 生成代码尤其爱用断言消除编译错误;禁掉后,未知数据必须走校验路径。lint 规则的个案豁免必须带理由注释,规则本身保持防护价值。

zod 边界:凡数据跨越信任边界(HTTP 请求体、API 响应、localStorage、Prometheus 响应、数据库自检结果、MCP schema、LLM 结构化输出、编排事件流、前端监控上报),进入系统时先过 schema。收益有三:脏数据在边界处变成明确错误或安全降级,而不是流窜到深处变成诡异行为;`z.infer` 让 schema 即类型,运行时校验与编译期类型永远同步;规范对生成代码是硬闸门,防止其用断言蒙混过关。成本是微秒到毫秒级的运行时开销,对秒级 LLM 延迟可忽略。

统一响应格式:API 响应包装为 `{ message, data }`,把"传输层结果"(HTTP 状态码)与"业务层结果"(message)分离。message 可以承载结构化错误详情,前端对每个响应先校验形状再判业务状态,一套逻辑走通多个接口;网关可能改写非 200 响应,而业务错误放在 body 里可以穿透。状态码并未被抛弃:参数校验失败返回 400、内部错误 500——状态码给基础设施(监控、重试、网关)看,message 给应用逻辑看。

测试策略:仓库当前以脚本级冒烟验证为主,系统性地覆盖纯函数(切分、时长计算、表达式转义、记忆淘汰、schema 拒绝)、协议契约(SSE 帧、响应形状、事件序列)与集成链路(向量库、编排图)。补测试的优先级建议是:纯函数单测(最高 ROI,全是确定性逻辑)、协议契约测试、用测试容器做向量库集成、用模型测试替身做管线回归(步数上限、事件序列、记忆回写时机、流过滤器的跨块语义)、最后才是端到端。原则是测试金字塔在 AI 应用里依然成立,只是塔尖换成模型评估——用确定性测试守住工程逻辑,用评估度量模型行为。

## 适用场景与扩展建议

适合用它的场景:团队内部的 AI 值班助手(把处理手册、告警、日志收进一个可追问、可溯源的入口);需要"确定性 SOP + 局部模型决策"的运维自动化;需要把结构化数据渲染成可交互界面的问答产品;需要在同一进程里同时承载问答与 GitHub 工程协作两个 AI 表面的团队;以及需要"检索 + 编排 + 可观测 + 指标闭环"完整参考实现的团队。

不适合的场景:面向公网的高并发多租户产品(当前无鉴权、CORS 全开、单进程长连接);需要无状态弹性伸缩的部署(内存记忆、本地知识库文件、托管检出都是硬约束);对写操作自主性要求高但又不接受人工确认的场景(A2UI 与草稿闸门的设计取向是保守);万级 chunk 以下的纯向量检索场景(用 Milvus Standalone 三件套属于能力过剩,可评估收敛到关系库的向量扩展)。

扩展建议按性价比排序。第一,补认证与 CORS 收敛,这是从"内部演示"走向"可信服务"的门槛;同时给高风险工具加人工确认与审计。第二,补齐对话路径的 token 计量与检索命中率、分数分布等输出侧监控,让优化有依据,而不是凭感觉调参。第三,把记忆与知识库文件外置到共享存储与对象存储,打通水平扩展;把索引操作从同步改为任务队列,使上传与重建不阻塞请求。第四,把 AI Ops 改造成流式体验:管线已是事件流,把每个事件序列化成一帧 SSE,前端按类型渲染进度时间线,用户十秒内看到计划、中途可发现跑偏并中止,这对运维工具的信任度是质变。第五,针对 OnCall 报告做程序化的引用核查——报告中提到的告警名是否都在工具真实返回里、时间是否与时间工具一致,不符则标注警告,把幻觉防线从提示词推进到结构性校验,并把三层评估(检索、生成、端到端)纳入持续集成。第六,把 SOP 本身存入知识库,按告警类型动态装配根指令,替代当前硬编码的单一指令。
