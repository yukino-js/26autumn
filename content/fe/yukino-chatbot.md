本文拆解一个 pnpm workspace 组织的全栈 LLM 聊天应用: 前端 React 单页应用, 后端 Koa 服务, 具备 JWT 会话、模型热切换、RAG 检索增强与 SSE 流式输出。内容以功能能力、实现思路与取舍为主线, 覆盖前后端分层、认证、AI 能力抽象、检索链路、流式渲染性能、数据与缓存, 以及水平扩展时的改造方向。适合正在做 LLM 聊天类产品、关心流式渲染与上下文管理的工程师阅读。

## 定位与技术选型

### 能力边界

应用提供账号注册登录、会话管理、普通对话与 RAG 增强对话两条链路、文件上传、流式打字机输出、中英文界面与亮暗主题。AI 能力通过 OpenAI 兼容端点接入, 因此同一套代码可以对接云端模型服务, 也可以对接本地推理服务。模型类型当前只有两个取值: `openai`(普通对话)与 `openai-rag`(检索增强对话)。

### 技术选型

| 维度     | 选型                                                                 |
| -------- | -------------------------------------------------------------------- |
| 前端     | [React](react) 19 + TypeScript + [Vite](vite) 8                      |
| 状态管理 | Jotai(客户端状态) + [TanStack Query](tanstack) v5(服务端状态)        |
| UI       | Base UI(headless 原语) + Tailwind CSS 4 + shadcn/ui 模式             |
| 后端     | Koa 3 + @koa/router                                                  |
| LLM      | LangChain(OpenAI 兼容接口)对接 Chat/Embedding 端点, 默认 qwen3       |
| 数据库   | MySQL, 通过 Knex 查询构建器访问                                      |
| 缓存     | Redis(ioredis), 不可用时降级到进程内 LRU                             |
| RAG      | LangChain MemoryVectorStore + OpenAIEmbeddings                       |
| 构建     | 前端 Vite, 后端 Rollup 打包为单文件 ESM                              |
| 认证     | `jsonwebtoken` 库签发/验签 + 自写 Koa 鉴权中间件 + 前端 axios 拦截器 |
| 国际化   | i18next + react-i18next, 中文/英文两套语言包                         |

这是一个前后端分离的 pnpm monorepo, 只声明 `client` 与 `server` 两个 workspace 包, 并没有共享类型包。`Message`、`Session` 等类型由前后端各自独立定义, 仅靠约定保持字段兼容(例如 `ModelType` 的取值两边一致, 但消息与会话的字段形状并不相同)。选择同仓管理的主要价值不在于共享类型, 而在于接口变更可以在一次提交内原子完成, 并且根脚本用 `concurrently` 一条命令同时拉起前后端开发服务器。

### 后端分层

```text
Router (@koa/router)          URL 映射, 中间件挂载
  └─ Controller               zod 参数校验 + 响应体格式化
       └─ Service             业务编排, 协调 DAO 与 AI Agent
            └─ DAO            纯数据访问, 封装 Knex 查询
                 └─ MySQL / Redis

AiAgent / AiModelFactory / AiAgentManager 系统独立于以上业务分层
```

| 层级       | 职责                                       |
| ---------- | ------------------------------------------ |
| Router     | URL 到 Controller 的映射, 挂载横切中间件   |
| Controller | zod 校验入参, 调用 Service, 组装统一响应体 |
| Service    | 业务逻辑编排, 协调 DAO、缓存与 AI Agent    |
| DAO        | 数据访问, 所有 SQL 只在这一层出现          |
| Model      | TypeScript 类型定义                        |
| Middleware | JWT 鉴权等横切关注点                       |
| AI         | Agent 系统(工厂、管理器、模型、流式回调)   |
| RAG        | 文档加载、分块、向量化、检索与 Prompt 增强 |

所有接口返回统一信封 `{code, message, ...data}`。`success()` 与 `codeOf()` 这类工具函数把业务层的返回值翻译成信封, 使 Controller 不用逐接口拼装响应结构。

### 前后端通信

开发环境由 Vite dev server 代理转发: `/api/*` 打到后端 `:8088` 的 `/api/v1/*`, 通过 path rewrite 去掉 `/api` 再加版本前缀, 因此前端业务代码统一使用 `/api/` 开头的相对路径, 不感知后端地址。生产环境把前端构建产物作为静态资源, 由反向代理统一分发: 静态文件直接返回, `/api/` 前缀转发到 Koa 服务。业务代码在两种形态下写法完全一致。服务端依赖里声明了 `koa-static` 并在打包 external 中列出, 但代码中没有任何引用——Koa 只处理 `/api/v1` 下的接口, 静态资源完全交给反向代理。

| 通道     | 协议                                    |
| -------- | --------------------------------------- |
| 普通请求 | JSON over HTTP(POST/GET)                |
| 流式响应 | Server-Sent Events, `text/event-stream` |
| 认证     | `Authorization: Bearer <token>`         |

## 工程化与配置体系

### 构建方案

| 端   | 构建工具                                       | 产物             |
| ---- | ---------------------------------------------- | ---------------- |
| 前端 | Vite(@vitejs/plugin-react + @tailwindcss/vite) | 静态 HTML/JS/CSS |
| 后端 | Rollup + TypeScript 插件                       | 单个 ESM bundle  |

后端选择 Rollup 而不是直接 `tsc` 输出多文件, 原因有三点。其一, 单文件 bundle 简化部署, 运行时不再需要 node_modules 中的本地源码树。其二, tree-shaking 能移除未使用的代码路径, 缩小部署体积。其三, 通过 external 配置把全部第三方依赖排除在 bundle 之外(`node:` 内建模块、`@langchain/` 与 `@koa/` 前缀走正则匹配, 其余逐个列名), 避免把大型依赖重复打包, 运行时再从 node_modules 加载。TypeScript 只在构建期做类型擦除, 产物是纯 JavaScript。

开发态后端用 `tsx watch` 直接运行 TypeScript, 无构建步骤, 文件变更自动重启, 与前端 Vite 的 HMR 组合成完整的本地开发闭环。代码规范上前端用 ESLint + Prettier, 后端用 Biome(把 lint 与 format 合并为单一工具)。

### 配置体系

模型端点全部通过环境变量注入, 代码里不出现任何硬编码地址。

| 变量                                       | 用途                | 默认值             |
| ------------------------------------------ | ------------------- | ------------------ |
| `OPENAI_MODE_NAME`                         | 聊天模型名          | `qwen3`            |
| `OPENAI_BASE_URL` / `OPENAI_API_KEY`       | 聊天端点与凭据      | OpenAI SDK 约定    |
| `EMBEDDING_MODEL`                          | 向量化模型名        | `nomic-embed-text` |
| `EMBEDDING_BASE_URL` / `EMBEDDING_API_KEY` | 向量端点与凭据      | 独立配置           |
| `REDIS_ENABLED`                            | 是否启用 Redis 缓存 | 非 `"true"` 走 LRU |

`qwen3` 与 `nomic-embed-text` 这类模型名通常对应 Ollama 之类的 OpenAI 兼容推理服务, 只要端点遵循 OpenAI 协议, 换用云端模型只需改环境变量。聊天与向量两套端点分开配置, 是因为二者在生产中经常落在不同服务上。聊天端点本身不在配置对象里出现: `ChatOpenAI` 只显式传入模型名, base URL 与 API key 由 OpenAI SDK 按 `OPENAI_BASE_URL`/`OPENAI_API_KEY` 的环境变量约定自行读取。

除模型端点外, 同一份配置还覆盖三组变量: 应用监听(`APP_HOST`/`APP_PORT`, 默认 `0.0.0.0:8088`)、MySQL 连接(`MYSQL_HOST`/`PORT`/`USER`/`PASSWORD`/`DB`/`CHARSET`, 默认 `localhost:3306` 的 `yukino_chatbot` 库、`utf8mb4`)、以及 JWT(`JWT_KEY`/`JWT_EXPIRE_DURATION`/`JWT_ISSUER`/`JWT_SUBJECT`)。所有默认值都写在代码里, 不配置也能起服务, 这正是上文安全弱点表中"密钥有默认值"的来源。

有一处配置是空转的: `DOCS_DIR`(默认 `./docs`)被解析进配置对象的 RAG 段, 但检索链路实际读取的是硬编码的 `uploads/<username>` 目录, 该变量没有任何消费者。

## 认证与会话管理

### JWT 流程

1. 用户登录或注册, 服务端校验凭据后用 `jsonwebtoken` 库签发 JWT: payload 为 `{id, username}`, 另带 issuer 与 subject(默认都是 `yukino-chatbot`), 有效期 8760 小时(一年)。验签同样走该库, 中间件只负责从请求里取出 token 并把解出的 `username` 写进 `ctx.state`。
2. 前端把 token 写入 `localStorage`, 后续请求在 `Authorization: Bearer <token>` 中携带。
3. 服务端鉴权中间件解析并验证 token, 把 `username` 注入 `ctx.state`, 供 Controller 与 Service 使用。

一个值得注意的行为: 注册接口并不接收用户名字段, 服务端直接用邮箱派生用户名(`username = email`), 并且注册成功即签发 JWT 返回, 也就是注册即登录。注册表单的前端校验因此只覆盖邮箱与密码, 用户名不在用户可控范围内。

### 前端 token 与请求层

token 在 Jotai 中以普通 `atom` 创建, 初值取 `localStorage.getItem("token")`, 由写入 action 手动调用 `setItem`/`removeItem` 持久化; 是否已登录由派生 atom 基于 token 是否存在计算。主题与语言通过 `atomWithStorage` 自动持久化, 刷新后恢复。设置 store 里还定义了一个同样持久化的模型类型 atom, 但全仓没有任何组件引用它——聊天页真正使用的选中模型是组件本地 state, 刷新后回到默认值, 并不跨刷新保留。

普通请求统一走一个 axios 实例, 其要点可以概括为四条:

1. baseURL 固定为 `/api`, 开发环境由 Vite 代理, 生产由反向代理, 业务代码不感知部署形态。
2. 超时设为 0(不限时), 因为 AI 生成回答的耗时不可预估。
3. 请求拦截器从 `localStorage` 读取 token 注入 Bearer header, 与 Jotai 的 token atom 共用同一个 storage key, 但不经过 React 体系。
4. 响应拦截器统一处理 401: 清除本地 token 并跳转登录页, 各业务 mutation 不必重复编写登出逻辑。

React Query 的全局默认值设置为 `retry: 1`、`refetchOnWindowFocus: false`、`staleTime` 5 分钟。流式请求完全绕开 axios, 用原生 `fetch` 消费 SSE, 因为需要手动控制响应体的 `ReadableStream`。

### 路由与权限守卫

路由表定义五条路由: 根路径的 loader 直接重定向到登录页, 以及登录、注册、菜单、AI 聊天四页。页面组件均通过 `lazy` 懒加载, 受保护的两页额外包裹 `withAuth` 高阶组件。`withAuth` 读取登录态派生 atom, 未登录时用 `useEffect` 跳转到登录页并返回 `null`, 已登录则渲染被包裹组件。仓库中另有一个逻辑等价的守卫组件, 但路由表挂载的是 `withAuth`, 该组件未被引用。

### SSE 场景的鉴权兼容

鉴权中间件同时支持两种取 token 的方式: 优先从 `Authorization` header 读取, 找不到时回落到 query 参数 `token`。前端的 SSE 走 `fetch`, 本可以直接设置 header, 保留 query 兜底是为了兼容那些无法自定义请求头的消费方式。由于 URL 可能进入日志与浏览器历史, header 是首选路径。

### 已知安全弱点

| 弱点                | 风险                                                        | 改进方向                         |
| ------------------- | ----------------------------------------------------------- | -------------------------------- |
| 密码用 MD5 哈希     | 无盐值, 可被彩虹表攻击                                      | 改用 bcrypt/argon2 + 随机盐      |
| JWT 有效期一年      | token 泄露后长期有效                                        | 缩短有效期并引入 refresh token   |
| JWT secret 有默认值 | 未配置时使用可预测密钥                                      | 启动时强制要求配置, 否则拒绝启动 |
| 无速率限制          | 暴力破解与资源耗尽                                          | 接入限流中间件                   |
| CORS 全开           | 扩大跨域攻击面                                              | 配置域名白名单                   |
| 请求体上限 100MB    | 大 payload 造成 DoS                                         | 按接口收紧限制                   |
| 鉴权日志打印 token  | 中间件以 info 级别把完整 token 写进日志, 日志泄露即凭据泄露 | 降为 debug 或只记不可逆指纹      |

## AI 能力层: Provider、工厂与热切换

### 三个角色的分工

| 角色           | 职责                                                                |
| -------------- | ------------------------------------------------------------------- |
| AiModelFactory | 模型注册表与创建入口: 注册创建器、按类型创建模型实例、创建 Agent    |
| AiAgentManager | 单例生命周期管理: 维护 `用户 -> 会话 -> Agent` 的映射, 负责热切换   |
| AiAgent        | 单会话实例: 持有内存对话历史与当前模型, 提供普通/流式对话与消息追加 |

设计原则是"工厂负责如何创建, 管理器负责在哪里、给谁, Agent 负责如何对话", 三者职责单一, 通过组合协作。工厂构造时已内置注册 `openai` 与 `openai-rag` 两种创建器, 其中 RAG 创建器要求配置里带上 `username`(用于定位该用户的文档目录)。新增模型类型时, 先在 `ModelType` 枚举中加取值, 再注册对应创建器即可, Agent、管理器与 Controller 无需改动。

### 对话上下文管理

每个 Agent 实例在内存中维护一个完整的历史消息数组, 每次调用 LLM 时把历史转换为 LangChain 的消息格式传入。选择内存存储有三个理由: LLM 调用需要完整上下文, 从内存读取是 O(1) 而查库有网络开销; 无需序列化与连接池竞争, 实现更简单; 消息写入内存后立即可用于下一次调用, 具备写后读一致性。

持久化采用 write-behind 模式: `addMessage` 先写内存, 再以 fire-and-forget 方式异步落库, 落库失败只记日志、不阻塞主流程。代价是进程重启后内存丢失, 必须靠启动物化流程重建。

### 模型热切换

管理器在被请求获取 Agent 时检查已有实例的模型类型: 若与请求携带的 `model_type` 不一致, 就用工厂创建新模型实例并替换 Agent 持有的引用, 而对话历史数组保持不变。于是用户在普通对话与 RAG 对话之间切换时, 上下文完整延续, 无需新建会话。切换的成本只是重建一个模型对象, 历史转移是引用赋值。

### 重启后的上下文重建

服务启动时执行一次全量重建: 从 MySQL 的 messages 表按 `created_at` 升序加载全部消息(不查 sessions 表, 会话按消息携带的字段隐式恢复), 逐条调用管理器的获取或创建, 再以"仅恢复内存、不重复落库"的方式注入 Agent 的历史数组。这样进程崩溃重启后, 用户回到原会话时 AI 仍记得此前内容。

两个代价需要注意: 启动耗时随历史消息总量线性增长; 重建时统一按普通模型创建 Agent, 如果用户上次停在 RAG 模型, 要等下一次请求携带新 `model_type` 时才由热切换纠正。面向生产更稳妥的做法是按会话分页懒加载, 而非启动时全量回放。

## RAG 检索链路

### 上传链路

文件上传到落盘的完整路径如下:

1. 前端用隐藏的 `input` 触发选择, 只放行 `.md`/`.txt`, 并由上传 hook 再做一次扩展名校验。
2. 以 `FormData` 提交到上传接口, 服务端经 multer 写入临时目录。
3. 服务端做白名单校验后, 以 CRC32 内容哈希命名, 拷贝到 `uploads/<username>/` 并删除临时文件。

关键设计是内容寻址去重: 文件名取文件内容的 CRC32 十六进制表示并补齐 8 位, 同一内容重复上传会得到相同路径, 拷贝时直接覆盖, 天然去重且无需额外索引。目标目录按用户名隔离, 与检索时定位用户目录的规则一一对应。multer 先落临时目录再拷贝, 使校验失败的请求不会污染用户目录。

存在一处前后端白名单不一致: 服务端允许 `.md`、`.txt`、`.json` 三种扩展名, 而前端 `accept` 与校验只放行前两种, 因此 `.json` 文件实际上无法通过界面传入。服务端白名单是最终防线, 前端校验只是体验层的先行过滤。

### 检索与增强

当请求的 `model_type` 为 `openai-rag` 时, 每轮对话会即时构建检索链路: 读取该用户目录下的文档, 用递归字符分块器切分, 经 Embedding 端点向量化, 用内存向量库建立索引并检索与问题最相关的 Top-5 片段, 最后把片段注入 Prompt 交给聊天模型生成回答。

Prompt 的结构包含三部分: 要求"基于参考文档回答, 文档中没有相关信息时明确说明未找到"; 编号列出的参考文档片段; 用户原始问题。增强方式是只替换最后一条用户消息, 历史消息保持原样, 因此多轮对话里只有当前问题会被检索结果增强。

### 容错降级

检索链路的每一步都可能失败: 用户没有上传任何文件、文档读取异常、embedding 调用失败、检索结果为空。`ragEnhanceMessages` 对前三种情况直接返回原始消息, 对空结果则不注入 Prompt, 三条路径都让本轮对话静默降级为普通问答, 而不是把错误抛给用户。这种"检索是增强而非依赖"的定位让 RAG 故障不会中断聊天主流程。

### 分块参数的选择依据

分块器参数为 `chunkSize=1000`、`chunkOverlap=200`。1000 字符约覆盖一个完整段落或代码块, 过小会丢失段落语义, 过大则引入噪声、降低相似度匹配的精度。200 字符对应约 20% 的重叠率, 用于覆盖被截断在块边界上的关键概念: 若某个概念恰好在第 1000 字符处被切开, 重叠部分保证下一个块仍包含完整语境。分割优先按空行、再按换行、空格逐级递归, 尽量落在自然语义边界; 最后的空串分隔符是兜底, 保证超长且无分隔符的文本也能被硬切分。

### 为什么用内存向量库

当前选型的合理性来自规模: 单用户文档量有限, 向量数量在百到千级别, 内存足以承载; 无需额外部署独立向量数据库, 降低运维复杂度; 每用户索引独立构建, 天然隔离, 不必在向量库中做 namespace 管理。

局限同样明确: 每次请求都重建索引, 文档未变也会重复向量化, 既有 embedding 调用的延迟也有费用; 文档量增长到数万页时内存与延迟都不可接受。演进方向是接入持久化向量库并做增量索引, 只在文档变更时重新向量化。

## SSE 流式输出与断线恢复

### 完整数据链路

```text
用户输入
  └─ useStreamMessage: 原生 fetch POST, 携带 Bearer token
       └─ Koa Controller: zod 校验 -> 直接操作 Node 原生 res
            └─ SessionService -> AiAgent.responseStream()
                 └─ ChatOpenAI.stream(): async iterator, 逐 token 回调
                      └─ res.write("data: <json>\n\n")
                           └─ 客户端 response.body.getReader() + TextDecoder
                                └─ 按行解析 SSE, 累加写入 streamTextRef (零 React 渲染)
                                     └─ StreamingMarkdown 的 rAF 循环拉取
                                          └─ Streamdown 增量解析 -> DOM 更新
                                               └─ 收到 data: [DONE] -> onDone 落单
```

服务端每产生一个 token 就立即写入并 flush, 客户端通过 `ReadableStream` 逐块读取。token 以 JSON 字符串编码写入 data 字段, 客户端再 `JSON.parse` 还原, 这样换行等特殊字符不会破坏 SSE 分帧。

### 服务端实现要点

- 绕过 Koa 的响应模型, 直接操作 Node 原生 `ServerResponse`, 用 `res.writeHead` 写出 `Content-Type: text/event-stream`、`Cache-Control: no-cache`、`Connection: keep-alive` 与 `X-Accel-Buffering: no`。
- `X-Accel-Buffering: no` 用于禁止 Nginx 之类的反向代理缓冲, 否则 token 会被攒成大块再下发, 打字机效果消失。
- 先创建会话(用 `randomUUID` 生成会话 ID 并落库), 再把 `{session_id}` 作为 SSE 首帧元数据下发, 之后才开始正文 token。
- 全部完成后发送 `data: [DONE]` 作为结束哨兵; 错误路径发送 `event: error` 帧。
- 同时提供非流式端点, 等待完整回答一次性返回, 前端用开关在两种模式间切换。

为什么必须绕过 Koa: Koa 的响应模型是一次性的, 中间件链执行完毕后才把 `ctx.body` 序列化发送, 而 SSE 需要在请求生命周期内持续写入并即时 flush; 连接关闭时机由业务逻辑(收到哨兵或出错)决定, 而非中间件链结束。直接操作原生响应对象也便于设置 `X-Accel-Buffering` 这类非标准头。

### 为什么用 Fetch 而非 EventSource

| 维度     | EventSource        | Fetch + ReadableStream          |
| -------- | ------------------ | ------------------------------- |
| 请求方法 | 只支持 GET         | 任意方法, 本项目用 POST         |
| 自定义头 | 不支持             | 可携带 `Authorization`          |
| 错误粒度 | 不暴露 HTTP 状态码 | 可检查 `response.ok` 与状态码   |
| 请求体   | 无                 | 可发送 `{question, model_type}` |

三点合起来决定了 `EventSource` 不可用: 流式接口需要 POST 请求体, 需要 Bearer header, 还需要区分 401(鉴权失败)与 500(服务错误)。实现上用 `body.getReader()` 拿到 `ReadableStreamDefaultReader`, 配合 `TextDecoder` 逐块解码, 再手动按行解析 SSE 协议。

### 流式会话的页面级编排

前端用 `currentSessionId = "temp"` 与 `tempSession = true` 表示尚未落库的临时会话。第一条消息的时序是:

1. 请求打到"创建会话并发送消息"的流式端点, 服务端生成 session_id 并先写入 sessions 表。
2. SSE 首帧是 `{session_id}` 元数据, 客户端解析命中对象且带 session_id 时触发 `onSessionCreated` 回调并跳过正文累加。
3. 回调把真实 session_id 写入会话映射, 切换当前会话并取消临时标记。

流文本的落定只做一次: chunk 全程只写 ref, 在 `onDone`/`onError` 时用一次状态提交把完整内容写回尾部 AI 消息, 并置状态为 `done`/`error`; 出错时同样保留已到达的部分回答。另有一层兜底: 若 mutation 正常返回但流里始终没出现结束哨兵(服务端没写完就关流), 再补一次提交。历史消息接口直接从内存中的 Agent 读取, 不查数据库, 它能查到历史的正是启动时重建的成果。

### 断线恢复现状

结论是: 没有实现流级自动重连, 但通过"生成与连接解耦"加上"结果级对账"保证回答不丢失。

客户端行为: fetch 失败或流中途读取出错时, mutation 的 `onError` 把尾部消息以 error 状态落定并提示; 已到达的部分回答不丢; 若流结束但没见到哨兵, 返回后再补一次提交。

服务端行为: 没有监听连接的 close/aborted 事件, 客户端掉线不会中断生成; 模型流继续跑完, 全量回答经 `addMessage` 进入内存并异步落库; 后续对已关闭连接的写入字节被丢弃, 但结果在服务端完整保留。

因此恢复模型是"流是一次性的, 结果是可找回的": 用户点击"同步历史"后, 服务端从内存读出完整对话, 断线那轮的回答就完整回来了。这是一次人工触发的结果级重连。

现状缺口: 客户端没有任何 `AbortController`, 无法主动中止, 也没有"停止生成"按钮, 组件卸载或路由切走时在途 fetch 不会被取消; 没有自动重试; 重发不幂等, 同样的问题再 POST 一次会再次执行生成, 用户消息被重复追加进上下文, 因此"直接重试原请求"是错误的重连方式。

### 标准 SSE 恢复机制为何不适用

标准机制是 EventSource 配套的三件套: 服务端为每个事件附 `id:` 字段, 浏览器记住最后收到的 id; 断线后按服务端 `retry:` 指定的间隔自动重连, 并自动带上 `Last-Event-ID` 请求头; 服务端据此重放该 id 之后的事件。三件套在本项目中全部失效。

| 机制                 | 失效原因                                              |
| -------------------- | ----------------------------------------------------- |
| EventSource 自动重连 | 传输层是 fetch POST, 不是 EventSource                 |
| `id:` 断点           | 主数据流帧只有 data 字段, 服务端没有事件序号概念      |
| `retry:` 间隔        | 只对 EventSource 生效, fetch 消费者不会读取也不会遵守 |

更深一层的错位在语义: 事件推送系统重连要解决"丢了哪几条事件、从哪条补放", 而 LLM 回答是一段持续增长的文本, 重连真正要做的是重新附着到仍在进行的生成过程, 拿到"到目前为止的全文加后续增量"。字节级重放只是手段之一, 全文快照重放同样正确, 甚至更简单。

### 真正的断点重连怎么设计

设计目标是弱网、切后台、服务发布导致连接断开后, 回答自动续上, 不重头生成、不重复调用 LLM。

服务端改造三步:

1. 输出流变成可重放日志。为每次回答分配 stream_id, 每个 chunk 单调递增 seq; chunk 除写入响应外同时追加进重放缓冲, 单机用内存映射, 多实例用 Redis Stream 并做长度修剪。本项目生成侧已天然解耦, 缺的只是把输出留痕。
2. 增加恢复端点, 参数为 `{stream_id, last_seq}`: 先重放缓冲中序号更大的事件, 再切换到实时尾随; 若生成已结束, 重放完补发结束哨兵。同时把帧格式升级为带 `id:` 的形式, 与标准 SSE 语义对齐。
3. 断连清理。监听 close 事件, 连接消失后停止写入与逐 token 日志以节省 CPU, 但不停止生成、不清空缓冲; 缓冲在生成完成后保留一段时间再回收。

客户端改造五项:

1. 游标加去重: 用 ref 维护 `{streamId, lastSeq}`, 只接受序号更大的事件, 让重放天然幂等。
2. 退避重连: 未收到哨兵就中断时, 指数退避加完全抖动重试, 重连请求携带 `last_seq`。
3. 死连接检测: SSE 长连接最大的坑是半开连接(传输层未断但数据不再流动), 客户端需设读取超时; 服务端可周期性发送注释帧作为心跳, 现有解析器天然跳过非 data 行, 协议解析零改动。
4. 补齐 AbortController: fetch 传 signal, 新增"停止生成"按钮, 组件卸载或路由离开时 abort; 配合服务端 close 监听还能实现"停止即取消生成"以节省 token。
5. 监听 `online` 事件: 网络恢复立即重连, 不等退避计时器。

重连循环应封装在 mutationFn 内部, 上层看到的仍是一次 mutation 的语义, 重试预算耗尽才触发 `onError`。本项目"累计全文回调加覆盖式落单"的数据模型让重放绝对安全: 无论重放多少次、顺序如何, 最后一次覆盖即最新状态。终态判据只有收到结束哨兵, 重连过程中不要提前落定消息。

低成本演进路径(不改服务端): 把现在人工点击的"同步历史"自动化, 出错后轮询历史接口直到完整回答出现。这利用了"服务端生成不中断"这一既有事实, 代价是拿不回生成中的打字机体验。

## 前端状态分层与流式渲染性能

### 三层状态

| 层             | 承载内容                                                  | 存储与同步               |
| -------------- | --------------------------------------------------------- | ------------------------ |
| Jotai atoms    | token、主题、语言等纯客户端状态                           | localStorage, 本地即真相 |
| React Query    | 会话列表、聊天历史等需要与后端同步的数据                  | 内存缓存 + 失效/重新获取 |
| 组件本地 state | messages 数组、streaming 标记、选中模型等高频或页面级状态 | 组件内, 不穿透到全局     |

分层的依据是数据性质而非偏好。Jotai 适合低频、本地即真相的状态, 不需要缓存键与失效策略; React Query 解决服务端状态的缓存失效、后台重取、请求去重与 loading/error 管理; 主聊天页的 messages 与 streaming 标记更新频率最高, 留在组件内避免高频更新穿透全局 store。仓库中另有一组聊天相关的 atom 定义(会话列表、当前消息、选中模型等)、一个持久化的模型类型 atom, 以及一个标注废弃、无人引用的 axios 实例副本, 全仓都没有组件引用; 实际聊天状态由页面本地 state 承载, 请求统一走 `fetch-client` 那个实例。这些都属于可以清理的冗余。

### 流式渲染的头号陷阱

LLM 流式输出常见为每秒几十到上百个 chunk。如果每个 chunk 直接 `setState`, 每次都会触发一次子树重渲染, 其中包括随文本长度增长的 reconciliation、O(文本长度) 的 markdown 全量重解析、以及浏览器布局与绘制。一条 2000 token 的回答约产生上千次渲染, 且单次成本随长度上升, 总成本接近平方级; 主线程被占满后就会出现掉帧、输入延迟与滚动抖动。

常见的误解是 React 的自动批处理能救场。实际边界是: 自动批处理只合并同一任务(含其微任务 flush)内的多次 `setState`; 而 `reader.read()` 随网络包到达在各个独立宏任务里被唤醒, 跨包的 chunk 永远不会被合并。即使一个传输段带多帧被合并成一次渲染, 渲染频率仍与包到达速率成正比, 量级问题依旧。批处理是缓解手段, 不是解法。

### 三层解耦方案

把热路径完全移出 React, 分三层:

| 层     | 职责                                                   | 效果                                |
| ------ | ------------------------------------------------------ | ----------------------------------- |
| 写入层 | onChunk 只写 mutable ref                               | 零渲染成本                          |
| 调度层 | 独立的 rAF 循环按帧拉取, 长度变化才 setState           | 渲染频率被钳制在帧率而非 chunk 频率 |
| 落单层 | 整个流只有一次真正的 state 提交, done/error 时写回全文 | 避免中途反复渲染                    |

渲染频率由此被钳制在 60/秒上限, 且没有新内容的帧零成本。这里还有一个容易被误判的细节: 累计全文的字符串拼接看似每次都全量复制, 实际现代 JS 引擎对 `+=` 采用惰性拼接的 rope 结构, 追加接近 O(1), 真正的摊平推迟到字符串被消费时, 因此"每帧传全文"的回调协议本身并不昂贵。

rAF 拉取的关键实现是: 用 `requestAnimationFrame` 循环检查 ref, 把文本长度与上次渲染比较, 长度未变则直接跳过 setState。这样即便每秒收到数百 chunk, React 调度器也几乎无感知, 同时通过长度比较避免无意义的 reconciliation。

### 节流方案对比

| 方案                 | 原理                              | 渲染频率                   | 后台标签页行为                   |
| -------------------- | --------------------------------- | -------------------------- | -------------------------------- |
| 逐 chunk setState    | 数据到即渲染                      | 等于 chunk 频率(数百/秒)   | 持续渲染                         |
| setInterval 节流     | 定时器周期采样最新值              | 由间隔决定                 | 被浏览器钳制到 1s+ 仍继续        |
| rAF 拉取(本项目)     | 每帧检查 ref, 有变化才 setState   | 60/秒上限, 空闲帧零成本    | 自动暂停, 恢复可见后首帧补齐全文 |
| useSyncExternalStore | 外部 store 推送通知               | 等于通知频率, 仍需自行节流 | 持续通知                         |
| transition/deferred  | 标记非紧急更新, React 自行调度    | 可能长期滞后               | 持续                             |
| 直接 DOM 写入        | 绕过 React 命令式设置 textContent | 无 React 成本              | 取决于实现                       |

rAF 方案胜出的三个理由: 帧对齐让渲染只发生在浏览器即将绘制下一帧的时刻, 不会做超出显示能力的无效渲染; 页面不可见时 rAF 自动暂停, 回到前台第一帧就拉到最新全文一次性补齐, 既没有后台空转也没有恢复时的补渲染风暴; 实现极简, 一个 effect 加一个循环加一次长度比较即可, 不需要 store 的订阅管道。若改用 `useSyncExternalStore`, `getSnapshot` 必须返回缓存的稳定引用, 否则每次返回新值会引发无限重渲染; 而本项目的流只被尾部一条消息消费, 没有多组件共享需求, 因此 rAF 更合适。

### 消息列表虚拟化与贴底滚动

消息列表用虚拟化做窗口化渲染, 只挂载视口附近的消息, 用约 120 像素的估算高度与 5 条 overscan 平衡首屏填充与内存占用。自动滚动策略以尊重用户控制权为前提:

1. 近底检测: `onScroll` 时计算距离底部的像素差, 小于约 80 像素记为"贴底"。
2. 新消息滚动: 用户自己发的消息强制滚到底部; AI 消息仅在用户已贴底时才滚动。
3. 流式增长跟踪: 用 `ResizeObserver` 监听容器高度变化(流式输出会让气泡持续增高), 仍在贴底状态才滚到末尾。
4. 用户阅读保护: 用户正在翻阅历史时自动滚动完全停止, 不打断阅读。

定型消息用 `React.memo` 包裹, 于是流式期间只有最后一条气泡在渲染, 已定型的旧消息不会因父组件更新而重渲染。

### Markdown 增量解析

流式 markdown 渲染器的核心优化是按语义块处理: 把文本按段落、代码围栏、标题、列表等切成块, 每块独立解析为 React 元素, 分块过程天然感知围栏边界。一旦某个块被完整接收(例如代码围栏闭合), 其解析结果就被缓存, 后续更新直接复用, 不再参与 diff; 因此每次文本更新只有最后一个未完成的块需要重新解析, 渲染成本与消息总长度解耦, 只与当前增量成正比。

流式文本中大量出现写到一半的代码围栏、粗体标记与链接。渲染器会智能补全未闭合标记, 避免半个围栏把后续内容全部吞进代码块; 代码高亮在流式过程中同样实时生效, 且围栏闭合后高亮结果随块缓存一起固化。

### 系统性检查清单

| 层     | 手段                              | 本项目状态                                                          |
| ------ | --------------------------------- | ------------------------------------------------------------------- |
| 数据层 | 高频数据走 ref, 不进 state        | 已落地                                                              |
| 数据层 | 覆盖式回调协议, 重放/去重安全     | 已落地(onChunk 传累计全文)                                          |
| 调度层 | rAF 加长度去重钳制渲染频率        | 已落地                                                              |
| 落单层 | 流结束单次 setState 落定          | 已落地                                                              |
| 组件层 | memo 隔离已定型消息               | 已落地(流式期间只有尾部气泡渲染)                                    |
| 组件层 | 虚拟化控制 DOM 规模               | 已落地                                                              |
| 滚动层 | ResizeObserver 驱动贴底加近底门控 | 已落地                                                              |
| 渲染层 | 块级增量解析加已定型块缓存        | 借助流式 markdown 渲染器实现                                        |
| 服务端 | 关闭代理缓冲                      | 已落地(`X-Accel-Buffering: no`)                                     |
| 服务端 | 避免逐 token 日志                 | 未落地: 每 chunk 一条 info 日志, 高并发下会成为热路径负担, 建议降级 |

没有测量的优化是盲调, 验证手段同样重要: 用 React DevTools Profiler 录制一次完整回答, 确认提交次数约等于帧数而非 chunk 数, 且单次提交耗时保持稳定(若随文本长度线性增长, 说明块缓存没生效); 用 Chrome Performance 面板观察长任务与掉帧, 长任务若恰好对齐 chunk 到达时刻, 说明有代码绕过 ref 直接 setState; 在流式输出期间于输入框打字应无卡顿; 用超长回答压测时尾部块解析耗时应当恒定, 这正是"渲染成本只与增量成正比"的直接验证。

## 数据模型与缓存

### 三张核心表

服务启动时通过 Knex 的 `hasTable` 检查自动建表:

| 表       | 关键字段                                                                   |
| -------- | -------------------------------------------------------------------------- |
| users    | 自增主键; name、email(索引)、username(唯一)、password; 软删除 `deleted_at` |
| sessions | 会话 ID 作主键(UUID, 服务端生成); username 索引、title; 软删除             |
| messages | 自增整型主键; session_id 索引、username、content(TEXT)、is_user; 无软删    |

设计要点: 会话主键由服务端生成 UUID, 不依赖数据库自增协调, 流式建会话接口先落库再通过 SSE 首帧把 ID 下发给前端; 消息用自增整型保证插入顺序与查询性能; 软删除用于用户与会话两张表, 查询统一附加非空条件; username 冗余存储在消息表中, 避免跨表 JOIN。

### 缓存抽象与降级

缓存层不定义抽象类, 而是导出模块级的读、写、删三个函数, 内部通过一个布尔开关分发到两套实现, 同文件里还包含消息落库的插入函数供 Agent 调用。这种"函数入口 + 布尔分发"的适配器写法, 让上层只需调用统一函数, 不感知底层是 Redis 还是进程内 LRU。

降级策略在服务启动时执行: 尝试连接 Redis 并做一次连通性测试, 成功则置位启用标记, 失败则回退初始化进程内 LRU。LRU 的参数为最大 10000 条目、最大 256MB、TTL 10 分钟。

| 形态     | 触发条件                       | 特点                       |
| -------- | ------------------------------ | -------------------------- |
| Redis    | 配置启用且连接、连通性测试成功 | 跨进程/跨实例共享          |
| 进程 LRU | 未启用或连接失败               | 无需外部依赖, 单实例内生效 |

设计意义在于开发环境无需安装 Redis 即可运行, 生产环境可用 Redis 做跨实例共享。需要注意当前业务代码尚未真正接入读写缓存函数, 只有消息落库使用了同文件的插入函数, 缓存读写属于预留的基础设施; 未来接入时上层无需改动调用形态。

## 设计模式与扩展性

| 模式        | 落点                       | 解决的问题                                 |
| ----------- | -------------------------- | ------------------------------------------ |
| 工厂模式    | AiModelFactory             | 解耦模型创建与使用, 新增类型只需注册创建器 |
| 单例模式    | AiAgentManager、工厂注册表 | 全局唯一的 Agent 管理器与模型注册表        |
| 策略模式    | 模型接口的多个实现         | 同一 Agent 可在不同推理策略间切换          |
| 观察者/回调 | 流式回调                   | 解耦 token 生成与 SSE 写入                 |
| 中间件模式  | Koa 鉴权中间件             | 横切关注点与业务逻辑分离                   |
| 分层架构    | Router 到 DAO              | 关注点分离, 各层可独立测试与替换           |
| 适配器模式  | 缓存层布尔分发             | 统一入口, 底层实现可替换                   |

## 水平扩展与部署取舍

当前架构的水平扩展瓶颈与对应方案:

| 瓶颈           | 原因                 | 方案                                  |
| -------------- | -------------------- | ------------------------------------- |
| Agent 内存状态 | 对话历史存在进程内存 | 迁移到 Redis/共享存储, 或使用粘性会话 |
| RAG 向量索引   | 每次请求重建, 无共享 | 引入独立向量数据库服务                |
| 文件存储       | 本地磁盘目录         | 迁移到对象存储                        |
| SSE 长连接     | 连接绑定到特定进程   | 用 Redis Pub/Sub 或消息队列广播       |

最小改造路径是负载均衡按 username 做一致性哈希, 同一用户的请求始终路由到同一实例。它无需改动 Agent 的内存模型, 但牺牲了故障转移能力。完整改造路径是让服务无状态: 对话历史存入 Redis 列表, 每次请求加载上下文、响应后写回, 服务即可任意扩缩容, 代价是每次请求多一次上下文读写往返。

## UI、主题与国际化

### 组件体系

采用 shadcn/ui 模式: 组件不是 npm 依赖, 而是源码拷贝进项目。基础原语用 Base UI(headless、可访问性优先), 样式层用 Tailwind CSS 4, 变体管理用 CVA, 类名冲突用 `tailwind-merge` 解决、条件组合用 `clsx`。这样组件源码在项目内可任意定制, 不受库版本约束, 同时由 Base UI 保证 WAI-ARIA 可访问性。

### 国际化

使用 i18next + react-i18next, 维护中英文两套语言包, 覆盖所有用户可见文本。语言检测优先读用户的手动选择, 未选择时回落 `navigator.language`。一个值得借鉴的设计是校验消息与展示文案解耦: 表单校验 schema 的 message 直接写成 i18n key(如 `auth.password_required`), 渲染时经翻译函数转换, 于是新增语言不需要改校验逻辑。

### 主题系统

主题状态三态: 亮色、暗色、跟随系统, 通过带持久化的 atom 存储到 localStorage。派生 atom 在"跟随系统"时用 `matchMedia("(prefers-color-scheme: dark)")` 解析出实际亮暗。应用层的 Provider 负责三件事: 在根元素上切换亮暗类供 Tailwind 的 dark 变体消费; 同步更新移动端浏览器状态栏颜色(需要页面先声明对应的 meta 标签, 未声明时这段逻辑不生效); 在"跟随系统"时额外监听系统主题变化事件, 卸载时移除监听。代码高亮的主题也跟随亮暗类联动, 为渲染器传入亮暗双主题即可自动切换。

## 适用场景与小结

这个项目的价值在于用一套清晰的分层把"LLM 聊天"从 demo 推到可维护的产品形态: 后端用工厂加管理器把模型抽象与生命周期隔开, 用内存上下文加 write-behind 落库换取低延迟, 用即时构建的检索链路实现零运维的 RAG, 用绕过框架的原生响应写入实现真正的流式; 前端则把高频流式数据挡在 React 之外, 用 ref 加 rAF 把渲染频率钳制在帧率, 再用块级增量解析把 markdown 渲染成本与文本长度解耦。

它适合单实例或小规模部署、需要快速验证 LLM 聊天形态的场景, 也适合作为学习流式渲染与上下文管理的参考实现。不适合直接用于大规模多实例生产: Agent 上下文、RAG 索引、文件与 SSE 连接都绑定单进程, 会话模型还停留在固定有效期的一长串 JWT, 缓存与限流是预留而非落地。要在生产规模使用, 优先补齐三件事: 把对话上下文迁到共享存储, 把向量索引改为独立服务加增量更新, 把断线恢复从人工点按升级为带游标的自动重连。
