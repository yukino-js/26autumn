本文系统梳理一个框架无关的浏览器监控 SDK 的能力面与实现思路: 它如何把错误、HTTP 请求、页面浏览与停留、性能指标、声明式点击、元素曝光、白屏与错误前操作录屏统一采集, 如何用发布订阅总线解耦采集与上报, 以及批量上报、离线缓存、服务端恢复、采样过滤、插件体系与体积控制等工程取舍。内容面向需要在 Web 应用中接入前端可观测能力的工程师, 也适合作为设计自有监控 SDK 的参考。

## 定位与分层架构

### 能力边界

SDK 采集的事件类型覆盖八类来源: JavaScript 运行时错误与资源加载错误、未处理的 Promise 拒绝、`console.error`; XHR 与 fetch 请求; 页面浏览与停留时长; 性能指标(Web Vitals、导航与资源计时、长任务、首屏、内存); 声明式点击; 元素曝光时长; 白屏检测; 错误触发点之前的操作录屏。此外提供手动上报错误、性能点、自定义事件与页面浏览的 API, 以及 React 与 Vue 两套框架接入。

| 猴子补丁调度 | 统一安装与卸载浏览器 API 拦截                  |

| 路由拦截     | History 与 Hash 路由变化监听                   |

| 数据上报器   | 批量队列、传输通道选择、离线缓存与服务端恢复   |
| 插件注册     | 插件集合管理与生命周期编排                     |
| 配置校验     | 运行时 schema 校验, 非法配置显式抛错           |

设计原则可以归纳为四条。其一, 采集与处理通过事件总线完全解耦。其二, 性能、录屏、曝光这类重能力做成插件按需加载。其三, 核心不依赖任何前端框架, 框架集成放在独立入口。其四, 多出口构建, 每个入口都提供 ESM、CJS 与类型声明三套产物, 框架依赖是可选 peer, 不用就不装。

## 生命周期

### init 的执行顺序

初始化入口按固定顺序完成六件事:

1. 单例守卫。若已经初始化过则直接返回, 放在最前面是因为重复调用是常见场景(例如热更新), 提前返回能省掉后续的解析开销。
2. 剔除显式 `undefined`。配置类型允许字段为 `T | undefined`, 合并默认值前先过滤掉值为 `undefined` 的键, 保证它们回落到默认值, 而不是把默认值冲成空。
3. 合并默认配置并做 schema 校验, 校验失败会抛出 `ZodError`。
4. 防护检查。`disabled` 为真则直接返回但仍保留已应用的配置; `dsn` 为空则记录错误并返回。
5. 按 `maxBreadcrumbs` 设置面包屑容量, 执行 setup。
6. 异步启动身份识别, 不阻塞主流程。

setup 的职责是按开关安装各事件类型的总线订阅与猴子补丁; 白屏检测开启时直接启动采样; 调用 PV 初始化立即上报首次页面浏览; 并注册页面隐藏监听在离开时补发当前页停留时长。它返回一个清理函数, 内部收集了所有取消订阅与还原补丁的函数, 销毁时按注册的逆序一次性还原, 因此 SDK 可以安全地从页面中完整移除。

### destroy 的清理顺序

销毁依次完成五步: 调用所有插件的销毁方法并清空插件注册表; 逆序执行 setup 的清理(还原全部拦截、停止白屏采样、移除页面隐藏监听、重置页面浏览状态、清空总线订阅); 销毁批量错误管理器; 重置上报器单例(清定时器、摘除在线/离线监听、丢弃队列); 复位会话级状态(面包屑缓冲、错误去重集合、录屏标记)。之后再次初始化会从全新状态开始, 这使它适合用于测试重置、微前端卸载或运行时动态关闭监控。

`isInitialized()` 在 setup 成功完成后为真, 销毁后复位为假; 因 `disabled` 或空 `dsn` 而提前返回的初始化不会让它变为真。

### 上报钩子

| 钩子               | 时机               | 语义                                        |
| ------------------ | ------------------ | ------------------------------------------- |
| `beforeBreadcrumb` | 面包屑写入前       | 同步返回(可修改的)条目, 可用于脱敏          |
| `beforeSend`       | 单条事件入队前     | 返回数据继续, 返回 `false` 丢弃; 可异步     |
| `beforeSendBatch`  | 单批事件进入传输前 | 返回数组继续, 返回 `false` 丢弃整批; 可异步 |
| `afterSend`        | 一批发送成功后     | 返回值被忽略且不等待                        |

钩子既可以在初始化配置里提供, 也可以在初始化后用同名导出函数注册(仅 `beforeSend`/`beforeSendBatch`/`afterSend` 三者有导出函数; `beforeBreadcrumb` 只能在配置里提供), 两者写入同一组配置字段, 后写覆盖先写。

## 事件总线

总线以"事件类型到处理器集合"的映射为核心, 发布时对每个处理器单独 try/catch: 一个消费者抛错不会中断其余消费者, 也不会把异常抛回生产者。订阅返回清理函数, 销毁时一次性清空全部订阅。

事件类型是枚举而非字符串: XHR、fetch、Click、Hash 变化、History 变化、资源错误、未处理拒绝、JS 错误、Vue 错误、React 错误、其他框架错误、性能、录屏、曝光、白屏、自定义、页面浏览。类型枚举让事件名拼写错误在编译期就能被发现。

选择发布订阅而非直接在补丁里处理, 收益有六点: 采集方只管发布原始事件, 不关心后续是上报、留面包屑还是触发录屏; 一个事件可以同时驱动多个消费者; 采集层与处理层可以分别测试; 插件能在运行时订阅或取消; 单处理器异常被隔离; 每个订阅自带清理函数, 生命周期清晰。与通用事件发射器相比, 这里用集合而非数组存储处理器(天然去重、删除 O(1)), 类型被约束为事件枚举, 并且不继承任何平台自带的事件发射器, 保持零依赖与更小体积。

## 错误采集

### 来源

| 来源            | 捕获方式                             | 结果形态                                                    |
| --------------- | ------------------------------------ | ----------------------------------------------------------- |
| 运行时 JS 错误  | 捕获阶段监听 `window` 的 error 事件  | 带文件名与行列号                                            |
| 资源加载错误    | 同上, 目标元素带 `src` 或 `href`     | 类型为资源错误, 合成"加载失败"消息                          |
| `console.error` | 装饰该方法                           | 取第一个 Error 参数, 否则把所有参数转字符串拼接             |
| 未处理 Promise  | 监听 `unhandledrejection`            | 解包 `reason`; 是错误事件则走带行列号的路径, 否则走通用路径 |
| React 组件错误  | ErrorBoundary 的 `componentDidCatch` | 带 React 的 ErrorInfo 上下文                                |
| Vue 组件错误    | `app.config.errorHandler`            | 带组件实例与生命周期信息                                    |
| 其他框架错误    | 业务方主动调用上报接口               | 显式指定类型与上下文                                        |

`console.error` 的装饰带重入保护: SDK 自身输出的错误不会再次触发采集; 调试日志使用装饰之前捕获的原生 `console.error` 引用; 原始方法始终会被调用, 不改变业务行为。资源错误只会暴露 `src` 或 `href` 之一(图片与脚本是前者, 链接是后者), 因此类型上两者都可选。

### 分类

通用错误处理入口按载荷中 `extra` 的具体类型分派:

| `extra` 是什么           | 走向           | 上报类型与要点                             |
| ------------------------ | -------------- | ------------------------------------------ |
| 错误事件(带文件名行列号) | 代码错误路径   | 类型为 JS 错误, 行列号入载荷, 堆栈进 extra |
| 目标疑似资源的普通事件   | 资源错误路径   | 类型为资源错误                             |
| Error 实例               | 运行时错误路径 | 类型为 JS 错误, extra 为堆栈或错误对象     |
| 其他任意值               | 未知错误路径   | 类型为 JS 错误, 名称标为 Unknown Error     |

### 去重

三条错误路径默认都按"原始字符串拼接"的键去重, 键存在一个有界集合中(容量 1000, 超出后淘汰最早插入的条目), 防止长生命周期单页应用里去重集合无限增长。

| 路径        | 去重键                        |
| ----------- | ----------------------------- |
| 代码错误    | `Error-消息-文件名-行-列`     |
| 资源错误    | `Resource-标签名-src 或 href` |
| 运行时/未知 | `Error-名称-消息`             |

来源文件名缺失或为 `unknown` 的错误视为来源不明, 跳过去重直接进入批量聚合。把 `repeatCodeError` 设为真可彻底关闭去重。一个容易忽略的细节是: 面包屑的写入发生在去重检查之前, 被去重(未上报)的错误依然会留下操作轨迹, 供后续错误的上下文还原。

### 批量聚合

只有代码错误路径会进入批量聚合: 距最后一条错误 2 秒后结算, 按"类型-名称-消息"分组; 组内少于 5 条则逐条上报, 达到或超过 5 条则折叠成一条批次错误, 携带 `batchError`、`batchErrorLength` 与最后一次发生时间。资源错误、运行时错误与框架错误绕过聚合立即上报。

这个"2 秒窗口加 5 次阈值"的组合针对的是循环错误(例如定时器里持续抛错)造成的上报风暴: 单次错误仍能及时上报, 高频重复错误被折叠, 同时通过最后发生时间让后端判断错误的持续性。

### 忽略规则

`ignoreErrors` 同时接受字符串与正则: 字符串按"消息包含该片段"匹配, 正则按 `test` 匹配。它作用于代码错误、运行时错误与未知错误, 但不作用于资源错误——后者由 HTTP 与资源自身的采集面覆盖。

## HTTP 请求采集

### XHR 与 fetch 的拦截方式

| 维度     | XHR                       | fetch              |
| -------- | ------------------------- | ------------------ |
| 拦截位置 | 原型上的 `open` 与 `send` | 全局 `fetch` 函数  |
| 响应获取 | `loadend` 事件            | Promise 链         |
| 计时起点 | `send` 时刷新时间戳       | 发起请求时的时间戳 |
| 数据存放 | 挂在实例上的私有属性      | 闭包变量           |

XHR 的 `open` 装饰记录方法与地址, `send` 装饰刷新时间戳并挂一个只执行一次的 `loadend` 监听, 在回调里记录状态码、解析 `server-timing` 响应头与耗时再发布。fetch 的装饰接受字符串、URL 与 Request 三种入参, 地址与方法按固定优先级推导; 命中忽略规则的请求直接透传原始 fetch, 零开销。

两者共同的要点: 请求体与响应体只在错误状态(状态码为 0 或大于等于 400)时捕获, 字符串响应截断到 8KB, 避免单个错误撑爆上报载荷; fetch 用 `clone().text()` 在后台读取, 不消费也不延迟业务方的响应体, 流式响应克隆读取失败时仍照常发布事件; 网络错误以状态码 0 上报并把原始异常继续抛出, 不吞掉业务错误。

### 状态分类

HTTP 数据会被转换成一个新对象并派生状态与消息, 不改动入参:

| 状态码     | SDK 状态 | 派生消息                             |
| ---------- | -------- | ------------------------------------ |
| 0          | 错误     | 原始网络错误消息, 否则 Network error |
| 100 到 199 | 正常     | 信息响应                             |
| 200 到 299 | 正常     | 成功响应                             |
| 300 到 399 | 正常     | 重定向                               |
| 400 到 499 | 错误     | 客户端错误                           |
| 500 到 599 | 错误     | 服务端错误                           |
| 其他       | 错误     | 非法状态码                           |

默认只上报错误状态的请求。开启 `enableHttpPerformance` 后, 成功的请求会额外上报为性能事件, 名称形如 `HTTP <方法>`, 消息为接口路径, 值为耗时, 附加方法、状态码与服务端计时。

### 请求过滤

请求在满足以下任一条件时被跳过: 向配置的 `dsn` 发起的 POST(避免上报请求自我采集导致死循环), 或匹配 `excludeAPIs`。这里有一个容易踩的差异: `excludeAPIs` 的字符串项是严格相等匹配, 正则项才按 `test` 匹配; 而 `ignoreErrors` 的字符串项是子串包含匹配。此外, 任何地址中含 `dsn` 的请求都不会写入面包屑, 保证 SDK 自身的流量不污染操作轨迹。

## 页面轨迹: 浏览与停留时长

页面浏览与停留时长共用同一个事件类型, 通过名称字段区分:

| 名称          | 触发时机           | 关键附加字段             |
| ------------- | ------------------ | ------------------------ |
| PageLoad      | SDK 初始化         | 地址、来源页、进入时间   |
| HistoryChange | History 路由切换   | 地址、来源页、进入时间   |
| HashChange    | Hash 路由切换      | 地址、来源页、进入时间   |
| PageDwell     | 路由切换、页面关闭 | 地址、来源页、停留毫秒数 |

路由变化时的处理顺序是: 先把目标地址归一化, 与当前页相同则跳过; 再为上一页上报停留时长; 最后重置当前页状态并上报新页 PV。停留时长小于等于 100 毫秒直接丢弃, 以过滤路由重定向产生的无意义数据。页面隐藏时用 `pagehide` 事件补发当前页停留时长: 它在移动端比 `beforeunload` 可靠得多, 标签切后台或被系统回收都会触发。业务也可以调用手动上报接口补充 PV, 其名称默认为 ManualPageView, 消息默认取当前地址。

## 声明式点击埋点

### 属性约定

点击埋点通过 HTML 属性声明, 业务方无需编写采集代码:

| 属性                   | 含义                                        |
| ---------------------- | ------------------------------------------- |
| `yukino-sentry-ev`     | 显式事件 ID, 事件标识的第一优先级           |
| `yukino-sentry-msg`    | 人类可读消息, 上报消息字段的最高优先级      |
| `yukino-sentry-view`   | 视图/容器标识, 无 `ev` 时作为事件 ID 的回退 |
| 其余 `yukino-sentry-*` | 自定义参数, 进入上报载荷                    |

纯点击不会被上报: 采集器沿事件路径查找, 只有某个元素带上述跟踪属性时才产出数据, 否则返回空。事件路径优先用 `composedPath()` 穿透 Shadow DOM, 取不到元素时回退到沿父节点向上遍历。

事件 ID 的解析顺序是: 路径上任意元素的 `yukino-sentry-ev`, 其次任意元素的 `title`, 再次任意元素的 `yukino-sentry-view`, 最后取最近元素的标签名。消息的解析顺序作用在"最近的带跟踪属性元素"上: 其 `yukino-sentry-msg`, 其次 `title`, 其次裁剪后的文本内容, 其次 `aria-label`, 最后标签名。

自定义参数从路径上最近的、带有任意跟踪属性的单个元素上收集, 不跨祖先合并; 空属性值转为 `null`。这意味着若把参数挂在容器上而点击发生在其子元素, 参数不会被采集——需要在真正会被点击的元素上重复声明所需属性。

### 上报载荷

点击数据包含事件 ID、消息、触发页地址、被点元素的绝对坐标(相对视口的矩形加滚动偏移)、自定义参数、元素路径与触发时间戳。其中元素路径由路径生成器产出, 形如 `body > div#app > button.btn.primary`: 从被点元素向上最多遍历 5 层, 每层生成 `标签#id.类名` 形式的选择器并用大于号连接, 累计长度达到 128 字符后丢弃整层而非截断半个, 被点元素本身始终保留, 任何异常都回退为 `<unknown>`。

上报时名称取事件 ID 或消息, 消息取消息或事件 ID, 完整点击数据放进附加字段。处理链会先写一条面包屑再上报。整条点击采集链只在初始化时 `enableClick` 为真才安装; 节流延迟绑定一次, 安装后修改配置不再生效, 默认为 0 即不节流。

## 白屏检测

白屏检测的核心是视口采样点检测: 页面就绪后周期性探测若干点, 看它们是否仍落在配置的根元素上。

算法步骤: 等待文档就绪或 load 事件; 以 1 秒为周期采样, 可用时把每次采样包在空闲回调中执行; 每个周期探测 18 个采样点(水平方向 3 个、垂直方向 6 个, 即 3×6 网格), 坐标按视口宽高比例计算; 某点判为"空"当且仅当它命中空元素, 或命中元素的 id、类名加属性、标签选择器落在配置的根选择器中; 全部采样点都为空才算本次采样为白。一旦出现非白采样(说明已渲染真实内容)立即停止采样且不上报; 只有连续 10 次采样全白才判定为白屏并上报, 上报后同样停止采样。

上报事件类型为白屏, 状态为错误, 名称为 WhiteScreen, 消息为采样次数, 附加字段记录采样计数。检测不走事件总线, 由 setup 在白屏开关打开时直接启动采样, 命中后通过回调交给上报器; 销毁时清除定时器与未触发的加载监听。

骨架屏场景单独处理: 开启骨架屏标志后, 第一次采样只记录巡视到的选择器集合作为基线、不上报; 后续每次采样把选择器集合与基线比较, 一旦不同就说明骨架屏已切换为真实内容并停止采样; 若集合始终与基线相同并撑到第 10 次采样, 说明骨架屏卡住, 判定为白屏。

性能上的注意点: 采样 API 依赖布局结果, 若调用时布局处于脏状态会强制同步回流; 因此需要保持连续只读、不在探测循环中穿插样式写入或 DOM 修改。采样整体已调度到浏览器空闲期执行, 避免阻塞渲染; 在无骨架模式下, 每次采样仍会查满全部 18 个点再判定, 短路发生在采样轮之间——一旦某轮发现非全白(已渲染真实内容)就停止后续所有采样, 不再周期探测。

## 身份与用户标识

### 三层身份

| 标识          | 来源                     | 持久化       | 用途           |
| ------------- | ------------------------ | ------------ | -------------- |
| `anonymousId` | 设备指纹库生成的访客标识 | localStorage | 匿名跨会话追踪 |
| `visitorId`   | 业务或后端设置           | 内存         | 业务侧访客标识 |
| `userId`      | 业务设置或初始化时传入   | 内存         | 登录用户标识   |

三者都会逐条附加到上报数据的外层, 查询身份接口返回它们以及两个"是否存在"的布尔值(即值不等于 unknown)。设备指纹默认关闭: 启用时先读本地缓存, 未命中才动态加载指纹库并写入缓存, 加载或生成失败只记日志、不阻断初始化; 关闭时匿名标识保持 unknown。这是一个隐私合规上的自觉默认——浏览器指纹属于敏感采集, 必须由使用方主动开启。

### 设备与会话标识

SDK 自动生成并持久化两个标识: 设备 ID 存在 localStorage(跨会话持久, 清缓存前不变), 会话 ID 存在 sessionStorage(标签页会话级, 关页即失效)。两者都在首次使用时惰性生成, 保证同一设备或同一会话内所有事件携带一致的 ID。

标识生成函数有三级降级: 优先用安全上下文才暴露的 `crypto.randomUUID`; 不可用时用随机数接口手写 v4(让 SDK 在纯 HTTP 页面也可用); 全局随机能力完全缺失时用时间戳加随机数兜底。存储访问全部包在 try/catch 中, 隐私模式或存储被禁用时直接返回新的随机标识, 不阻塞上报。

设备信息(浏览器名与版本、操作系统、语言、屏幕分辨率、UA 等)采用惰性采集: 首次组装上报数据时才解析 UA, 之后缓存复用。SDK 的单例挂在全局对象上, 便于在控制台查看实时配置与设备信息。

## 上报管道

上报器是统一出口, 首次使用时才实例化。它把采集载荷转换为带外壳的上报数据, 并批量发送到配置的 `dsn`。

### 入队阶段

```text
载荷进入
  └─ 前置检查: dsn 非空 + 采样率随机判定 + 命中录屏触发类型则置录屏标记
       └─ 组装上报外壳(附加地址/身份/项目/设备信息, 错误类附面包屑)
            └─ 执行 beforeSend 钩子(可修改或返回 false 拒绝)
                 └─ 入队
                      ├─ 离线? 裁剪到队列上限 + 写入 localStorage 镜像
                      ├─ immediate 或队列达到单批上限? 立即发送
                      └─ 否则延迟批量等待时间后发送
```

### 发送阶段

1. 队列为空或已有发送在途(防并发标记)则返回。
2. 离线则裁剪队列、写入镜像并中止本轮。
3. 从队头切出不超过单批上限的一批, 交 `beforeSendBatch`(异步时等待); 若返回空则安排下一轮发送。
4. 批次只序列化一次, 再按通道优先级发送。
5. 传输失败时把这一批回插到队头、裁剪并持久化, 同时启动服务端恢复探测。
6. 成功后执行 `afterSend` 钩子。
7. 队列仍有数据则 100 毫秒后继续, 形成流水线。

### 传输通道

| 通道         | 上限     | 优势                             | 局限                              |
| ------------ | -------- | -------------------------------- | --------------------------------- |
| `sendBeacon` | 约 60KB  | 页面卸载时仍可靠发送, 不阻塞页面 | 仅 POST, 无法自定义头, 拿不到响应 |
| `fetch` POST | 无硬限制 | 可自定义头, 可获取响应状态       | 页面卸载时可能被取消              |

双通道的理由有三点。页面关闭场景下 `fetch` 可能被取消而浏览器会保证 beacon 发出; beacon 入队失败或载荷超过 60KB 时自动落到 fetch; 只有 fetch 能拿到响应状态, 非 2xx 会触发失败回插与服务端恢复探测。fetch 的条件性 `keepalive` 只在载荷不超过 60KB 时设置, 因为浏览器对 keepalive 请求有约 64KB 的在途预算, 超限会被拒绝, 而失败的请求会一直卡在队列头部。

### 同步快路径与定时器处理

无异步钩子时, 整条管道从入队到传输层必须保持同步: 一个无条件 `await` 即使面对同步返回值也会强切一个微任务, 而页面隐藏时触发的停留时长上报等不起这个微任务——页面可能在回调恢复前就被销毁, beacon 永远发不出去。因此代码用"是否 Promise"的守卫代替无条件等待: 同步结果走同步分支, 异步结果才等待, 兼顾钩子灵活性与卸载场景的可靠性。

批量发送定时器与服务端恢复探测定时器都会尝试取消对 Node 进程的引用: SDK 会被导入到服务端渲染或测试等 Node 环境, 若不取消引用, 定时器会阻止进程正常退出(测试挂住、脚本不结束)。结构判断让同一份代码兼容浏览器与 Node——浏览器定时器句柄是数字, 没有取消引用的方法, 直接跳过即可。

### 上报器单例的懒加载

上报器以代理对象导出, 首次属性访问时才真正实例化。这样做有四个原因: 构造过程会注册在线/离线监听并从本地存储恢复上个会话的离线数据, 若在模块加载时就实例化, 这些副作用会早于初始化应用配置; 支持重置——销毁时把模块级实例置空并释放旧实例, 下次访问自动创建新实例; 作为中间层避免多模块间的循环依赖; 方法访问时绑定正确的 `this`, 使用方可以安全地解构取用。

### 上报数据结构

每条上报数据由统一外壳与原始载荷两层组成。外壳是检索维度, 载荷保留事件细节。

| 字段                                   | 说明                                         |
| -------------------------------------- | -------------------------------------------- |
| `id`                                   | 所属上报器实例的 id, 同一实例的所有事件共享  |
| `type` / `name` / `message`            | 事件类型、名称与消息                         |
| `status`                               | 正常或错误                                   |
| `time` / `timestamp`                   | ISO 时间与数值时间戳                         |
| `url`                                  | 事件发生时的页面地址                         |
| `userId` / `anonymousId` / `visitorId` | 三层身份标识                                 |
| `projectId` / `sdkVersion`             | 归属信息                                     |
| `breadcrumbs`                          | 仅错误类事件携带的操作轨迹                   |
| `deviceInfo`                           | 惰性采集的设备、浏览器、系统、语言与屏幕信息 |
| `payload`                              | 原始事件载荷, 内含事件级唯一 id              |

面包屑只附加到错误类事件(JS 错误、未处理拒绝、资源错误、Vue、React、其他框架), 因为它是故障前的操作轨迹; 若给每条批量事件都带上, 载荷体积会成倍放大且没有诊断价值。

一条 JS 错误最终携带的信息包括: 外壳上的类型、名称(出错脚本地址)、消息、状态、页面地址、三层身份、项目与 SDK 版本、设备信息; 以及载荷里的行列号(供 Source Map 反解)与堆栈字符串。框架错误额外携带错误对象、堆栈与框架上下文; 批次错误额外携带批次标记、条数与最后发生时间; 录屏事件携带压缩后的记录流与事件条数。

## 离线缓存与断点恢复

离线容错由三个模块协作完成, 它们区分了"客户端离线"与"服务端不可达"两种故障。

### 网络状态与本地镜像

上报器构造时读取初始在线状态并监听在线/离线事件; 离线期间事件仍留在内存队列, 本地存储只是它的镜像, 因此恢复在线后无需重新加载即可立即发送。镜像写入时机是: 入队时发现离线、发送时发现离线、发送失败回插之后; 下次发送成功后清除镜像, 防止后续会话重放已送达的数据。队列在每次持久化前裁剪到上限, 避免撑爆本地存储。

从本地存储加载镜像时用 schema 校验: 只有校验通过的缓存才被删除, 不合法的缓存原样保留便于排查; 只有 JSON 解析直接抛错才删除。这体现了对"坏数据"的处理原则——宁可留证据, 也不要静默丢弃。

### 服务端恢复探测

当发送失败(拒绝或非 2xx)时, 上报器进入离线态并启动恢复探测: 用 HEAD 请求探测配置的 `dsn`, 失败则指数退避重新安排(1 秒起步, 每次失败翻倍, 封顶为配置的重试间隔), 成功则重置退避、恢复在线并立即冲刷内存队列。探测定时器会取消对 Node 进程的引用。上报器还导出手动冲刷离线缓存的方法, 用于需要主动重放的场景。

```text
网络断开
  └─ offline 事件: 标记离线
       └─ 后续事件: 入队 -> 裁剪 -> 写本地镜像
            └─ 网络恢复
                 ├─ online 事件: 标记在线 -> 冲刷内存队列 -> 成功后清除镜像
                 └─ 或发送失败: 启动 HEAD 探测 -> 指数退避(1s 起, 翻倍, 封顶)
                      └─ 探测成功: 重置退避 -> 冲刷队列
```

这套机制覆盖了三种数据不丢的场景: 网络中断期间事件留在内存并镜像到本地; 页面中途刷新也能在下个会话把镜像装回队列继续发送; 服务端故障恢复后自动冲刷积压。

## 插件机制

插件抽象基类只要求实现初始化方法, 销毁方法可选但推荐。启用插件时逐个调用其初始化方法并把实例加入集合(天然去重); 销毁时遍历调用其销毁方法并清空集合。核心对插件零侵入: 插件通过事件总线订阅事件, 不修改核心代码; 插件从独立入口导入, 不引入就不会进入产物。

| 插件               | 功能                                            | 关键技术               |
| ------------------ | ----------------------------------------------- | ---------------------- |
| PerformancePlugin  | Web Vitals 与导航、资源、长任务、首屏、内存指标 | 性能观察器与变更观察器 |
| ScreenRecordPlugin | 错误触发点之前的操作回放                        | rrweb 录制与 gzip 压缩 |
| ExposurePlugin     | 元素曝光时长追踪                                | 交叉观察器             |

### PerformancePlugin

该插件不接收构造参数, 全部指标统一为性能事件, 靠名称字段区分:

| 名称                         | 来源                                                                        |
| ---------------------------- | --------------------------------------------------------------------------- |
| LCP / FCP / CLS / INP / TTFB | Web Vitals 库, 携带数值与评级; 指标的 id 会覆盖载荷 id 便于后端归并         |
| FSP(首屏时间)                | 自定义: 变更观察器追踪最新的视口内 DOM 变化时间, 页面就绪后经动画帧回调收尾 |
| NavigationTiming             | 导航计时: 绘制、DOM 交互、内容加载、首字节、DNS、TCP、TLS、重定向、卸载等   |
| ResourceList                 | 页面就绪时缓冲区里全部资源条目的快照                                        |
| ResourceTiming               | 每条实时资源条目一条事件, 值为耗时                                          |
| LongTask                     | 超过 50 毫秒的长任务, 用于定位主线程阻塞                                    |
| Memory                       | 浏览器支持时采集的 JS 堆内存使用                                            |

资源采集排除 fetch、XHR 与 beacon 类型(这些由 HTTP 采集面覆盖)以及含 `dsn` 的地址; 是否命中缓存由传输字节数为 0 或编码体为空推导。当浏览器不支持资源类型的性能观察器时, 有变更观察器兜底: 监听新增的图片、脚本与链接元素, 在其加载或出错事件中上报(每个地址只报一次), 能查到真实资源计时就复用, 否则用零耗时对象兜底。

首屏时间是一个值得展开的自定义指标, 它与标准的最大内容绘制不同:

| 维度     | 首屏时间(自定义)                               | 最大内容绘制(标准)               |
| -------- | ---------------------------------------------- | -------------------------------- |
| 定义     | 首屏所有可视 DOM 元素完成渲染的时间            | 视口内最大内容元素完成渲染的时间 |
| 关注点   | 首屏整体完成度                                 | 单个最大元素                     |
| 实现     | 变更观察器收集新增节点, 交叉观察器判定视口可见 | 性能观察器监听对应条目           |
| 排除     | 链接、脚本、样式                               | 由浏览器判定                     |
| 终止条件 | 文档就绪                                       | 用户交互或完全加载               |

最大内容绘制只关注单个最大元素, 对由多个小组件拼成的单页应用首屏不够准确; 首屏时间追踪所有视口内的 DOM 变化, 取最后一个可视元素的渲染时间, 更贴近用户感知的"首屏完成"。实现上优先用交叉观察器判定视口, 其可见时间取条目自带的时间戳; 环境不支持时回退到逐节点用矩形相交判定。所有能力检测统一读取 `PerformanceObserver.supportedEntryTypes` 的类型列表, 不支持的能力安全跳过; 销毁时逆序执行全部清理。

### ScreenRecordPlugin

录屏基于 rrweb, 采用滚动窗口而非全量录制: 录制事件不断进入窗口, 窗口原地裁剪掉早于设定时长的事件(默认保留最近 3 秒)。构造参数可配置窗口时长与触发事件类型, 初始化时把二者写入 SDK 配置(数组做拷贝, 插件实例间不共享引用)。

录制库与压缩库都是动态导入, 不阻塞主包; 加载失败时记录日志并降级为空操作。触发是事件驱动的: 当上报的事件类型命中录屏触发集合(默认错误、XHR、fetch、资源、未处理拒绝)时, 前置检查会置一个录屏标记; 录制回调检测到标记且窗口非空, 就把当前窗口序列化、gzip 压缩、base64 编码(按 32KB 分块)后作为一条独立的录屏事件发送, 并复位标记。因此录屏不是持续上报, 而是错误发生时的"现场回放"。

窗口时长默认 3 秒是对隐私与体积的双重约束: 只保留最近的操作片段, 不记录完整历史; gzip 后通常只有原始 JSON 的一到两成。解码用一个导出的解压函数完成: base64 解码、gzip 解压、再 JSON 解析, 输入为空时返回空, 插件尚未加载压缩库时会自行动态导入, 因此在任何上下文都可用。销毁时调用录制库返回的停止函数。

需要说明一个取舍: 录制默认开启画布内容记录, 这对含 canvas 的页面(如图表应用)才能完整回放, 但会带来额外开销; 输入与文本的掩码开关全部关闭(`maskAllInputs: false`, `maskInputOptions` 恒为 false), 定义的掩码函数只在原值后追加元素的 DOM 路径选择器以保留来源定位, 并不隐藏原始内容。

### ExposurePlugin

曝光插件用交叉观察器统计元素在视口内的可见时长, 用于广告或推荐场景的曝光归因。使用方式是命令式 API: 启用插件后持有一个实例, 调用观察方法登记元素(可一次登记多个), 卸载时调用取消观察。

| 参数        | 说明                             |
| ----------- | -------------------------------- |
| `target`    | 目标元素, 必填                   |
| `threshold` | 可见面积比例阈值, 省略时默认 0.5 |
| `params`    | 随曝光事件上报的业务自定义参数   |

入参经过校验, 非元素或越界阈值会抛错; 显式的阈值 0 会被尊重(只有省略才落到默认值); 重复观察同一元素是空操作, 保留首次的阈值与参数。曝光事件在元素从可见变为不可见时结算一次, 名称为 Exposure, 消息为 `Element Exposure`, 附加阈值、开始观察时间、进入视口时间、离开视口时间、时长与自定义参数。始终未进入视口的元素不会上报, 卸载时仍在视口内的元素也不会补发。

实现上按阈值分桶复用观察器: 相同阈值的元素共享一个实例, 因此观察器数量恒等于阈值种类数, 而与被观察元素数量无关; 取消观察时调用对应观察器并从映射中移除, 销毁时断开全部观察器并清空映射, 无泄漏。

## 框架接入

### React

[React](react)接入提供一个 ErrorBoundary 组件: 它用 `displayName` 保持组件栈可读, 在渲染阶段先用静态方法把错误写入状态使降级界面立即可见, 在 `componentDidCatch` 中上报 React 类型的框架错误并携带 React 的 ErrorInfo 上下文。降级内容既可以是节点, 也可以是渲染函数; 渲染函数的上下文参数是可选的, 因为边界可能在渲染阶段先以空上下文渲染一次, 待 React 交付信息后再带上上下文渲染一次。

需要清醒认识边界: ErrorBoundary 捕获不到异步回调、事件处理器与服务端渲染中的错误, 这些场景需要用 `traceError` 手动上报。

### Vue 与通用框架

Vue 3 插件接入时先保存原有的 `app.config.errorHandler`, 再安装新的处理器: 上报 Vue 类型的框架错误(上下文含组件实例与生命周期信息), 然后链式调用原处理器, 最后用传入的配置初始化 SDK。其他框架可以直接调用通用的框架错误上报接口, 显式指定类型为 React、Vue 或其他框架, 并提供错误对象与上下文。该接口对错误名称与消息做了多级回退(错误对象属性、原型构造名、字符串化、JSON 序列化), 保证任何形态的输入都能得到可读的上报。

## 采样与前置过滤

从事件产生到最终上报, 过滤分为多层, 越靠前的层越省成本:

```text
事件产生
  └─ 采集层过滤: excludeAPIs(HTTP) / ignoreErrors(错误)
       └─ 去重层过滤: 有界集合按签名去重
            └─ 采样层过滤: tracesSampleRate 随机丢弃
                 └─ 用户钩子过滤: beforeSend(单条)
                      └─ 批量钩子过滤: beforeSendBatch(整批)
                           └─ 最终上报
```

采样是全局随机判定: 采样率为 1 表示全量, 0.5 表示随机丢弃一半。被采集层与去重层拦下的事件不会进入采样, 因此这三层共同决定了后续所有环节的成本。

## 构建期与开发期集成

### 开发期 mock 上报端点

本地开发通常没有日志后端, 因此 SDK 为 Vite 与 webpack 的 dev server 各提供一个 mock 插件: 拦截向配置路径发起的 POST, 解析请求体, 用 dev server 的内存 Source Map 反解错误堆栈, 把每条批次作为一行 JSON 追加写入带时间戳的日志文件, 并始终返回成功。Vite 插件只对 dev server 生效(`apply: serve`), 生产构建完全不受影响。webpack 侧提供对应插件, 并额外导出一个可手动挂载的中间件用于自定义接入; 它把 mock 中间件插入到最前且刻意不声明路径, 因为带路径挂载会剥掉请求地址前缀、破坏精确匹配。webpack 插件还通过编译器的资源产出钩子收集 `.map` 产物用于反解, 精确路径优先、找不到再按文件名兜底以容忍未知的公共路径前缀。

这个设计的价值在于本地闭环: 开发阶段不必部署日志后端, SDK 的 `dsn` 直接指向 dev server 路径就能跑通"页面报错、上报、反解到源码"的完整链路; 日志用一行一条批次的格式, 方便用 tail 观察或脚本分析。

### Source Map 反解

反解模块只在 Node 环境使用, 不会被打进浏览器产物。它先解析堆栈字符串(兼容两种主流浏览器格式), 再逐帧加载对应的映射文件查询原始位置。判定哪些记录需要反解有三条规则: 类型为错误且载荷带数值行列号的, 用名称(即出错脚本地址)反解单帧; 载荷附加字段是堆栈样字符串的, 解析并反解最多 30 帧; 类型为 React、Vue 或其他框架的, 从顶层堆栈字段(回退到载荷 extra 里嵌套的堆栈字段)反解最多 30 帧。产出至少一帧的记录会获得反解字段, 其余原样透传。

每一帧携带原始地址与行列号、解析出的源码位置与函数名; 当映射文件包含源码内容时, 还附带出错行上下各 3 行的源码片段, 出错行带高亮标记。映射来源按构建工具不同: Vite 从 dev server 的内存模块图中取, 先试带查询串的地址再试纯路径; webpack 用资源产出钩子收集的 `.map`。候选映射文件先用 schema 校验再使用。浏览器堆栈的行列号是 1 起始, 查询映射前会把列号转为 0 起始。所有反解失败都静默处理: 单帧失败保留原始帧并标记未解析, 记录级失败则原样写入。

生产环境推荐使用"隐藏式 Source Map"并移走映射文件: 产物里不追加映射注释, 浏览器与外部用户拿不到源码; 映射文件单独收集到内部监控平台, 按"出错脚本地址加构建版本"匹配后还原原始位置与源码片段。剥离映射文件也不影响用户下载体积。

### 调试能力

SDK 自身的控制台输出默认关闭, 打开 `debug` 后可看到事件采集、入队、传输结果(含耗时)、插件初始化等分组日志。日志开关在每次调用时实时读取, 因此运行时切换立即生效, 无需重新初始化; 错误级输出使用装饰前捕获的原生 `console.error`, 保证打开调试不会让 SDK 把自己的日志当成错误上报。

## 体积与运行时开销取舍

| 依赖          | 用途               | 加载策略                   |
| ------------- | ------------------ | -------------------------- |
| 校验库        | 运行时 schema 校验 | 随核心加载                 |
| Web Vitals 库 | 核心网页指标       | 随性能插件加载             |
| UA 解析库     | 设备信息           | 随核心加载, 解析惰性执行   |
| 设备指纹库    | 匿名访客标识       | 启用指纹时才动态加载       |
| rrweb         | 屏幕录制           | 录屏插件初始化期动态加载   |
| 压缩库        | 录屏数据压缩       | 与录制库一同动态加载       |
| Source Map 库 | 开发期堆栈反解     | 仅 Node 侧, 不进浏览器产物 |

围绕体积与开销的主要取舍:

- 重能力全部插件化并支持独立入口, 不使用就不进包; 录制与指纹做动态导入, 但需注意录屏插件初始化时就会触发录制库加载, 未发生错误的会话也会付出这次加载代价。
- 手表类能力按需启用: HTTP 成功请求转性能事件、指纹、调试日志默认都关闭, 避免默认全量采集。
- 浏览器兼容采用渐进增强: `sendBeacon` 优先、`fetch` 兜底; 性能、变更、交叉观察器与空闲回调都做能力检测, 缺失时安全跳过或走回退路径; 随机标识三级降级, 存储访问失败不阻塞上报。
- 已知边界: 离线缓存受本地存储容量限制且写入是同步的, 队列上限与单条大小共同约束总量; 录屏压缩在主线程执行, 大量数据时可能占用主线程; 用户卸载时仍在视口内的曝光元素不会补发。

## 适用场景与小结

这套 SDK 适合: 需要一次性接入错误、性能、页面轨迹与行为埋点而不想引入多套前端可观测库的项目; 需要在 React 或 Vue 之外保持框架无关、或要在微前端里按需挂载卸载的场景; 需要错误现场录屏与开发期 Source Map 反解的团队; 以及希望用声明式 HTML 属性完成埋点、避免业务代码侵入的产品。

不太适合: 需要全量会话回放(它只保留错误前几秒)或需要跨标签页统一会话存储的场景; 对上报体积极度敏感、无法接受校验库与 UA 解析库常驻主包的项目; 对离线队列容量有很高要求、需要突破本地存储限制的场景。

综合来看, 它的设计主线是"用总线隔离采集与处理, 用插件隔离重能力, 用多层过滤隔离成本, 用镜像加探测隔离网络故障"。理解这条主线后, 接入与排障都有据可依: 采集异常先看对应开关与总线订阅, 体积异常先看动态导入与插件启用, 丢数据先看过滤链与离线缓存, 堆栈看不懂就检查映射文件的收集与匹配。
