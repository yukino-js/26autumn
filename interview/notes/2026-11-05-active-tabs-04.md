## 一、腾讯互娱 全栈开发(AI) 二面 · 可见 10 题

### 1. 项目架构与事件溯源（Q2）

链路：`WebSocket 上传音频切片 → 接入层（鉴权 / 限流 / 会话路由）→ Kafka → 语音服务（VAD / ASR / 说话人识别，产出带时间戳与序列号的转写事件）→ 决策分析服务（按语义段落聚合，抽结论 / 待办 / 负责人 / 截止时间）→ 会后异步生成摘要 + 建检索索引`。

**关键设计：事件溯源**，转写文本不是最终状态。原始音频事件 / 临时转写 / 修订转写 / 决策事件分别保存，前端按 `meeting_id + segment_id + revision` 合并；**ASR 后续修正不会覆盖审计记录**。

### 2. 重复 / 乱序 / 修订下前端如何收敛（Q3）

| 机制       | 要点                                                                                                                                                                  |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 版本       | 音频分片带单调递增 `sequence`；转写片段带稳定 `segment_id` + 递增 `revision`；前端只接受更大 `revision`（`applyEvent` 里 `event.revision > current.revision` 才覆盖） |
| 不永久阻塞 | 缺某个序号**不能永久阻塞后续消息**：短缺口进有限**重排序缓冲区**，超过等待窗口先展示现有内容并请求服务端补发                                                          |
| 重连       | 服务端保存会话游标，客户端重连带**最后确认的事件位置**                                                                                                                |
| 去重与审计 | 事件 ID 去重；修订覆盖视图但**历史版本仍留在事件日志**                                                                                                                |

### 3. Kafka 分区扩容后仍保证同会议有序（Q4）

- `meeting_id` 作 Key **只保证分区内有序**；分区数变化后哈希结果改变，新旧事件可能落不同分区 → **业务正确性不能建立在物理顺序上**。
- 事件加**会话 Epoch + 业务序列号**，消费者按会议维护有限重排序窗口。
- 迁移：控制面**冻结旧路由 + 记录切换位点 → 提升 Epoch** → 之后新事件只走新分区；消费者**拒绝旧 Epoch 的迟到写入**；DB 更新校验会议版本，防旧消费者覆盖新状态。

### 4. 换 Embedding 模型不重跑全量历史（Q5）

索引里除向量外还存 **原文哈希 / 切分版本 / 模型版本 / 向量维度** → 建**影子索引** → 按访问热度与业务优先级**渐进回填** → 查询先新索引，未迁移数据回退旧索引 → **不同模型的向量距离不可直接比较，所以各自算排名后用 RRF 融合**（`1/(k+rank)`，`k=60`）→ 新索引达到**覆盖率与质量阈值**后切主读，旧索引保留回滚窗口再异步删除。

:::danger ⚠️ 与本仓库项目事实的对照（别讲混）
面经用「影子索引 + 渐进迁移」；而 `content/docs/yukino-ecomm-agent/rag.md` 记载的是 **`vectorizePending` 检测到 `embeddingModel` 与当前 `EMBED_MODEL` 不一致就自动全量重嵌**。两者都对，但适用规模不同：本项目 **6 份文档 / 74 条 chunk**，全量重嵌成本可忽略；面经是海量历史索引才需要影子索引。面试里可以主动说清这个 trade-off，比背一种方案强。
:::

### 5. HNSW 参数与线上评估（Q6）

| 参数                           | 影响                               |
| ------------------------------ | ---------------------------------- |
| `M`（邻接边数）                | ↑ 召回率，但索引内存与构建成本上升 |
| `efConstruction`（建图候选集） | ↑ 索引质量，写入变慢               |
| `efSearch`（查询候选数）       | ↑ 召回，查询延迟上升               |

线上不看单次耗时，看 **Recall@K / P95 延迟 / 索引大小 / 并发吞吐**（真实数据分布上测）。租户过滤选择性很高时「先向量搜索再过滤」会召回不足 → 用支持**过滤下推**的实现，或扩大候选集后重排。

### 6. 语义一致的增量切分（Q7）

固定 Token 切分会拆开发言、决策依据与结论；overlap 虽缓解边界但引入**重复内容与召回污染**。做法：按**说话人切换 / 静音区间 / 标点**形成基础语义单元 → 按**主题相似度**合并相邻单元 → 每个 chunk 保存父级议题、时间范围、说话人集合。局部修订时用**内容哈希定位受影响区间**，只重切该区间及相邻边界，不重建整场会议索引。

### 7. 检索系统三段归因（Q8）

| 阶段 | 指标                                         | 判据                                              |
| ---- | -------------------------------------------- | ------------------------------------------------- |
| 召回 | `Recall@K`、`MRR`                            | 正确证据**是否进入候选集**                        |
| 排序 | **`NDCG`**（固定候选集上看正确证据位置）     | 存在但排名太低 → 重排问题                         |
| 生成 | 忠实度 / 完整性 / 引用正确性（固定输入证据） | 证据正确但答错 → 查上下文组织、模型能力、答案约束 |

线上必须保存：**查询改写、过滤条件、召回列表、重排分数、最终引用**，才能事后归因。

> 对照 [R08 Q4](../rounds/round-08.md)：项目 `eval-rag.ts` 用 Recall@5 / MRR / 证据覆盖率 / 答案覆盖率 / faithfulness，**没有 NDCG**。NDCG 是补强排序阶段评估的好切口。

### 8. 动态上下文预算（Q9）

- 固定预算：系统提示、输出格式、安全约束；**当前用户问题最高业务优先级**；近期对话 / 会议摘要 / 检索证据按相关性**竞争剩余空间**。
- 证据不能只按相似度截断，还要考虑**来源多样性、时间范围、重复度、证据覆盖率**。
- 先对历史生成**层级摘要**，用小模型估各段信息价值；**证据冲突时保留冲突双方**而不是只留最高分。
- 预留足够输出空间，避免输入占满窗口导致答案被截断。

> 对照 `content/docs/yukino-ecomm-agent/context.md` 的 `fixed / peak / sliding` 分账与 [R05 Q7](../rounds/round-05.md) 的证据放尾部 turn-ctx：思路同源，但面经多了「冲突保留双方」「小模型估信息价值」两层。

## 三、MySQL 页 · 日志 / 调优 / 架构板块（补前三轮）

| 题                                     | 核心结论                                                                                                                                                                                                                                                             |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| redo log 如何保证持久性                | **WAL + redo 持久化 + 崩溃恢复**，不是「顺序写就自动不丢」。数据页刷盘前相关 redo 先持久化；`innodb_flush_log_at_trx_commit=1` 时提交等 redo 刷盘、不等所有脏页；崩溃后从 **checkpoint** 起按页 **LSN** 判断重放哪些、再回滚未提交事务。顺序写/组提交只是降 I/O 成本 |
| binlog 两阶段提交                      | redo 与 binlog 两套日志需协调，否则崩溃后主库恢复结果与从库按 binlog 复制结果不一致。用**内部 XA 事务**，**binlog 作协调者、存储引擎作参与者**                                                                                                                       |
| `innodb_flush_log_at_trx_commit` 0/1/2 | `0` 提交不要求写出/刷盘（进程崩可能丢）；`1` 写入并刷盘（默认、最强，组提交可共用一次刷盘）；`2` 写文件但不立即同步（OS 崩/掉电仍可能丢）。后台刷盘周期通常 1 秒                                                                                                     |
| 组提交                                 | 把一批事务的日志写入与刷盘合并，**减少 fsync 次数而不是取消持久化保证**；「双 1」也不代表每事务各触发一次独立刷盘                                                                                                                                                    |
| double write buffer                    | 解决**部分写入 / torn page**：InnoDB 页 16KB 但刷页非原子。先成批写双写区并持久化，再写数据文件位置；崩溃时可用副本恢复。它**不替代 redo**                                                                                                                           |
| `EXPLAIN`                              | `possible_keys` 可能用的索引、`key` 实际用的（NULL=没走索引）、`key_len` 索引键字节数（可判断联合索引用了哪些前缀列）、`rows` 优化器**估算**扫描行数、`filtered` 估算过滤后保留百分比                                                                                |
| 深分页为什么慢 / 优化                  | `LIMIT 1000000,20` 要读过并丢弃前 100 万条，还可能回表+排序。优化用**游标分页**：`WHERE id > 上一页末尾实际 ID ORDER BY id LIMIT 20`（不能把「第 100 万条」当成 `id=1000000`）                                                                                       |
| 主从延迟                               | 先分清「复制为什么追不上」与「业务怎么避免读旧数据」。原因：主库大事务/批量改、从库 CPU/IO/Buffer Pool 不足、从库长事务或 DDL 阻塞、网络或复制线程异常、并行复制能力不足；用 `SHOW REPLICA STATUS` 与复制相关 Performance Schema 定位                                |

> 四轮合计：MySQL 页已覆盖 **标题索引（全 8 板块）+ SQL 基础前 12 题 + 索引/事务正文 + 日志/调优/架构正文**，剩余主要是 SQL 手写题与少量索引边角。

## 五、速记卡

- **事件溯源**：转写不是状态而是事件；`revision` 大才覆盖视图，历史版本永不删。
- **顺序不能靠分区**：物理顺序只保证分区内；扩容用 **Epoch + 业务序列号 + 版本校验**。
- **换 embedding**：影子索引 + 渐进回填 + **RRF 按排名融合**（不同模型距离不可比）+ 覆盖率阈值切主读 + 回滚窗口。
- **检索归因**：没召回 → 索引/查询；召回但排低 → 重排（NDCG）；证据对答错 → 上下文/模型/约束。
- **MySQL 日志**：WAL + redo 刷盘才保持久；binlog 两阶段提交是内部 XA，binlog 当协调者；doublewrite 防 torn page 不替代 redo。
- **深分页**：游标 `WHERE id > 上一页末尾 ID`，别用大 OFFSET。
