## 一、腾讯互娱 全栈开发(AI) 一面 · 15 题知识点

### 1. 实时通信与媒体（Q2 / Q3 / Q4）

| #   | 题                                   | 核心知识点                                                                                                                                                                                                                                                                                                                                                                                                  |
| --- | ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 2   | ICE / STUN / TURN / SDP 各负责什么   | **SDP** 描述媒体能力（编解码、方向、指纹、ICE 参数）但**不负责传输**；**ICE** 收集并连通性检查候选路径（host / STUN 反射 / TURN 中继）后提名；**STUN** 只发现 NAT 映射，不保证直连；对称 NAT、严格防火墙需 **TURN**。流程：信令交换 Offer/Answer → 持续交换 Candidate → DTLS 握手 → 音视频 SRTP、数据通道 SCTP over DTLS。TURN 凭证须**服务端签发带过期时间的临时凭证**，不能硬编码在客户端                 |
| 3   | 弱网下拥塞控制 / 丢包恢复 / 码率调整 | 发送端按传输反馈估带宽 → 动态调码率/分辨率/帧率；丢包恢复 = **NACK 重传 + RTX 重传包 + FEC 冗余**；重传适合低 RTT 且数据仍有播放价值，FEC 适合高丢包或来不及重传但额外耗带宽。**不能见丢包就加 FEC/疯狂重传**——先结合 RTT、丢包率、队列延迟判断是不是拥塞；巡检场景音频连续性优先于画面，降视频保音频，关键画面按需请求高分辨率关键帧                                                                       |
| 4   | SFU 万人房间，为何加机器仍可能失效   | SFU **不混流**，按订阅关系转发媒体包；瓶颈不只是连接数，还有**出口带宽、包复制、加密、拥塞控制状态、订阅频繁变更**。单机接收所有流再扇出会先打满网卡/内核包处理；房间状态与订阅关系集中在单节点时加机器无效。解法：按发布流/订阅用户**分片 + 级联 SFU**（上游流跨区只传一次、区域本地扇出）、限制同时可见视频轨、**Simulcast / SVC** 选层；**控制面**（成员/分配/故障迁移）与**媒体面**（只留转发状态）分离 |

### 2. Agent Runtime 工程（Q5 / Q6）

| #   | 题                                         | 核心知识点                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| --- | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 5   | Agent Runtime 与 Go 业务服务高吞吐双向通信 | **短耗时同步请求用 gRPC**（Protobuf 约束 + HTTP/2 复用）；**长任务不能占着同步 RPC**，Go 建任务写消息系统、Python Runtime 消费并持续发事件。Go 管鉴权/配额/外部 API，Python 管推理/工具规划/工作流，双方**共享协议不共享内存**。事件字段：`run_id`、单调递增 `sequence`、`event_type`、`payload`、`schema_version`、`created_at_ms`（+ 幂等键）；消费侧按 `run_id+sequence` 去重并检测缺口。token 可走流式 RPC，但**完整状态必须落持久化存储**，防断连丢状态 |
| 6   | asyncio 混入 CPU 密集代码                  | 事件循环单线程，协程里直接做 PDF 解析/图片编码/复杂排序会**长时间占住 loop**，导致其他请求的超时、心跳、流式输出全部饿死。纯 Python CPU 任务受 **GIL** 限制，加线程未必提速；释放 GIL 的原生库可用线程池，纯 Python 计算用**进程池**（`loop.run_in_executor(ProcessPoolExecutor, ...)`）或独立计算服务。进程池也不是无限扩展：大对象序列化、进程启动、内存复制都是开销，生产用独立 worker + 队列做并发与背压                                                 |

### 3. 上下文与检索（Q7 / Q8）

| #   | 题                                     | 核心知识点                                                                                                                                                                                                                                                                                                                                                                                                                                |
| --- | -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 7   | Prompt / 运行时状态 / 外部证据如何分层 | 三类信息**必须分层**：系统策略 = 不可修改的控制信息；运行时状态 = 编排器生成的可信结构；检索文档/网页/用户上传 = **不可信数据**。不能拼成一个自然语言串让模型自己区分。工具结果带 `trust` / `source` / 时间 / 内容类型，用明确数据边界（`system` / `developer` / `user` / `tool`）。**真正的权限边界在运行时和工具网关**：执行器对工具调用二次校验，不因来自高优先级 Prompt 就放行                                                        |
| 8   | Agentic Retrieval 何时继续/改写/终止   | 需要**显式停止条件**：每轮先判断证据是否覆盖关键实体、约束条件、时间范围，再检查证据冲突；缺关键证据才继续。查询改写不是生成近义句，而是把原问题拆成**原子命题**，分别标记已证实/被否定/未知，下一轮只围绕未知命题生成查询。收益函数：`retrieval_utility = 新增证据收益 − 重复惩罚 − 检索成本 − 延迟惩罚`；收益低于阈值、预算耗尽、连续召回重复、已达到证据覆盖率即终止；关键事实始终找不到应**返回证据不足**，而不是多跑几轮模型补全结论 |

### 4. 多 Agent 与工具生态（Q9–Q12）

| #   | 题                                           | 核心知识点                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| --- | -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 9   | 多 Agent 改共享状态如何防写覆盖/分叉         | 状态不是可随意改的 JSON；每个 Agent 提交**事件或补丁**，状态服务按版本条件写入：`UPDATE ... SET state=?, version=version+1 WHERE run_id=? AND version=expected_version`，**影响行数为 0 即并发冲突**，重新读取后重试。无关字段用**字段级补丁**降冲突，同一决策竞争交给仲裁节点/确定性规则。消息乱序 → 事件需带**逻辑时间、因果父事件、生产者 ID**，仅靠 DB 更新时间无法恢复因果                                                                                           |
| 10  | 任务拆分如何避免重复与依赖错误               | 规划器输出**结构化任务图**（不是自然语言列表），节点含输入契约、预期产物、依赖、完成条件、预算；调度前检查**是否有环、依赖是否存在、是否有节点产出互斥产物**。子任务去重不能只比文本相似度：归一化为「动作 + 资源 + 时间范围 + 输出类型」算**语义指纹**，文本不同但读同一资源产同一产物通常应合并。运行中新增依赖须提交**图变更请求**，由调度器重新做环检测/预算/权限校验                                                                                                 |
| 11  | MCP 的 Host / Client / Server 职责与信任边界 | **Host** 承载模型与用户交互，负责权限、用户确认、上下文、生命周期；**Client** 在 Host 内维护与某个 Server 的连接；**Server** 暴露工具/资源/提示模板，**不应自动获得 Host 全部能力**。MCP 只解决能力发现与调用协议，**不自动解决安全**：Server 返回的工具描述、资源内容、错误信息都可能不可信，Host 仍要做 Schema 校验、权限判断、输出清洗。**本地 Server 也不能默认可信**（可读环境变量/文件/凭证），应放在受限进程或容器；远程还需认证、传输加密、租户隔离、服务身份绑定 |
| 12  | 能力协商、会话恢复、取消传播                 | 建连先交换**协议版本 + 能力集合**（资源订阅、进度通知、日志级别、采样等），只使用协商成功的能力，不按 Server 名字推断。长任务用**稳定请求 ID**；断线重连可带会话令牌查未完成请求，但**不能把进程内 Future 当唯一状态**，任务状态与结果位置要持久化。取消沿调用链传播：Host → Client → Server → DB 查询/模型请求/子进程；底层不可取消时**停止继续处理其结果并标记「取消中」**，不向用户虚报已终止                                                                          |

### 5. Coding Agent 安全与契约（Q13–Q15）

| #   | 题                                 | 核心知识点                                                                                                                                                                                                                                                                                                                                                           |
| --- | ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 13  | 可审计的文件修改                   | 先读**文件版本 + 内容哈希** → 生成结构化补丁 → 应用前**复检哈希**，若用户或其他进程改过则重新读取重新规划，避免覆盖并发改动。至少记录：读取集合、补丁、命令、退出码、测试结果；高风险操作在**隔离工作树/容器**中执行、验证后再合并。**仅限制路径不够**：符号链接可能指向工作区外，执行器必须解析真实路径并确认仍在允许根目录内                                       |
| 14  | Shell 命令的沙箱隔离               | 临时容器 + 最小工作目录挂载 + 只读基础镜像 + 非特权用户 + 移除多余 capabilities + **seccomp** + 资源限制。网络**默认关闭**，需要下载依赖时只放通内部代理/白名单仓库并记录包名/版本/校验值，防测试脚本或恶意依赖外发源码与凭证。限制 CPU、内存、进程数、文件大小、执行时间（防 fork bomb / 磁盘写满 / 无限编译）；生产凭证不进沙箱，临时令牌限权限与有效期            |
| 15  | Agent Skill 组合时避免前置条件冲突 | Skill 不能只有自然语言说明，需**机器可检查的契约**：输入、输出、前置条件、副作用、权限、失败模式、补偿能力。组合时把前置条件与产物建成**依赖图**，检查无法满足的条件与循环依赖（示例：「生成检修报告」依赖「故障证据已确认」，「关闭工单」依赖「报告已签名」）。⚠️ **原文在此处被订阅墙截断**（代码片段停在 `requires: - report.status ==`），后续要点不可见，不补写 |

## 四、速记卡

- **信息分层**：系统策略不可改 · 运行时状态可信结构 · 外部证据不可信；权限边界在**运行时与工具网关**，不在 Prompt。
- **检索终止**：原子命题拆分 + 证据覆盖率 + 收益函数，找不到就返回「证据不足」。
- **共享状态**：事件/补丁 + 版本号条件写入，乱序靠逻辑时间与因果父事件。
- **Coding Agent**：读哈希 → 补丁 → 应用前复检 → 隔离环境验证；符号链接要解析真实路径。
- **MCP**：协议只解决能力发现，安全靠 Host 校验 + Server 沙箱；取消要沿链传播，不可取消就标「取消中」。
- **WebRTC**：SDP 描述、ICE 选路、STUN 找映射、TURN 兜底；弱网先判拥塞再加冗余；SFU 靠分片级联而非堆机器。
