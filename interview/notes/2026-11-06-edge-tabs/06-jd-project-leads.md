## 一、协同文档项目线索（1266366776）

原帖自述：在做**协同文档**，技术栈 **Tiptap**，支持 **Word 文件导入 / 编写 / 导出**、**修订模式**、**评论**，并发现与腾讯/字节 AI 全栈工程师 JD 高度匹配。

由这条线索推出**必须准备的追问**（若简历上也写了这个项目）：

| 方向          | 高频追问                                                                                                                                                                                |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 编辑器内核    | Tiptap 基于 **ProseMirror**：Schema 定义文档结构、Transaction/Step 变更、Plugin 体系、Selection 与 Decoration；为什么不用直接 contentEditable                                           |
| **协同**      | OT vs **CRDT**（Yjs）；冲突合并、undo/redo 在协同下的语义、awareness（光标/在线状态）、断线重连与离线编辑、服务端持久化与快照压缩                                                       |
| **Word 互转** | 导入：`mammoth` / `docx` 解析 → 映射为 ProseMirror 节点；导出：反向序列化为 OOXML。难点是**样式/列表/表格/图片/批注的损失与往返一致性（round-trip）**                                   |
| **修订模式**  | 用 mark/annotation 记录 insert/delete 与作者、时间；接受/拒绝修订的事务设计；与协同光标、评论锚点的位置映射（相对位置 / `RelativePosition`）                                            |
| 评论 / 锚点   | 评论如何绑定文档位置并在编辑后仍不漂移；线程状态与已读                                                                                                                                  |
| 性能          | 大文档分块渲染、虚拟滚动（[R07 Q1](../../rounds/round-07.md)）、增量同步、输入延迟                                                                                                      |
| AI 结合       | 若接 Agent：把编辑器内容暴露成工具/资源、AI 建议如何以「修订」而非直接覆盖写入、人在回路确认（可对照 `content/docs/yukino/permission.md`、`content/docs/yukino-dev-agent/` 的草稿闸门） |

> ⚠️ 这些是**从项目描述推导的准备清单**，不是原帖内容，也不是本仓库项目事实。原帖只有两句话，无实现细节。
