## 一、PG vs MySQL（底层引擎差异）

| 维度       | MySQL (InnoDB)                                                      | PostgreSQL                                                                                                                   |
| ---------- | ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 存储模型   | **聚簇索引**：数据行存在主键 B+ 树叶子；二级索引叶子存主键值 → 回表 | **堆表 (heap)**：元组独立存放，所有索引都是二级索引、指向 `ctid`（页号+偏移）；无「聚簇索引」概念（有 `CLUSTER` 一次性重排） |
| 并发控制   | **MVCC via undo log**：旧版本放 undo 段，回滚段 + ReadView 判可见性 | **MVCC via 多版本元组**：新版本直接插入堆表，旧版本靠 VACUUM 回收 → 需要关注膨胀与 autovacuum                                |
| 索引类型   | B+Tree、Hash（Memory/自适应）、Fulltext、R-Tree/Spatial             | B-Tree、**GIN / GiST / BRIN / SP-GiST**、部分索引、表达式索引、全文检索内建更完整                                            |
| 事务与 DDL | DDL 多数非事务式（隐式提交）                                        | **DDL 可事务化**（可回滚）                                                                                                   |
| 复制       | binlog 逻辑复制 / 半同步                                            | **WAL 流复制**（物理复制）+ 逻辑解码                                                                                         |
| 类型与扩展 | 相对保守                                                            | 数组 / JSONB / hstore / 范围类型 / 自定义类型 / 扩展（PostGIS）、窗口函数与 CTE 更完整                                       |
| 选型       | 简单 OLTP、读多写少、生态成熟                                       | 复杂查询、地理/JSON、分析型混合负载、需要扩展                                                                                |

> 项目互证：`content/be/mysql.md` 讲清了 InnoDB 聚簇索引、undo/redo/binlog、间隙锁与 MVCC；`content/docs/yukino-ecomm-agent/llm.md` 提到 Prisma + PostgreSQL 作为业务库、`CHECKPOINTER_DB_URL` 单独库。**PG 侧知识库暂无系统笔记**，这是待补项。

## 二、登录安全与防攻击（网安背景追问）

分层清单（从外到内）：

| 层   | 手段                                                                                                              |
| ---- | ----------------------------------------------------------------------------------------------------------------- |
| 传输 | 全站 HTTPS / HSTS、证书校验、敏感 cookie `Secure + HttpOnly + SameSite=Lax`（见 [R03](../../rounds/round-03.md)） |
| 凭证 | 密码加盐慢哈希（Argon2id/bcrypt）、**永不存明文**、密钥轮换；MFA/TOTP；口令强度与泄露库检测                       |
| 会话 | 服务端会话 + 轮换 session id、闲置/绝对超时、异地登录提醒、设备指纹                                               |
| 爆破 | 按账号 + IP + 全局三级**限流**（[Code 01 限流器](../../code/rate-limiter.md)）、指数退避、验证码、账号锁定策略    |
| 注入 | 参数化查询 / ORM、输入校验、最小权限 DB 账号                                                                      |
| CSRF | `SameSite` + CSRF Token / 自定义头 + `Origin` / Fetch Metadata（[R03](../../rounds/round-03.md)）                 |
| XSS  | 输出编码 + CSP、富文本白名单                                                                                      |
| 越权 | 服务端逐次鉴权，**身份参数系统注入不经过模型/前端**（`yukino-ecomm-agent/llm.md` 的 `injectUserId`）              |
| 审计 | 登录/失败/敏感操作日志、异常告警、追溯链路                                                                        |

## 三、云服务商视角的 DDoS 防护

与「自己站点做限流」不同，云厂商要解决**带宽耗尽**与**多租户**：

| 层            | 手段                                                                                                         |
| ------------- | ------------------------------------------------------------------------------------------------------------ |
| 网络层 (L3/4) | **Anycast / BGP 引流 + 清洗中心**、黑洞路由（blackhole）、限速与 SYN Cookie、UDP/ICMP 泛洪过滤、超大带宽储备 |
| 传输/连接层   | 连接数限制、TLS 握手限速、慢连接（Slowloris）防护、**只能靠网关/边缘节点**扛，源站不应暴露                   |
| 应用层 (L7)   | WAF、CC 防护、行为/指纹挑战（JS Challenge / CAPTCHA）、按 URL/租户的速率与配额、Bot 管理                     |
| 架构          | 高防 IP / CDN 边缘吸收、**源站隐藏**、弹性扩容 + 降级（静态化、只读模式）、多区域容灾                        |
| 运营          | 基线画像（正常流量模型）、异常检测、演练、按租户计量与配额、攻击报告与溯源                                   |

> 与 [R02 20MB JSON × 数万并发](../../rounds/round-02.md) 呼应：接入层早拒绝、双维度限流（连接数 + 字节）、有界队列、异步削峰。**区别**：云厂商还要处理「带宽被打满」这一单机限流解决不了的问题。

## 四、内存泄露检测（与项目事实互证）

| 手段             | 项目锚点                                                                                                                                                  |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 指标分层         | `content/docs/ieg.md`：RSS / heapUsed / external 三线叠加，先判堆内 vs 堆外；`nodejs_heap_space_size_used_bytes`、GC 耗时占比、eventloop lag              |
| 趋势而非绝对阈值 | `predict_linear(process_resident_memory_bytes[1h], 6*3600)` 外推 6 小时后 RSS 越线才告警（RSS 绝对值受实例规格与流量影响）                                |
| 堆快照对比       | Chrome DevTools / Node `--heapsnapshot-signal`，三次 GC 后对比 retained size，看 dominator 树找**闭包引用**                                               |
| 常见成因         | 全局缓存无淘汰、事件监听未解绑、闭包持有大对象、定时器未清、连接池/文件句柄未归还（`ieg.md` 的闭包引用泄漏排查、`node-pool.md` 的连接申请超时与快速失败） |
| 告警分级         | 症状优先（内存水位 + GC + eventloop lag 联看），原因级指标只上看板；`for` 持续时间 + 分组抑制（`ieg.md:557-568`）                                         |
