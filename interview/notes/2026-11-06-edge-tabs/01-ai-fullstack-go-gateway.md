## 一、算法

- **手写 LRU Cache**：哈希表 + 双向链表，`get`/`put` 均 `O(1)`；容量满淘汰链表尾；更新已存在 key 要移到头部。可延伸 [03 面经里的分布式 LRU](../2026-11-05-active-tabs-03.md)（一致性哈希分片 + 本地 LRU + 热点 key）。
- **打家劫舍**（暑期实习帖）：经典 DP，`dp[i] = max(dp[i-1], dp[i-2] + nums[i])`，可滚动数组压到 `O(1)` 空间。

## 二、Go 八股（两篇完全相同，逐条必背）

| 题                        | 要点                                                                                                                                                                                                                                        |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| goroutine vs 线程         | goroutine 是**用户态**轻量协程，初始栈约 2KB 可增长，由 Go runtime 调度；线程是内核调度、栈大（MB 级）、切换要陷内核。创建/销毁/切换成本与数量级都不同                                                                                      |
| GMP 模型                  | `G` = goroutine、`M` = 内核线程、`P` = 处理器（持有本地运行队列与调度上下文）；`GOMAXPROCS` 决定 P 数；M 必须绑定 P 才能执行 G；`work stealing` 从其他 P 偷一半 G；阻塞系统调用时 `handoff` 把 P 交给别的 M                                 |
| **本地队列挂在 P 还是 M** | **挂在 P**（`P.runq`，通常 256 容量）；另有全局队列 `sched.runq`。这是高频陷阱题                                                                                                                                                            |
| channel 理解与场景        | CSP「通过通信共享内存」；`make(chan T, n)` 有缓冲 vs 无缓冲同步；场景：goroutine 间传值、信号通知/取消、限流信号量、任务分发、结果汇聚、`select` 多路复用与超时                                                                             |
| channel close 后行为      | 已关闭 channel：**发送 panic**、接收会先取完剩余值再得到零值（`v, ok := <-ch` 的 `ok=false`）、**close 已关闭的 channel panic**、重复 close panic；**由发送方关闭**，接收方不关；`for range` 会在关闭后自动退出；关闭后所有阻塞接收者被唤醒 |
| defer                     | 用途：释放资源（关文件/解锁/`recover`）；**LIFO 逆序执行**；参数在 `defer` 语句处即求值；`defer` 在 `return` 之后、函数真正返回之前执行，命名返回值可被 defer 修改                                                                          |

> 项目互证：`content/be/go.md` 有 GMP / channel / Go 并发原语；`content/be/wanproxy.md` 用了 `sync.WaitGroup` / channel / `sync.Once` / `context` 级联取消。

## 三、项目 / 场景追问（网关 + MCP，本组最有区分度）

| 题                                           | 可讲的答题骨架                                                                                                                                                                                                                                |
| -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 如何把**存量 API 适配成 MCP 调用形式**       | 从 OpenAPI/路由表抽取「方法 + 路径 + 参数 schema + 描述」→ 映射成 MCP `tools/list` 的 tool 定义（name / description / inputSchema）→ `tools/call` 时由网关翻译回原 HTTP 请求 → 响应整形为 MCP content；存量服务零改造，鉴权/限流/审计复用网关 |
| 为什么**在网关层做协议转换**而不是用现成 SDK | 存量多语言服务无法逐个嵌 SDK；网关统一收口鉴权、限流、审计、超时、重试与灰度；协议升级只改一处；SDK 会把协议版本与依赖散落到各服务。**代价**：网关成为单点、schema 同步与版本漂移要治理、流式/长连接需额外打通                                |
| OAuth 鉴权流程怎么设计                       | 授权码 + PKCE；网关做 token 校验/刷新/作用域映射，把身份转成内部可信 header；**token 不透传给下游业务**；scope 与 tool 权限做映射；短期 token + 轮换 refresh token；MCP 远程场景还要服务身份绑定与租户隔离                                    |
| 服务注册发现 / 配置管理怎么接                | 注册中心（etcd/Consul/Nacos）+ 健康检查 + watch 增量；配置走版本化 + 灰度 + 回滚；**工具列表变化会让 LLM 的 tools 数组变动 → prompt cache 失效**（见下方事实锚点）                                                                            |
| 高并发下网关怎么扩展与治理                   | 无状态水平扩容 + 连接池 + 熔断/限流（令牌桶，按租户/API 维度）+ 超时与重试预算 + 背压 + 分片/一致性哈希；控制面与数据面分离                                                                                                                   |
| 大量调用失败如何排查                         | 先分层定位（客户端/网关/上游/依赖），按 status、错误码、P99、重试次数、实例维度聚合；trace 串联；区分瞬时故障与系统性故障；看是否重试风暴放大；熔断与降级是否生效                                                                             |

:::note 事实锚点（项目里能直接引用）
`content/docs/yukino/mcp.md` / `function-calling.md` 记载：**tools 数组渲染在 system 之后、messages 之前，任何变动都会使整段历史缓存失效**；源码注释实测「20k token 历史下，仅在 tools 末尾追加一个工具，缓存命中率从 **99.4% 掉到 9.5%**」。所以「网关动态发现工具」这道题必须顺带答 **tools 数组稳定性与 prompt cache**，否则会漏掉真正的工程难点。
:::

## 四、AI 工程认知（开放题，考观点不是背概念）

| 题                                 | 高分答法方向                                                                                                                                                                                                                    |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 平时 AI coding 怎么用              | 具体到场景：脚手架/样板代码、单测生成、重构建议、报错定位、代码阅读理解；说清**哪些不交给 AI**（安全敏感、并发/事务、对外契约）                                                                                                 |
| AI 生成代码与人工 review 的关系    | AI 负责产出候选，人负责**意图对齐、边界、并发正确性、安全、可维护性**；review 不可省，且要针对 AI 常见失误（幻觉 API、过度抽象、吞异常、忽略幂等）设检查单                                                                      |
| **AI review AI 是否有效**          | 有效但有边界：适合格式/规范/明显逻辑/测试覆盖等**可判定**问题；对需求理解、架构取舍、隐式业务规则仍会同源犯错（同一个模型家族盲区一致）。更稳的做法是「AI 生成 + 确定性工具（类型检查/lint/测试/静态分析）把关 + 人工抽样复核」 |
| OpenClaw / OpenCode 一类工具的理解 | 归类为**终端/CLI 形态的 coding agent**：工具循环 + 权限确认 + 上下文管理 + 会话持久化；可与 `content/docs/claude-code.md`、`pi.md`、`content/docs/yukino/` 27 篇源码笔记对照讲                                                  |
